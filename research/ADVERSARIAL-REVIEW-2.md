## Database / event-sourcing engineer — log storage, schema evolution, replay determinism. I read the code first, ran every suite (39/39 green at HEAD 94fed44), then wrote nine throwaway attack scripts under /tmp/atk. Every finding below is backed by a reproducing script, not an argument. Where the prose and the code disagreed, I took the code as truth and the prose as the bug.

Severity totals: **17 FATAL, 34 SERIOUS, 9 MODERATE, 0 MINOR**; **44 findings block the record-format freeze**.
**Freeze vote:** NOT READY TO FREEZE
**Reasoning:** The kernel is a genuine advance over phase 1 — the structural commit barrier holds (I could not reach durable truth from inside a provider), fork/resume are correctly separated, and uncertainty is a real state rather than a guess. None of that is in question. But the RECORD FORMAT specifically is not ready, for four independent reasons, each with a reproducing script.\n\n1. The format cannot express what a fork inherited. `execution.forked` carries a checkpointId and nothing else, and recovery never re-hydrates from it, so a forked lineage's entire state — cells, artifacts, effect index, protected effects, grants — evaporates on restart and an irreversible effect executes a second time with zero invariant violations (/tmp/atk/a-fork-restart.ts). Doc 17 §3's \"the journal is the source of truth... MUST be reconstructable from it\" is simply false for any forked execution, and the kernel already knows it: `resumeFromCheckpoint` returns consistent:false for every fork's own checkpoint. Fixing this adds fields to the fork event. That is a format change by definition.\n\n2. There is no canonical encoding contract. `canonical()` collapses every non-plain object to `{}`, so distinct requests collide on one effect key; and because writes use JSON.stringify while validation uses canonical(), a payload containing a Date makes the kernel discard its own successfully-written commit record as \"torn\", leaving a permanent seq gap and chain break (/tmp/atk/b-canonical.ts, /tmp/atk/d-more.ts §O). A record format whose bytes cannot be read back reliably is not a format yet; the value domain has to be closed and enforced first.\n\n3. There is no redaction path, and doc 17 §2 normatively describes one using a `payloadHash` field that does not exist in `KernelEvent`. The hash covers the payload inline, so tombstoning reads as tampering (/tmp/atk/d-more.ts §Q). Adding payloadHash changes the hashed envelope — the most format-y change possible.\n\n4. There is no schema evolution mechanism at all: `schemaVersion` is hardcoded once and read by nothing, `protocolVersion` is written everywhere and read by nothing, and there is not a single upcaster in the codebase. This is what turns every other gap into a freeze blocker — you cannot freeze a format and then migrate it when the migration machinery does not exist. Freezing now would freeze a snapshot of the current in-memory shapes and call it a protocol.\n\nAdditionally the commit checksum does not bind `executionId`, so a commit record can be re-parented on disk into another execution and recovery will fold it there with every invariant green (/tmp/atk/d-more.ts §P) — the integrity envelope's scope is a format decision that is currently wrong.\n\nWhat would change my vote: payloadHash added and payload removed from the hash preimage; checksum extended to the whole record; a closed, enforced payload value domain with matching write/read encoders; a fork-origin commitment (inherited-state digest) on `execution.forked`; per-kind payload schema ids with one exercised upcaster and defined unknown-version behaviour; and the fork disposition vocabulary extended to cover `suspended`. Those six are all envelope-level, all small, and all cheap now versus impossible later. The behavioural findings (evidence gate on resume, adopt-landed double-apply, recovery triage, blob integrity, budget units) are serious but do not gate the freeze — they can be fixed against a frozen format.
**Strongest objection:** The single strongest objection: for a forked lineage, the journal is not the source of truth, and the record format has no way to say so. Everything a fork inherits lives in a checkpoint blob that the fork event references but does not attest, and that recovery never reads. I proved this end-to-end — fork, restart, re-attempt, and the same irreversible charge executes twice while `checkInvariants()` returns zero violations and the invariant suite, the property suite, the fuzzer and the crash sweep all stay green.\n\nWhat makes this more than one bug is the pattern. Doc 20 F-6 records exactly this failure mode being found and fixed one week ago, with the lesson written down: \"Any protection held in memory must be re-derivable from committed evidence, or it is a protection that lasts until the next crash.\" The fix rebuilt protection from the execution's OWN journal — which is correct for a lineage that started with `execution.created` and wrong for every lineage that started with `execution.forked`. F-6 was closed at the front door while the same defect stood at the back. The deeper cause is that this codebase has two folds: `applyToProjection`, which is documented as \"the fold, used identically by live commit, recovery, and fork\", does not maintain the effect index, the dedup window, or the protected-effect set at all — those are maintained ad hoc in three other places that disagree with each other. Until the safety-critical structures are derived by one fold over committed events, and the events carry everything that fold needs, every fix of this class will hold only until someone finds the next path that writes an event without going through `settle()`. I found two more of those in an afternoon: `resolveUncertainty` (adopt-landed, then the same effect runs again) and `fork()` itself.\n\nFreezing the record format before that is settled freezes the wrong thing, because the fix is precisely to put more into the records.

#### [FATAL] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/kernel.ts:869 (fork) and :1120 (recover) — the `execution.forked` record format
**Attack.** F-6 was fixed through the front door and left the back door open. `recover()` rebuilds each execution from ITS OWN journal records only. A forked child's inherited state (cell, artifacts, effectIndex, protectedEffects, grants) comes exclusively from the checkpoint snapshot blob at fork time and is never written to the child's journal — `execution.forked` carries only {parentExecution, checkpointId, cutSeq, dispositions, definitionHash, replayOverride}. So a restart erases everything the fork inherited.

Repro (/tmp/atk/a-fork-restart.ts and /tmp/atk/c-rest.ts §A'), with a capability that counts its own executions:
  invoke(A,'pay.count',{amount:500}) -> completed, protectedEffects={K}
  cp = checkpoint(A); B = fork(cp,{dispositions:{}})
  live child: cell=[[file:ledger,balance=100]], protected=1, effectIndex=2, grants=[grant_000004]; replay correctly ForkError
  --- Kernel.recover(storage) ---
  child cell=[]  artifacts=0  protectedEffects=0 (was 1)  effectIndex=0 (was 2)  grants=[] (was [grant_000004])
  invoke(B,'pay.count',{amount:500}) -> state=completed, deduplicated=undefined
  capability body executed 2 times; checkInvariants() = 0 violations

One logical irreversible charge, executed twice, with no journal evidence that anything was replayed and every invariant green. Corollary proved separately (/tmp/atk/e-final.ts §T): `resumeFromCheckpoint` on a fork's OWN checkpoint returns consistent:false, i.e. the kernel already reports every forked lineage's checkpoint as corrupt — it just never asserts on it. This falsifies doc 17 §3 ("The journal is the source of truth. Checkpoints, projections, caches and indexes are derived and MUST be reconstructable from it"), §7 ("MUST be byte-reproducible by folding the journal prefix"), §8.2 ("inheritance is by causal reference to the cut, not by copying the parent's log" — it is in fact a copy, and an unrecoverable one), and §5.1 at-most-once. It also re-opens F-1 exactly as F-6 did, one restart later.
**Proposed resolution.** The fork's origin state must be committed, not just referenced. Two viable shapes: (a) `execution.forked` carries the full inherited-state commitment — snapshot ref plus effectIndex entries (key, class, landed, outcome, inherited), protectedEffects, dedupWindow and grant states — so the child's own journal is self-sufficient; or (b) recovery re-hydrates a child from `checkpointId` by loading the durable checkpoint before folding the child's suffix, and `execution.forked` carries a digest of the inherited state that recovery MUST verify against the loaded checkpoint (so a missing or altered checkpoint is a loud failure, not silent amnesia). Either way the fork event must gain an inherited-state digest field before the format is frozen. Then add the universal law test (below) that recovered state deep-equals live state for every execution.

#### [FATAL] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/storage.ts:25 (canonical), :74 (appendCommit), :125 (readJournal)
**Attack.** The record format has no encoding contract. `canonical()` uses `Object.keys()`, so EVERY non-plain object collapses to `{}`, and `appendCommit` writes with `JSON.stringify` while `readJournal` re-validates with `canonical` — two different encodings on the two sides of the durability boundary.

(a) Effect-key collision (/tmp/atk/b-canonical.ts): canonical(new Date(0)) === canonical(new Map([['a',1]])) === canonical(new Set([1,2,3])) === canonical({}) === '{}'. Therefore sha({cap:'payment.charge',step:'pay',request:new Map([['amount',10]])}) === sha({...request:new Map([['amount',99999]])}) = 07a9a41c2174de507312a17cf4abdf45. Two different charges share one effect key: the second is silently deduplicated and returns the first's outcome. Doc 17 §9's content-inclusive key guarantee is void for any request that is not a plain JSON tree.

(b) Self-inflicted torn record. A capability yields {type:'state', key:'due', value:new Date(...)}. Commit hashes it as '{}'; JSON.stringify writes "2026-08-16T00:00:00.000Z"; readJournal recomputes sha over the parsed string and gets a mismatch, so the kernel DISCARDS its own successfully-written record as torn. Measured (/tmp/atk/c-rest.ts §C'): LIVE seq=8, invocation completed, settled={invocations:1}; RECOVERED seq=5, invocation stuck 'dispatched', reserved={invocations:1}, settled={}, cell write gone, discarded=1, invariant violations=0. No error is raised anywhere.

(c) It is permanent, not trailing. readJournal `continue`s past a bad record and keeps everything after it, so the poisoned record becomes a hole in the middle (/tmp/atk/d-more.ts §O): after recovery, `I6: chain break in exec_000001 at seq 9` and `I6b: seq gap at position 5`. Doc 17 §3 and doc 19 §1 only ever contemplate a TRAILING torn record.

(d) Values canonical() cannot encode at all wedge the kernel (/tmp/atk/c-rest.ts §H): a cyclic output raises RangeError out of `invoke()` (not a KernelError), leaving the invocation 'dispatched' with its budget reserved forever; on restart the kernel declares that external-irreversible effect `uncertain` — asserting the world may have seen an effect that provably never left the process. That is the kernel guessing, from a serializer failure.
**Proposed resolution.** Define the payload value domain normatively in doc 17 §2 and enforce it at the proposal boundary: a closed set (null, boolean, finite number, string, array, plain object with string keys), with an explicit encoding for anything else (ISO-8601 tagged, or CAS-by-reference). Reject out-of-domain proposals at STAGING time with a typed KernelError so the failure is attributable to the capability and settles as `failed` — never after dispatch and never as `uncertain`. Then make write and read use the SAME encoder: store `canonical(record)`, validate with `canonical`, and add a property test asserting sha(live events) === sha(reloaded events) for every record the kernel writes, plus `readJournal().discarded === 0` for any run with no injected crash. Separately, recovery MUST reject a journal with a seq gap or chain break rather than folding a state that never existed.

#### [SERIOUS] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/kernel.ts:1007 (applyToProjection), :761 (resolveUncertainty), :316 (effect key)
**Attack.** There are two different folds and they disagree. `applyToProjection` — the function the code comments call "The fold. Used identically by live commit, recovery, and fork" — does not maintain effectIndex, dedupWindow, or protectedEffects at all. Those are maintained ad hoc in `settle()`/`fork()` on the live path and by a SECOND, differently-written rebuild inside `recover()` (kernel.ts:1171-1187). Any path that writes committed events without going through `settle()` therefore updates one fold and not the other.

Repro (/tmp/atk/c-rest.ts §G, /tmp/atk/d-more.ts §G): external-compensatable capability, crash after dispatch, recover -> uncertain, `resolveUncertainty(adopt-landed, authority:'ops')` -> 'completed'. resolveUncertainty commits invocation.completed but never touches effectIndex. Re-issuing the identical request executes the capability body a second time: "capability body ran 2 times for ONE logical transfer", and the invariant checker then fires `I13: effect 1c04... completed twice in exec_000001 with no dedup/fork/resolution record`. A further restart WOULD dedup it, because recover()'s fold reads the completed event — so the live kernel and a recovered kernel give different answers to "has this effect run?". Doc 17 §5.1's "an effect key that has completed in a lineage will not execute again in that lineage" is false on the live path.

Second instance of the same root cause (/tmp/atk/e-final.ts §W): the effect key preimage is {cap, step, request} and excludes effectClass, so invoking the same request with `effectClassOverride:'external-irreversible'` dedups against the earlier `pure` entry and the effect index keeps the WEAKER class ('pure'). A later fork then inherits an irreversible effect marked pure and will redo it without refusal.
**Proposed resolution.** Make effectIndex/dedupWindow/protectedEffects genuine projections: derive them ONLY inside `applyToProjection`, delete the bespoke rebuild in `recover()` and the ad hoc writes in `settle()`/`fork()`/`resolveUncertainty`. That requires the events to carry the facts the fold needs — `invocation.completed`/`failed`/`canceled` and `invocation.uncertainty.resolved` must all carry {effectKey, effectClass, landedExternal} explicitly rather than relying on a lookup into the invocation table. That is a payload-shape change to four event kinds, hence it must land before the freeze. Also either fold effectClass into the effect-key preimage or reject a second invocation of a known key under a different declared class.

#### [SERIOUS] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/types.ts:183-202 (KernelEvent) and src/kernel.ts:977
**Attack.** There is no schema evolution mechanism of any kind. Grep of the whole prototype: `schemaVersion` appears exactly once outside the type declaration — `schemaVersion: 1,` hardcoded at kernel.ts:977 — and is read by nothing. `protocolVersion` is written into every event and every checkpoint and read by nothing. Zero occurrences of 'migrat' or 'upcast' anywhere in src/, tests/, reference-model/ or fuzz.ts. Recovery reads payloads by positional `as` casts (`p['capabilityId'] as string`, `p['effectClass'] as EffectClass`), so an old record with a missing or renamed field yields `undefined` cast to a type, which then flows into the invocation table and the triage decision — a record written by v1 and read by v2 produces `effectClass: undefined`, which is not in UNSAFE_TO_AUTO_RETRY, so an irreversible effect from an old record recovers as safe. There is also no reader-side behaviour defined for an unknown schemaVersion (accept? reject? quarantine?), and `Checkpoint.protocolVersion` is never compared against PROTOCOL_VERSION at resume or fork — a checkpoint written under any past or future protocol is loaded blindly.

This is what makes several other findings freeze blockers by transitivity: with no evolution story, every value-domain or payload-shape gap found below becomes unfixable-after-freeze rather than a routine migration.
**Proposed resolution.** Before freezing: (1) give each event KIND its own payload schema identity, not one global integer — `schemaVersion` per kind, or a `payloadSchema: 'invocation.completed/2'` field; (2) define reader behaviour for an unknown version normatively (MUST refuse to fold and surface it, never best-effort cast); (3) add an upcast hook point in the recovery path with at least one exercised identity upcaster plus a test that folds a v1 fixture under a v2 reader; (4) make `protocolVersion` load-bearing — resume/fork MUST compare the checkpoint's protocolVersion and refuse or upcast; (5) replace every `as` cast in `applyToProjection`/`recover` with a validating decoder that throws on a missing required field. Freeze the format only once a written-and-tested v1→v2 migration exists.

#### [SERIOUS] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/types.ts:201 (integrity) and src/kernel.ts:989; docs/17-KERNEL-SEMANTICS.md §2
**Attack.** Doc 17 §2 states normatively: "Redaction is performed by tombstoning payload content while preserving the hash chain (the envelope's `payloadHash` continues to attest what was there)." There is no `payloadHash` field in `KernelEvent`. The chain is `self = sha({...base, prev})` where `base` contains the payload INLINE, so redacting any payload necessarily breaks `self` and every link after it.

Repro (/tmp/atk/d-more.ts §Q): write state {path:'pii', content:'SSN 123-45-6789'}; perform a GDPR erasure by replacing the payload with {key, value:'[REDACTED]', tombstone:true} and re-signing the record checksum. Result: `I6: tampered event ev_000013 in exec_000001 at seq 6`. The redaction is indistinguishable from tampering, and the only alternative — leaving the PII in place — means the journal can never satisfy an erasure request. For a system whose entire value proposition is an auditable durable log of AI actions carrying user data, an un-redactable log is not a shippable format.
**Proposed resolution.** Add `payloadHash` to the hashed envelope and take the payload OUT of the hash preimage: `self = sha({id, seq, kind, schemaVersion, protocolVersion, executionId, invocationId, correlationId, causationId, actorId, grantId, occurredAt, payloadHash, artifacts, prev})`. Redaction then replaces `payload` with a tombstone while `payloadHash` continues to attest the original bytes and the chain verifies unchanged. Add a `redacted: true` marker and a `redaction.applied` event so erasure is itself journaled, and extend the I6 checker to verify payloadHash against the payload only when not tombstoned. This is a pure envelope change and is the single clearest reason the format cannot be frozen as written.

#### [SERIOUS] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/kernel.ts:995 (record construction) and src/storage.ts:131 (validation)
**Attack.** The commit record's checksum is `sha(events)` — it does not cover `executionId` or `commitToken`. Recovery then trusts the RECORD-level `executionId` (kernel.ts:1133) to decide which execution a record belongs to, while the integrity checker groups by the EVENT-level `executionId` (invariants.ts:29). An attacker with disk access can re-parent an entire commit record between executions and nothing notices.

Repro (/tmp/atk/d-more.ts §P): take the journal line containing exec A's `state.updated`, set `record.executionId = <exec B>`, leave events and checksum untouched.
  readJournal accepts it: discarded === 0
  after recovery, execution B folds A's write: [['file:secret','A-only']]
  checkInvariants(): [] — zero violations
The hash chain is intact for both executions (B's own events still chain correctly; A's events were filed under B by recovery but still carry executionId=A, so the checker never sees a break). Doc 17 §2's "What makes an event authoritative: it appears inside a commit record whose checksum validates, in an execution whose hash chain is unbroken up to it" is exactly the check that fails to bind here — the record's execution attribution is outside the integrity envelope.
**Proposed resolution.** Extend the checksum preimage to the whole record: `checksum = sha({commitToken, executionId, events})`. Additionally, recovery MUST verify that every event's own `executionId` equals the record's, and MUST verify the hash chain as it folds (currently `recover()` never recomputes `integrity.self` at all — it just assigns `exec.lastHash = ev.integrity.self`), refusing to fold a record that fails either check rather than reporting it only through the `discarded` count.

#### [SERIOUS] **[BLOCKS FREEZE]** /home/user/kyxo-runtime/prototypes/kernel-semantics/src/kernel.ts:869-961 (fork) and :252 (revoke)
**Attack.** Fork copies grant state per lineage (`grants: new Map(cp.grants.map(...))`) with each lineage's own reserved/settled ledger, and `revoke()` walks only `exec.grants` for the one execution it is given. Two consequences:

(a) Fork mints budget (/tmp/atk/e-final.ts §U). One grant, limit invocations=3: parent spends 3, then four forks from the same checkpoint each spend 3. TOTAL completed invocations under that single grant = 15; per-execution settled = [3,3,3,3,3]; checkInvariants() = 0 violations, because I5 is checked per execution. Doc 17 §9a asserts "actual spend is nevertheless bounded by every ancestor" — that bound is per-lineage only, and fork is unbounded, so the real ceiling is limit x (1 + number of forks). For a budget denominated in money or tokens, fork is a mint.

(b) Revocation does not cross a fork (/tmp/atk/c-rest.ts §F). grants.test.ts:178 covers revoke-BEFORE-fork ("a post-cut revocation still binds"). Revoke AFTER the fork exists is not covered and escapes: parent invoke denied=true, the SAME handle in the fork -> completed, child grant.revoked=false, zero invariant violations. An operator who revokes authority does not revoke it in lineages that already branched — and there is no API that would let them, because `revoke` takes an executionId.
**Proposed resolution.** Decide the semantics explicitly and put it in the record: either (i) grants are family-scoped — the ledger and the revoked bit are keyed by GrantId across the whole correlationId family, so spend and revocation are shared, which requires a family/ledger identity field on GrantState and on the checkpoint's grants[]; or (ii) grants are lineage-scoped by design — in which case fork MUST attenuate, journaling a `grant.attenuated` (or a new `grant.forked`) event per inherited grant with the child's ceiling, so the multiplication is explicit, bounded and auditable rather than emergent. Either way the checkpoint's `grants[]` shape changes. Also extend the I5 invariant to check the whole family, not one execution.

**Attack.** `resumeInvocation` ends with `return this.settle(exec, invocationId, grantState.id, inv.effectKey, inv.effectClass, inv.capabilityId, next.value, {})` — an empty options object. `opts.requiresEvidence` is therefore dropped on every resume. The flag IS durably journaled in `invocation.admitted` (kernel.ts:392) and is simply never read back.

Repro (/tmp/atk/d-more.ts §N), two API calls, shipped capabilities only:
  invoke(e,'human.approval',{q:'ship it?'},g,{step:'gate',requiresEvidence:true}) -> suspended
  resumeInvocation(e, inv, {approved:false}, g)   // the human says NO

Strengthen I17 to also fire when a gated invocation completes with zero passing evidence, not only with a failing verdict. No format change (the flag is already journaled), so this does not block the freeze — but it must be fixed before anything is built on the commit barrier.

## Distributed-systems engineer (consensus, replication, failure detectors)
**Freeze vote:** NOT READY TO FREEZE
**Reasoning:** Eleven of my twelve findings block the freeze, and four of them are FATAL against attacks I reproduced as running scripts, not arguments. The disqualifying pattern is not the individual bugs — it is that the format encodes mechanisms the code does not implement, so the freeze would lock in fields whose semantics have never been exercised. `leaseEpoch` is a constant 1 that is never compared: freezing a fencing token before deciding the concurrency model is backwards, especially since the concurrency model is what finding #1 shows is missing (five real irreversible charges under one effect key, via plain `Promise.all`, with the kernel's own I13 firing). `causationId` is populated exactly zero times in 22 events and `actorId` only ever holds 'kernel', so the audit-reconstruction story the per-execution-seq decision depends on has never been demonstrated to work — you cannot freeze a causality format you have not once used. `payloadHash` is required by doc 17 §2's redaction rule and does not exist in `KernelEvent`, and `integrity.self` hashes the payload directly, so the format as written can never satisfy its own normative deletion requirement; that is a one-way door. `Checkpoint` has no integrity envelope and is nonetheless the authoritative source of grants for every fork — editing one blob widened a `['read']/{invocations:1}` grant to `['read','write','pay','admin']/{invocations:100000}` with zero invariant violations. `Checkpoint.protectedEffects` is a point-in-time list that cannot express a lineage-tree-wide irreversible-effect ledger, which is why forking from a pre-charge checkpoint double-charged with no refusal and no violation. `Checkpoint.dedupWindow` is advertised and never read while the mechanism that actually decides dedup is hidden inside an opaque snapshot blob. `Checkpoint.pending[]` cannot carry a suspension, so a forked human approval is unresumable by construction. `InvocationRecord` has no field for the commit gate, which is precisely why suspend→resume promoted a production artifact past failing evidence and violated I17. Each of those is a field the freeze would make expensive to change, and each is currently either wrong or untested.

The engineering underneath is genuinely good — the structural commit barrier, the effect-class taxonomy, the explicit `uncertain` state, the handle-as-object-identity fix, and the honesty of doc 20 leading with its own falsifications are all better than most systems at this stage. That is exactly why the freeze should wait: the format is one revision away from being defensible, and freezing now would preserve the gaps rather than the design.

Two meta-observations that should temper confidence in the green suite. First, doc 18 documents 24 invariants; `invariants.ts` asserts 14 ids, and doc 20 cites enforcement by 'invariant I21', 'I22' and 'I24' — none of which exist in the checker. Second, four documented invariants (I13, I16, I17, I23) are demonstrably violated by scenarios the generator never produces: the suite runs 9,300 invariant evaluations and issues not one concurrent invoke, not one throw on the resume path, not one gated resume, and not one fork from a pre-effect checkpoint. Doc 18's 'Violations outstanding: 0' is a statement about the generator's reach, not about the kernel. The right reading of this phase is that the invariant checker is strong and the workload generator is weak — most of my findings were caught by the project's own checker the moment I drove it into an unexercised state.
**Strongest objection:** The atomicity claim in doc 19 §2 — "Kyxo has no separate append and commit phases... the design eliminates the failure class rather than handling it" — is true and load-bearing for a SINGLE WRITER, and the entire record format has been designed as if that were a stated premise when it is not. Nothing in doc 17 states a concurrency model. Meanwhile doc 17 §8.2 says parent and child "MAY execute concurrently", the graph strategy negotiates a `parallelism: fan-out` axis, and the phase-1 prototype's own success criterion is "both gather branches progressed inside each other's journal lifetime". So the design demands concurrency at the layer above and assumes its absence at the layer below, and the seam is invisible because every test is sequential.

Everything expensive falls out of that seam. At-most-once is a check-then-act across an `await` (five real charges, one effect key). The reservation-then-settle budget model is per-execution mutable state that a fork forks, so N forks buy N× the ceiling. Revocation walks one execution's map, so it cannot reach a concurrently-running child. `leaseEpoch` — the one field that exists specifically to fence a second writer — is the constant 1. And the checkpoint is the authoritative, unsigned carrier of grants and protected effects for a fork that may run alongside its parent.

Freezing the record format before the concurrency model is written down freezes the wrong artifact. The format's shape depends on answers that have not been given: is an execution a single-writer domain with a lease, or a multi-writer domain needing per-key fencing? Is a grant a per-execution copy or a lineage-scoped record with its own event stream? Is `protectedEffects` a snapshot or a reference into a durable irreversible-effect ledger rooted at the ancestral execution? Every one of those changes the bytes. Write doc 21 — the concurrency and ownership model — before doc 22 declares the format frozen, because doc 22 cannot be correct until doc 21 exists.

## Security engineer (object-capability discipline; runtime red-teaming)
**Freeze vote:** NOT READY TO FREEZE
**Reasoning:** Seven of the twelve findings are record-format defects, and three of those sit under FATAL or SERIOUS attacks that I reproduced against the running code with all 39 tests green, the fuzzer clean over 200 seeds, and the invariant checker returning [] every time.

The format-blocking set is not stylistic. Terminal invocation events omit `effectKey`/`landedExternal` on two of four failure paths, so the replay cache and the protected-effect set are provably not reconstructable from the journal — I wired $100,000 twice across a restart with no dedup record for the second application. `invocation.suspended` carries neither field either, which is the same hole on a path that needs no crash at all. `grant.issued` omits `expiresAt`, so a time-boxed grant becomes eternal. Grants carry no holder or principal, so there is no field a post-restart re-binding could authenticate against and the only continuation path today is `issueGrant` with arbitrary rights — which the test suite itself performs after every recovery. Checkpoints carry `cutSeq` but no hash binding them to the cut, and `fork()` verifies nothing, so a corrupted snapshot silently seeds a lineage including its weakened protection set. Grants have no lineage-spanning identity, so nothing can even express the invariant that 24 invocations under a 4-invocation grant is wrong. And the event envelope has no label channel while doc 11 §5 declares taint a kernel invariant with a non-bypassable gate.

Every one of these is additive-field-shaped. That is exactly why they must land before the freeze and not after: each becomes a migration of every record ever written, and the security-relevant ones (protected effects, grant expiry, grant holder, cut binding) are unrecoverable retroactively — records written without them are permanently unaudita ble for the property they encode.

Two procedural facts reinforce this. `docs/22-RECORD-FORMAT-FREEZE-DECISION.md`, cited by the normative spec §12 as the source of both the serialization-evolution mechanism and the freeze criteria this document must satisfy, does not exist. And there is no per-kind payload schema at all — `payload` is `Record<string, unknown>` — so there is nothing concrete to freeze and no validator that could have caught the two missing `effectKey` fields. You cannot freeze a format you have not written down.

What I would freeze today: the envelope shape (id, seq, kind, versions, executionId, correlationId, causationId, actorId, occurredAt, integrity{prev,self}) and the commit-record framing. Those held up under every attack — the hash chain, per-execution dense seq, torn-record discard and kernel-stamped actorId are all sound. Freeze the envelope, add the six missing fields, write doc 22 and the per-kind schemas, then freeze payloads per kind.
**Strongest objection:** The kernel enforces the ledger, not the world — and it is fully hardened only on the path where nothing goes wrong.

All three FATALs are one shape. On the success path the kernel does everything the design promises: it records the effect key, protects the irreversible effect, settles the budget, promotes artifacts with provenance. On suspend, on failure, on policy denial, on cancellation, on mid-flight revocation it takes a shortcut — writes a partial record, releases the reservation, skips the effect index. Those are precisely the paths an adversary controls. A capability chooses whether to fail. A capability chooses whether to suspend. A capability chooses whether the effect lands before it does either. So the attacker gets to select the code path that the kernel treats as an exception, and the exception paths are where the truth is not written.

The result is a system that will journal `landedExternal: true` immediately adjacent to `grant.released` — literally recording that the world changed and that nobody was charged — while every invariant reports clean. 500 irreversible external effects executed under a grant permitting 3, ledger says 1. An irreversible effect applied 3 times from 3 identical requests with no crash and no fork. The commit barrier genuinely does prevent a capability from WRITING durable truth; it does not constrain what a capability can CAUSE, and that distinction is invisible in the current framing.

The measurement apparatus cannot see any of this, which is the part that should worry you most. Not one provider in `ALL_CAPABILITIES` ever returns `status: 'failed'` (grep count: zero). None suspends after landing an effect. None proposes hostile `usage`. The differential test only ever passes `outcome: 'ok'`, and the reference model refunds on failure with exactly the same rule as the kernel (model.ts:124-127) — so the independent oracle encodes the same mistake and certifies it. Twelve of the twenty-four documented invariants have no executable assertion at all (I1-I4, I11, I14, I19-I24), and the ones that exist are mislabelled: the file pushes `I10` for doc 18's I11 and `I13` for its own I14 comment, so you cannot map an assertion back to the invariant it claims to enforce. The suite is a strong regression harness for the bugs already found and a weak detector for the class of bug that remains, because the adversary was modelled as a capability that LIES (evil.bypass, caught by the evidence gate) rather than one that FAILS or SUSPENDS on purpose.

Fix the fields, then fix the corpus: an adversarial capability that fails after landing, one that suspends after landing, one that proposes negative usage, and a fold-equivalence invariant. Until the oracle can see the failure paths, a green suite is evidence about the success path only.

## Programming-language / runtime engineer (generators, effect systems, API design)
**Freeze vote:** NOT READY TO FREEZE
**Reasoning:** NOT READY. Seven of the twelve findings are record-format defects, not implementation bugs, and each is the kind that cannot be repaired after a freeze without a breaking change.

The decisive one is that the journal is not sufficient to reconstruct the state the design depends on. `protectedEffects` and `effectIndex` — the entire basis of fork safety, dedup and irreversible-effect protection — are built by two different code paths (settle vs recover) with different rules, from payload fields several emitters do not write. I reproduced a real double-charge across a restart with all 39 tests green and all invariants clean, and a case where the identical journal yields protection=0 live and protection=1 after a restart. Until protection is a deterministic fold over committed events (which requires a new event kind for external landing), there is nothing stable to freeze: the format does not determine the semantics.

Four more format-level gaps compound it. Effect identity is computed by a canonicalization that maps distinct requests to the same key (Dates, Maps, NaN/Infinity, class instances) and throws on BigInt, with no conformance vectors — and effect keys are wire-visible identity. The effect index stores no result, so dedup returns `undefined` and silently changes answers; fixing that changes the checkpoint snapshot shape. `dedupWindow`, `leaseEpoch` and `EffectIndexEntry.outcome:'uncertain'` are carried in the format with no implementation at all — `dedupWindow` is written three times and read nowhere, so amendment A11's two-mechanism claim is unimplemented. And `schemaVersion`/`protocolVersion` are write-only: no negotiation, no unknown-kind rule, no migration document (doc 17 §12 defers to `22-RECORD-FORMAT-FREEZE-DECISION.md`, which does not exist). Doc 17 §2 also makes redaction normative via a `payloadHash` the envelope does not have, and `integrity.self` hashes the payload inline — so the specified redaction path is provably impossible in this record.

What I am NOT saying: the architecture is wrong. Pure proposers, the generator delegation channel, handle-shaped authority, the resume/fork split, explicit uncertainty and the crash matrix are sound, and several held up under direct attack. The suspend/resume path, concurrency and the recovery fold are where the executable form has not caught up with the specification — and the record format is downstream of exactly those.

Minimum to reach a freeze vote: (1) an `effect.landed` event and a single fold shared by commit, recovery and fork; (2) a per-kind payload schema enforced at commit; (3) a normative canonicalization plus conformance vectors for effect keys; (4) results in the effect index; (5) delete-or-implement for every dead field; (6) a version-negotiation and unknown-kind rule plus doc 22 with a worked migration; (7) a `payloadHash` split so redaction is representable. Findings #2, #4, #6, #9, #10, #11 and #12 must be fixed before anything is built on this foundation, but they do not by themselves change the record.
**Strongest objection:** The commit barrier is real for the channel it was designed for and absent everywhere else — and the test suite was written along the designed channel.

`invoke` is carefully guarded: admission, reservation, dispatch intent, staging, commit-phase policy, evidence gate, staging release on throw. Every one of those guards is missing from `resumeInvocation`, which re-implements the settlement path in 34 lines and drops the gate obligation, the admission policy, the authority chain check, the reservation, the try/catch and the delegate interception. The result is not a subtle race: invoking `human.approval` under `requiresEvidence:true` and resuming with `{approved:false}` produces a `completed` invocation whose own journal records the human's rejection, and the project's own invariant checker calls it `[I17]`. The suite calls `resumeInvocation` exactly once, on the happy path, in a test that asserts only `state === 'completed'` — precisely the assertion the bug satisfies.

The same shape recurs at every seam. Staging was hardened against a throwing provider (documented falsification F-5) — in `invoke` only. Protection was made to survive restart (F-6) — by writing a SECOND fold inside `recover` that disagrees with the live one. Irreversible replay was made to refuse loudly (F-1) — but a suspension throws the landing evidence away before protection is ever computed. Each fix was applied to the path the falsifying test walked, not to the invariant the falsification exposed.

That is why 39 green tests, 150 coverage seeds, 120 property seeds, a 32-point crash sweep and 41 seeds of differential agreement coexist with a proven double-charge, a defeated commit gate, a bypassed deny-class policy, a budget overspend and a 33-calls-under-a-3-call-grant authority escape. The reference model does not help, because it was written from the implementation's decision order rather than from doc 17 — it checks dedup before authority exactly as the kernel does. The suites are excellent at re-testing known falsifications and structurally unable to find the next one. Before freezing anything, the harness needs adversarial capabilities that misbehave at the seams (suspend after landing, throw on resume, delegate on resume, yield forever, request payloads that are not plain JSON) and invariants for the properties nothing currently asserts: no stranded reservation, every non-terminal invocation reachable to a terminal state, live projection equals recovered projection over the same journal, and spend per grant summed across the whole correlation family.

#### [FATAL] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:537-542 (settle, suspend branch)
**Attack.** A suspension silently discards ALL staged proposals, including `{type:'external', landed:true}`. A capability that performs an irreversible external effect and then suspends (3-D Secure, human confirmation, provider callback — the normal shape) leaves the journal with ONLY `invocation.suspended`. There is no record the effect landed, `protectedEffects` stays empty, and on resume the provider runs again. Proven — the world is charged twice, the journal shows one completed invocation, and ALL invariants pass:

     journal = created,grant.issued,admitted,reserved,dispatched,suspended

Aggravating factor in the same repro: `resumeInvocation` sets `ctx.request = inv.suspension.payload`, so the provider re-executes against a DIFFERENT request than the one the effect key was computed over — the second charge was for `{q:'confirm'}`, not `{amount:500}`, yet it settles under the original key. #### [FATAL] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:692-726 (resumeInvocation)

  canonical({when: new Date('2020-01-01'), amt:10}) === canonical({when: new Date('2026-08-16'), amt:10})   // both -> {"amt":10,"when":{}}
  sha({amount: NaN}) === sha({amount: Infinity}) === sha({amount: null})   // 2ccd94e2...
  sha({m: new Map([['a',1]])}) === sha({m: new Map([['b',2]])})            // true
  sha({amount: 10n})  -> throws TypeError 'Do not know how to serialize a BigInt' inside the kernel

Any class instance, Date, Map, Set or typed array collapses to `{}`; distinct requests collide. Proven end-to-end: charging two different invoices
  k.invoke(e,'payment.charge',{amount:10,due:new Date('2026-01-01')},g,{step:'inv'})
  k.invoke(e,'payment.charge',{amount:10,due:new Date('2026-02-01')},g,{step:'inv'})
throws `ForkError: refusing to replay protected irreversible effect 7ab1cf39...` — the February invoice is refused as a replay of January, and can only be forced by `allowReplayOfProtected`, which simultaneously un-protects the real January charge. Lost effects are as bad as duplicated ones, and here they present as a security refusal. The BigInt case is worse: an unhandled TypeError escapes `invoke` before any admission record, so a request shape crashes the kernel with a non-KernelError.
**Proposed resolution.** Freeze a normative canonicalization (RFC 8785 JCS or dag-cbor) and specify the admissible request domain. Reject non-canonicalizable values at admission with a typed KernelError rather than hashing them to a collision; distinguish absent from undefined; forbid NaN/Infinity or encode them distinctly. Add a conformance vector file of (request, expected effect key) pairs — an effect key is a wire-visible identity and must be reproducible by a second implementation.

#### [SERIOUS] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:919-935, 940-944 (fork: grants inherited from the checkpoint)
**Attack.** A fork copies `cp.grants` — including the `reserved`/`settled` counters as of the cut — into a fresh execution, and the SAME `GrantHandle` object authorizes in every child (`authorize` only checks the WeakSet and `exec.grants.has(id)`). So forking from a pre-spend checkpoint rolls the budget back, and forking N times multiplies it. Proven:

  const g = k.issueGrant(e, {rights:['remote'], limits:{invocations:3, spawnDepth:1}});
  const cp = k.checkpoint(e);              // cut taken before any spend
  ...spend all 3 in the parent -> 4th throws BudgetError...
  for (let f=0; f<10; f++) { const child = k.fork(cp.id,{dispositions:{}});
                             for (let i=0;i<3;i++) await k.invoke(child,'remote.a2a',...,g,...); }
  -> grant ceiling = 3 invocations; ACTUAL external calls made = 33; invariants = []

Doc 17 §9a's guarantee ("actual spend is nevertheless bounded by every ancestor") holds only within one lineage; the grants suite tests exactly that case and misses this one. Since fork is an ordinary kernel verb available to any driver, a bounded grant is not bounded. The revocation guard at kernel.ts:940-944 shows the authors already knew a checkpoint must not resurrect authority — it resurrects budget instead.
**Proposed resolution.** Decide and specify whether a grant is lineage-scoped or family-scoped. Either (a) the budget ledger is keyed by grant id across the whole correlation family so ancestors see fork spend, or (b) fork MUST re-issue/attenuate authority — the child gets no grant until the operator mints one, and `execution.forked` records the derivation. Silently copying spent counters into a new lineage is the one option that cannot be defended. #### [SERIOUS] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:62-74 (EffectIndexEntry) and 344-355 (dedup return)
**Attack.** The replay cache cannot replay: `EffectIndexEntry` stores `{invocationId, effectClass, landed, outcome}` and no result, so the dedup path returns `{invocationId, state, deduplicated:true}` with `output` undefined. Dedup is therefore not transparent — it changes the answer. Proven with the shipped `strategy.graph` capability, whose delegated sub-work dedups on a second run:

  second run total = 0   evidence verdict 'fail'      // identical program, identical inputs
  direct re-request of a known effect: deduplicated=true, output=undefined (2 expected)

No invariant fires. A delegating capability silently receives `undefined` where it expects a value, coerces it (`Number(undefined ?? 0)`), and commits a wrong artifact under a passing pipeline. This is worse than re-executing: the caller is told the work succeeded and handed nothing. #### [SERIOUS] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/types.ts:183-213, 303-317, 351; docs/17-KERNEL-SEMANTICS.md §2, §12
**Attack.** The format is not evolvable, and the document that was supposed to say how it evolves does not exist.

#### [SERIOUS] prototypes/kernel-semantics/src/kernel.ts:1120-1195 (recover) and src/storage.ts:125-141 (readJournal)
**Attack.** The hash chain is verified ONLY by the test-only invariant checker. `Kernel.recover` never compares `ev.integrity.prev` with the running head and never recomputes `self`. Two consequences:

(a) HISTORY REWRITE IS ACCEPTED. `sha` is exported and the record checksum is `sha(rec.events)`, so anyone with journal write access can edit an event and repair the checksum. Proven: flipping `invocation.completed` -> `invocation.failed` with `landedExternal:false` and zeroing a `grant.settled` payload gives
  discarded records = 0
  protectedEffects: 1 (before) -> 0 (after)   grant settled: {invocations:1} -> {invocations:0}
Protection erased and budget restored, and `recover` raises nothing. Only the test harness notices ([I6]).
(b) A HOLE IS NOT A TRUNCATION. `readJournal`'s comment says "discarding any TRAILING torn record", but the loop skips ANY invalid record and continues. Corrupting a middle record gives `discarded=1, recovered cells = 3 of 4`, no error, and the kernel then continues appending on top of a broken chain ([I6],[I6b] from the harness only). Doc 19 §1 assumes "a torn trailing record is detectable" — the implementation does not distinguish trailing from interior, so silent partial history passes as a successful recovery.
**Proposed resolution.** Move chain verification into the read path: `recover` MUST verify `prev`/`self` per event and MUST fail loudly (or enter a quarantined read-only mode) on a break, rather than returning a plausible-looking kernel. Distinguish a torn TRAILING record (discard, log) from an interior gap (hard failure). If tamper-evidence rather than tamper-detection is a goal, the checksum must not be computable from public inputs alone — anchor the chain head with a MAC or external attestation, or state explicitly in doc 19 that the threat model excludes an attacker with journal write access.

#### [SERIOUS] prototypes/kernel-semantics/src/kernel.ts:104, 313 (effectClassOverride); src/kernel.ts:136-138 (register)
**Attack.** Doc 17 §11 rests on the kernel branching only on "declared, negotiated properties". `effectClassOverride` lets the CALLER unilaterally overwrite the capability's declared class, downward, with no floor and no journaled attribution of who overrode what. Proven — it defeats a deny-class policy AND every irreversible protection at once:

  await k.invoke(e,'payment.charge',{amount:1},g,{step:'b', effectClassOverride:'pure'});

Nothing checks either.
**Proposed resolution.** Remove the downgrade. If a per-request class is genuinely needed, permit MONOTONIC STRENGTHENING only (a caller may make an effect more dangerous, never less), require the manifest to declare an allowed range, and journal both the manifest class and the effective class with the overriding authority in `invocation.admitted`. Validate traits at `register()`: reject `probeable`/`compensatable` without the method, and enforce `resumable` in `settle`'s suspend branch.

#### [MODERATE] prototypes/kernel-semantics/src/kernel.ts:378-384, 650-654, 801-822, 1197-1215 (budget and resource bounding)
**Attack.** The kernel bounds exactly one quantity — invocation count within one lineage — and nothing else, while presenting itself as a general budget/resource authority.

(a) NON-INVOCATION UNITS ARE UNENFORCED. Reservation only checks `invocations`; `usage` proposals are summed and committed verbatim. With `limits:{tokens:100}`, one `llm.mock` call proposing 120 tokens commits, and the project's own checker reports `[I5] grant overspent tokens: 120 > 100`. A capability sets its own meter.
(b) RESERVATIONS LEAK PERMANENTLY, THREE WAYS. A crash between the admission commit and the dispatch commit (two separate records) leaves state `admitted`; recovery triage only inspects `state === 'dispatched'`, so the invocation is a zombie with no path to any terminal state and its hold is never released: `state=admitted, uncertain[]=0, reserved={invocations:1}, limit={invocations:1}` — the grant is dead forever. Doc 19 crash-matrix row 1 asserts "Reservation is released by recovery triage"; it is not, and the sweep passes because no invariant checks for stranded holds. `resolveUncertainty` commits no `grant.released`/`grant.settled`, so resolving even by `compensate` (effect reversed!) leaves `reserved={invocations:1}, settled={}`. `suspended` never releases either.
(c) ONE INVOCATION CAN WRITE UNBOUNDED DURABLE RECORDS. There is no cap on proposals or delegations per generator. A capability yielding 2000 delegates under a grant of TWO invocations produced 4007 durable writes and 4011 journal events in 240ms, outcome `completed`, invariants clean — each refused delegation still commits `grant.attenuated` + `grant.denied`. Budget bounds successful work, not journal growth.
**Proposed resolution.** Enforce every declared unit at admission and at settlement (reject or fail the settlement when a usage proposal would exceed a chain ceiling, rather than committing an overspend). Add a recovery triage rule for `admitted`-without-`dispatched` (release the hold, mark the invocation abandoned) and emit `grant.released`/`grant.settled` from `resolveUncertainty` and from the suspend path. Add per-invocation caps on proposal count, delegation count and staged bytes, and add invariants for "no stranded reservation" and "every non-terminal invocation is reachable to a terminal state".

#### [MODERATE] prototypes/kernel-semantics/src/kernel.ts:1223-1225 (state) and 326-355 (dedup before admission); reference-model/model.ts:95-107
**Attack.** Two holes on the DRIVER side of the barrier, plus a reason the differential oracle cannot find either.

(a) `state()` returns the LIVE `ExecutionState` typed `Readonly<ExecutionState>` — shallow, so every Map and Set inside is mutable. A driver (doc 17 §1: may "read committed projections", may NOT append events) can do strictly worse than appending: mutate truth leaving no record at all. Proven — `st.protectedEffects.clear(); st.effectIndex.clear(); st.grants.set(id, {...g, settled:{}})` then replay the identical irreversible charge -> `completed`, two `invocation.completed` records, `[I13]` from the harness, and nothing in the journal explains why protection vanished.
(b) The dedup fast path returns BEFORE the revoked/expired/policy checks (which start at kernel.ts:359). Revoked authority yields success responses.
(c) The "independent" oracle is not independent: `ReferenceModel.invoke` (model.ts:95-107) checks dedup first and authority second — the same ordering, so the differential test structurally cannot detect (b). **Proposed resolution.** Return deep-frozen or structurally copied projections (or narrow the public surface to accessor methods); never hand out live kernel containers. Rewrite the reference model from the normative document rather than from the implementation, and have a second person write it — an oracle that shares the implementation's decision order tests only for typos.

## Workflow / durable-execution engineer (Temporal, Restate, DBOS background) — adversarial review #2 of the executable Kyxo semantic kernel
**Freeze vote:** NOT READY TO FREEZE
**Reasoning:** Eight of my twelve findings require changes to the record format itself, and four of those are FATAL. Concretely, freezing today would freeze: (1) an effect index derived only from terminal outcomes, so an in-doubt effect key is unowned and double-applies (a1b: 2 irreversible wires, 0 invariant violations); (2) per-execution grant copies in the checkpoint, which make fork an authority multiplier (a3: 55 invocations under a 5-invocation grant); (3) an effect key with no attempt/epoch dimension and no invalidation record, which makes retry structurally impossible (a2: provider ran once, ever); (4) a decorative `leaseEpoch` with no fencing semantics next to a dedup gate that two concurrent callers both pass (a12: 2 charges, I13 fires); (5) no wall clock, no deadline, no timer event kinds, while doc 08 §7.4 normatively promises durable timers and deadline escalation; (6) a checkpoint with no digest binding it to the journal fold, so live memory and journal can silently diverge and the fork redoes an adopted effect (a11: 2 shipments, `consistent === true`); (7) a fork event with no parent-cut hash, so no child can attest its ancestry; (8) grant payloads that omit `expiresAt`, so recovery erases expiry (a5). Retrofitting a claim record, an attempt dimension, a lease epoch, a timestamp, a fold digest and a parent-cut hash into a frozen journal is the most expensive migration in this class of system — it is exactly the migration Temporal spent years on and DBOS designed around.  A second, methodological reason to withhold the vote: the evidence base cannot currently detect these classes of bug. The reference model re-encodes the kernel's own decisions (model.ts:96-97 dedups on ANY prior key including failures; model.ts:138-155 copies grants at fork), so the differential oracle is blind to findings 1, 2 and 3 by construction. The property and fuzz harnesses issue a fresh full-budget grant after every simulated restart (property.test.ts:139-149, fuzz.ts:141-149), which hides budget leakage and expiry loss across recovery. Every suite is strictly sequential, so nothing has ever exercised concurrency. And invariants.ts contains no I20 at all, despite kernel.ts:731-734 advertising it as the checkpoint-consistency guarantee. The work is genuinely good — the structural commit barrier holds, handle-identity authority holds against forgery, the fork/resume verb split is right, and the 32-point crash sweep is real engineering. But 39 green tests plus 150 clean fuzz seeds currently means 'the kernel agrees with a model that shares its assumptions, under workloads that avoid its failure modes'. Fix the four FATALs, land the format fields for time/claim/lease/fold-digest/parent-cut-hash, rebuild the oracle so it is written from doc 17 rather than from kernel.ts, add concurrent and multi-restart generators — then re-vote. I would expect that to be weeks, not months, and I would expect the freeze to pass on the second attempt.
**Strongest objection:** You have reinvented Temporal's activity lifecycle without its two load-bearing parts, and the parts you dropped are the ones that make it safe. Temporal writes ActivityTaskScheduled BEFORE dispatch — that marker owns the idempotency slot, carries the attempt counter, and carries the lease — so an in-flight activity can be re-leased with a fencing token, retried with a policy, or timed out by the server. Kyxo writes `invocation.dispatched` with the effect key in the payload and then discards that information at recovery (kernel.ts:1171-1187 folds only completed/failed/canceled). The result is that the kernel's headline feature, `uncertain`, is a label on an invocation that does not own its effect key: a1b.ts shows the same logical step wiring a million dollars twice, with an unresolved `uncertain` record and a `completed` record sitting side by side in one execution and `checkInvariants()` returning []. The very next thing an operator does in a real incident — re-run the step — is the thing the design exists to prevent, and nothing stops them.  The reply I expect is 'the operator should have resolved the uncertainty first'. That is a process control, not a semantic one, and this document set spends its credibility on the claim that the kernel makes these properties structural rather than cooperative. Meanwhile `resolveUncertainty` does not even update the effect index (a11: live fold size 0, journal fold size 1), does not release the reservation it is settling, and produces no output for the original caller — so 'resolve it first' does not close the hole either. Uncertainty as currently built is a state you can enter, observe, and label, but not one you can safely leave: there is no probe scheduler, no deadline, no bulk disposition tooling, no way to list what is in doubt across executions, and no fencing to stop a second actor acting while you decide. It moves the in-doubt-transaction problem to a human, and then gives the human strictly less tooling than a 1990s XA transaction manager's `xa_recover` gave them.

### Findings

#### [FATAL] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:1171-1215 (recover: effect-index rebuild + uncertainty triage) and :326-355 (dedup gate)
**Attack.** `uncertain` is a state on the INVOCATION but not a claim on the EFFECT KEY. recover() only writes effectIndex on `invocation.completed` / `.failed` / `.canceled`; a dispatched-then-uncertain invocation therefore leaves its key completely absent from the replay cache AND from protectedEffects. Any at-least-once caller — a supervisor, a retry loop, an upstream queue redelivery — that re-issues the identical logical step is admitted with zero refusal and re-performs the irreversible effect. Reproduced at /tmp/.../scratchpad/atk/a1b-uncertain-doubleapply.ts: crash after the wire leaves the bank -> recover() reports 1 uncertain -> `invoke(exec,'bank.wire',{to:'ACME',amount:1_000_000},g,{step:'payout'})` returns `completed, deduplicated=undefined`, WIRES SENT: 2, and `checkInvariants()` returns []. The execution now holds an `uncertain` record and a `completed` record for the SAME effect key and nothing flags it. This is precisely the failure the uncertainty state exists to prevent; Temporal blocks it by writing an ActivityTaskScheduled marker that owns the idempotency slot before dispatch, Restate by journaling the invocation id at request time. Kyxo journals `invocation.dispatched` WITH the effectKey in its payload and then throws that information away at recovery.
**Proposed resolution.** Make the effect key claimed at DISPATCH, not at outcome. recover() must fold `invocation.dispatched` into effectIndex as `{outcome:'in-doubt'}`, and invoke()'s dedup gate must treat an in-doubt entry as a hard refusal for every class in UNSAFE_TO_AUTO_RETRY (and as a re-lease for safe classes, once a lease exists). Add an `in-doubt` outcome to EffectIndexEntry and a corresponding invariant: no execution may hold both an unresolved `invocation.uncertain` and an `invocation.completed` for one effect key. Record-format impact: `invocation.dispatched` must be a first-class claim record, so the freeze must state that.

#### [FATAL] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:919-935 (fork: `grants: new Map(cp.grants.map(...))`) and :278-282 (remaining) and src/invariants.ts:166-197 (I5/I18 are per-execution)
**Attack.** Grant budgets are a PER-EXECUTION projection. fork() copies the GrantState objects (same grant ids, same limits, reserved/settled as of the cut) into a brand-new execution, so every fork receives a fresh copy of the remaining budget under the same authority. The invariant checker only ever compares used-vs-limit inside one execution, so it never fires. Reproduced at /tmp/.../scratchpad/atk/a3-fork-budget.ts: one grant with `limits:{invocations:5}`, checkpoint immediately, spend the parent to exhaustion (5), then fork the SAME checkpoint ten times and spend each child to exhaustion -> TOTAL 55 admitted invocations against a 5-invocation grant, `checkInvariants()` length 0. This generalises to money: fork N times, spend N x budget. It also breaks revocation — a revoke() issued on the parent after a fork does not touch the child, and there is no lineage-global grant ledger anywhere in the record format to make it possible. A14/ADR-014 sell 'attenuated quantitative grants'; forking is an unattenuated multiplier.
**Proposed resolution.** Budgets must be accounted against a grant ledger keyed by grant id ACROSS the lineage tree, not against a per-execution copy. Either (a) fork MUST attenuate: mint a fresh child grant id whose limits are carved out of the parent's remaining and journal `grant.attenuated` in the child, or (b) introduce an explicit lineage/tenant ledger record and make `remaining()` read it. Add an invariant that sums reserved+settled for a grant id over ALL executions sharing it and asserts <= limit. Record-format impact: the checkpoint's `grants: readonly GrantState[]` currently encodes copy-semantics; freezing it freezes the bug.

#### [FATAL] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:661-676 (settleFailure writes outcome:'failed' into effectIndex) and :343-355 (dedup gate returns the cached failure)
**Attack.** The replay cache conflates 'this key ran' with 'this key succeeded'. A transient failure permanently poisons the effect key for the whole lineage, and there is NO retry primitive in the kernel. Reproduced at /tmp/.../scratchpad/atk/a2-failed-poison.ts: a provider that returns `{status:'failed',error:'ECONNRESET'}` on attempt 1 and succeeds thereafter. attempt1=failed; attempt2 = `failed, deduplicated=true, error=undefined` (the error string is also lost); after `Kernel.recover()` attempt3 = same. Provider attempts actually made: 1, forever. There is no `attempt` in EffectKey (kernel.ts:316-320 hashes only cap+step+request), no `effect.invalidated` event kind, and no API to clear an entry short of fork(). A durable-execution engine whose activities cannot be retried is not a durable-execution engine — Temporal's RetryPolicy and Restate's automatic retry are the single most-used feature of both. Worse, the reference model encodes the SAME rule (reference-model/model.ts:96-97 `if (prior !== undefined) return {state:'deduplicated'}`), so the differential oracle is structurally incapable of catching it.
**Proposed resolution.** Split the two questions the effect index answers. Keep a terminal-success index (dedup / at-most-once) and a separate attempt log. A `failed` outcome must NOT occupy the key; instead journal `invocation.failed` with an attempt number and permit re-admission under a declared retry policy, with the attempt folded into the invocation record but NOT into the effect key (so the key still dedups a real success). Add `effect.invalidated` for the operator escape hatch. Record-format impact: needs an attempt/epoch dimension and a retry-policy field on `invocation.admitted`.

#### [FATAL] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:300-355 (invoke's synchronous prologue) and :404 (`leaseEpoch: 1` hardcoded) and src/types.ts:279,299 (leaseEpoch)
**Attack.** invoke() reads the dedup gate and commits admission/dispatch synchronously before its first `await`, and writes effectIndex only at settle. Two concurrent invocations of the same effect key therefore both pass the gate and both execute. Reproduced at /tmp/.../scratchpad/atk/a12-concurrent-dedup-race.ts: `await Promise.all([invoke(...charge...), invoke(...same charge..., {duplicateDelivery:true})])` with 1ms of I/O inside the provider -> CHARGES EXECUTED: 2, dedup/duplicate records journaled: 0, two `invocation.completed` for one key, and invariant I13 fires. This is not exotic: at-least-once delivery, a doubled webhook, or two workers is the ONLY reason a dedup mechanism exists. There is no lease, no mutex, no compare-and-set on the effect key, and `leaseEpoch` — the one field in the record format that could fence a stale worker — is hardcoded to 1 at dispatch, copied verbatim into PendingInvocation, and never incremented anywhere, including by the `re-lease` fork disposition. The entire test corpus (7 suites + fuzz) is strictly sequential, so the model has never been executed under the conditions it claims to handle. Temporal/Restate solve this with a single-writer partitioned task queue plus a monotonic run/attempt token; Kyxo freezes a decorative epoch field and no ownership concept at all.
**Proposed resolution.** Either declare single-writer-per-execution NORMATIVE and make the kernel enforce it (an execution-scoped async mutex around admission-through-settle, plus a documented storage-level compare-and-set requirement), or make the effect key a real lease: journal a `effect.claimed` record with an incrementing leaseEpoch and reject a settle whose epoch is stale. Either way `leaseEpoch` must be defined and incremented, and the fuzz driver must generate interleaved concurrent invocations. Record-format impact: leaseEpoch semantics and a claim record must be pinned before freeze.

#### [SERIOUS] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:985 (`occurredAt: this.tick()`), :364 (`this.logicalClock > g.expiresAt`), src/types.ts:97-99; contradicts docs/08 §7.4 and §9 rows 2/10
**Attack.** There is no time in this system. `grep -niE 'timer|deadline|timeout|Date.now|heartbeat|wall.?clock' src/` returns nothing but `expiresAt` and the word `settled`. `occurredAt` is a monotonic counter incremented once per event, so grant expiry is denominated in EVENTS, not seconds: a quiet execution's grants never expire and a chatty one's expire in milliseconds. Doc 08 §7.4 states 'Every invocation and every suspension may carry a deadline; the scheduler enforces them with durable timers' and §9 row 10 specifies deadline-driven approval escalation; doc 19 row 15 claims a suspension that survives 'a human who never answers'. The kernel implements none of it: InvocationRecord has no deadline, there is no timer event kind, no `invocation.deadline.exceeded`, no scheduler, and no wall-clock field on KernelEvent (doc 17 line 72 even says occurredAt 'MUST NOT be used as an ordering authority', leaving nothing that can). A suspension that must survive three weeks is a Map entry holding a budget reservation with no expiry, no escalation, and no way for an operator to query 'what has been waiting longest' — the only durable evidence is `invocation.suspended` stamped with a logical tick.
**Proposed resolution.** Before freeze: add a real `wallClockAt` (or `observedAt`) to KernelEvent alongside the logical `seq`; add `deadline` to `invocation.admitted` and `invocation.suspended` payloads; add `timer.armed` / `timer.fired` / `invocation.deadline.exceeded` event kinds; denominate grant `expiresAt` in wall-clock. Alternatively, scope doc 08 §7.4 down to 'deferred to Wave N' and say so in the freeze decision — but the format must reserve the fields either way, because retrofitting time into a frozen journal is the single most expensive migration in this class of system.

#### [SERIOUS] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:829-860 (checkpoint snapshots LIVE memory), :735-755 (resumeFromCheckpoint's I20 check), :801-823 (resolveUncertainty)
**Attack.** The checkpoint is a snapshot of the live projection, but resolveUncertainty commits to the journal WITHOUT updating the live effectIndex (kernel.ts:801-823 touches only protectedEffects, and only for external-irreversible). The two folds diverge, and I20 cannot see it because resumeFromCheckpoint compares ONLY `cell` — artifacts, effectIndex, evidence and grants are in the snapshot blob and are never validated against the journal. Reproduced at /tmp/.../scratchpad/atk/a11-checkpoint-divergence.ts with an `external-compensatable` shipment: crash -> uncertain -> operator `adopt-landed` (the sanctioned disposition, journaled with authority 'ops:jane') -> LIVE effectIndex size 0 while a fresh `Kernel.recover()` on the same journal yields size 1. Checkpoint taken from that live state carries protected:[] and an effectIndex missing the adopted key; `resumeFromCheckpoint().consistent === true`; fork from it and re-invoke the same step -> `completed`, REAL SHIPMENTS: 2, `checkInvariants()` = []. So: a checkpoint whose own history records the adoption produces a fork that redoes the adopted effect, and the invariant advertised as guarding exactly this (I20, 'snapshot-fold equals journal-fold at the cut') is a `cell`-only spot check that is not even present in invariants.ts.
**Proposed resolution.** (1) resolveUncertainty must update effectIndex for ALL classes, not just protectedEffects for irreversible. (2) Build checkpoints by folding the journal to cutSeq, never from live memory — or, if live snapshotting stays for speed, store a `foldDigest` in the Checkpoint and verify it against a journal re-fold at checkpoint time AND at fork/resume time, failing closed. #### [SERIOUS] **[BLOCKS FREEZE]** prototypes/kernel-semantics/src/kernel.ts:1120-1195 (recover) and src/storage.ts:125-141 (readJournal) and :946-959 (fork chain restarts at 'genesis')
**Attack.** recover() performs ZERO integrity verification. readJournal() silently drops any record whose checksum fails and CONTINUES with the next one (`continue`, not `break`), so corruption anywhere — not just a trailing torn write — removes committed evidence and recovery proceeds happily on a broken chain. Reproduced at /tmp/.../scratchpad/atk/a9-corruption-erases-evidence.ts: flip four bytes in the settlement record carrying `invocation.completed` for a landed `external-irreversible` charge -> recover() returns discarded:1 (a value no caller is obliged to inspect), protectedEffects drops from 1 to 0, and re-invoking the identical charge is ADMITTED and executed. checkInvariants() would have caught it (I6 chain break at seq 8, I6b seq gap) but the kernel never calls it; the invariant checker lives only in tests. Separately, a fork's hash chain restarts at 'genesis' and `execution.forked` records parentExecution/cutSeq but NOT the parent's chain hash at the cut, so no child can cryptographically attest which parent state it descends from — tampering with the parent leaves every fork's chain intact and 'valid'.
**Proposed resolution.** recover() must verify the hash chain as it folds and FAIL CLOSED on any break or gap (mark the execution `quarantined`, refuse invoke/fork, surface it), rather than returning a count. readJournal() must stop at the first invalid record rather than skipping it, so a mid-journal corruption cannot be papered over by later records. Add `parentCutHash` to the `execution.forked` payload and make each execution's genesis chain into it. Record-format impact: parentCutHash is a new field.

#### [SERIOUS] prototypes/kernel-semantics/src/kernel.ts:537-542 (settle's suspend branch discards all staged proposals) and :692-726 (resumeInvocation)
**Attack.** Two holes on the suspend/resume path, which is the path every long-running human-in-the-loop workflow uses. (1) settle() computes `landedExternal` and then, on `status:'suspend'`, commits only `invocation.suspended` and drops the entire staged set. A capability that lands an irreversible external effect and then suspends for a countersignature loses all evidence: /tmp/.../scratchpad/atk/a6b-suspend-lost-effect.ts shows 1 real escrow release, protectedEffects:[], zero artifact events, and after the human declines, the journal's durable truth is `invocation.failed {landedExternal:false}` for an effect that LANDED — the exact 'external effect lost without journal evidence' state, with invariants clean. (2) resumeInvocation is a second, unguarded copy of the invoke loop: it has no `delegate` branch, so a resumed capability's delegate proposal is pushed into staging, silently dropped by settle()'s switch (no case, no default), and the generator receives `undefined` where the contract promises a DelegationOutcome — no child invocation, no attenuated grant, no journal record (/tmp/.../scratchpad/atk/a7-resume-path.ts: 'child invocations journaled: 1 (expected 2)', 'attenuated grants minted: 0'). It also has no try/catch, so a provider that throws on resume leaks its staging set permanently: stagedCount 1 and I16 violated forever, in a live kernel.
**Proposed resolution.** Commit staged `external` and `artifact` proposals at the suspend barrier (a suspension is a settlement of everything before it) or refuse the suspension when unflushed external proposals exist. Factor the generator-driving loop into ONE private method used by both invoke() and resumeInvocation(), including the delegate branch, the try/catch that releases staging, the cancel check, and the commit-phase policy pass. Add an exhaustiveness check (`default: assertNever(p)`) to settle()'s proposal switch so a new proposal type can never be silently dropped again.

#### [SERIOUS] prototypes/kernel-semantics/src/kernel.ts:312-320 (rights + effectClassOverride) and :634-636/:1095-1107 (usage -> moveBudget)
**Attack.** Three authority holes reachable from ordinary API surface. (1) `rights` are NEVER read by invoke(): they are checked only inside attenuate() and by the test invariants. A grant carrying `rights:['weather:read']` invokes payment.charge and completes (/tmp/.../scratchpad/atk/a10-rights-and-override.ts). ADR-013's ocap story protects the HANDLE and then ignores what the handle authorizes. (2) `InvokeOptions.effectClassOverride` lets the CALLER declare a manifest-irreversible capability to be `pure`, with no check that the override narrows rather than widens. Same script: charge declared `pure`, crash after landing -> recovery reports 0 uncertain, the invocation sits `dispatched/pure`, protectedEffects 0, and the replay is admitted and executed. The kernel's entire safety story is 'we branch on the declared effect class' — and the declaration is caller-controlled. (3) usage proposals are never validated and moveBudget applies them to the whole ancestor chain, so a capability can propose `{type:'usage',units:{tokens:-1e9}}` and zero its own AND its ancestors' settled budget: /tmp/.../scratchpad/atk/a4-negative-usage.ts takes settled tokens 240 -> 0, then spends 960 more against a 1000-token limit, invariants clean.
**Proposed resolution.** invoke() must require a right that covers the capability (a manifest-declared required-right, matched against the grant chain) and journal `grant.denied` otherwise. effectClassOverride must be constrained to be no weaker than the manifest class (or removed and replaced by a policy-stage decision). Reject usage proposals with negative or non-finite units at the commit gate, and make moveBudget throw on underflow instead of `Math.max(0, ...)`, which currently masks every accounting error.

**Attack.** Authority does not survive its own record format. #### [MODERATE] prototypes/kernel-semantics/src/kernel.ts:1197-1215 (triage) and :801-823 (resolveUncertainty); contradicts docs/19 §3 rows 1 and 2
**Attack.** Doc 19 row 1 says 'Reservation is released by recovery triage' and row 2 says 'safe -> re-lease'. Neither exists in the code. recover() triages ONLY UNSAFE_TO_AUTO_RETRY classes into `uncertain`; a crashed `external-idempotent`, `local` or `pure` invocation stays `dispatched` forever, and no code path anywhere releases a reservation at recovery. /tmp/.../scratchpad/atk/a8-leaked-inflight.ts: three crashes mid-flight on remote.a2a under a 3-invocation grant -> recovery reports 0 uncertain, three permanently `dispatched` zombies, reserved:{invocations:3}, remaining budget 0, and every one of them appears in every future checkpoint's `pending`, so every future fork must supply a disposition for them. The prototype has no re-lease, no lease timeout, no reaper, and no API that could perform one. Separately, resolveUncertainty commits `uncertainty.resolved` + a terminal event but NEVER emits `grant.settled`/`grant.released`, so resolving an uncertainty also leaks its reservation permanently. Operationally this is where the fork-disposition design also fails: ForkOptions.dispositions is a flat `Record<invocationId, ForkDisposition>` with a hard throw per missing id, no default, no bulk predicate (by effect class / capability / age), no per-disposition authority or reason field in the journal, and no query API to enumerate pendings other than reading cp.pending. With 500 pendings in a real incident, the operator's interface is a hand-built 500-entry object literal.
**Proposed resolution.** Implement recovery triage as documented: release reservations for invocations with no outcome, and add an explicit `reLease(invocationId)` that increments leaseEpoch and journals it. Add `grant.released` to every resolveUncertainty terminal path. For forks: allow `{default: ForkDisposition}` plus per-effect-class rules, require an `authority` and `reason` per non-default disposition, journal the resolved per-invocation map, and add a `pendingReport(checkpointId)` projection. Then correct doc 19 §3 rows 1 and 2, which currently assert behaviour the kernel does not have.

### Tests this reviewer would add
- Concurrency: an interleaving fuzz driver that issues N overlapping invoke() calls per execution (identical and distinct effect keys, with real awaits inside providers) and asserts at-most-once per key plus I13 after every interleaving — today every suite is sequential and a12 breaks the model with two calls.
- Retry semantics: a flaky provider that fails k times then succeeds, asserting the effect actually executes k+1 times, that the error string survives each attempt, that budget settles once, and that the same holds across a Kernel.recover() in the middle of the retry sequence.
- Lineage-global budget: fork a checkpoint N times and spend every branch, asserting sum(reserved+settled) for a grant id ACROSS all executions never exceeds its limit; plus a revoke() on the parent after fork that must bind in every live descendant.
- Snapshot/journal equivalence (a real I20, promoted into invariants.ts and run after every property op): fold the journal to cutSeq independently and assert byte-equality with the checkpoint snapshot over cell, effectIndex, protectedEffects, evidence and grants — with a dedicated case covering a resolveUncertainty between two checkpoints.
- Recovery fail-closed: corrupt a non-trailing committed record (and separately, tamper with one event's payload leaving the checksum stale) and assert that recover() refuses to serve the execution rather than returning a `discarded` count and continuing; plus crash injection INSIDE recovery, during the `invocation.uncertain` commit, followed by a second recovery.
- Suspension durability over long horizons: land an external effect then suspend; assert the landed evidence is committed at the suspend barrier; then assert deadline expiry produces a typed outcome, that the reservation is released, and that resume after a restart re-enters the provider with the journaled payload and correctly handles a delegate proposal (today it is silently swallowed).
