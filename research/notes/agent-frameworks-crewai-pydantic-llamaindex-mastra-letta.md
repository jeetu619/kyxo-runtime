# Agent Frameworks II: CrewAI, PydanticAI, LlamaIndex Workflows, Mastra, Letta, smolagents — Computational Models

Research note for the universal-runtime kernel investigation. Date of research: 2026-08-15.

## Scope

This note covers the six remaining materially-different agent frameworks, focused on each one's **fundamental computational model** rather than its feature list:

- **CrewAI** (Python, v1.15.16) — role-based crews + event-driven flows (a duality inside one framework)
- **PydanticAI** (Python, v2.31.0, released 2026-08-14) — typed agents with structured outputs as the spine, plus `pydantic-graph` and a first-class **"capabilities"** extension system
- **LlamaIndex Workflows** (`llama-index-workflows` 2.23.1, released 2026-08-12; now part of the `llama-agents` monorepo) — event-driven pub/sub step orchestration
- **Mastra** (`@mastra/core` 1.59.0, TypeScript) — schema-typed step graphs with suspend/resume, plus durable agents and layered memory
- **Letta** (formerly MemGPT; Python server `letta` 0.16.8, now labeled legacy; active development moved to `letta-code`) — the memory-architecture reference: agents as persisted server-side state
- **smolagents** (HuggingFace, 1.26.0) — code-as-action ReAct agents

For each: computational model, state/persistence model, delegation model, and what it hard-codes. The closing sections answer the domain's key question: which computational models keep re-appearing, and what does each imply for a minimal kernel that should host all of them as strategies.

**Method caveat**: the official doc sites (docs.crewai.com, ai.pydantic.dev, docs.llamaindex.ai, mastra.ai, docs.letta.com, arxiv.org, deepwiki.com) were egress-blocked from this environment. All doc claims below were instead taken from the **in-repo documentation sources** (the same .md/.mdx files that build those sites) and from **direct source-code inspection** via raw.githubusercontent.com. This is generally *more* current than the rendered sites (CrewAI claims come from the `docs/edge/` pre-release tree). PyPI/npm version numbers are from the registries; exact release *dates* extracted by the fetch summarizer carry MEDIUM confidence unless noted.

## Findings

### 1. CrewAI — role teams AND event-driven flows in one framework

**Computational model in one sentence**: CrewAI is two computational models stapled together — *Crews* are LLM-orchestrated role teams executing an ordered task list (sequential) or a manager-delegated task pool (hierarchical), while *Flows* are developer-orchestrated event-reaction graphs built from decorated methods with typed shared state.

- FACT: A Crew requires `agents` and `tasks`; `process` is `sequential` (tasks in definition order) or `hierarchical` (a manager agent — from `manager_llm` or `manager_agent` — "coordinates task delegation and validates outcomes"). Crews support short-term/long-term/entity memory, tool-result `cache`, an `AgentPlanner` when `planning` is enabled, streaming, and checkpoint-resume of interrupted runs. Kickoff variants: `kickoff()`, `kickoff_for_each()`, `akickoff()` (native async), `akickoff_for_each()`, `kickoff_async()` (thread-wrapped). Output is a `CrewOutput` with `raw`, `pydantic`, `json_dict`, `tasks_output`, `token_usage`.
- SOURCE-CODE OBSERVATION (HIGH): The per-agent inner loop (`CrewAgentExecutor`) implements **two interchangeable action grammars**: `_invoke_loop_native_tools()` (provider-native function calling) and `_invoke_loop_react()` (text `Action:`/`Action Input:` parsing into `AgentAction`/`AgentFinish`). Both bound iterations with `max_iter`, execute tools through `execute_tool_and_check_finality()` with caching and `max_usage_count` limits, run before/after tool-call hooks, and emit events on a global `crewai_event_bus`. The module carries a deprecation note — the current tree adds `step_executor.py` and `agent_builder/`, indicating an executor rework in the v1.x line (INFERENCE, MEDIUM: the dual-grammar design persists).
- FACT: Flows are defined by decorating methods of a `Flow[StateT]` subclass: `@start()` marks entry points (multiple allowed; all satisfied starts execute, "often in parallel"), `@listen(x)` fires when method/label `x` completes (receiving its output as argument), `@router()` returns a string label that downstream `@listen("label")` methods match on, and `and_()`/`or_()` compose trigger conditions ("only when all … emit an output" / "when any…").
- FACT: Flow state is either **unstructured** (`self.state` dict, auto-UUID under `state['id']`) or **structured** (Pydantic model as the generic parameter). `@persist` (class- or method-level) snapshots state through `SQLiteFlowPersistence` by default. Two rehydration modes: **resume** (`kickoff(inputs={"id": uuid})` continues under the same flow UUID) and **fork** (`kickoff(restore_from_state_id=uuid)` loads the snapshot under a fresh id, "preserving source history"). This resume-vs-fork distinction is one of the cleanest checkpoint semantics in the survey.
- FACT: Flows gained a **unified memory API** — `self.remember(content)`, `self.recall(query)`, `self.extract_memories(content)` — persisted on disk via LanceDB, i.e., memory that belongs to the *orchestration layer*, not to an agent. Also `@human_feedback` (v1.8.0+) pauses execution and routes the human's reply "via LLM interpretation into outcomes"; `stream = True` yields incremental outputs; `plot()` renders the reaction graph; `usage_metrics` aggregates token usage across every LLM call inside the flow.
- SOURCE-CODE OBSERVATION (HIGH): The flow implementation is split into `crewai.flow.dsl` (decorators), `crewai.flow.flow_definition` ("serializable contracts" — the flow graph as data), and `crewai.flow.runtime` (execution), with a `FlowMeta` metaclass collecting decorated methods, plus `persistence/`, `visualization/`, `human_feedback.py`, and an experimental `_ConversationalMixin`. The definition/runtime split means CrewAI internally already treats "flow" as a portable description executed by an engine.
- INFERENCE (HIGH): CrewAI's own docs push Flows as the production pattern and Crews as an embedded component (`@listen`-wrapped `crew().kickoff()` calls). The framework has effectively conceded that role-team autonomy is a *strategy invoked from* deterministic orchestration, not the outer control structure.
- **Hard-codes**: the role/goal/backstory agent template; Task as a first-class unit; exactly two crew processes; the decorator DSL names; SQLite as default persistence.

### 2. PydanticAI — types as the spine, and a native "capability" system

**Computational model in one sentence**: A PydanticAI agent is a typed state machine (`Agent[Deps, Output]`) whose run traverses an explicit pydantic-graph (`UserPromptNode → ModelRequestNode → CallToolsNode → … → End`), where structured, schema-validated output is the termination condition and validation failure feeds a bounded retry loop.

- FACT: `Agent` is generic over dependency type and output type. Run surface: `run()` (async), `run_sync()`, `run_stream()`, `run_stream_events()`, and `iter()` which exposes the underlying graph run node-by-node (`AgentRun`). Cancellation (`CancellationToken` → `RunCancelled` with resumable state) and `UsageLimits` (tokens, requests, tool calls, spend) are built into the run contract.
- FACT: Output handling is the richest surveyed: `output_type` accepts Pydantic models/dataclasses/TypedDicts/scalars/unions, plus mode markers — `ToolOutput` (default: "tool calls are used to produce the output"), `NativeOutput` (provider structured-output feature), `PromptedOutput` (schema injected into instructions), `TextOutput`, and **output functions** ("the model is forced to call one of them, the call ends the agent run"). `@agent.output_validator` + `ModelRetry` implement a validation-driven repair loop with an explicit retry *budget* (`AgentRetries`).
- FACT: Dependency injection: `deps_type` + `RunContext[Deps]` carried into tools, dynamic instructions, and validators — runtime context is a typed parameter, not ambient globals.
- FACT (v2, significant for the mission): PydanticAI defines a **Capability** as "a reusable, composable unit of agent behavior" that can contribute any combination of: tools/toolsets, lifecycle hooks (intercepting model requests, tool calls, runs), instructions, model settings, and model *selection* — attached via `Agent(capabilities=[Thinking(...), WebSearch(...)])`. Twenty-five documented capabilities include `Compaction` (context summarization), `ToolSearch`, `ThreadExecutor`, `ProcessEventStream`, `ProcessHistory`, `ResolveModelId`, `SelectModel`, and the durability capabilities. Capabilities "can be always-on or loaded on-demand by the model itself." This is the closest existing artifact to the kernel-mission's "capability" primitive: an attachable bundle that spans tool surface + context policy + model choice + interception.
- FACT: `pydantic-graph` (separate library): nodes are dataclasses subclassing `BaseNode`; **edges are inferred from the return-type annotations of `run()`**; `GraphRunContext` carries typed state + deps; `End` terminates; `GraphBuilder(state_type, deps_type, input_type, output_type)` assembles graphs; `graph.iter()` gives step-through execution; mermaid diagrams are generated from the type structure. State persistence is supported so runs can be interrupted and resumed (FACT for the mechanism's existence; exact persistence classes not re-verified in this pass, MEDIUM).
- FACT: Durable execution: six integrations — Temporal, DBOS, Prefect (shipped as capabilities you "attach to an agent"), Restate ("lives in the Restate SDK and builds only on Pydantic AI's public interface"), plus Kitaru and Airflow externally. The Temporal doc is precise about the determinism boundary: the **agent run loop is workflow code** (deterministic, replayable, no I/O), while **model requests, tool calls, and MCP communication run as activities**; payloads crossing the boundary must be Pydantic-serializable (2MB default limit); streaming is buffered in activities and replayed; `Agent.run_sync()` raises `UserError` inside workflows.
- FACT: Multi-agent patterns are deliberately minimal: (1) *delegation* — a tool function calls another agent with `usage=ctx.usage` so child usage accrues to the parent's budget; (2) *programmatic hand-off* — application code sequences agents, passing `message_history`; (3) *graph-based control* via pydantic-graph. There is no built-in team/crew construct.
- **Hard-codes**: the shape of the agent step graph (prompt → model request → tool calls → repeat); Pydantic as the universal validation substrate; Python type annotations as the graph-edge language.

### 3. LlamaIndex Workflows — pub/sub steps, now the core of "LlamaAgents"

**Computational model in one sentence**: A workflow is a set of async functions that *subscribe to event types* (declared via parameter annotations on `@step` methods) and *emit events* (declared via return annotations), with a shared `Context` store — a typed pub/sub dataflow rather than an explicit graph.

- FACT: The repo formerly `workflows-py` is now the **llama-agents monorepo** ("an event-driven, async-first, step-based way to control the execution flow of AI applications"), containing `llama-index-workflows` (the core library, v2.23.1, 2026-08-12), `llama-agents-server`, `llama-agents-client`, `llama-agents-control-plane`, `llama-agents-dbos`, and `llamactl`. The workflow library is standalone (`pip install llama-index-workflows`), independent of the main `llama_index` package.
- SOURCE-CODE OBSERVATION (HIGH): In `workflow.py`, steps are discovered from `@step`-decorated methods (`_get_steps_from_class()`) or free functions registered via `add_step()`; each carries a `_step_config`. The workflow *infers* its `start_event_class` and `stop_event_class` from step signatures and return annotations. `_validate()` performs static graph checks before running: every event produced must be consumed, all steps reachable from `StartEvent` (or `HumanResponseEvent` — human input is a first-class entry point), and only `StopEvent`/`InputRequiredEvent` may be terminal. `run()` returns a `WorkflowHandler`, "a future-like object" that can be awaited for the result or iterated via `handler.stream_events()`. `num_concurrent_runs` bounds simultaneous runs, with scoping delegated to the runtime ("How the limit is scoped is up to the runtime; the basic runtime applies it to this workflow instance within the process") — i.e., there is an explicit **runtime abstraction** beneath the workflow definition (`runtime/control_loop/` in the tree).
- FACT: The `Context` object spans steps and runs: `ctx.store.edit_state()` for shared typed state; contexts are serializable — "launch a workflow, save information within it, serialize the state of a workflow and resume it later." The context package separates `state_store.py`, `serializers.py`, `external_context.py`/`internal_context.py`. Retry policies (`retry_policy.py`) and resource injection (`resource.py`) are per-step concerns. Instrumentation is automatic and OpenTelemetry/Arize-Phoenix compatible.
- FACT (MEDIUM on details): The monorepo advertises "pluggable durability"; the presence of `llama-agents-dbos` (SOURCE-CODE OBSERVATION of the package listing) indicates a DBOS-backed durable runtime for workflows, consistent with the runtime abstraction above. The server packages expose workflows as REST services with human-in-the-loop support.
- INFERENCE (HIGH): Compared with graph frameworks, routing here is *nominal typing*: emitting `MyEvent` is the act of routing; fan-out is multiple steps subscribing to one event type; fan-in is `ctx.collect_events` (`collect.py`). The graph exists only implicitly — recoverable by static analysis of type annotations (which `_validate()` and the visualization utilities do).
- **Hard-codes**: asyncio as the substrate; event classes as the only routing currency; one Context per run; Python type annotations as subscription declarations.

### 4. Mastra — schema-typed step graphs, suspend/resume, and agents-wrapped-in-workflows

**Computational model in one sentence**: Mastra workflows are explicitly composed step graphs (`createStep` → `.then/.parallel/.branch/.dowhile/.dountil/.foreach/.map` → `.commit()`) where every step boundary is a validated schema contract (Zod/Valibot/ArkType), and pausing is a first-class typed operation.

- FACT: `createStep({inputSchema, outputSchema, execute})`; `createWorkflow({inputSchema, outputSchema})` chains steps and is finalized with `.commit()`. Control flow: `.then()` sequential; `.parallel()` (all must complete; results keyed by step id); `.branch()` ("only one branch executes based on which condition evaluates to true first", branches must share schemas); `.foreach()` with a `concurrency` option (default 1); `.dowhile()/.dountil()` with `iterationCount` guards; `.map()` for data reshaping (`getStepResult()`, `getInitData()`, `mapVariable()`); nested workflows and `cloneWorkflow()`. Runs execute via `run.start()` or `run.stream()` (event-emitting), with `restart()`/`restartAllActiveWorkflowRuns()` for interrupted runs; execution can use the built-in engine "or external runners like Inngest".
- FACT: **Suspend/resume is typed**: a step calls `suspend()` with a payload validated by its `suspendSchema`; resumption supplies `resumeData` validated by `resumeSchema`, targeting a step object or id. "When a workflow is suspended, its current execution state is saved as a snapshot" persisted in the configured storage provider, "surviving application restarts and deployments"; suspended runs are recovered via `getWorkflowRunById()` + `createWorkflowStateReader()`. Docs also cover snapshots, workflow-state, and **time-travel** as separate pages (existence FACT; time-travel details not fetched).
- FACT: Agents (`Agent` from `@mastra/core`) hold `id/name/instructions/model` (model addressed through Mastra's router as `'provider/model-name'` strings), run via `.generate()`/`.stream()`, and are positioned as the tool for "open-ended tasks" where "the steps aren't known in advance" — explicitly contrasted with workflows for predetermined processes.
- SOURCE-CODE OBSERVATION (HIGH): `@mastra/core@1.59.0` depends on the Vercel AI SDK provider packages (`@ai-sdk/anthropic`, `@ai-sdk/openai`, …), zod + arktype, and hono; **there is no xstate dependency** — the brief's hypothesis of XState-like internals is not supported at the dependency level; the workflow engine is Mastra's own.
- FACT: Memory is multi-layer and scoped by `resource` (user/entity) and `thread` (conversation): `lastMessages` history; **working memory** (persistent structured user data injected as system messages); **semantic recall** (thread- or resource-scoped vector retrieval); **observational memory** (background agents compress history into "dense observations"); **memory processors** trim/prioritize when context exceeds limits. Subagent delegation auto-scopes memory with deterministic ids (`{parentResourceId}-{agentName}`), and agents share memory by matching `resourceId`/`threadId`.
- FACT: **Durable agents** close the loop between the two models: `createDurableAgent()` "wraps a regular Agent so the agentic loop runs inside a workflow" — messages serialize into workflow input, steps are memoized, run state is persisted, streams are pubsub-backed and resumable via `observe(runId)`, and crash recovery is automatic (`recovery.durableAgents: 'auto'`) or manual (`recoverAllDurableAgents()`). Variants: `createEventedAgent()` (fire-and-forget), `createInngestAgent()` (Inngest-powered). A whole `long-running-agents` doc section covers background tasks, schedules, signals/signal-providers, and goals.
- FACT: Evals are runtime infrastructure, not just offline tooling: scorers ("automated tests that evaluate Agents outputs using model-graded, rule-based, and statistical methods") attach to agents *and to individual workflow steps*, run asynchronously with a `sampling.rate`, and write to a `mastra_scorers` table.
- **Hard-codes**: schema validation at every step boundary; the fluent combinator vocabulary; storage-provider abstraction as the persistence interface; AI SDK as the model layer.

### 5. Letta — memory-as-agent-state, agents as services

**Computational model in one sentence**: A Letta agent is a server-persisted state machine whose context window is *compiled on every step* from database-resident memory (blocks + message history + tool schemas), and whose defining tools edit that memory — the agent is its state, not its process.

- FACT: Letta descends from MemGPT (arXiv:2310.08560, Oct 2023 — the OS-inspired "virtual context management" paper: main context vs external context, self-editing memory via function calls; cited from prior knowledge since arxiv.org was blocked). The Python server (`letta` 0.16.8) is now labeled **"the legacy Letta server for V1 APIs"**, with active development moved to **letta-code** (Node 22+) and Letta Cloud ("Constellation"). This is a major 2026 shift: the reference memory architecture is migrating from a Python REST server toward a harness + cloud-state model.
- SOURCE-CODE OBSERVATION (HIGH): `letta/schemas/memory.py`: in-context memory is a list of `Block` objects — `label`, `value`, `limit` (character capacity) — plus `FileBlock` for attached files. `Memory.compile()` renders blocks into the prompt, wrapping each in XML tags with current/limit character counts; rendering strategy varies by agent type (standard, line-numbered for certain Anthropic agent types, git-style `<self>`/`<memory>` sections). A `ContextWindowOverview` schema gives full token accounting (system prompt, core memory, functions, message tiers). Memory rendering is thus a *deterministic function of persisted state*, versioned per agent type.
- SOURCE-CODE OBSERVATION (HIGH): `letta/functions/function_sets/base.py` defines the self-editing toolset: `core_memory_append`, `core_memory_replace` (exact-string replace; empty string deletes), plus the newer surgical editors `memory_replace`, `memory_insert`, `memory_rethink` ("large sweeping changes"); `archival_memory_insert` (tagged, embedded passages) and `archival_memory_search` (semantic + tag/date filters); `conversation_search` ("hybrid search (text + semantic similarity)" over full message history); `send_message` ("Send a message to the human user") — i.e., *even user output is a tool call*, making the action space uniform.
- FACT (docs via search snippets, HIGH): The three memory tiers: **core memory** = editable blocks pinned in the prompt ("the RAM"); **recall memory** = complete searchable message history; **archival memory** = explicitly stored passages in external vector storage (PostgreSQL + pgvector in the server implementation). Memory blocks can be **shared between agents** with consistent real-time views.
- FACT (docs via search snippets, HIGH) + SOURCE-CODE OBSERVATION: **Sleep-time agents**: creating a sleeptime-enabled agent actually creates two agents sharing memory blocks — the primary agent talks to the user but *lacks memory-editing tools*; those tools attach to the background sleep-time agent, which reorganizes memory asynchronously during idle periods. In source, `AgentLoop.load()` is a factory dispatching on agent type to `LettaAgentV2`/`LettaAgentV3` or `SleeptimeMultiAgentV3/V4`. Memory management is thus a *separable capability assigned to a different principal* over shared state.
- FACT: Letta Code persists agents ("memory, identity, and conversation history") in Letta Cloud while "the execution harness runs on various machines"; context and memory blocks are "tracked via git" in a **memory filesystem (MemFS)** with optional GitHub sync; skills load from global/project/agent scopes; `/sleeptime` performs "periodic dreaming" for offline self-improvement; agents "rewrite their context to improve and adapt over time." The agent/harness split — durable identity server-side, interchangeable executor client-side — is stated design.
- FACT: The API model is REST-first: agents are created and messaged over HTTP; conversation state lives server-side, so a client sends only the new message (contrast with every other framework in this note, where the caller owns history). Agent portability exists via the `.af` "agent file" export format (FACT, MEDIUM — from ecosystem knowledge and search results; not re-verified this pass).
- **Hard-codes**: the memory hierarchy and its tool names; server-side persistence of everything; the block abstraction (labeled, char-limited) as the unit of context; sequential per-agent message processing (OBSERVED BEHAVIOR, MEDIUM).

### 6. smolagents — code as the action language

**Computational model in one sentence**: A smolagents agent is a ReAct loop in which the model's action output is a *Python code snippet* executed by a restricted interpreter (CodeAgent) — tools are just Python functions in scope — with JSON tool calling (ToolCallingAgent) as the fallback grammar.

- FACT: The conceptual docs define an *agency spectrum* from "simple processor" to full "code agents" where the "LLM acts in code, can define its own tools / start other agents," and argue code beats JSON as action format because "we crafted our code languages specifically to express the actions performed by a computer" — composability, object management, generality, and training-data familiarity. They also counsel *against* agents when a deterministic workflow suffices.
- SOURCE-CODE OBSERVATION (HIGH): `MultiStepAgent._run_stream()` implements the loop: optional planning step (`planning_interval` → `_generate_planning_step()`), then `_step_stream()` per iteration up to `max_steps`. Memory is a typed step log — `SystemPromptStep`, `TaskStep`, `PlanningStep`, `ActionStep`, `FinalAnswerStep` — replayed into messages by `write_memory_to_messages()` each turn (memory is *recomputed into context every step*, not a rolling transcript). `CodeAgent._step_stream()` parses code via `parse_code_blobs()`, validates syntax, and executes through the configured executor; `ToolCallingAgent` uses native tool calling and executes tool calls in parallel via `ThreadPoolExecutor`. Termination: a tool/code flag `is_final_answer`; at `max_steps` exhaustion, `provide_final_answer()` asks the model to answer from accumulated memory. `step_callbacks`/`CallbackRegistry` hook every step; `RunResult` carries output, steps, token usage, timing.
- SOURCE-CODE OBSERVATION (HIGH): Delegation = **managed agents exposed as tools**: `managed_agents` are listed alongside tools in the model's action space; invocation routes through `execute_tool_call()` → the sub-agent's `__call__()`, wrapping its run with a `managed_agent` prompt template. There is no separate orchestration layer.
- FACT: Execution security is tiered: default `LocalPythonExecutor` is a custom AST interpreter ("executes … operation by operation") with an import allowlist, submodule blocking (e.g. `random._os`), and a cap on "total count of elementary operations"; docs state plainly that "no local python sandbox can ever be completely secure." Remote code-snippet executors: E2B, Docker, Modal, Blaxel (selected by `executor_type`), or full-system sandboxing for multi-agent setups.
- FACT: PyPI 1.26.0; the pitch is minimalism — "core agent logic fits in approximately 1,000 lines"; model-agnostic via transformers/LiteLLM/etc.
- ABSENT: durable execution, state persistence beyond the in-process `AgentMemory`, workflow constructs, policy beyond the executor sandbox. smolagents is a pure harness + action-grammar + executor stack.
- **Hard-codes**: the ReAct loop shape and prompt templates; code-block parsing grammar; the tool/managed-agent calling convention.

### 7. Cross-cutting: the recurring computational models (the key question)

Across the six frameworks, five computational models recur, and every framework is a composition of two or more of them:

1. **Event-driven steps** (LlamaIndex Workflows; CrewAI Flows; Mastra's evented/signals layer). Two sub-variants matter architecturally: *type-routed pub/sub* (LlamaIndex: emitting an event of type T is the routing act) and *completion-listening* (CrewAI: `@listen(method_or_label)` reacts to a producer finishing). Both reduce to: a scheduler that matches emitted facts against subscriptions and starts step executions.
2. **Typed step graphs / state machines** (Mastra workflows; pydantic-graph; CrewAI flow_definition's "serializable contracts"). Edges come either from explicit combinators (`.then/.branch/.parallel`) or from type annotations (pydantic-graph return types; LlamaIndex event signatures). In all cases the graph is *static enough to validate and visualize before running* — every one of these frameworks ships a validator and a diagram generator (INFERENCE, HIGH: pre-run static checkability is a de facto requirement of the model).
3. **Role-team orchestration** (CrewAI Crews; loosely, Mastra agent networks). Notably this survey shows it is a *shrinking* model: CrewAI itself repositions crews as callable components inside flows; PydanticAI and smolagents refuse the construct entirely, reducing teams to "agent as tool." Role teams are a *prompt-layer pattern plus a scheduling policy*, not a distinct runtime primitive (INFERENCE, HIGH).
4. **Code-as-action** (smolagents CodeAgent; echoed in CrewAI's dual ReAct/native grammars in `CrewAgentExecutor`). The general lesson: the *action grammar* — how model output is decoded into effects — is a pluggable pair (decoder, executor), with JSON-tool-call and Python-snippet as the two dominant grammars. A framework that hard-codes one cannot express the other.
5. **Memory-as-agent-state / agent-as-service** (Letta wholly; Mastra memory subsystem; CrewAI flow memory; Letta Code MemFS). Letta demonstrates the limit case: if all durable state (blocks, history, archival passages) lives behind an addressable store and context is a *compile function over that store*, then "the agent" is a database row plus policies, and any harness can execute a step of it.

Two orthogonal infrastructure convergences:

- **Durability has exactly two implementation families**: (a) *snapshot/resume inside the framework* — CrewAI `@persist` with resume-vs-fork, Mastra suspend/snapshot/time-travel, LlamaIndex serializable Context; and (b) *delegation to an external durable-execution engine* — PydanticAI × Temporal/DBOS/Prefect/Restate, Mastra × Inngest, LlamaIndex × DBOS. The Temporal integration is the most instructive because it forces an explicit **determinism boundary**: agent-loop orchestration must be replayable; model calls and tool calls are effectful activities. Every framework that gets serious about durability rediscovers this split (FACT for the integrations; INFERENCE HIGH for the generalization).
- **Everything emits typed step events for observability**: `crewai_event_bus`, `handler.stream_events()`, Mastra's `run.stream()` chunks + OTel, smolagents `step_callbacks`, PydanticAI `run_stream_events()`/`AgentStreamEvent`. The event stream is already the universal observation interface; no framework treats it as the *execution* substrate except LlamaIndex (INFERENCE, HIGH).

## Architecture decomposition

Mapping the layer stack across the six systems (per-layer: who provides it, and its portability status):

- **Product/UI**: CrewAI AMP Suite (proprietary control plane over the OSS framework); Mastra Studio (open-source-adjacent, plus Mastra platform/cloud); Letta ADE + Letta Cloud "Constellation" (proprietary); LlamaAgents server/control-plane/`llamactl` (open source in-repo) + LlamaCloud (proprietary); PydanticAI ships a dev web chat UI + Pydantic Logfire (proprietary observability SaaS); smolagents: none (library only). Pattern: OSS framework + proprietary hosted control plane is the universal business shape.
- **Agent/Harness**: all open source, all framework-specific: `CrewAgentExecutor` (dual-grammar loop), PydanticAI's graph-run agent, smolagents `MultiStepAgent`, Mastra `Agent` (over Vercel AI SDK), Letta's server-side `LettaAgentV2/V3` loops (and the letta-code harness). **Non-portable**: each hard-codes its loop shape and prompt scaffolding.
- **Planning/orchestration**: CrewAI Flows (decorator reaction graph) + crew processes + `AgentPlanner`; pydantic-graph; LlamaIndex event routing + validator; Mastra combinator graphs; smolagents optional `PlanningStep` (planning *inside* the loop, in-context); Letta: ABSENT (orchestration is external to the agent; multi-agent groups exist for memory management). All open source; none interoperable — five mutually incompatible orchestration description formats.
- **Context construction**: the sharpest differentiator. Letta: deterministic `Memory.compile()` over persisted blocks + tiers (the only system where context construction is a *first-class, inspectable, tokenized-accounted* function — `ContextWindowOverview`). smolagents: `write_memory_to_messages()` replay of typed step log. Mastra: memory processors + working memory + semantic recall + observational memory composition. PydanticAI: message history + `Compaction`/`ProcessHistory` capabilities. CrewAI: prompt templates + memory retrieval. LlamaIndex: user-managed via Context store. All open source, all provider-independent, all framework-specific.
- **Model invocation**: all six delegate to provider adapters — CrewAI's `LLM` class (LiteLLM-based historically, OBSERVED BEHAVIOR MEDIUM), PydanticAI's model classes (provider-prefixed ids), Mastra via Vercel AI SDK `@ai-sdk/*` (SOURCE-CODE OBSERVATION), smolagents via transformers/LiteLLM, Letta via its own provider layer, LlamaIndex via llama-index LLM classes. **Provider-specific at the wire, portable at the abstraction** — every framework independently maintains a model-adapter layer; none share one.
- **Tool selection/execution**: model-selected in all; execution in-process by default everywhere. smolagents uniquely makes execution an *interpreter with a security model*; PydanticAI uniquely wraps tool *surface management* in capabilities (`ToolSearch`, `prepare-tools`, deferred tools); MCP support exists in PydanticAI, Mastra, smolagents, Letta (standardized protocol — the only cross-framework tool portability that exists).
- **Environment**: smolagents: sandboxed executors (E2B/Docker/Modal/Blaxel) — the only framework with environment isolation as a core concern. Letta Code: local machine/VM/managed sandbox harnesses. Others: the host process, unmanaged.
- **Observation**: typed event streams everywhere (see above); OTel-compatible in Mastra and LlamaIndex; Logfire for PydanticAI. Semi-standardized (OTel/OpenInference) at the telemetry layer only.
- **Verification**: Mastra scorers (runtime, sampled, per-step — the most developed); PydanticAI output validators + `ModelRetry` (verification *inside* the loop as typed validation); CrewAI hierarchical manager "validates outcomes" (LLM-judged, informal); guardrails on CrewAI tasks (FACT, MEDIUM — not re-verified). Letta/smolagents/LlamaIndex: ABSENT as a distinct layer.
- **State update**: Letta: server DB (agent state, messages, blocks, passages) — the system of record *is* the runtime. Mastra: storage providers (snapshot + memory + scorer tables). CrewAI: SQLite flow persistence + LanceDB memory. LlamaIndex: serializable Context / pluggable state store. PydanticAI: caller-owned message history + graph persistence + external durable engines. smolagents: in-process only.

## Implications for a universal runtime kernel

1. **The five recurring models are all reducible to one scheduling contract.** Type-routed pub/sub (LlamaIndex), completion-listening (CrewAI flows), combinator graphs (Mastra), annotation-derived graphs (pydantic-graph), the ReAct loop (smolagents, CrewAI agents, PydanticAI), and role teams (CrewAI crews) can each be expressed as *a strategy that, given (event log, state, capability results), decides the next set of capability invocations*. Nothing in any of the six requires the kernel to know what an "agent," "crew," "flow," or "graph" is. This directly supports the mission thesis — with one caveat: the kernel must support *both* eager reaction (events trigger steps immediately, possibly in parallel) and blocking joins (`and_`, `collect_events`, `.parallel()` barriers), i.e., subscription matching plus join/barrier semantics, not just a queue.
2. **PydanticAI's capabilities system is prior art for the kernel's capability model — study it closely.** It independently converged on "capability = attachable bundle contributing tools + lifecycle hooks + instructions + model settings + model selection, optionally loaded on demand by the model." A kernel capability contract should subsume this: contribution surfaces (what the capability injects into context/tool space), interception points (hooks), and effect execution. That PydanticAI ships durability itself as a capability (`TemporalDurability`) shows even *execution semantics* can be late-bound through the same mechanism.
3. **The determinism boundary must be a kernel-level line.** Temporal×PydanticAI, Mastra durable agents ("the agentic loop runs inside a workflow" with memoized steps), and LlamaIndex×DBOS all converge on: orchestration decisions must be replayable; model calls and tool calls are effectful, retryable, journaled activities. A kernel that records every capability invocation (with serialized inputs/outputs) in an event log gets snapshot/resume, fork (CrewAI's resume-vs-fork is the semantics to copy), time-travel (Mastra), and external-engine delegation from one mechanism.
4. **Action grammar must be pluggable, and code-as-action forces the environment primitive.** smolagents proves the decode-execute pair (JSON tool call vs Python snippet) is swappable within the same loop; CrewAI's executor contains both grammars in one class. Code-as-action additionally requires a sandboxed execution environment with an explicit policy (allowlists, resource caps, isolation levels) — the only real policy layer found in this survey lives in smolagents' executors. Kernel implication: "environment" is a capability with a policy contract, and the action decoder is harness-, not kernel-level.
5. **Memory should be kernel-addressable state with framework-level semantics — Letta is the existence proof.** Letta shows that when durable state is labeled, size-budgeted, and stored behind an API (`Block(label, value, limit)`), then (a) context construction becomes a deterministic compile function, (b) memory editing becomes ordinary tool calls, (c) memory management can be *reassigned to a different principal* (sleep-time agent) over shared state, and (d) the harness becomes stateless and interchangeable (letta-code's cloud-state/local-harness split). The kernel needs labeled, quota'd, shareable state cells and a context-compile hook; tiering (core/recall/archival) and self-editing are strategies on top.
6. **Typed contracts at boundaries are the interop currency.** Every framework validates *something* at a boundary: Mastra step schemas and suspend/resume payload schemas, PydanticAI output types and retry budgets, LlamaIndex event types, CrewAI structured flow state. The kernel should make every boundary payload (event, checkpoint, suspension request, capability result) schema-carrying. Mastra's `suspendSchema`/`resumeSchema` is the cleanest design for typed suspension points and should inform the kernel's checkpoint/HITL contract.
7. **Budgets must propagate across delegation.** PydanticAI's `usage=ctx.usage` accrual and CrewAI's flow-level `usage_metrics` aggregation show demand for hierarchical metering. Kernel budgets should be a resource lineage tree spanning delegated executions, not per-run counters.
8. **The observability event stream and the execution event log should be the same thing.** Five frameworks bolt an event bus onto execution for observability; only LlamaIndex makes events the execution substrate. A kernel whose execution *is* an event log gets tracing, streaming UIs, replay durability, and eval sampling (Mastra scorers subscribe to results) for free from a single primitive.
9. **Verification is an attachable observer, not a pipeline stage.** Mastra's sampled, async, per-step scorers writing to storage are the most production-shaped verification found; PydanticAI's `ModelRetry` shows verification can also feed back *into* the loop. The kernel needs both: non-blocking observers over the event stream and blocking validators on capability results with retry budgets.
10. **What NOT to put in the kernel**: role/team semantics (prompt-layer pattern), planning (a strategy or an in-context step), memory tiering policy, action grammar, and specific model adapters. Every framework that hard-coded these is now unwinding them (CrewAI demoting crews under flows; Letta moving memory policy into swappable agent-type compile functions; PydanticAI moving features out of Agent parameters into capabilities).
