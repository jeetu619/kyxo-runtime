# Cursor: A Proprietary Multi-Model Agent Harness and What It Proves About Model/Harness Separability

Research note — 2026-08-15. Part of the universal-runtime architecture research sweep.

## Scope

This note covers Cursor (Anysphere) as of August 2026: the IDE agent, Cursor CLI and its headless/SDK modes, cloud (formerly "background") agents and `environment.json`, the Merkle-tree codebase index, context construction (@-symbols, rules, AGENTS.md, memories), the fast-apply pipeline and speculative edits, the Tab model, the (removed) shadow workspace, subagents and Plan Mode, skills/hooks/MCP, checkpoints, sandboxing and permissions, model routing (Auto / Cursor Router) and in-house models (Composer, Tab, apply, embeddings), agent state and resumability, and enterprise runtime-relevant controls.

**Method caveat.** The research environment's egress proxy blocked direct fetches of `cursor.com`, `docs.cursor.com`, `forum.cursor.com`, and `web.archive.org`. Evidence therefore comes from (a) search-engine extracts of official Cursor docs/blog/changelog pages (URLs recorded; content quoted by the search layer), (b) GitHub-hosted primary artifacts I fetched directly (community-captured Cursor system prompts and tool schemas), and (c) credible third-party engineering analyses. Where a claim rests only on a search extract of an official page, I label it FACT but note the indirect retrieval; where it rests on third-party reporting, I downgrade to OBSERVED BEHAVIOR or INFERENCE. Cursor is closed-source: nothing here about server internals is verified from code.

## Findings

### 1. Product surfaces and trajectory

- FACT: Cursor began as a VS Code fork (Electron IDE). Cursor 2.0 (Oct 29, 2025) introduced the in-house Composer model and a multi-agent UI running up to 8 parallel agents isolated in git worktrees, plus best-of-N execution of one prompt across multiple models with side-by-side result selection. (cursor.com/blog/2-0, InfoWorld, SD Times.)
- FACT: Cursor 3.0 (April 2, 2026) added a standalone "Agents Window" — an agent-orchestration surface separate from the editor, showing every agent running locally, in worktrees, in the cloud, or over SSH, including agents launched from Slack, GitHub, Linear, web, and mobile. Cloud agents moved out of the editor entirely into this window. (cursor.com/changelog/3-0 via search; DataCamp.)
- FACT: The same agent runtime is exposed through five surfaces: IDE, Agents Window, CLI (`cursor-agent`/`agent`), web/mobile (cursor.com/agents, iOS/iPad app), and the TypeScript SDK (public beta April 29, 2026). Cursor's SDK marketing states it is "the same agent that runs in the Cursor IDE, CLI, and web app." (cursor.com/docs/sdk/typescript via search; MarkTechPost.)
- OBSERVED BEHAVIOR (MEDIUM): Third-party architecture write-ups describe the stack as TypeScript/Electron UI, a TypeScript backend monolith, Rust for indexing/orchestration-critical paths, and Firecracker microVMs for cloud agent isolation. Cursor has not published an official stack description; treat the Firecracker and Rust claims as unverified.
- FACT: Business milestone context: ~$2B ARR by April 2026 per press coverage of Cursor 3 (DataCamp/press, indirect).

### 2. Model layer: heterogeneous frontier models plus in-house models under one harness

- FACT: Cursor runs third-party frontier models (OpenAI, Anthropic, Google, xAI, others) alongside in-house models. All AI requests are routed through Cursor's AWS-hosted backend — the client never talks directly to model providers; code snippets for prompts are processed in-memory on Cursor's infrastructure and forwarded to inference providers. (cursor.com/security via search extract.)
- SOURCE-CODE OBSERVATION (traffic-level, HIGH): Speedscale's traffic analysis shows the IDE speaking gRPC/protobuf to `api2.cursor.sh`, uploading directory structure, git status, and selected-file snippets per request — confirming the thin-client / server-side-context-assembly split at the wire level.
- FACT: "Auto" mode is, since July 2026, powered by **Cursor Router**: a server-side classifier that analyzes each agent request and routes it to a model by task type and complexity, with three optimization modes (Cost / Balance / Intelligence). Balance and Intelligence bill at the routed model's rate; Cursor claims frontier-comparable quality at ~60% lower cost. Initially Teams/Enterprise-only. (cursor.com/changelog/router via search.) OBSERVED BEHAVIOR (MEDIUM): reports say the router pool depends on specific cost-efficient frontier models (e.g., blocking a required model disables the router).
- FACT: **Composer** (announced with 2.0, Oct 29, 2025) is Cursor's in-house agentic coding model: mixture-of-experts, long-context, post-trained with large-scale RL executed *inside the production Cursor agent harness* — same tools, same prompt format, same system message; Cursor maintained a shadow deployment of its backend during training so tools like semantic search behaved identically to production. Training used custom MXFP8 low-precision kernels and hundreds of thousands of concurrent sandboxed cloud VMs (they rewrote their VM scheduler for RL rollouts). (cursor.com/blog/composer and composer-2-technical-report via search extracts; philschmid.de.)
- FACT: Composer 2/2.5 was post-trained on an open-weights base — Moonshot's Kimi K2.5 — which Cursor initially did not disclose; after community weight-analysis, Cursor leadership confirmed it and acknowledged the omission. (VentureBeat; yage.ai analysis.) INFERENCE (HIGH): Cursor's differentiation is post-training + harness co-design + serving speed, not pretraining.
- OBSERVED BEHAVIOR (LOW): Leak-based reports claim a "Composer 3" trained from scratch (very large parameter count) was announced/teased at a mid-2026 Cursor event. Unverified; excluded from conclusions.
- FACT: **Tab model** (autocomplete / next-action prediction) is an in-house model improved by *online RL*: reward +0.75 for accepted suggestion, −0.25 for rejected, 0 for showing nothing — folding the "should I show a suggestion at all" policy into the model. New checkpoints ship multiple times per day; the Sept 2025 model made 21% fewer suggestions with 28% higher accept rate. (cursor.com/blog/tab-rl via search.) OBSERVED BEHAVIOR (MEDIUM): retraining loops complete in ~1.5–2 hours; ByteByteGo reports a ~90-minute cycle and an in-house sparse model plus codebase-aware speculative decoding for completions.
- FACT: **Fast-apply model**: a fine-tuned Llama-3-70b that rewrites full files from a model's loose edit specification, served with "speculative edits" — a deterministic speculative-decoding variant exploiting the strong prior that most draft tokens equal the original file — reaching ~1000 tok/s (~13x vanilla inference; ~9x their prior GPT-4 speculative deployment). Cursor found full-file rewrite beats diff formats for files under ~400 lines. Deployed in partnership with Fireworks. (cursor.com/blog/instant-apply; fireworks.ai/blog/cursor; both via search extracts. Blog era: mid-2024; the apply stack has since evolved — MEDIUM confidence it remains architecturally similar.)
- FACT: **Embedding model**: indexing uses a custom embedding model (reportedly trained on agent-session data) rather than an off-the-shelf embedder. (Cursor docs/blog via Towards Data Science analysis; MEDIUM-HIGH.)

### 3. The harness: agent loop, tools, and per-model adaptation (the key question)

- FACT: Cursor's own vocabulary (blog "Continually improving our agent harness," Apr 30, 2026): the **agent harness** "bundles system prompts, tool definitions, error handling, and context management to teach the model how to work." Improvements are validated through an offline eval suite (**CursorBench**) plus production A/B testing, guided by "vision-driven development."
- FACT: When Cursor gets early access to a new frontier model, they spend *weeks* customizing the harness to that model's strengths and quirks, "until the same model inside their specially tuned harness is noticeably faster, smarter, and more efficient." (Same blog, via search extract.)
- FACT: Concrete per-model adaptation (blog "Improving Cursor's agent for OpenAI Codex models"): GPT-5.1-Codex-Max was trained in OpenAI's shell-oriented Codex CLI harness with few tools; Cursor adapted by renaming/re-defining its tools closer to shell equivalents (e.g., ripgrep-like), adding steering instructions ("if a tool exists for an action, prefer the tool"), preserving reasoning traces across turns (dropping them cost ~30% performance for Codex), and reordering messages to avoid contradictory instructions. OpenAI collaborated on the alignment.
- SOURCE-CODE OBSERVATION (community-captured artifacts, MEDIUM confidence on provenance, fetched directly from GitHub): Cursor's agent tool surface circa v1.0 comprised 13 tools: `codebase_search` (semantic), `read_file` (range-limited, 200–250 lines/call), `run_terminal_cmd` (approval-gated, background support), `list_dir`, `grep_search`, `edit_file` (change spec with `// ... existing code ...` markers), `search_replace`, `file_search` (fuzzy), `delete_file`, `reapply` (escalate a failed apply to "a smarter model"), `web_search`, `create_diagram` (Mermaid), `edit_notebook`. The "Agent Prompt 2.0" (captured Nov 2025) adds `todo_write` (task management), `update_memory`, `read_lints`, `glob_file_search`, and a `parallel` multi-tool wrapper, and instructs that `edit_file` output is applied by "a less intelligent model" — the apply model — with rules for disambiguating edit locations. It also mandates strict tool-schema compliance, autonomous continuation ("do not wait for the user to confirm"), and a code-citation format.
- INFERENCE (HIGH): The harness is therefore a *two-model editing pipeline* (frontier model proposes sloppy edit → fine-tuned apply model materializes it → `reapply` escalates on failure) wrapped in a tool loop whose tool *names and semantics are themselves per-model tunable surface*. Tool identity is not stable across models — direct evidence that "one universal tool contract for all models" is currently a fiction even inside a single product.
- FACT: Queued messages: users can queue instructions while the agent runs; queued messages execute in order and can be reordered (changelog 1.2 via search).
- FACT: Plan Mode (Shift+Tab; `/plan`; `--mode=plan` in CLI): agent researches the codebase, asks clarifying questions, emits an editable plan with structured to-dos, then executes. (docs/blog via search.)

### 4. Context construction: index, @-symbols, rules, memories

- FACT: **Codebase indexing**: the client computes a Merkle tree of file hashes for the workspace (respecting .gitignore/.cursorignore); only differing branches sync to the server (~every 10 minutes). Changed files are chunked (AST/syntactic chunking per third-party analyses), embedded with Cursor's custom model, and stored in Turbopuffer with obfuscated/masked file paths and line-range metadata. Plaintext source is not persisted server-side; at query time, the server returns matched metadata (masked paths + line ranges) and the *client* re-reads the actual code locally and ships relevant chunks with the request. (cursor.com/blog/secure-codebase-indexing via search; Towards Data Science; Engineer's Codex. Turbopuffer/AST details are third-party — MEDIUM-HIGH.)
- INFERENCE (MEDIUM): This is a split retrieval architecture — index server-side, ground truth client-side — chosen for privacy posture, at the cost of a mandatory server round-trip in the retrieval path and Cursor-controlled retrieval semantics.
- FACT: Cursor reports semantic search improves agent performance for essentially every model tested in its harness (their eval claim: meaningful accuracy gains vs grep-only agents), and it was especially effective for Composer. (Composer/harness blogs via search; digitalapplied summary cites ~12.5% agent accuracy improvement — MEDIUM on the specific number.)
- FACT: **@-symbols** let users explicitly pin context: @Files, @Folders, @Code, @Docs, @Git, @Web, @Past Chats, @Cursor Rules, @Recent Changes, @Linter Errors, @Notepads, plus #Files. (docs via search.)
- FACT: **Rules**: four mechanisms — project rules (`.cursor/rules/*.mdc`, MDC = YAML frontmatter + markdown), user rules, Team Rules (Team/Enterprise, cloud-distributed, admins can *recommend or require* them), and AGENTS.md (plain markdown, nested files supported). `.cursorrules` is legacy. Rule activation types: Always (`alwaysApply`), Auto-Attached (`globs`), Agent-Requested (model reads `description` and decides), Manual (`@rule-name`). Precedence: Team → Project → User; nested AGENTS.md, more-specific wins. The CLI also reads AGENTS.md and CLAUDE.md at the project root. (docs via search extracts.)
- INFERENCE (HIGH): Agent-Requested rules make rule *selection* itself a model-mediated capability discovery step — the same pattern as skills (below): metadata in, model decides what to load.
- FACT: **Memories**: auto-generated durable facts per project per user. A background "sidecar" model observes chats and proposes memories; the user approves before saving; managed in Settings (Rules → "Generate Memories"). Cursor's memory engineer describes evaluating both a sidecar-observer approach and a main-agent `update_memory` tool-call approach; the sidecar was chosen for user-control conservatism. (Docs via search; Leverage interview.) SOURCE-CODE OBSERVATION (MEDIUM): the captured Agent Prompt 2.0 nonetheless contains an `update_memory` tool — both paths appear to exist in some form.

### 5. Apply pipeline and verification loops

- FACT: Edit materialization is delegated to the fast-apply model (Section 2); `reapply` escalates to a stronger model on failure. (Blog + captured tool schema.)
- FACT: The **shadow workspace** (blog, 2024) was Cursor's background-iteration mechanism: a hidden Electron window loading the same workspace, where AI-proposed edits were applied invisibly and LSP lints fed back to the model; the blog envisioned a future kernel-level folder proxy for full execution isolation. OBSERVED BEHAVIOR (HIGH): the feature was removed around v0.45 (early 2025) without an official announcement; the role was superseded by the agent's direct lint access (`read_lints`), terminal execution, checkpoints, and (in 2.0+) sandboxed execution and worktrees.
- INFERENCE (MEDIUM): The shadow-workspace arc is instructive: a bespoke "hidden simulacrum environment" for safe iteration lost to a simpler design where the agent acts on the real workspace under checkpoints + sandbox + revert. Verification moved from *environment virtualization* to *state snapshotting + policy*.
- FACT: Cursor 2.0 added a native browser tool so the agent can drive/test web UIs and iterate to a verified result; cloud agents support computer-use for Debian/Ubuntu-based Docker environments. (Changelog/docs via search.)
- FACT: **Bugbot** (PR review product) runs multiple parallel analysis passes with majority voting plus a validator model over PR diffs; Bugbot Autofix spawns a Cloud Agent to fix findings; Cursor 3 pulls PR review threads into the IDE where the agent reads them as iteration context. (Third-party analyses + changelog via search; the "8 passes" figure is third-party — MEDIUM.)

### 6. Execution environments

- FACT: **Local terminal sandboxing** (Cursor 2.0, macOS first): agent shell commands run under Seatbelt (`sandbox-exec`) profiles generated dynamically at runtime from workspace-level and admin-level settings plus `.cursorignore`. Default policy: read/write workspace and /tmp; read broader filesystem; no writes outside workspace; no network without explicit approval. Allowlisted commands auto-run in the sandbox; failures can escalate to a user prompt for unsandboxed re-run. `sandbox.json` (global + per-repo, merged with per-repo priority) configures network access and filesystem paths. (cursor.com/blog/agent-sandboxing + docs via search.) OBSERVED BEHAVIOR (MEDIUM): independent security analysis (Nov 2025) documented secret/env exposure edge cases in early sandboxing.
- FACT: **CLI permissions**: `~/.cursor/cli-config.json` (global) and `<project>/.cursor/cli.json` hold `permissions.allow` / `permissions.deny` with typed tokens — `Shell(ls)`, `Shell(git)`, `Read(src/**/*.ts)`, `Write(package.json)`, `WebFetch(docs.github.com)`, `Mcp(datadog:*)` — i.e., a capability grammar over tool × argument patterns. `--force` bypasses prompts; `--sandbox <mode>` toggles sandboxing. (docs/cli/reference/permissions via search.)
- FACT: **Worktrees**: parallel local agents each get an isolated git worktree (own branch/files); up to 8 in 2.0's UI; the Agents Window (3.0) manages agents across worktrees, cloud, and SSH targets. (Docs/press via search.)
- FACT: **Cloud Agents** (formerly Background Agents): isolated VMs on Cursor's AWS infrastructure; clone the repo (GitHub App integration), work on their own branch, push commits/PRs; reachable from IDE, web, mobile, Slack, Linear, GitHub; an encrypted copy of code exists only for the run's duration. Environment defined by `.cursor/environment.json`: `snapshot` (base machine image id), `dockerfile` (alternative base), `install` (idempotent dependency step, may run on partially cached state), `start` (long-lived processes), `terminals` (tmux sessions shared between user and agent), `agentCanUpdateSnapshot` (agent may persist environment changes back to the snapshot). (docs/cloud-agent/setup via search extracts.)
- FACT: **Builds** (Aug 2026): Cursor pre-bakes bootable snapshots of prepared cloud environments ahead of agent runs (install runs in the background at build time), giving ~3x faster agent starts and fallback to the last successful build. (Changelog via search.)
- FACT: **Automations**: cloud agents can run on schedules or in response to events (GitHub, GitLab, Slack, webhooks, Linear). (docs/cloud-agent/automations via search.)
- INFERENCE (HIGH): Cursor's execution-environment story converged on the same triad as its competitors: (a) local, policy-sandboxed processes; (b) git-worktree parallelism; (c) declaratively-provisioned cloud VMs with snapshot/build caching — with `environment.json` as an environment-as-data contract equivalent in role to a devcontainer spec.

### 7. Extension mechanisms: MCP, hooks, skills, subagents

- FACT: **MCP**: full client support in editor and CLI — stdio, SSE, Streamable HTTP transports; OAuth for remote servers (stored credentials, `${env:VAR}` interpolation); config in `.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (global); one-click "Add to Cursor" deeplinks; a marketplace/Customize page consolidating plugins, skills, and MCPs (2026). Docs list tools, prompts, resources, roots, elicitation, and MCP Apps as supported primitives. (docs/mcp via search extracts.)
- FACT: **Hooks** (v1.7, Oct 2025; extended through 2026): `.cursor/hooks.json` registers external programs invoked at agent-loop lifecycle points — `beforeShellExecution`/`afterShellExecution`, `beforeMCPExecution`/`afterMCPExecution`, `beforeReadFile`/`afterFileEdit`, `subagentStart`/`subagentStop`, and later `beforeSubmitPrompt`, `afterAgentResponse`, `afterAgentThought`, `stop`, plus compaction-related events. Hooks receive JSON on stdin, may emit JSON on stdout, and can allow/block the action via exit status/payload. Cloud agents honor project hooks. Use cases: command blocking, secret redaction before the model sees content, post-edit formatting, audit streaming (Elastic ships a Cursor-hooks audit integration). (docs/hooks + InfoQ + GitButler + Elastic via search.)
- INFERENCE (HIGH): Hooks are Cursor's policy/observability *extension bus* — the only sanctioned way for third parties to interpose on the proprietary loop. Functionally isomorphic to Claude Code hooks (same stdin-JSON/exit-code idiom), suggesting convergent de-facto standardization of "loop interposition points" across vendors.
- FACT: **Skills** (Cursor 2.4, early 2026): `SKILL.md`-based Agent Skills — explicitly described by Cursor as an open standard shared with the wider ecosystem — supported in editor and CLI; skills carry instructions, scripts, and commands; discovered dynamically and loaded when relevant; `disable-model-invocation: true` restricts a skill to explicit slash-command invocation; a built-in `/migrate-to-skills` converts legacy dynamic rules and slash commands. (changelog/2-4 + docs/skills via search.)
- FACT: **Subagents** (2.4+): named child agents with their own context window, prompt, tool access, and model; defaults include codebase-research, terminal, and parallel-work subagents; initially synchronous, later asynchronous (parent continues while children run) and recursive (subagents spawn subagents, forming a tree); each execution returns an agent ID that can be resumed with full context; transcripts persist to disk for tooling and hooks. (docs/subagents via search extracts.)
- INFERENCE (MEDIUM): Delegation is thus modeled as *addressable, resumable child sessions* rather than fire-and-forget tool calls — a durable-execution-flavored design choice.

### 8. State, sessions, durability

- FACT: **Checkpoints**: automatic workspace snapshots around agent turns, stored locally, separate from the user's git repo; restore reverts files to a chosen point; manual (human) edits are not tracked; positioned explicitly as undo-for-agent, not version control. (docs via search.) OBSERVED BEHAVIOR (MEDIUM): community analysis describes shadow-git-style implementations in this product class; Cursor's exact mechanism is not documented.
- FACT: **Sessions/resume**: CLI supports `--resume [thread id]`, `agent resume`/`--continue`, `/resume`, and `agent ls` to list and reopen prior chats; conversation state persists locally.
- FACT: **Cloud handoff** (CLI changelog Jan 16, 2026): prefixing a message with `&` pushes the current local conversation to a Cloud Agent which continues it server-side; the task can then be picked up on web/mobile. Cloud agents on dedicated VMs maintain persistent state so clients can disconnect/reconnect. (Changelog + SDK docs via search.)
- INFERENCE (HIGH): Cursor treats "an agent" as a *portable conversation + workspace state* that can migrate between execution substrates (local process → cloud VM) while remaining one logical thread. This is the strongest durable-execution signal in the product; there is, however, no evidence of deterministic replay — continuity is achieved by state transfer, not event-sourced re-execution.

### 9. Policy, security, enterprise

- FACT: All model traffic transits Cursor's backend (no BYO direct-to-provider path); Privacy Mode guarantees no plaintext code storage server-side and no training on privacy-mode data; SOC 2 Type II; annual pentests. (cursor.com/security via search.)
- FACT: Enterprise controls: SSO/SCIM, RBAC, MDM policies, audit logs (19 event types, exportable), model and integration allow/deny management, network configuration, admin-required Team Rules, hooks as an enterprise governance surface, multi-team console (2026), rebuilt usage analytics. (docs/enterprise via search extracts.)
- FACT: Cloud Agents API (REST, v0→v1 public beta): `POST /v0/agents` launches agents programmatically with prompt, model, repo URL, starting ref, MCP servers; Basic/Bearer auth with user or service-account API keys; strict rate limits on some endpoints. OBSERVED BEHAVIOR (MEDIUM): forum reports document permission gaps (API-spawned agents could push commits but not comment on PRs) — the GitHub App scope, not the agent, defines the blast radius.

### 10. Interop protocols

- FACT: Cursor CLI implements **ACP (Agent Client Protocol)**: `agent acp` speaks JSON-RPC over stdio so third-party editors (Zed officially lists Cursor as an ACP agent; neovim via avante.nvim) can host Cursor's agent loop inside their UI. (zed.dev/acp/agent/cursor + docs/cli/acp via search.)
- FACT: MCP is the tool-ingestion protocol; ACP is the UI-hosting protocol; AGENTS.md and SKILL.md are cross-vendor context/capability file formats Cursor consumes. INFERENCE (HIGH): Cursor's *periphery* is standardizing rapidly (MCP, ACP, AGENTS.md, SKILL.md) while its *core* (harness, context engine, apply pipeline, router, index) remains fully proprietary — the moat is the loop, not the edges.

## Architecture decomposition

| Layer | What it is in Cursor | Status |
|---|---|---|
| Product/UI | Electron IDE (VS Code fork), Agents Window (3.0), web/mobile apps, Slack/Linear/GitHub surfaces | Proprietary (VS Code base is open source; Cursor's layer is not) |
| Agent/Harness | "Agent harness": system prompts + tool definitions + error handling + context management; per-model variants; CursorBench-evaluated | Proprietary, explicitly named by Cursor as its unit of engineering |
| Planning/orchestration | Plan Mode (research → editable plan → to-dos), todo_write, queued messages, subagent trees, best-of-N across models, Cursor Router (model selection), Automations (event/cron triggers) | Proprietary; no user-visible graph/workflow language |
| Context construction | Merkle-tree incremental index → AST chunks → custom embeddings → Turbopuffer; client-side chunk re-hydration; @-symbols; rules (4 types + Team Rules + AGENTS.md); memories (sidecar model); server-side prompt assembly | Proprietary engine; AGENTS.md/SKILL.md inputs standardized; retrieval requires Cursor's cloud |
| Model invocation | All requests through Cursor backend (gRPC/protobuf to api2.cursor.sh) to third-party providers or in-house models (Composer, Tab, apply, embedder); router classifier in front | Proprietary + provider-specific; no client-side model API surface at all |
| Tool selection/execution | Fixed built-in tool set (~13–18 tools) defined by the harness; MCP for third-party tools; per-model tool renaming; `parallel` wrapper; approval gates | Built-ins proprietary; MCP standardized |
| Environment | Local workspace + Seatbelt-sandboxed shell; git worktrees; cloud VMs from environment.json snapshots/Builds; browser tool; SSH targets | Proprietary provisioning; environment.json is an open-format-in-spirit config, Cursor-specific schema |
| Observation | Terminal output, `read_lints` (LSP), browser results, PR threads (Cursor 3); hooks as external observation taps; transcripts on disk | Proprietary; hooks give a semi-open tap |
| Verification | Lint feedback, agent-run tests, browser iteration, Bugbot multi-pass + validator voting, best-of-N human selection, CursorBench (internal, pre-ship) | Proprietary |
| State update | Checkpoints (local snapshots, per-turn), git worktrees/branches/PRs, session threads (resumable IDs), cloud handoff state transfer, memories | Proprietary; git portion portable/standard |

Portability summary: the only portable/standardized elements are at the boundary — MCP, ACP, AGENTS.md, SKILL.md, git, Dockerfiles inside environment.json. Every layer of the loop itself is closed and, crucially, *server-coupled*: even local-looking operation (Tab, semantic search, apply) requires Cursor's cloud.

## Precise vocabulary

- **Model**: any of ~10+ third-party frontier models plus in-house Composer (agentic MoE), Tab (next-action), fast-apply (edit materialization), and embedding models. "Model" in Cursor is a *routed backend choice*, sometimes made by another model (Router).
- **Model API**: ABSENT as a user-facing concept. Clients speak Cursor's private gRPC/protobuf API (api2.cursor.sh); Cursor's backend speaks provider APIs. No BYO-key direct path in the current architecture.
- **Model adapter**: the per-model harness variant — tool names/definitions, prompt phrasing, message ordering, reasoning-trace retention tuned per model family (documented for Codex models). This is Cursor's most distinctive concept: the adapter adapts the *harness*, not the wire format.
- **Agent**: a running conversation thread bound to a workspace and an execution substrate (local, worktree, cloud VM, SSH), listed and managed in the Agents Window; addressable, resumable, migratable.
- **Agent loop**: proprietary tool-calling loop (propose → tool call → observe → continue) with todo tracking, queued user messages, and apply-model edit materialization; runs identically (per Cursor) under IDE, CLI, web, and SDK.
- **Harness**: Cursor's own term — system prompts + tool definitions + error handling + context management, versioned and eval-gated (CursorBench + A/B), per-model customized.
- **Context-management system**: server-side prompt assembly fed by the semantic index, @-symbols, rules hierarchy, memories, and dynamic agent-fetched context; includes compaction (hook-observable).
- **Memory system**: approved-by-user memories generated by a sidecar observer model (plus an `update_memory` tool path); per-user per-project; distinct from rules (curated) and index (derived).
- **Tool runtime**: built-in tool implementations inside the client/backend + MCP client for external tools; hooks interpose; permission tokens gate.
- **Execution environment**: local sandboxed shell (Seatbelt policies), git worktrees, cloud VMs (environment.json → snapshot/Build), browser; tmux `terminals` shared human/agent.
- **Planner**: Plan Mode — a mode of the same agent, not a separate planner component; output is a human-editable plan artifact with to-dos.
- **Workflow/graph construct**: ABSENT. No DAG/graph language. Closest analogues: subagent trees (dynamic, model-directed), Automations (trigger → agent run), best-of-N (parallel fan-out + human join).
- **State/session model**: thread IDs with on-disk transcripts (CLI), checkpoints for workspace state, persistent cloud VM state, resumable subagent IDs.
- **Delegation mechanism**: subagents (named, per-model, per-toolset, async, recursive, resumable) and cloud handoff (`&`) migrating a thread to a cloud agent.
- **Protocol usage**: MCP (tools in), ACP (agent out, to other editors), AGENTS.md/SKILL.md (context/capability files in), GitHub App (repo access), private gRPC (everything else).
- **Capability discovery/negotiation**: partial — Agent-Requested rules and Skills are metadata-described capabilities the model chooses to load; MCP discovery for external tools. No formal negotiation.
- **Policy/security layer**: permission token grammar (Shell()/Read()/Write()/WebFetch()/Mcp()), OS sandbox profiles generated from workspace+admin settings, hooks (allow/block), .cursorignore, enterprise-required rules, audit logs.
- **Durable-execution features**: state-transfer durability (cloud handoff, persistent VMs, resumable threads/subagents, Builds); no deterministic replay, no event sourcing observed. Checkpoints are workspace-state, not execution-state.
- **Event system**: hooks (lifecycle events out), Automations (external events in). No public unified event log.
- **Observability**: transcripts on disk, hook streams (e.g., Elastic audit), enterprise analytics/audit dashboard, Bugbot/PR surfaces. No OTel-style public trace format.

## Implications for a universal runtime kernel

1. **The harness is the product, and it is model-specific by necessity.** Cursor — the strongest existing proof that heterogeneous frontier models can run under one harness — achieves it only via weeks of per-model adaptation, down to renaming tools to match what a model saw in RL training and preserving provider-specific reasoning traces. A universal kernel must therefore treat "harness" as a *pluggable, versioned artifact keyed by (model, task-class)*, not as neutral infrastructure; and the capability contract must permit per-model aliasing/skinning of the same underlying capability without changing its identity for policy and audit purposes.
2. **Separability is asymmetric and eroding from both directions.** Cursor tunes the harness to models (harness→model adaptation) and trains models inside the harness (Composer's RL used the production tools/prompts verbatim, with a shadow backend). The harness is becoming part of the model's training distribution. A kernel that assumes clean model/harness independence will underperform integrated stacks; the realistic design goal is *a stable capability/event substrate beneath swappable harness-model pairs*, not a universal harness.
3. **Two-model (or N-model) pipelines are normal, not exotic.** Frontier model + fast-apply model + reapply escalation + router classifier + sidecar memory model + Bugbot validator: a single "agent turn" in Cursor may involve five specialized models. Kernel implication: model invocation should be a capability like any other — cheap, composable, multi-instance — not a singleton "the model" slot in the loop.
4. **Policy interposition points are converging on a de-facto standard.** Cursor hooks (stdin-JSON, allow/block, before/after each tool class, prompt-submit, compaction, subagent lifecycle) mirror Claude Code's hooks almost exactly. A kernel should natively expose these as first-class *policy events on the capability bus*, making vendor hook systems thin adapters.
5. **Environment-as-data works and wants a build cache.** environment.json (snapshot/dockerfile/install/start/terminals) plus Builds (pre-baked bootable snapshots, background install, fallback-to-last-good) is a complete declarative environment lifecycle. A kernel's environment capability should model *declared spec → cached build → instance*, with idempotent install steps and agent-writable snapshots as explicit permissions (`agentCanUpdateSnapshot`).
6. **Durability via state transfer, not replay, is shipping today.** Cursor migrates live threads local→cloud (`&` handoff) and resumes by ID; nobody replays. A kernel can win by offering *checkpointable session state as a portable artifact* (transcript + workspace delta + environment ref), making Cursor-style handoff a kernel primitive instead of a product feature.
7. **Context retrieval is a privileged, split-trust capability.** Cursor's index keeps embeddings+masked metadata server-side and code client-side, re-hydrating at query time. A kernel capability model should support such split-trust capabilities natively: a capability whose index lives in one trust domain and whose ground truth lives in another, with the join happening under client policy.
8. **Checkpoints are workspace-scoped, not run-scoped — and that's a gap.** Cursor's checkpoints cover agent file edits only (manual edits untracked; terminals/side effects untracked). A kernel checkpoint primitive spanning *all* effectful capabilities (files, env, spawned processes, external calls via compensation metadata) would exceed the current state of the art in this product class.
9. **Routing is a policy decision made by a model.** Cursor Router puts a classifier in front of model choice with explicit cost/quality modes and per-request billing consequences. Kernel implication: budgets and model selection belong in the same policy layer; "which model" is an attribute resolved at dispatch time under budget constraints, and must be auditable (Cursor bills at the routed model's rate — the routing decision is financially load-bearing).
10. **The open edges show where standards are viable now.** MCP (tools), ACP (UI/host), AGENTS.md (context), SKILL.md (procedural capability) are the interfaces Cursor was willing to standardize; index, apply, router, prompts are the ones it was not. A kernel should adopt the former as compatibility surfaces and expect to compete on the latter.

## Open questions

2. Is there any deterministic replay or event log behind cloud agents/Automations (for retry semantics), or is retry purely "re-run from last Build + branch state"?
3. How are checkpoints implemented (shadow git vs custom snapshot store), and do they capture anything beyond file state (e.g., terminal/session state)?
4. What is the Router's actual model pool and classifier architecture, and how are routing decisions logged for billing audit? (Third-party claims about required pool models are unverified.)
5. Did the apply pipeline change post-2024 (e.g., replaced by stronger base models doing native diffs, as some commentators claim "fast-apply models are dead"), and is `reapply` still present in the 2026 harness?
6. How does the SDK's "self-hosted cloud" enterprise target work — does Cursor's control plane orchestrate customer-owned VMs, and what parts of the context engine (index, embeddings) can run inside the customer boundary?
