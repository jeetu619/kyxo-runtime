# OpenAI's Agent Stack: Agents SDK (Python/JS), Responses API, and Codex

Research note for the universal-runtime kernel investigation. Date of research: 2026-08-15. All source inspection was done against the `main` branches of `openai/openai-agents-python`, `openai/openai-agents-js`, and `openai/codex` as of this date (plus the `rust-v0.48.0` tag of `openai/codex` where `main` docs had been moved off-repo). OpenAI's own doc sites (`platform.openai.com`, `developers.openai.com`, `openai.github.io`, `openai.com`) were blocked by this environment's egress proxy; wherever a claim rests on a search-result snippet of those pages rather than a fetched page, it is labeled accordingly.

## Scope

- OpenAI Agents SDK, Python (`openai/openai-agents-python`, MIT, open source) — Agent model, Runner loop, tools, handoffs, guardrails, sessions, RunState/HITL, tracing, model-provider abstraction, MCP, realtime, and the new (beta) sandbox-agents subsystem.
- OpenAI Agents SDK, JS/TS (`openai/openai-agents-js`, MIT, open source) — RunState, run loop, model layer, realtime/voice, extensions.
- Responses API + Conversations API — the server-side state model (`previous_response_id`, `store`, reasoning items, background mode), and the Assistants API sunset.
- Codex — the open-source Rust CLI/core (`openai/codex`), its core↔UI protocol (SQ/EQ and the App Server JSON-RPC), sandboxing (Seatbelt/Landlock), approval policies, AGENTS.md, `codex exec`, and Codex cloud as documented.
- Out of scope: pricing, model quality, ChatGPT consumer product surfaces.

## Findings

### 1. The Agents SDK's core object model: Agent = data, Runner = loop

**FACT (source: agent.py).** `Agent` is a dataclass of pure configuration — no behavior loop lives on it. Fields: `name`, `instructions` (str | callable | None — the system prompt, possibly dynamic), `prompt` (server-stored prompt object), `handoff_description`, `handoffs: list[Agent | Handoff]`, `model: str | Model | None`, `model_settings`, `tools: list[Tool]`, `mcp_servers: list[MCPServer]`, `mcp_config`, `input_guardrails`, `output_guardrails`, `output_type` (type | `AgentOutputSchemaBase` | None), `hooks: AgentHooks | None`, `tool_use_behavior` (default `"run_llm_again"`), `reset_tool_choice: bool = True`. Methods `clone()` (shallow `dataclasses.replace`) and `as_tool()` (agent-as-tool, see §4).

**FACT (source: run.py + run_internal/).** The loop lives in `Runner`/`AgentRunner`. `Runner.run/run_sync/run_streamed` delegate to a `DEFAULT_AGENT_RUNNER`. The loop is a `while True` over turns: increment `current_turn`, call the model, process the response, then dispatch on a `next_step`. `current_turn > max_turns` raises `MaxTurnsExceeded` (a run-level error handler can convert this into a final result — `resolve_run_error_handler_result()` / `finalize_max_turns_handler_output()`; `max_turns=None` disables the limit). The JS SDK documents the identical loop with `maxTurns` default 10 and `MaxTurnsExceededError` (FACT, running-agents.mdx).

**SOURCE-CODE OBSERVATION (run_steps.py), HIGH.** Turn outcomes are a closed union: `NextStepHandoff(new_agent)`, `NextStepFinalOutput(output)`, `NextStepRunAgain`, `NextStepInterruption(interruptions: list[ToolApprovalItem], ...)`, carried on `SingleStepResult.next_step`. This four-way union *is* OpenAI's control-flow vocabulary for agents: continue, delegate, finish, pause-for-human.

**SOURCE-CODE OBSERVATION (turn_resolution.py), HIGH.** Final-output detection is heuristic and hard-coded: (a) if `tool_use_behavior` says stop (`"stop_on_first_tool"`, a `StopAtTools` name list, or a custom callable via `check_for_final_output_from_tools()`), the tool result is the final output; (b) else if `not processed_response.has_tools_or_approvals_to_run()`, the last message's text is the final output — validated with `output_schema.validate_json(...)` when an `output_type` is set (failure raises `ModelBehaviorError`). There is no explicit "done" token from the model; termination is inferred from "no pending tool calls."

**INFERENCE, HIGH.** The SDK's decomposition (`run_internal/` split into `run_loop`, `turn_preparation`, `tool_planning`, `tool_execution`, `turn_resolution`, `approvals`, `session_persistence`) shows the loop itself is the product. Everything configurable hangs off data (`Agent`, `RunConfig`); the loop's *shape* — turn counting, step union, final-output heuristics — is not pluggable.

### 2. Handoffs are literally function tools that swap the active agent

**SOURCE-CODE OBSERVATION (handoffs/__init__.py + models/openai_responses.py), HIGH — this was a mission "verify in source" item, and it verifies.** A `Handoff` carries `tool_name`, `tool_description`, `input_json_schema`, `on_invoke_handoff` (async), `agent_name`, `input_filter`, `nest_handoff_history`, `strict_json_schema=True`, `is_enabled`. `Handoff.default_tool_name()` returns `transform_string_function_style(f"transfer_to_{agent.name}")`; default description is "Handoff to the {agent.name} agent to handle the request." The Responses adapter's `_convert_handoff_tool()` serializes it as a plain function tool: `{type: "function", name: handoff.tool_name, parameters: handoff.input_json_schema, strict: ..., description: ...}` — indistinguishable on the wire from any other function tool. When the model calls it, the runner (not the model provider) intercepts it, resolves the target, applies `input_filter` over a `HandoffInputData` (input_history, pre_handoff_items, new_items), optionally nests history, and returns `NextStepHandoff(new_agent)`; the loop continues with the new agent's config. Multiple simultaneous handoff calls: only `run_handoffs[0]` executes; the rest get synthesized rejection outputs ("Multiple handoffs detected, ignoring this one.").

**INFERENCE, HIGH.** "Handoff" is thus not a runtime primitive at all — it is a *naming convention plus an interception rule* layered on the generic tool-call channel. The only genuinely new mechanics are (a) the runner swapping which config it reads on the next iteration and (b) history filtering at the swap boundary.

### 3. Guardrails: policy hooks pinned to fixed loop positions

**FACT (guardrail.py + run.py).** `InputGuardrail` (fields: `guardrail_function`, `name`, `run_in_parallel: bool = True`) runs only on the first turn — sequentially before the model call, or concurrently with it via `asyncio.gather` when `run_in_parallel`. `OutputGuardrail` runs only when a `NextStepFinalOutput` is produced. Both return `GuardrailFunctionOutput(output_info, tripwire_triggered)`; a tripped wire raises `InputGuardrailTripwireTriggered` / `OutputGuardrailTripwireTriggered`, aborting the run. Agent-level and `RunConfig`-level guardrail lists are concatenated. Tool-level guardrails also exist (`tool_guardrails.py` in Python; `_toolInputGuardrailResults`/`_toolOutputGuardrailResults` serialized in JS RunState — SOURCE-CODE OBSERVATION, HIGH).

**INFERENCE, MEDIUM.** Guardrails are validators bound to three hard-coded positions (run input, run output, tool I/O). There is no general "predicate over any event" facility; anything else must be done in `hooks` (lifecycle callbacks) or tool wrappers.

### 4. Tools: a closed 13-type union where the *execution venue* is baked into the type

**SOURCE-CODE OBSERVATION (tool.py), HIGH.** `Tool = FunctionTool | FileSearchTool | WebSearchTool | ComputerTool | HostedMCPTool | CustomTool | ShellTool | ApplyPatchTool | LocalShellTool | ImageGenerationTool | CodeInterpreterTool | ToolSearchTool | ProgrammaticToolCallingTool`. `FunctionTool` carries `params_json_schema`, `on_invoke_tool`, `strict_json_schema=True`, `is_enabled`, `needs_approval` (bool | callable), `timeout_seconds`/`timeout_behavior`, `allowed_callers`, `output_json_schema`.

The venues, per docs/tools.md (FACT):
- **Provider-hosted** (execute inside OpenAI's Responses API, no SDK round-trip): `WebSearchTool`, `FileSearchTool`, `CodeInterpreterTool`, `ImageGenerationTool`, `HostedMCPTool` — serialized as typed tool entries (`type: "web_search"`, `type: "file_search"`, `type: "computer_use_preview"`, …) by the adapter (SOURCE-CODE OBSERVATION, openai_responses.py).
- **SDK-process**: `FunctionTool`, `CustomTool`, agents-as-tools.
- **Host machine ("local runtime tools")**: `ShellTool`, `ApplyPatchTool` (with an `editor` abstraction), `ComputerTool` (a `Computer` harness object), legacy `LocalShellTool`.
- **Hosted V8**: `ProgrammaticToolCallingTool` — the model emits JavaScript that calls eligible tools ("combines their outputs, and returns one result" without intermediate model round-trips); the program runs in "a fresh hosted V8 environment" with no filesystem/network, only tools that opted in via `allowed_callers=["programmatic"]`; requires `ModelSettings(tool_choice="programmatic_tool_calling")` (FACT, docs/tools.md).
- **Deferred discovery**: `ToolSearchTool` — tools declared with `defer_loading=True` are hidden until the model searches for and loads them; namespacing via `tool_namespace()` (FACT, docs/tools.md). (Structurally identical to the "deferred tools + ToolSearch" pattern in this very harness — INFERENCE: convergent evolution on context economy.)

**FACT (agent.py, docs/tools.md).** Agents-as-tools: `agent.as_tool(tool_name=..., tool_description=..., custom_output_extractor=..., on_stream=..., is_enabled=..., parameters=...)` runs a nested `Runner` inside a tool call, without swapping the outer conversation — the composition dual of handoffs.

**FACT (docs/mcp.md).** MCP is a first-class tool source: `MCPServerStdio`, `MCPServerSse` (deprecated), `MCPServerStreamableHttp` attach via `Agent.mcp_servers`; `list_tools()` runs each turn (cacheable with `cache_tools_list=True`, invalidated via `invalidate_tools_cache()`); static/dynamic tool filters (`create_static_tool_filter`, `ToolFilterContext` callables); MCP prompts (`list_prompts`/`get_prompt`) can supply instructions. `HostedMCPTool` moves MCP execution server-side (Responses API calls the MCP server itself) with `require_approval` and `on_approval_request`.

**INFERENCE, HIGH.** The union type means adding a new *kind* of execution venue is an SDK change, not user extension: the taxonomy is closed, and adapters must know each member. Contrast with a capability model where venue/isolation/approval are orthogonal attributes on one primitive.

### 5. Sessions and conversation state: three mutually exclusive regimes

**SOURCE-CODE OBSERVATION (run.py, memory/), HIGH.** The runner supports exactly three history regimes:
1. **Server-managed** — any of `conversation_id` (Conversations API object), `previous_response_id`, or `auto_previous_response_id` engages an `OpenAIServerConversationTracker`; the OpenAI backend owns history; the SDK sends only deltas (buffered `pending_server_items`).
2. **Session-persisted** — a `session` object implementing the `Session` protocol: `@runtime_checkable Protocol` with `session_id`, `async get_items(limit)`, `add_items(items)`, `pop_item()`, `clear_session()` (FACT, memory/session.py). Implementations in-repo: `SQLiteSession`, `OpenAIConversationsSession` (Conversations-API-backed), `OpenAIResponsesCompactionSession` (compaction), plus `SessionSettings`. The runner does `prepare_input_with_session()` before and `save_result_to_session()` after each turn.
3. **Stateless** — caller passes the full item list each run (`result.history` / `to_input_list()` pattern).

The JS docs name the same four options at the API surface: `result.history`, `session`, `conversationId`, `previousResponseId` (FACT, running-agents.mdx).

**INFERENCE, HIGH.** "Memory" in this stack is only conversation-item storage with pluggable backends. There is no semantic memory abstraction in the core SDK; the new sandbox subsystem (§8) is where a real memory system (extraction/consolidation) first appears.

### 6. RunState: the de facto checkpoint format, and HITL as a loop outcome

**SOURCE-CODE OBSERVATION (run_state.py, runState.ts), HIGH.** Both SDKs now have a serializable `RunState` — "a serializable snapshot of an agent run, including context, usage, and interruptions … the durable pause/resume boundary for human-in-the-loop flows" (Python docstring). Python `CURRENT_SCHEMA_VERSION = "1.15"`; JS `CURRENT_SCHEMA_VERSION = '1.18'` with `SUPPORTED_SCHEMA_VERSIONS` back to 1.0. Contents: current/starting agent, `_currentTurn`, original input, `_pendingInput` ("input staged for admission immediately before the next resumed model call"), generated items vs full session items, model responses, `_lastProcessedResponse`, the resumable `_currentStep` (interruption or run-again), guardrail results, and — in JS — `_completedToolInvocations` ("canonical invocation fingerprints whose local tool outputs are committed to run history") for exactly-once tool semantics across resumes. `toJSON()/toString()/fromString()` (JS `toJSON` has `includeTracingApiKey`); `approve(item, always_approve=...)` / `reject(item, always_reject=..., rejection_message=...)`; `get_interruptions()`.

**FACT (docs/human_in_the_loop.md).** The HITL flow: a tool's `needs_approval` (bool or async callable receiving run context, parsed params, call id) halts execution → `RunResult.interruptions` holds `ToolApprovalItem`s → `result.to_state()` → approve/reject → `Runner.run(agent, state)` resumes ("continues where it left off and will re-enter this flow if new approvals are needed"). Applies to `function_tool`, `Agent.as_tool()`, `ShellTool`, `ApplyPatchTool`, MCP. Docs recommend versioning agent definitions alongside serialized state.

**INFERENCE, HIGH.** This is checkpointing implemented *above* the runtime: a versioned JSON blob whose semantics only the same SDK version range can interpret, and which explicitly excludes the agent definitions themselves (code must be re-supplied at resume). A kernel-level checkpoint would instead capture or content-address the definition graph too.

### 7. The model boundary: a fat adapter interface, and the Responses API absorbing the runtime

**FACT (models/interface.py).** `Model.get_response(system_instructions, input, model_settings, tools, output_schema, handoffs, tracing, *, previous_response_id, conversation_id, prompt)` (+ streaming twin) and `ModelProvider.get_model(name)`. Note what is *in* the signature: `handoffs` (an agent concept), `output_schema`, and two OpenAI-specific state tokens (`previous_response_id`, `conversation_id`). Adapters: `OpenAIResponsesModel` (default; required for `ToolSearchTool`/`ProgrammaticToolCallingTool`), `OpenAIChatCompletionsModel` (fallback, wider provider compatibility), LiteLLM via `litellm/` prefix through `MultiProvider` or `LitellmModel`; JS mirrors this (`Model`/`ModelProvider`, `setDefaultModelProvider`, Vercel AI SDK adapter `@openai/agents-extensions` `aisdk`). Default model as of Aug 2026 docs: `gpt-5.6-luna` (reasoning effort "none") with `gpt-5.6-sol` as the frontier option; overridable via `OPENAI_DEFAULT_MODEL`. Documented non-OpenAI-provider caveats: tracing uploads to OpenAI 401 without an OpenAI key (`set_tracing_disabled(True)`), most providers lack Responses API (`set_default_openai_api("chat_completions")`), some lack json_schema structured output.

**FACT (search-confirmed official docs).** Responses API state model: `store=true` persists response objects; `previous_response_id` chains turns server-side (instructions are NOT carried over and must be resent); the Conversations API provides a persistent conversation object (`conversation` parameter); reasoning items from prior turns are auto-available when chaining, and should be passed back manually otherwise; encrypted reasoning items exist for ZDR orgs (OBSERVED BEHAVIOR, MEDIUM — from cookbook/community, not fetched first-hand). Background mode: `background=true` returns immediately; poll the response object; with `stream=true` you can resume a dropped stream from a `sequence_number` cursor (FACT via search snippets of platform docs). Hosted tools (web_search, file_search, code_interpreter, image_generation, hosted MCP) execute *inside* a single response on OpenAI's side — a server-side mini-agent-loop. The Assistants API (the previous server-side agent runtime) is deprecated with a hard sunset on **2026-08-26** — eleven days after this note — replaced explicitly by Responses + Conversations (FACT, official announcement).

**INFERENCE, HIGH.** OpenAI is deliberately migrating runtime concerns (conversation state, tool execution, background/durable execution, reasoning-state carryover) *into the model API*. The "model API" is no longer items-in/items-out: it is a stateful execution service. Any runtime that treats providers as pure functions will misrepresent this provider; a kernel must model "provider-side session state" and "provider-side tool execution" as a federated foreign runtime.

### 8. Sandbox agents (Python, beta): OpenAI's own "capabilities" vocabulary appears

**FACT (docs/sandbox_agents.md + sandbox/ source), with the caveat the docs themselves give: beta, "expect details … to change before general availability."** The agent loop stays in the SDK; the *model-facing tools* execute in an isolated filesystem workspace: "search large document sets, edit files, run commands, generate artifacts, and pick work back up from saved sandbox state." Backends via `SandboxRunConfig.client`: `UnixLocalSandboxClient`, Docker (`openai-agents[docker]`, default image `python:3.14-slim` — SOURCE-CODE OBSERVATION), and hosted providers. Workspace defined by a `Manifest`; **capabilities** are sandbox-native tools — filesystem editing, image inspection, shell, **skills** (`Skills`, `LocalDirLazySkillSource` lazy loading), and **memory** — composed via `Capabilities.default()`. Memory generation is a configured two-phase model pipeline (`MemoryGenerateConfig`: `phase_one_model`/`phase_two_model`, consolidation caps; `MemoryReadConfig.live_update`) writing under a `MemoryLayoutConfig` filesystem layout (SOURCE-CODE OBSERVATION). State continuity via `SandboxRunConfig.session`, `session_state`, or `snapshot`; `run_as` selects the sandbox user account.

**INFERENCE, HIGH.** This subsystem is the closest thing in OpenAI's stack to the kernel thesis: an execution environment with declared capabilities, snapshots, skills-as-packaged-procedures, and derived memory — but it is bolted onto the existing Agent/Runner as a parallel configuration object rather than being the substrate underneath everything.

### 9. Tracing and durable execution

**FACT (docs/tracing.md).** Traces (workflow_name, group_id, metadata) contain typed spans: `agent_span`, `generation_span`, `function_span`, `guardrail_span`, `handoff_span`, `custom_span`, `response_span`-era plus audio spans (`transcription_span`, `speech_span`, `speech_group_span`) and now `task_span`/`turn_span`. Default export: OpenAI Traces dashboard via global `TraceProvider` → `BatchTraceProcessor` → `BackendSpanExporter`. Pluggable: `add_trace_processor()` (additive) vs `set_trace_processors()` (replace); 30+ third-party processors documented. Kill switches: `OPENAI_AGENTS_DISABLE_TRACING=1`, `set_tracing_disabled(True)`, `RunConfig(tracing_disabled=True)`; sensitive-data inclusion defaults to True (`trace_include_sensitive_data`).

**FACT (Temporal docs/blog).** Durable execution is delivered as an *external integration*: Python OpenAI-Agents ↔ Temporal GA on 2026-03-23. The TypeScript integration "places the agent loop, tool selection, and handoffs inside the Workflow while model calls execute as Activities"; `activity_as_tool` wraps Temporal Activities as agent tools. Crash recovery, rate-limit persistence, resume-after-deploy come from Temporal, not the SDK.

**INFERENCE, HIGH.** The SDK's loop is deterministic enough to replay (model calls and tools abstracted behind interfaces), which is exactly what let Temporal wrap it. Durability is therefore proven to be layerable *if* the loop cleanly separates decision from effect — a design confirmation for a kernel that makes that separation native instead of retrofit.

### 10. Realtime agents: a second, event-driven runner

**FACT (Python docs/realtime/guide.md; JS voice-agents.mdx).** `RealtimeAgent` + `RealtimeRunner`/`RealtimeSession` (+ `RealtimeModel` transport abstraction) wrap the Realtime API: WebRTC default in browsers (ephemeral client tokens), WebSocket server-side (`OpenAIRealtimeWebSocketModel`), SIP for telephony (`OpenAIRealtimeSIPModel`); Cloudflare Workers and Twilio adapters in JS. `runner.run()` returns a live session, not a result; the client iterates events (`audio`, `tool_start`, `agent_end`, `history_added`, `guardrail_tripped`). No `output_type`; handoffs via `realtime_handoff()`; output guardrails are **debounced** over accumulated transcript deltas.

**INFERENCE, MEDIUM.** The text Runner's turn loop could not absorb speech-to-speech, so OpenAI built a *second* loop with a different contract (session/event-driven, no final output). Evidence that a turn-based loop is not a universal execution primitive; an event-loop kernel could host both.

### 11. Codex: one Rust harness, many surfaces, an event-sourced protocol

**SOURCE-CODE OBSERVATION (codex-rs workspace listing), HIGH.** The workspace has grown to roughly 100 crates. ## Precise vocabulary

For *this* system:

- **Model** — a named generation endpoint (e.g. `gpt-5.6-luna`); in-SDK, anything implementing `Model.get_response/stream_response`.
- **Model API** — Responses API (default; stateful, item-based, hosted tools, background) or Chat Completions (stateless fallback). The Responses API is *more than* a model API: it holds conversation state and executes tools.
- **Model adapter** — `OpenAIResponsesModel`, `OpenAIChatCompletionsModel`, `LitellmModel`, AI-SDK adapter; resolved by `ModelProvider`/`MultiProvider`. Notably fat: receives `tools`, `handoffs`, `output_schema`, state tokens, and owns their wire encoding.
- **Agent** — a *configuration dataclass* (instructions + tools + handoffs + guardrails + output_type + model). Not a process, not a runtime object; identity is by name.
- **Agent loop** — `AgentRunner`'s `while True` turn loop with the closed `NextStep` union; termination by no-pending-tools heuristic, `tool_use_behavior` short-circuit, `max_turns`, tripwire, or interruption.
- **Harness** — not OpenAI SDK vocabulary; the concept maps to Codex core ("the Codex harness" in OpenAI's own blog title) — loop + sandbox + approvals + state behind a protocol.
- **Context-management system** — items lists assembled per-turn from Session/server-tracker; handoff `input_filter`/`nest_handoff_history`; Codex adds `Compact`, `ThreadRollback`, AGENTS.md walk, skill progressive disclosure. No token-budget manager in the SDK core.
- **Memory system** — conversation stores only (`Session` protocol; SQLite/Conversations/compaction). True derived memory exists only in the beta sandbox package (two-phase generate/consolidate pipeline) and Codex's `memories` crate.
- **Tool runtime** — heterogeneous by tool type: SDK process (function tools), OpenAI infra (hosted tools, hosted MCP, V8 programmatic calling), host machine (shell/apply_patch/computer), sandbox workspace (sandbox capabilities), MCP servers.
- **Execution environment** — ABSENT in the core SDK (your process is the environment); beta sandbox Manifest/workspace; Codex: OS-sandboxed working directory or cloud container.
- **Planner** — ABSENT as a component. The model plans; Codex ships a `plan_tool` (todo list) as UI affordance.
- **Workflow/graph construct** — ABSENT, deliberately. Docs recommend code-orchestration around `Runner` calls; graphs/DAGs are explicitly not provided.
- **State/session model** — three-regime conversation state (client items / `Session` store / server `previous_response_id`+Conversations); `RunState` as versioned pause/resume snapshot; Codex: rollout JSONL event log + thread store.
- **Delegation mechanism** — handoffs (tool-call-triggered agent swap, first-wins), agents-as-tools (nested run), Codex subagent profiles/threads, cloud parallel attempts. All conventions over tool calls or threads — no first-class spawn primitive in the SDK.
- **Protocol usage** — MCP (client in SDK and Codex; Codex is also an MCP server via `mcp-server` crate); Codex SQ/EQ protocol; App Server JSON-RPC 2.0; JSONL event stream in `codex exec`; W3C trace context on submissions. No A2A support observed anywhere in these repos (ABSENT).
- **Capability discovery/negotiation** — MCP `list_tools` (+ caching/filtering); `ToolSearchTool` deferred loading; App Server `initialize` capabilities handshake; protocol-level `capabilities.rs`/`request_permissions`. No cross-runtime capability negotiation.
- **Policy/security layer** — SDK: guardrails + `needs_approval` + tool timeouts + `allowed_callers`; Codex: `AskForApproval` × `SandboxPolicy` matrix, OS mechanisms (Seatbelt/Landlock/seccomp), `execpolicy`, network-off defaults, env-var redaction, `.git`/`.env` protection.
- **Durable-execution features** — `RunState` serialization (pause/resume, not crash-safe mid-turn); Responses API `background=true` + resumable streams + server-stored state; Temporal integration (external) for real durability; Codex rollout JSONL (replayable log).
- **Event system** — SDK: stream events + lifecycle hooks (`AgentHooks`/`RunHooks`); Codex: EventMsg/`item/*` streams, filesystem `notify`, hooks (PreToolUse etc.). No pub/sub bus; all point-to-point streams.
- **Observability** — traces/spans with typed span data, pluggable processors, default export to OpenAI's dashboard; Codex `otel` + rollout-trace; token accounting via `TokenCount` events / `Usage`. Budget *enforcement* (cost/token ceilings): ABSENT everywhere except `max_turns`.

## Implications for a universal runtime kernel

1. **Delegation needs no primitive — interception does.** Handoffs are provably (source-verified) just function tools plus a runner-side interception rule and a history filter. A kernel that exposes (a) interceptable tool-call events and (b) a "replace active policy/config" operation gets handoffs, agents-as-tools, and subagents as userland conventions. Hard-coding any one of them would repeat OpenAI's mistake of needing three separate delegation mechanisms (handoff, as_tool, Codex subagents) that can't compose.

2. **The four-way `NextStep` union is the real control-flow contract.** Continue / delegate / finalize / pause-for-approval covers everything both SDKs and Codex do. But OpenAI hard-codes the *detection heuristics* (no-pending-tools ⇒ done; first handoff wins). A kernel should make step resolution a pluggable policy over an event stream, keeping the union as the vocabulary.

3. **Checkpointing above the runtime is fragile; make it kernel-native.** RunState (schemas 1.15/1.18, explicit supported-version lists, agent definitions excluded, JS needing invocation fingerprints to get exactly-once tool commits across resumes) shows what it costs to retrofit snapshots onto an in-memory loop. A kernel with an event-sourced log (like Codex's rollout JSONL — the healthier design already inside OpenAI's own stack) gets resume, fork (`thread/fork`), rollback (`ThreadRollback`), and audit from one mechanism.

4. **Keep the model boundary thin.** OpenAI's `Model` interface leaks agent semantics (`handoffs`) and provider state (`previous_response_id`, `conversation_id`) into every adapter, so every non-OpenAI provider must understand OpenAI's session tokens. A kernel model-adapter contract should be items-in/items-out plus a declared capability set, with provider-side statefulness modeled explicitly (see next).

5. **Providers are becoming runtimes; federate, don't wrap.** The Responses API stores state, executes hosted tools and MCP calls server-side, runs V8 programs, and executes in background — and the Assistants sunset (2026-08-26) confirms this is the permanent direction. A universal kernel must treat "execution that happens inside the provider" as a foreign execution domain with its own artifacts, policies, and budgets that the kernel mirrors (or it silently loses policy/budget/observability coverage exactly where the interesting work happens).

6. **Venue must be an attribute, not a type.** The SDK's closed 13-member Tool union encodes where code runs (SDK process, host, OpenAI infra, V8, sandbox) in the type system, forcing adapter churn per venue. A capability model should declare {schema, executor-binding, isolation requirement, approval requirement, caller-eligibility (`allowed_callers`), discoverability (deferred vs eager)} as orthogonal fields of one primitive — every one of these fields already exists somewhere in OpenAI's stack, just scattered across types.

7. **Approvals are the one HITL primitive you need.** `needs_approval` → typed interruption → serialize → approve/reject → resume, and Codex's server→client approval RPCs, are the same shape: an *effect gated on an external decision event*. Generalize to "any effect may block on a policy verdict from any principal (human, guardian model, execpolicy rule)" — Codex's `Granular`/`guardian`/`execpolicy` variants show the verdict source must be pluggable.

8. **Policy separates cleanly into intent × mechanism.** Codex proves a two-axis model works in production: approval policy (when to ask) × sandbox policy (what's physically possible), with mechanisms (Seatbelt/Landlock/bwrap/containers) hidden behind the policy enum and an `ExternalSandbox` escape hatch for pre-isolated environments. A kernel should standardize the declarative layer (filesystem scopes, network on/off, env-var redaction classes) and delegate mechanism to per-platform plugins.

9. **Durability layers on iff decisions and effects are separated.** Temporal wrapped the unmodified SDK by putting the loop in a Workflow and model/tool calls in Activities. That this worked externally, GA, without SDK changes is strong evidence the kernel should natively enforce the deterministic-orchestration/effectful-execution split rather than treat durability as a feature.

10. **One harness, many surfaces requires an event protocol, not an API.** Codex's SQ/EQ + App Server (submission ops, correlated event streams, server-initiated approval requests, capability handshake, replayable log, generated schemas) is the strongest existing template for the kernel's outer protocol — and its documented weakness (schema drift per CLI version, experimental gating) argues for the kernel to version its protocol as a real spec, not generated types.
