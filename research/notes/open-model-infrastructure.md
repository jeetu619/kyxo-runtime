# Open-Model Infrastructure: The Heterogeneity of Model Interaction Paradigms

Research note — 2026-08-15. Part of the kyxo-runtime ecosystem sweep.

## Scope

This note maps the open-model serving stack (vLLM, SGLang, llama.cpp, Ollama), the Hugging Face chat-template layer that is the *actual* contract between harnesses and open models, constrained-decoding engines (Outlines, XGrammar, GBNF), and the closed-provider interaction paradigms (OpenAI, Anthropic, Google, DeepSeek) that any runtime must interoperate with. The purpose is not a feature inventory: it is to enumerate, with evidence, the **axes on which model interaction paradigms diverge**, because that axis list is the requirements list for a capability-negotiation design — and the proof that a single lowest-common-denominator (LCD) "universal model API" necessarily loses capabilities.

Method note: several primary documentation hosts (docs.vllm.ai, docs.sglang.io, huggingface.co, platform.openai.com, docs.anthropic.com, ai.google.dev, api-docs.deepseek.com, learn.microsoft.com) were blocked by this environment's egress proxy. Wherever possible I fetched the *source files* of those docs from raw.githubusercontent.com; Anthropic API details come from the locally bundled vendor reference (`claude-api` skill, cached 2026-06); remaining gaps were filled by web search over indexed copies and issue trackers, and are labeled accordingly.

## Findings

### 1. Serving engines: the open-model "model API" is a locally-run server with a shim

**FACT.** vLLM, SGLang, llama.cpp (`llama-server`), and Ollama all expose an OpenAI-compatible HTTP surface as their primary integration point, while each maintains a *native* API and engine-specific extensions underneath. vLLM implements Completions, Chat Completions (plus a batch variant), Responses, Embeddings, and audio Transcription/Translation endpoints; it does not support OpenAI's `suffix` (completions), `user` (chat), or `image_url.detail` parameters, and it accepts engine-specific parameters through `extra_body` (e.g. `top_k`, `structured_outputs`) and `extra_headers` (`X-Request-Id`, priority scheduling).

**FACT.** SGLang's engine differentiators are RadixAttention (automatic prefix caching over a radix tree of past requests), zero-overhead CPU scheduling, continuous batching, speculative decoding, and prefill–decode disaggregation; the README claims production use at "trillions of tokens per day" across 400K+ GPUs. **INFERENCE (HIGH):** RadixAttention means open-model servers give *implicit, automatic* prefix caching as an engine property — a fourth caching paradigm distinct from all three closed-provider contracts (see §8).

**FACT.** Ollama's native API is not OpenAI-shaped at all: `/api/generate` and `/api/chat` stream newline-delimited JSON (not SSE), take a `think` parameter (boolean or `"low"|"medium"|"high"|"max"`), accept `format` as either `"json"` or a full JSON schema, and expose local-runtime concepts absent from every cloud API: `keep_alive` (model residency in RAM/VRAM), `options.num_ctx` (per-request context-window size), model load/unload via empty prompts. **INFERENCE (HIGH):** local serving surfaces *resource-lifecycle* concerns (load, residency, quantization, context allocation) that a runtime abstraction must either model or delegate; cloud APIs hide these entirely.

### 2. Chat templates are the real harness↔model contract

**FACT.** For open models, the interface between "list of messages + tools" and "token sequence" is a Jinja template stored in the model's tokenizer configuration and executed by `apply_chat_template()`. Templates differ per model family even for the same base architecture (Mistral `[INST]` vs Zephyr `<|user|>` control tokens), and the docs warn that omitting `add_generation_prompt=True` makes the model "continue the user's message instead of replying." `continue_final_message` exists to support response-prefill workflows by suppressing the EOS-closing of the last turn.

**FACT.** Hugging Face's unified tool-use extension lets `apply_chat_template(tools=...)` accept one standardized JSON-schema tool format which each template renders into model-specific tokens — but the blog states plainly that **parsing tool calls back out of model output remains model-specific and un-unified**. The inbound direction is standardized; the outbound direction is not.

**FACT.** Ollama does not use Jinja: templates are Go `text/template` files embedded in Modelfiles, with `.System`, `.Prompt`, `.Messages`, `.Tools`, `.ToolCalls` variables. The default template for imported models is `{{ .Prompt }}` — raw passthrough. **INFERENCE (HIGH):** there are at least *two incompatible template languages* for the same job, so "the chat template" is itself not a portable artifact; what is portable is the abstract message/tool structure that both template systems consume.

**INFERENCE (MEDIUM):** the chat template is best understood as a *model-supplied renderer*: a piece of code shipped with the weights that the harness must execute to talk to the model. This is an existence proof that "model" in an open ecosystem is not weights alone but weights + tokenizer + template + (see §3) output parsers — a bundle with code on both the encode and decode edges.

### 3. Tool-call wire formats: one JSON schema in, N token grammars out, parser plugins to reconcile

**FACT.** vLLM ships ~25 named tool-call parsers (`hermes`, `mistral`, `llama3_json`, `llama4_pythonic`, `pythonic`, `granite`, `granite-20b-fc`, `internlm`, `jamba`, `xlam`, `deepseek_v3`, `deepseek_v31`, `openai` (gpt-oss), `kimi_k2`, `qwen3_xml`, `glm45`, `glm47`, `cohere_command3`, `hunyuan_a13b`, `functiongemma`, and more), selected with `--enable-auto-tool-choice --tool-call-parser <name>`; custom parsers can be registered at runtime via `--tool-parser-plugin` implementing a `ToolParser` interface with both `extract_tool_calls()` (complete) and `extract_tool_calls_streaming()` (incremental) methods. SGLang has the analogous `--tool-call-parser` with 13 named parsers (`llama3`, `llama4`, `mistral`, `qwen`, `qwen3_coder`, `deepseekv3`, `deepseekv31`, `deepseekv32`, `kimi_k2`, `gpt-oss`, `glm`, `step3`, `pythonic`).

**FACT.** The underlying model-emitted formats genuinely differ in kind, not just syntax: Hermes-style `<tool_call>{json}</tool_call>` tags, Mistral `[TOOL_CALLS]` token + JSON array, Llama-3.1 bare-JSON convention, Qwen XML-ish variants, and *pythonic* formats where the model emits literal Python call expressions `[get_weather(location="Tokyo")]` (Llama-4 default). SGLang's docs note models "heavily finetuned on JSON" may ignore a pythonic template without prompt engineering.

**FACT.** llama.cpp implements the same reconciliation natively: with `--jinja` it auto-detects the model's template and applies a per-family handler (Llama 3.x, Functionary v3, Hermes 2/3, Qwen 2.5, Mistral Nemo, Firefunction v2, Command R7B, DeepSeek R1); for unrecognized templates it falls back to a *generic* mode that uses grammar-constrained sampling to force well-formed tool calls, at higher token cost. Tool calls are returned OpenAI-style with `finish_reason: "tool"`; DeepSeek R1 is flagged as reluctant to call tools without a custom template.

**INFERENCE (HIGH):** "tool calling" for open models is therefore a *三-layer* construct — (a) a schema-level contract (JSON-schema function definitions), (b) a template that renders tools into the prompt, and (c) a parser (or grammar constraint) that lifts model tokens back into structured calls — and layers (b) and (c) are per-model-family plugins in every serving engine. A universal runtime cannot treat "emits tool calls" as an atomic capability; it must model *where* the lifting happens (server-side parser vs harness-side parser vs grammar-forced) and allow the parser/template pair to be a pluggable, model-shipped artifact.

**FACT.** Tool-result *re-encoding* also diverges: OpenAI-compatible surfaces use a `role: "tool"` message; Ollama's native API uses `role: "tool"` with `tool_name`; Anthropic encodes results as `tool_result` content blocks inside a `role: "user"` message (all results for parallel calls must be in a single user message); OpenAI's Responses API uses `function_call_output` items. Same concept, four wire encodings.

### 4. Constrained decoding: a capability open models expose at the logit level and closed APIs expose only as a service feature

**FACT.** Outlines constrains generation via logit masking driven by finite-state machines compiled from regexes, JSON schemas, or context-free grammars, and runs against transformers, llama.cpp, vLLM, and Ollama backends — plus OpenAI/Gemini, where (INFERENCE, HIGH) it can only delegate to the provider's native structured-output feature since no logit access exists. XGrammar is a CFG-based engine with near-zero-overhead token-mask generation and is the *default* structured-output backend of vLLM, SGLang, TensorRT-LLM, and MLC-LLM (XGrammar-2 released May 2026, per README).

**FACT.** vLLM's unified `structured_outputs` parameter (the older `guided_json` / `guided_regex` / `guided_choice` / `guided_grammar` / `structural_tag` request params were deprecated in v0.12.0) supports five constraint classes: choice, regex, JSON schema, EBNF grammar, and structural tags (schema enforcement only inside designated tag regions — designed exactly for "free reasoning text + constrained tool-call spans"). It is exposed both through OpenAI-standard `response_format` and through `extra_body`. Structured output can be combined with reasoning models (constraint applies after the think section; Qwen3 needs `--structured-outputs-config.enable_in_reasoning=True`).

**FACT.** llama.cpp's GBNF is a distinct grammar dialect (BNF + repetition operators + char classes) with an automatic JSON-schema→GBNF converter supporting a *subset* of JSON Schema (including `minLength`/`pattern`/integer ranges); the docs note the grammar constrains output only — the schema is *not* shown to the model — and warn that badly written grammars (chained optionals) make sampling "extremely slow."

**FACT.** Closed providers expose the same underlying need as narrower, schema-only service features: OpenAI `response_format: json_schema` / strict function schemas; Anthropic `output_config.format` (json_schema) and `strict: true` tools — with a documented *unsupported* list (no recursive schemas, no numeric min/max, no string length constraints, `additionalProperties: false` required); Gemini responseSchema. **INFERENCE (HIGH):** grammar expressivity is a negotiable capability with at least four tiers — (1) full CFG/EBNF + regex + structural tags (vLLM/SGLang/llama.cpp), (2) JSON-schema-subset-only (closed APIs, each with a *different* subset), (3) "json mode" (validity only), (4) nothing. An LCD API keeps only tier 2∩3 and destroys tier 1, which is precisely the tier agentic pipelines use for non-JSON DSLs, diff formats, and typed code edits.

### 5. Reasoning exposure: at least five incompatible paradigms, differing in *visibility*, *replay contract*, and *budget control*

This is the sharpest divergence axis in the entire landscape.

1. **Open-weights, open trace (DeepSeek R1 family, QwQ, etc.).** The model emits literal `<think>…</think>` tokens. Serving engines strip them with a *reasoning parser*: vLLM `--reasoning-parser` (named parsers: `deepseek_r1`, `deepseek_v3`, `qwen3`, `granite`, `gemma4`, `glm45`, `ernie45`, `cohere_command3`, `hunyuan_a13b`, `minimax_m2_append_think`, …) moves the trace into a `reasoning` field (formerly `reasoning_content`) on the message and on stream deltas, and documents that tool calls are parsed *only* from `content`, never from reasoning (FACT). The OpenAI client SDK has no typed field for it — vLLM tells users to read it with `getattr` (FACT). **OBSERVED BEHAVIOR (HIGH):** DeepSeek's own hosted API additionally *requires* `reasoning_content` to be passed back on assistant messages once tool calls are in play in thinking mode, and returns HTTP 400 when OpenAI-compatible clients strip the unknown field — a failure reported across n8n, Spring AI, Codex, and opencode issue trackers. So even within the "OpenAI-compatible" world, the replay contract for reasoning is provider-specific and violates the assumption that unknown response fields can be dropped.
2. **OpenAI o-series / GPT-5: hidden, stateful-or-encrypted reasoning items.** Reasoning tokens are billed but never shown (summaries at most). In the Responses API, reasoning is a first-class *item* that must be preserved between function calls within a turn — via server-side state (`previous_response_id` / `store: true`) or, for ZDR/stateless callers, via `include: ["reasoning.encrypted_content"]`, which returns an encrypted blob the client must round-trip (FACT, cookbook). The cookbook reports that keeping reasoning items raised cache utilization from 40% to 80% and measurably improved benchmark scores. Chat Completions, by contrast, simply *drops* reasoning between turns (FACT).
3. **Anthropic: visible-or-summarized thinking blocks with cryptographic replay integrity.** Thinking is returned as typed `thinking` content blocks carrying a `signature`; when continuing a conversation (especially across tool use), blocks must be passed back **unchanged** — the API rejects tampering (FACT, vendor reference). `redacted_thinking` blocks carry encrypted `data`. Newer models (per the cached vendor reference) never return the raw chain of thought at all — `display: "summarized" | "omitted"` — and replay onto a *different* model silently drops the blocks. Budget control moved from `budget_tokens` to an `effort` level plus "adaptive" thinking (FACT for the documented API surface; note this reference is Anthropic-internal-cached and postdates public web sources).
4. **Google Gemini: thinking budgets/levels + enforced thought signatures.** Gemini 2.5 uses `thinkingBudget` (token count; `-1` dynamic, `0` off where allowed); Gemini 3 replaces it with `thinkingLevel` and *enforces* thought signatures: encrypted opaque strings attached to response parts, which must be returned on subsequent calls — omitting the signature on the first `functionCall` part of a step is a documented 400 (FACT, indexed official docs). Summaries via `includeThoughts`.
5. **No reasoning at all** — the majority of deployed open chat models; plus Ollama's simplification, where `think` is a boolean/level and (in its Anthropic-compat layer) budget enforcement is explicitly not implemented (FACT).

**INFERENCE (HIGH):** the reasoning axis is really three orthogonal sub-axes — *visibility* (raw / summarized / hidden / absent), *replay contract* (drop-forbidden with 400, drop-required, drop-tolerated, signature-verified, encrypted-blob, server-held-state), and *budget control* (token budget / discrete level / effort / boolean / none). Any two providers differ on at least one sub-axis; several fail *loudly* (400s) when treated as another. This is the strongest single argument that a universal runtime needs typed, negotiated reasoning capabilities and an *opaque, provenance-tagged carry-through channel* for provider state the harness must not touch.

### 6. The OpenAI-compatible API as de facto wire standard — and what it silently drops

**FACT.** Everything in the open ecosystem speaks some subset of OpenAI's Chat Completions dialect: vLLM, SGLang, llama.cpp server, Ollama `/v1/*`, plus routers (LiteLLM, OpenRouter — not directly examined here). But subsetting is real and inconsistent: Ollama's compat layer documents `tool_choice`, `logit_bias`, `user`, `n` as unsupported on chat, and `best_of`/`echo` on completions; vLLM rejects `suffix` and ignores `user`; llama.cpp requires explicit `"parallel_tool_calls": true`. Each engine also *extends* the dialect differently (vLLM `extra_body` for `top_k`/`structured_outputs`/`chat_template_kwargs`, priority headers; Ollama aliases via `ollama cp`).

**FACT.** Ollama now also ships a `/v1/responses` implementation ("only the non-stateful flavor... no `previous_response_id`") and an *Anthropic* `/v1/messages` compat layer built explicitly so Claude Code can drive local models — with thinking "accepted but budget not enforced," no `tool_choice`, no caching, approximate token counts. **INFERENCE (HIGH):** the ecosystem is converging on *two-plus* wire dialects (OpenAI Chat Completions ∪ Responses, Anthropic Messages), each of which is itself being re-implemented as a lossy subset by third parties. "OpenAI-compatible" is a family of dialects, not a spec: there is no conformance suite, no capability discovery beyond `/v1/models` (which returns names, not capabilities), and unknown-parameter behavior (silent-ignore vs 400) is itself divergent.

**INFERENCE (HIGH):** the `extra_body` mechanism is the ecosystem's confession that the standard is insufficient — every engine's real capability surface leaks through an untyped escape hatch that no client library validates. A capability-negotiation design should be read as "typed `extra_body` with discovery."

### 7. Session-based, bidirectional paradigms: not request/response at all

**FACT.** OpenAI's Realtime API (GA August 2025) is a *session* protocol over three transports — WebRTC (browser, ephemeral client secrets minted at `/v1/realtime/client_secrets`, SDP exchange at `/v1/realtime/calls`), WebSocket (server), and SIP (telephony) — with a typed vocabulary of client-sent and server-sent events (`session.created`, conversation-item events, response events), server-held conversation state for the session's duration, in-session function calling, and audio in/out.

**FACT.** Gemini Live API is a WebSocket protocol (`BidiGenerateContent`): the first client message must be a `BidiGenerateContentSetup` config, the client then streams continuous PCM audio / JPEG video frames, and the server streams responses; sessions have resumption handles (config-changeable on resume except the model) and in-session memory. Vertex publishes context-window-compression options for long sessions (OBSERVED BEHAVIOR, MEDIUM — referenced in cookbook/deepwiki material, primary page not fetched).

**INFERENCE (HIGH):** these APIs break every assumption of the request/response abstraction at once: connection lifecycle ≠ request lifecycle, state lives server-side, events are bidirectional and typed per provider, media is continuous rather than tokenized turns, and auth is split (long-lived key mints ephemeral session credentials). A runtime that models "model invocation" as a function call cannot express these; they need a session/stream primitive with event routing — which is also the natural home for local engines' long-lived server processes.

### 8. Prompt caching: four incompatible contracts for the same optimization

| Paradigm | Who decides | Contract surface | Billing shape |
|---|---|---|---|
| Anthropic **explicit** | caller | `cache_control: {type: "ephemeral", ttl}` breakpoints (max 4), prefix-hash semantics, per-model minimum prefix (512–4096 tokens), order `tools→system→messages` | write premium 1.25×/2×, reads ~0.1× (FACT, vendor ref) |
| OpenAI **automatic** | provider | nothing to declare; ≥1024-token prompts auto-cached by prefix; `prompt_cache_key` as routing *hint*; `cached_tokens` reported in usage | ~50% discount on cached input (FACT, indexed docs) |
| Gemini **implicit + explicit** | both | implicit on by default (2.5+); explicit `cachedContents` are *named server-side objects* with TTL you create, reference, and pay storage for | ~90% cached-token discount + storage cost for explicit (FACT, indexed docs) |
| Open engines **engine-level** | engine | RadixAttention / vLLM automatic prefix caching — a property of the KV-cache manager, no wire contract at all, no billing | latency win only (FACT for SGLang README; INFERENCE HIGH for generalization) |

**INFERENCE (HIGH):** caching contracts leak into *harness architecture*: Anthropic's explicit model forces prompt-assembly discipline (stable prefixes, breakpoint placement, "silent invalidator" audits — extensively documented in the vendor reference), Gemini's explicit model introduces a server-side *resource* with lifecycle (create/update-TTL/delete), OpenAI's needs only a routing hint, and open engines need nothing. A universal runtime can treat caching as a per-provider capability with three distinct shapes (annotation, resource, nothing) — it cannot silently paper over them because the *cost model and prompt-construction obligations* differ.

### 9. Context windows, and the small-model menagerie

**FACT.** Context windows in current production span roughly 8K (older open models) to 200K–1M (frontier closed models; 1M now standard on Anthropic's top tier per vendor ref, and 1–2M on Gemini Pro tiers per indexed docs). Local engines make the window a *deployment* parameter (Ollama `num_ctx`, llama.cpp `--ctx-size`) constrained by VRAM, with quantized KV-cache options that degrade quality (llama.cpp docs warn extreme KV quantization degrades tool calling — FACT).

**FACT (structural).** Real pipelines are not one-model systems: embedding models and rerankers (served by vLLM/SGLang/TEI as separate task types with different endpoints — vLLM serves `/v1/embeddings`; SGLang supports embedding models), classifier guards (Llama-Guard-class safety models), and fast "apply" models (e.g. speculative edit-application models used by coding products, per the broader sweep's Cursor note) sit alongside the frontier chat model. **INFERENCE (HIGH):** these interaction shapes (embed: batch text→vectors; rerank: query+docs→scores; classify: text→label; apply: file+edit→file) are request/response but *not chat* — a runtime whose only model primitive is "chat completion" forces these through prompt hacks. Task type belongs on the capability axis list.

### 10. The axes of divergence (the key deliverable)

Each axis below is evidenced above; together they are the requirements list for capability negotiation, and the proof that a pure-LCD universal API loses capabilities on every row.

1. **Statefulness of the conversation** — fully stateless resend-everything (Anthropic Messages, Chat Completions, all open engines) vs optional server-side state (OpenAI Responses `store`/`previous_response_id`) vs mandatory session state (Realtime, Gemini Live). Third-party Responses implementations are stateless-only (Ollama).
2. **Prompt encoding level** — structured messages rendered server-side via a model-shipped template (open engines) vs opaque provider rendering (closed APIs) vs raw token/text access (llama.cpp completions). Only open models let the harness choose the rendering; only they *require* the harness to care about it.
3. **Reasoning visibility** — raw trace / separate field / summarized / hidden-but-billed / absent.
4. **Reasoning replay contract** — must-echo-verbatim (DeepSeek 400, Anthropic signatures, Gemini thought signatures) vs must-carry-opaque-blob (OpenAI encrypted items) vs dropped-server-side (Chat Completions) vs no contract. Failures are loud (400s) and asymmetric.
5. **Reasoning budget control** — token budget (`budget_tokens`, `thinkingBudget`) vs discrete level (`reasoning_effort`, `thinkingLevel`, `effort`, Ollama `think` levels) vs boolean vs always-on/none. Not inter-convertible without policy decisions.
6. **Tool-call emission format** — typed API objects (closed) vs per-family token grammars requiring named parsers/plugins (Hermes/Mistral/Llama-JSON/pythonic/XML) vs grammar-forced generic fallback. Plus `tool_choice` support itself varies (absent in Ollama compat).
7. **Tool-result re-encoding** — `role:tool` message vs `tool_result` block in user turn vs `function_call_output` item vs template-specific rendering.
8. **Streaming grammar** — OpenAI chunk/delta SSE vs Anthropic typed block-event SSE (`content_block_start/delta/stop` with `thinking_delta`, `input_json_delta`) vs NDJSON (Ollama native) vs bidirectional event protocols (Realtime, Live). Parsers are not shared; even "SSE" differs in event vocabulary.
9. **Transport & session model** — HTTP request/response, SSE, WebSocket bidi, WebRTC, SIP; plus ephemeral-credential minting for client-side transports.
10. **Structured-output mechanism & expressivity** — logit-level CFG/EBNF/regex/structural-tags (open engines, with *pluggable backends*: xgrammar/guidance/outlines/GBNF) vs provider JSON-schema subsets (each subset different) vs json-mode vs none; and whether the schema is also *shown* to the model.
11. **Caching contract** — explicit annotations, automatic prefix, server-side cache resources, engine-internal; different billing and different obligations on prompt construction.
12. **Sampling-parameter surface** — `temperature/top_p/top_k/min_p/repetition_penalty` fully exposed (open engines, with per-model defaults pulled from HF `generation_config`) vs progressively *removed* (newest Anthropic models reject temperature per vendor ref; OpenAI reasoning models ignore/reject it — OBSERVED BEHAVIOR HIGH). A parameter can be required on one target and a 400 on another.
13. **Modality & task type** — chat, completion, FIM/suffix, embeddings, rerank, classification, transcription, image-gen, realtime audio/video; engines advertise these as distinct endpoints, not as one universal call.
14. **Context/resource management** — window size as deployment knob vs fixed; model residency (`keep_alive`), quantization, KV-cache budget — local-only concepts; server-side compaction (Anthropic) vs client-side truncation.
15. **Capability discovery** — near-absent everywhere: `/v1/models` returns IDs; Anthropic's Models API returns a typed capability tree (vendor ref — the exception that proves the point); open models rely on out-of-band metadata (tokenizer_config, model cards, engine flags). Nothing negotiates; clients hardcode.
16. **Error semantics for the unsupported** — silent ignore (Ollama unsupported fields), documented rejection (vLLM `suffix`), hard 400 (Gemini missing signatures, DeepSeek missing reasoning_content, Anthropic tampered signatures). The *same* client behavior (strip unknown fields) is correct on one provider and fatal on another — the single most dangerous property of the current ecosystem.

## Architecture decomposition

Mapping the open-model stack onto the mission's layer model (marks: **P**=proprietary, **OS**=open source, **STD**=standardized, **PS**=provider-specific, **PORT**=portable):

- **Product/UI** — n/a for serving engines; Ollama's CLI/desktop is the closest (OS, PS).
- **Agent/Harness** — out of scope here; consumes the layers below through OpenAI/Anthropic-dialect clients (PORT in theory, PS in the failure modes — axis 16).
- **Planning/orchestration** — ABSENT in this domain; serving engines schedule *tokens/requests* (continuous batching, priority headers — OS, PS), not tasks.
- **Context construction** — split: harness assembles messages (PORT); the **chat template** renders them to tokens (OS artifact, *model-specific*, executed engine-side; two template languages). Closed providers do this opaquely (P).
- **Model invocation** — OpenAI-dialect HTTP (de facto STD, unversioned, subset-per-engine); native APIs (PS); session protocols (PS, two of them).
- **Tool selection/execution** — selection is model behavior shaped by template+prompt; *emission parsing* is engine plugins (OS, per-family); execution is entirely harness-side (out of engine scope) except closed providers' server-side tools (P).
- **Environment** — for local engines, the host machine is part of the model API (VRAM, residency, quantization — OS, PS); for closed providers, hidden (P).
- **Observation** — streaming deltas + usage blocks; engine metrics (Prometheus in vLLM/SGLang — OS). No standard.
- **Verification** — constrained decoding is the only in-band verification layer (OS: xgrammar/outlines/GBNF at logit level; P: schema subsets as service). Everything else is harness-side.
- **State update** — stateless engines hold only KV-cache state (implicit, unaddressable except via SGLang radix reuse); session APIs hold real state (P); explicit cache resources (Gemini) are addressable state (P, PS).

The load-bearing observation: in the open stack, *the model boundary is not a line but a band* — template rendering, tool-call parsing, reasoning-trace parsing, and grammar constraint all sit between "harness" and "weights," implemented as engine-hosted, model-family-specific plugins.

## Precise vocabulary

For the open-model serving stack specifically:

- **Model**: weights + tokenizer + chat template + generation-config defaults + (implicitly) the tool-call and reasoning grammars it was trained to emit. Not just weights.
- **Model API**: the engine's HTTP surface — an OpenAI-dialect subset plus native endpoints plus `extra_body` extensions. De facto, unversioned, no conformance suite.
- **Model adapter**: the per-family plugin set inside the engine — chat template + tool-call parser + reasoning parser (+ optional grammar backend config). vLLM makes all three explicitly pluggable (`--chat-template`, `--tool-parser-plugin`, `--reasoning-parser`).
- **Agent / agent loop / harness**: ABSENT — serving engines are deliberately loop-free; the loop lives in the client.
- **Context-management system**: ABSENT at the wire level (client resends everything); *present* as engine memory management (paged KV cache, radix prefix reuse) — the same words meaning different layers.
- **Memory system**: ABSENT.
- **Tool runtime**: ABSENT (parsing only, no execution) — except closed providers' server-side tools.
- **Execution environment**: the GPU host itself; for local engines, exposed as API knobs (`num_ctx`, `keep_alive`).
- **Planner / workflow-graph construct**: ABSENT. (SGLang's *frontend language* is a partial exception: a programmatic DSL for multi-call generation programs with shared prefixes — closer to a prompt-program runtime than a workflow graph.)
- **State/session model**: stateless per-request for HTTP engines; KV/radix cache as *transparent* state; true sessions only in Realtime/Live paradigms.
- **Delegation mechanism**: ABSENT.
- **Protocol usage**: OpenAI dialect (+ growing Anthropic-dialect second standard); NDJSON/SSE/WebSocket transports; no MCP/A2A at this layer.
- **Capability discovery/negotiation**: essentially ABSENT — engine flags and model cards out-of-band; `/v1/models` names only; Anthropic's capability tree is the lone counterexample.
- **Policy/security layer**: ABSENT beyond API keys (Ollama: "api_key required but ignored"); guard *models* exist but are pipeline components, not layer features.
- **Durable-execution features**: ABSENT.
- **Event system**: streaming deltas only; typed event vocabularies exist only in the session APIs.
- **Observability**: usage objects (divergent field names: `cached_tokens` vs `cache_read_input_tokens` vs `cachedContentTokenCount`), engine Prometheus metrics; no cross-provider standard.

## Implications for a universal runtime kernel

1. **Capability negotiation must be axis-typed, not boolean.** "Supports tools" or "supports reasoning" is meaningless; the 16 axes above show each headline feature decomposes into 2–4 sub-axes (format, replay contract, budget control, error mode) that vary independently. The kernel's model-capability schema should encode axes and *tiers within axes* (e.g. grammar expressivity: cfg > regex > json-schema-subset(X) > json-mode > none), with the provider's schema-subset itself as data.
2. **An opaque, provenance-tagged carry-through channel is mandatory.** Encrypted reasoning items, thinking signatures, thought signatures, and DeepSeek's echo-required reasoning_content are all the same kernel requirement: the runtime must persist and replay provider-opaque state *bound to (provider, model, conversation position)*, must never let generic "history sanitizers" strip it, and must know it is non-portable across models. This is a first-class artifact type, not a JSON field to hope survives.
3. **The model adapter is a code-bearing plugin, not a config record.** Open models prove the adapter includes executable renderers (Jinja/Go templates) and parsers (tool-call, reasoning) that ship *with the model* and evolve per family. The kernel should treat "adapter" as a sandboxed plugin with encode(messages,tools)→prompt and decode(tokens)→typed-events duties — matching what vLLM/SGLang already made pluggable.
4. **Invocation needs two primitives, not one:** request/response (with streaming) *and* session/stream (bidirectional typed events over WS/WebRTC, ephemeral credentials, server-held state). Realtime/Live cannot be lowered onto request/response; local engine processes and their lifecycle map naturally onto the session primitive too.
5. **LCD flattening is empirically fatal, not just lossy.** The failure cases are 400s (Gemini signatures, DeepSeek reasoning, Anthropic tampering), silent capability loss (Ollama dropping `tool_choice`; Chat Completions dropping reasoning → measurably worse results per OpenAI's own cookbook), and silent cost regressions (cache-contract mismatch). A kernel should *refuse* to route a plan onto a target missing a required axis rather than degrade silently — and unknown-field behavior must be part of the target's declared contract.
6. **Caching is a policy/budget concern with three contract shapes** (annotation, server resource, automatic) and materially different economics; the kernel's budget/policy layer needs caching as a negotiated capability because it changes *how context must be constructed* (stable-prefix discipline) — i.e., a model capability that constrains a different subsystem (context construction). Cross-layer constraints like this are why capabilities can't live in per-layer silos.
7. **Constrained decoding should be modeled as a verification capability at the model boundary** — the only verification that can run *inside* generation. Where present (logit access), the kernel can offer grammar-checked artifacts cheaply; where absent, the same guarantee must be re-implemented as post-hoc validation + retry, at different cost. Same abstract capability, two execution strategies — a good template for the kernel's capability-to-strategy resolution generally.
8. **Task types beyond chat (embed, rerank, classify, apply, transcribe) deserve first-class invocation shapes**, since every serving engine already exposes them as distinct endpoints and pipelines compose them constantly.
9. **Two wire dialects are becoming load-bearing infrastructure** (OpenAI-dialect and Anthropic-dialect), each with lossy third-party reimplementations. The kernel should target neither as its internal model; both are projections. Internal representation should be the superset event/block model (typed content blocks + typed stream events), with dialect adapters at the edge — the direction Ollama's dual compat layers and vLLM's parser architecture are already groping toward.
10. **Capability discovery is the open niche.** Nobody negotiates today; clients hardcode. A runtime that ships accurate, versioned capability manifests for the top ~20 targets (and a probe suite to generate them) would provide immediate value independent of the rest of the kernel — and the manifest schema *is* the axis list above.

## Open questions

1. Does the OpenAI Responses API's item/event model (typed items, `include` projections, server-optional state) already constitute a viable superset wire format, or does Anthropic's block/signature model contain elements (signed replay integrity) that Responses cannot express?
2. How stable are tool-call parser plugins in practice — what is the breakage rate when model families revise their emission format between checkpoints (e.g. DeepSeek v3→v3.1→v3.2 each needing a new SGLang parser), and can a manifest version-pin them?
3. Is there any de jure standardization effort for the OpenAI dialect (conformance suite, unknown-field semantics), or should the kernel assume permanent dialect drift? (None found in this sweep.)
4. What are the exact semantics of KV-cache/prefix reuse as *addressable* state — could a runtime pin/lease radix-cache prefixes across requests the way Gemini leases `cachedContents`, and do engine APIs expose enough to build that?
5. For the session paradigm, can Realtime's and Live's event vocabularies be unified into one bidirectional session capability, or do turn-detection/VAD semantics differ enough that sessions also need axis-typed negotiation?
6. Primary-source verification pass: DeepSeek's official reasoning-model doc and Gemini Live's context-window-compression page were reconstructed from secondary sources here; both should be re-fetched from an unblocked network before the architecture docs cite them normatively.
