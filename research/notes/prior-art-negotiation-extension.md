# Prior Art Outside AI: Capability Negotiation, Protocol Evolution, and Minimal-Kernel Architectures

Research note for the kyxo-runtime architecture mission. Written 2026-08-15.

## Scope

This note surveys battle-tested mechanisms from ~15 non-AI systems for the two hardest problems in our runtime design:

1. **Capability discovery/negotiation and protocol evolution without redesign** — LSP, HTTP content negotiation, TLS extensions/ALPN/GREASE, QUIC transport parameters, Wayland's registry, browser feature detection (and vendor prefixes as a failure case).
2. **Minimal-kernel + userland-strategy architectures** — L4/seL4 microkernels, object-capability security (E, Cap'n Proto, seL4, Fuchsia/Zircon), Erlang/OTP behaviours and supervision, Kubernetes' resource model and CRDs, VS Code's extension architecture, Plan 9/9P, Linda tuple spaces, and Linux's ABI-stability discipline.

For each system I extract the *mechanism* (not the whole system), why it worked or failed, and its direct translation to our capability/extension/versioning design. The note closes with a synthesized shortlist of 12 proven patterns the kernel should adopt.

Method note: the research sandbox's egress proxy blocked most canonical spec hosts (rfc-editor.org, datatracker.ietf.org, httpwg.org, microsoft.github.io, capnproto.org, wayland.freedesktop.org, component-model.bytecodealliance.org, gitlab.freedesktop.org, trustworthy.systems, sel4.systems). All of these documents have canonical or official GitHub mirrors, which I fetched directly (raw.githubusercontent.com); remaining gaps were closed with web search over official sources. Each claim is labeled FACT / SOURCE-CODE OBSERVATION / OBSERVED BEHAVIOR / INFERENCE with confidence.

## Findings

### 1. LSP — declared capability sets at bind time (the closest cousin)

**Mechanism.** FACT: At `initialize`, client and server exchange structured capability objects: the client sends `ClientCapabilities` (including, per feature, whether it supports `dynamicRegistration`), and the server answers with `ServerCapabilities` in `InitializeResult`. The spec: "A development tool and the language server announce their supported features using capabilities." FACT: After initialization, servers can register/unregister capabilities at runtime via `client/registerCapability` / `client/unregisterCapability`, but only for features where the client declared dynamic-registration support. FACT: The tolerance rules are explicit: "Clients should ignore server capabilities they don't understand (e.g. the initialize request shouldn't fail in this case)," and any message whose method starts with `$/` may be ignored by a receiver that doesn't implement it. FACT: The protocol does not version-gate features; features are annotated `@since 3.17.0` and gated by capability flags, so "compatibility is maintained through capability negotiation rather than version checking." LSP 3.17 is current-stable; 3.18 is published as an evolving draft (OBSERVED BEHAVIOR, HIGH).

**Why it worked.** INFERENCE (HIGH): Per-feature capability flags let a 2016 client talk to a 2026 server: each side simply does the intersection. The `experimental` capability field plus `@since` annotations gave a sanctioned path from experiment to standard without a version cliff. Dynamic registration decouples *what you could ever do* from *what is active right now* (e.g. after a config change) without restart.

**Translation.** Our capability contract should be a two-sided structured declaration at session bind, feature-granular (not version-granular), with (a) a must-ignore rule for unknown fields, (b) an experimental namespace, and (c) a runtime register/unregister channel for capabilities whose availability changes mid-session. This is also exactly the shape MCP borrowed (MCP is LSP's descendant), which validates the pattern in-domain.

### 2. HTTP content negotiation — preference-weighted selection plus provenance

**Mechanism.** FACT (RFC 9110, June 2022): Proactive negotiation: the server selects a representation based on client preferences (`Accept`, `Accept-Encoding`, `Accept-Language`) weighted by quality values (`q=`, 0..1, "1 being preferred and 0 being unacceptable"); reactive negotiation returns choices for the client to pick. FACT: `Vary` records which request dimensions influenced selection, so caches know when a stored response applies. FACT: `406 Not Acceptable` signals negotiation failure. FACT: extensibility rests on recipients treating unrecognized header fields as opaque and ignoring them.

**Why it worked.** INFERENCE (HIGH): Negotiation over *orthogonal dimensions* (media type, encoding, language) with scalar preferences degrades gracefully — there is always a lawful default (server picks its best guess) rather than a hard failure. `Vary` is underrated: it is negotiation *provenance*, making cached results safe.

**Translation.** Artifact exchange in our runtime (model outputs, tool results, checkpoints) should carry negotiated media types with q-weighted preferences, and any cached/derived artifact should record its `Vary`-equivalent: which capability/context dimensions the result depended on. That is the difference between a reusable checkpoint and a stale one.

### 3. TLS 1.3 + ALPN + GREASE — extension vectors, frozen version fields, and anti-ossification

**Mechanism.** FACT (RFC 9846, July 2026, obsoletes RFC 8446 — the current TLS 1.3 spec): "Servers MUST ignore unrecognized extensions." Conversely, unsolicited extensions are a protocol violation: "Implementations MUST NOT send extension responses ... if the remote endpoint did not send the corresponding extension requests ... Upon receiving such an extension, an endpoint MUST abort the handshake with an 'unsupported_extension' alert." FACT: TLS 1.3 abandoned the version field for negotiation: `legacy_version` is frozen at 0x0303 (TLS 1.2) and real negotiation moved into the `supported_versions` *extension*, because "many servers do not properly implement version negotiation, leading to 'version intolerance' in which the server rejects an otherwise acceptable ClientHello with a version number higher than it supports." FACT (RFC 7301): ALPN lets the client list application protocols in ClientHello and the server pick one in ServerHello — negotiation of the *next layer up* folded into the existing handshake with zero added round trips. FACT (RFC 8701, Jan 2020): GREASE reserves values that will never mean anything, which implementations advertise at random; "correctly implemented peers will ignore these values and interoperate. Peers that do not tolerate unknown values will fail to interoperate, revealing the mistake before it is widespread." The reserved values are deliberately sparse so peers can't just special-case them.

**Why it worked / what failed.** OBSERVED BEHAVIOR (HIGH): The TLS 1.2→1.3 transition demonstrated that *any field an intermediary can read will be ossified by that intermediary* — middleboxes broke connections with honest version numbers, forcing TLS 1.3 to masquerade as 1.2. The extension vector survived where the version field died, because ignore-unknown had been normative there for years. GREASE turned the must-ignore rule from parchment into a continuously-tested invariant.

**Translation.** (1) Do not put a load-bearing protocol version integer in our kernel handshake; negotiate per-capability and keep any version field decorative from day one. (2) Asymmetric rules: liberal on unknown *offers*, strict (fail-fast) on unsolicited *responses* — that combination catches implementation bugs without blocking evolution. (3) Build GREASE in from v0: the kernel should routinely inject nonsense capability IDs, event types, and artifact fields to keep every plugin's ignore path exercised. (4) ALPN's lesson: piggyback higher-layer negotiation (e.g. which harness protocol an agent speaks) on the one bind handshake instead of adding round trips.

### 4. QUIC — typed parameter bags plus reserved values

**Mechanism.** FACT (RFC 9000, May 2021): Endpoints exchange transport parameters during the handshake and "An endpoint MUST ignore transport parameters that it does not support"; further, "Some identifiers are reserved in order to exercise this requirement" — greasing is in the core spec, not an add-on. FACT: Version negotiation is a distinct server-initiated packet listing acceptable versions. FACT: New frame types are added via extension and their use is subject to negotiation (documented in the extensions section; the MUST-ignore rule applies to parameters, while unknown *frames* are a connection error — the safety valve is negotiating before use). (Frame-type detail: FACT, HIGH, from spec structure; my excerpt tool did not surface the exact frame normative line, noted honestly.)

**Why it worked.** INFERENCE (HIGH): QUIC learned from TLS: it encrypted almost everything so middleboxes *cannot* ossify it, made ignore-unknown normative for the negotiation surface, and shipped greasing in the base protocol. QUIC v2 (RFC 9369) exists substantially to exercise version negotiation before it rusts (OBSERVED BEHAVIOR, MEDIUM).

**Translation.** Our session-establishment record should be a typed key-value parameter bag (budgets, limits, policy hints) with mandatory ignore-unknown and reserved greased keys. Distinguish parameters (ignorable) from operations (must be negotiated before use): an unknown *event type* in a stream a plugin subscribed to may be ignorable; an unnegotiated *capability invocation* must be a hard error.

### 5. Wayland — minimal core + registry-advertised globals with versions

**Mechanism.** FACT: Wayland's core is tiny (connection, `wl_display`, `wl_registry`); everything a compositor offers is advertised as *globals* through registry events. The `global` event "notifies the client that a global object with the given name is now available, and it implements the given version of the given interface"; `global_remove` retracts it. Clients call `wl_registry.bind(name, interface, version, id)` choosing an actual version ≤ the advertised maximum. FACT: Globals appear and disappear at runtime ("as a result of device or monitor hotplugs, reconfiguration or other events"). FACT: Whole protocol families (xdg-shell, wlr-protocols) live outside the core as separately-versioned XML-defined extensions (OBSERVED BEHAVIOR, HIGH).

**Why it worked.** INFERENCE (HIGH): The registry makes capability discovery an *event stream*, not a static handshake — hotplug is the normal case, not an error. Version-at-bind (client picks ≤ advertised) gives per-object version pinning without global lockstep. The failure mode to note: Wayland extension fragmentation across compositors (wlroots vs GNOME vs KDE protocol support matrices) shows that a minimal core pushes the compatibility problem into the extension ecosystem — discoverability must come with a conformance/profile story (OBSERVED BEHAVIOR, MEDIUM).

**Translation.** Our kernel should own only the connection + registry + event plumbing; every capability (model adapters, tools, harness strategies) is an advertised global with an interface name and max version, bound by consumers at a chosen version, and *retractable at runtime with an event*. Add what Wayland lacks: named profiles ("baseline agent world") so the ecosystem doesn't fragment into per-vendor capability matrices.

### 6. WASI Component Model + WIT — typed capability contracts and virtualizable worlds

**Mechanism.** FACT: WIT is the IDL of the Component Model: packages are semver-identified (`wasi:clocks@1.2.0`); interfaces group functions/types; a **world** is "a complete description of both imports and exports of a component" — equivalently, a component type. FACT: The type system is language-neutral (records, variants, options, results, lists) and includes **resources** accessed via **handles**, owned or borrowed — capability-shaped references with lifetime semantics. FACT (Goals.md): the model targets "portable, virtualizable, statically-analyzable, capability-safe, language-agnostic interfaces," where virtualizable means any import can be satisfied by another component (shimmed) rather than the real host.

**Why it works.** INFERENCE (HIGH): A world makes the *totality* of a component's authority statically visible: nothing enters except through declared imports — no ambient authority by construction, checkable before instantiation. Virtualizability is the killer feature for a runtime like ours: a "filesystem" import can be a sandbox, a recorder, or a policy filter, and the component cannot tell.

**Translation.** WIT is the strongest candidate for our capability contract format: define capabilities as WIT-style interfaces, agent/plugin types as worlds (imports = required capabilities, exports = provided behaviours), and let policy interpose by virtualizing imports. Semver-at-package plus per-interface evolution handles versioning. Even if we don't adopt Wasm as the execution substrate, adopting the *contract algebra* (worlds, resources, owned/borrowed handles) is low-cost and high-value.

### 7. Object-capability security — authority as unforgeable reference

**Mechanism.** FACT (erights.org/E lineage): In the ocap model, designation conveys authority ("no designation without authority"); "ambient authority" — permissions available without being handed a reference — is the anti-pattern (term coined by Tribble and Miller); POLA (Principle of Least Authority) is the operating rule. FACT (Cap'n Proto RPC docs): "Interface references — or, as we more commonly call them, capabilities — are a first-class type"; "they both designate an object to call and confer permission to call it"; passing one over a connection grants the receiver, and only the receiver, the ability to call; promise pipelining lets `bar(foo())` travel as one round trip; level-3 implementations do three-party handoff (vats forming direct connections as references are passed). FACT (seL4): a capability is "a unique, unforgeable token that constitutes a permission to access an entity or object in the system"; caps live in kernel-managed CNodes; *all* kernel-object access is by capability invocation; copies can be minted with a *subset* of rights (attenuation — never amplification); `seL4_CNode_Revoke` deletes a capability *and every capability derived from it*; at boot the initial task holds all authority and everything else is explicit delegation. FACT (Fuchsia/Zircon): handles are process-local references to kernel objects carrying rights (READ/WRITE/EXECUTE...); "kernel objects do not have an intrinsic notion of security and do not do authorization checks; security rights are held by each handle"; "an empty process has no ambient authority" — everything a process can do arrives via handles passed by its creator.

**Why it worked.** INFERENCE (HIGH): Four independent systems (a language, an RPC protocol, a verified microkernel, a production OS) converged on the same invariants: unforgeability, possession = authority, attenuate-on-delegate, hierarchical revocation, no ambient authority. That convergence is the strongest signal in this entire note. Ocap also composes with distribution (Cap'n Proto) and with formal verification (seL4's proofs hang off the capability model).

**Translation.** This is THE security model for "the AI cannot grant itself privilege." Concretely: (1) capabilities are kernel-issued unforgeable references, never strings the model can fabricate — a model emitting the *name* of a tool must not be the same thing as holding the *capability* to invoke it; (2) delegation to a subagent mints an attenuated child capability (narrower scope, tighter budget, shorter TTL); (3) revocation is transitive over the delegation tree — killing an agent kills everything it delegated; (4) policy is interposition: wrap a capability in a filter, the holder can't tell (seL4 "interpose access", Component Model "virtualize imports" — same move); (5) budgets attach naturally to capabilities as attenuated quantitative rights.

### 8. Erlang/OTP — behaviours as strategy contracts, supervision as failure policy

**Mechanism.** FACT: "Behaviours are formalizations of these common patterns. The idea is to divide the code for a process in a generic part (a behaviour module) and a specific part (a callback module)." The generic part (gen_server, gen_statem, gen_event, supervisor) implements the loop, message handling, and system messages; the user supplies only callbacks. FACT: Supervisors "keep child processes alive by restarting them"; strategies are one_for_one, one_for_all, rest_for_one, simple_one_for_one; restart intensity is bounded ("If more than MaxR restarts occur in the last MaxT seconds, the supervisor terminates all the child processes and then itself" — escalation, not looping); child specs declare restart class (permanent/transient/temporary) and shutdown policy; `auto_shutdown` lets significant-child termination end a whole work unit.

**Why it worked.** INFERENCE (HIGH): The generic/specific split is why OTP code is legible and robust: hot upgrade, tracing, and supervision integration live in the behaviour once, and every server in the ecosystem inherits them. Let-it-crash works only because supervision turns failure into a *policy decision* (restart class, intensity, escalation) rather than in-line error handling.

**Translation.** A "harness" in our design is precisely an OTP behaviour: the kernel (or stdlib) ships the generic agent loop — event intake, checkpointing, budget accounting, cancellation — and a strategy plugin supplies callbacks (`on_event`, `plan`, `act`, `verify`). Different harnesses (ReAct-ish loop, graph executor, workflow engine) are different behaviour implementations over the same callback contract. Supervision maps to agent lifecycle policy: restart classes for crashed agents, MaxR/MaxT as loop-runaway budgets, escalation up the supervision tree as the containment story for cascading failures.

### 9. Microkernel history (Mach → L4 → seL4) — the minimality principle and its tax

**Mechanism/history.** FACT (Liedtke, SOSP'95): "A concept is tolerated inside the µ-kernel only if moving it outside the kernel, i.e., permitting competing implementations, would prevent implementation of the system's required functionality." FACT (Heiser/Elphinstone, "L4: Lessons from 20 Years," ACM TOCS 2016): first-generation microkernels (Mach) had IPC costs around 100µs, which killed the architecture's promise; Liedtke's L4 achieved order-of-magnitude faster IPC by radical minimality and cache-conscious design; Mach's in-kernel memory-object machinery was replaced by low-level address-space mechanisms with memory objects, copy-on-write etc. built in userland. FACT (same source): several original L4 features were later dropped as insufficiently minimal or unsafe (long IPC, IPC timeouts, hierarchical process models), and the family converged on capabilities (seL4, Fiasco.OC, OKL4); seL4 pushed even kernel memory allocation into userland (kernel objects are created from user-held "untyped" capabilities). OBSERVED BEHAVIOR (HIGH): seL4's ~10kloc kernel is formally verified end-to-end, feasible only because of that minimality.

**Why it worked / failed.** INFERENCE (HIGH): Mach failed not because minimalism was wrong but because the *primitive it forced everything through* (IPC) was slow — decomposition is only viable when the kernel's hot path costs roughly nothing. L4's second lesson: minimality is a test you keep applying — features migrate *out* over time (even memory management), and each removal made the kernel more analyzable.

**Translation.** (1) Adopt Liedtke's sentence verbatim as our kernel-admission test: models, tools, agents, planners, graphs all fail it (competing implementations are obviously permittable), so they are userland; capability issuance/attenuation/revocation, event delivery, and checkpoint/budget accounting plausibly pass it. (2) Identify our IPC-equivalent — the cost of crossing the kernel boundary between strategy, model adapter, and tool runtime, including context serialization — and make it near-free (zero-copy artifact references, not payload copying), or the minimal kernel will lose to monolithic frameworks on latency exactly as Mach lost to monolithic kernels. (3) Expect to *remove* concepts over time; design the boundary so removal is possible.

### 10. Kubernetes — declarative desired state, CRDs, and version conversion

**Mechanism.** FACT: Object identity is (Group, Resource, Namespace, Name); "different API versions (such as v1 and v1beta1) of the same Group and Resource represent the same underlying data." Objects are declarative desired-state records; controllers reconcile actual toward desired; `resourceVersion` strings order changes and drive **watch** subscriptions. FACT: The API is extended without touching the core by CustomResourceDefinitions (new types served by the same API machinery) and by the aggregation layer (delegating whole API subtrees to external servers). FACT (CRD versioning): multiple versions can be served concurrently; "one and only one version must be marked as the storage version"; conversion between served versions is done by user-supplied **conversion webhooks** (round-trip-safe, metadata-preserving); `status.storedVersions` tracks what exists on disk, and deprecating a version requires migrating stored objects.

**Why it worked.** INFERENCE (HIGH): CRDs are the most successful "userland types" mechanism in production software: the kernel (API server) provides storage, validation, versioning, RBAC, watch, and audit *generically*, and the semantics live entirely in userland controllers. Reconciliation loops absorb partial failure by construction — a controller that crashes just resumes reconciling. Conversion webhooks make version evolution a userland concern with a kernel-enforced contract (round-trip).

**Translation.** Our runtime's registry of capability/agent/workflow definitions should be CRD-shaped: userland declares new *types* (a new harness kind, a new artifact schema) and the kernel supplies persistence, schema validation, versioned serving, watch streams, and policy hooks without code changes. Orchestration itself can be reconciliation: a "desired run state" object plus a controller loop is a durable, resumable alternative to imperative workflow engines. Adopt storage-version + conversion-adapter for evolving our own record formats (checkpoints, manifests).

### 11. VS Code — manifest contributions, lazy activation, out-of-process extensions

**Mechanism.** FACT: "Contribution Points are a set of JSON declarations that you make in the `contributes` field of the package.json Extension Manifest" — commands, menus, languages, views, configuration, debuggers etc. are registered *statically*, read by the workbench without running extension code. FACT: Activation events (`onLanguage`, `onCommand`, `workspaceContains`, `onStartupFinished`, ...) load extensions lazily; since VS Code 1.74, declared contributions auto-imply their activation events. FACT: Extensions run in a separate **extension host** process (local Node, web worker, or remote), explicitly so that "misbehaving extensions should not impact the user experience"; extensions reach the workbench only through the vscode API, never the renderer.

**Why it worked.** INFERENCE (HIGH): The static-manifest/lazy-activation pair solves the cold-start problem of plugin ecosystems: thousands of installed extensions cost nothing until an event proves them relevant. Process isolation converts extension crashes from product bugs into recoverable events. The declared-contribution model also gives the marketplace and the UI full knowledge of an extension's surface without executing it — the same property WIT worlds give components.

**Translation.** Plugins in our runtime (tools, harnesses, adapters) should ship a static manifest of contributions (capabilities provided, event subscriptions, artifact types) that the kernel indexes without executing plugin code, plus activation events ("activate when event X / capability request Y occurs") for lazy start. Execution belongs in an isolated host process/sandbox with the kernel API as the only door — which is also where the ocap boundary naturally lives.

### 12. Web platform evolution — feature detection wins, vendor prefixes failed

**Mechanism/failure.** FACT (MDN): "Feature detection involves working out whether a browser supports a certain block of code, and running different code depending on whether it does"; browser sniffing is "a terrible practice that should be discouraged at all costs." FACT (MDN): vendor prefixes (`-webkit-` etc.) failed because "web developers included prefixed features on production websites, despite their experimental nature," ossifying experiments, and "smaller browser vendors ... ended up having to add other browsers' prefixes in order to render popular websites"; the replacement is experimental features behind flags plus detection.

**Why prefixes failed.** INFERENCE (HIGH): Prefixes put the experiment *in the production namespace with a different name*, so content depended on it; competitors then had to implement the competitor-branded name, entrenching it. Flags keep experiments out of production reach entirely; detection branches on capability, not identity.

**Translation.** (1) Never branch runtime behavior on implementation identity ("model == claude-x", "provider == openai") — always probe the declared capability; identity sniffing is the UA-string mistake reborn, and it's currently endemic in AI frameworks. (2) Experimental kernel capabilities must live behind opt-in flags in a namespace that cannot ship to production dependents, not behind vendor-branded names — or we will inherit `-webkit-`-style permanent legacy aliases.

### 13. Plan 9 / 9P — one tiny protocol as the universal capability interface

**Mechanism.** FACT: In Plan 9, every resource — storage, network (`/net/ether0`), graphics, process control — is a file tree served over 9P, a protocol with 13 message types over any reliable transport; there are no special-case syscalls/ioctls. FACT: Each process has a *private, malleable namespace* built by bind/mount/union-mount, no privilege required, and mounts are visible only within the process tree that created them; 9P is network-transparent, so remote resources mount like local ones.

**Why it worked (and didn't).** INFERENCE (HIGH): Uniformity is the point — one small verb set makes wildly heterogeneous capabilities scriptable with the same tools, and *namespace construction becomes the security/policy mechanism*: what an agent can touch is exactly what was mounted into its view, which is attenuation by construction (a namespace is a capability list spelled as a directory tree). Commercially Plan 9 failed (ecosystem gravity, OBSERVED BEHAVIOR HIGH), but the mechanism survives in Linux namespaces/containers, FUSE, and /proc.

**Translation.** Give every agent a constructed namespace of its capabilities rather than a global service directory plus ACLs: the kernel mounts capability providers into the agent's view; delegation = re-mounting a subset into the child. A small uniform verb set over all capabilities (open/read/write/watch-equivalent) keeps generic tooling (tracing, replay, policy filters) writable once.

### 14. Linda tuple spaces — decoupled coordination through a shared space

**Mechanism.** FACT (Gelernter 1985): generative communication — producers deposit tuples into a shared associative space; consumers match on content; the parties are decoupled in space (don't name each other) and time (needn't coexist). 

**Translation.** INFERENCE (MEDIUM): This is the blackboard model for our *artifact space*: agents coordinate by publishing/consuming typed artifacts matched on schema/content, not by addressing each other — which composes cleanly with dynamic agent populations (agents appearing/disappearing mid-run, as in Wayland's hotplug). Its historical weakness — unscoped shared mutable space becomes a contention and security mess (OBSERVED BEHAVIOR, MEDIUM) — is fixed by combining it with ocap: an agent sees only the artifact-space *view* it holds a capability to.

### 15. Linux ABI discipline — "we don't cause regressions"

**Mechanism.** FACT: The kernel's "first rule": "We don't cause regressions"; Linus: "If the kernel used to work for you, the rule is that it continues to work for you," and "no amount of 'you shouldn't have used this' ... is at all relevant." FACT: Scope is precise — the rule protects *userspace-visible behavior*, while "we do API breakage inside the kernel all the time." FACT: Documented ABI stability classes (stable/testing/obsolete/removed) with a minimum 2-year guarantee for stable interfaces.

**Translation.** INFERENCE (HIGH): The kernel↔userland boundary needs a constitution, not a semver habit: once a capability contract is marked stable, behavior observed by plugins is guaranteed even when it was "wrong," while everything inside the kernel stays freely refactorable. Publish stability classes per capability (experimental/testing/stable/deprecated) as first-class metadata in the registry.

## Architecture decomposition

Prior-art is a pattern library, not one system, so this maps *which proven mechanism should govern each layer of our target runtime*, with the provenance's openness status:

- **Product/UI** → VS Code workbench model: UI composed from statically declared contributions; plugins never touch the renderer. (Provenance: open source, provider-specific to VS Code but widely cloned; portable pattern.)
- **Agent/Harness** → OTP behaviour: kernel/stdlib generic loop + userland callback strategy module. (Open source, standardized within the Erlang ecosystem; portable.)
- **Planning/orchestration** → Kubernetes reconciliation: desired-state objects + userland controllers; workflow/graph engines become controllers over run objects. (Open source, de-facto standardized; portable.)
- **Context construction** → HTTP negotiation + Vary: context assembly is representation selection with recorded provenance of what it depended on. (Standardized, portable.)
- **Model invocation** → ALPN posture: which model protocol/adapter to speak is negotiated at bind on the existing handshake; adapters are userland globals. (Standardized pattern; the AI-specific layer itself is ABSENT in prior art — see vocabulary.)
- **Tool selection/execution** → ocap + Plan 9 namespace: tools are capabilities mounted into the agent's namespace; invocation requires the reference; policy is interposition. (Ocap: open literature + open source kernels; standardized in no single spec; portable.)
- **Environment** → VS Code extension host + seL4 isolation: plugin code runs out-of-process/sandboxed with the kernel API as sole door. (Open source patterns; portable.)
- **Observation (events)** → Wayland registry + K8s watch: capability appearance/disappearance and state changes are ordered event streams with resume tokens (resourceVersion). (Open source, portable.)
- **Verification** → GREASE + feature detection: continuous self-testing of the extension surface; conformance profiles instead of implementation sniffing. (Standardized, portable.)
- **State update / durability** → K8s storage-version + conversion adapters; Linux regression rule for the contract. (Open source discipline; portable.)

## Precise vocabulary

For the prior-art corpus as a whole (AI-specific rows are deliberate ABSENTs — these systems achieve capability negotiation, extension, and failure containment with zero notion of intelligence in the kernel, which is the thesis of our design):

- **Model / model API / model adapter**: ABSENT across all surveyed systems. The nearest analog is Wayland's/LSP's *server implementation behind a negotiated interface* — the kernel-side concept is only "an endpoint that declared capabilities."
- **Agent**: nearest analogs — an Erlang process under a supervisor; a Fuchsia process whose entire authority is its handle set; a Plan 9 process defined by its namespace. All three define an agent *extensionally*: it is what it holds, not what it is.
- **Agent loop**: OTP behaviour generic module (gen_server's receive loop) — the loop is infrastructure; the strategy is callbacks.
- **Harness**: the behaviour contract itself (gen_server/gen_statem): a named, versioned callback interface with kernel-provided generic machinery. ABSENT elsewhere.
- **Context-management system**: ABSENT as such; closest is HTTP representation negotiation + caching metadata (Vary) — context as negotiated, provenance-stamped representation.
- **Memory system**: ABSENT (K8s etcd-backed object store with resourceVersion is the closest structural analog: durable, versioned, watchable records).
- **Tool runtime**: seL4/Zircon capability invocation, Cap'n Proto RPC, 9P file service — invocation of held references over a small uniform verb set.
- **Execution environment**: VS Code extension host (local/web/remote), Wasm component instance, Erlang node — an isolated substrate whose only interface is the declared one.
- **Planner**: ABSENT. Kubernetes controllers are the closest thing: goal-state comparison and convergence, with no deliberation in the kernel.
- **Workflow/graph construct**: ABSENT as kernel concept everywhere (K8s expresses workflows as CRDs + controllers — i.e., userland).
- **State/session model**: LSP session from `initialize` to `shutdown`; QUIC connection with transport parameters; K8s objects with resourceVersion. Common shape: session = negotiated parameter set + ordered event stream + resumable position.
- **Delegation mechanism**: capability minting with attenuated rights (seL4 mint/copy, Zircon handle duplication with reduced rights, Cap'n Proto passing references); Plan 9 namespace sub-mounting. Uniformly: delegation = handing a narrower reference, never editing a policy database.
- **Protocol usage**: JSON-RPC (LSP), 9P, Cap'n Proto RPC, HTTP, TLS records — all small fixed message vocabularies with extension vectors.
- **Capability discovery/negotiation**: the star of this note — LSP initialize capability objects, Wayland registry globals, TLS/QUIC extension+parameter vectors, HTTP Accept, WIT worlds (static rather than negotiated). Two distinct species: *negotiated at bind* (LSP/TLS/QUIC/HTTP) and *statically declared in the artifact* (WIT worlds, VS Code manifests); mature systems need both.
- **Policy/security layer**: ocap (unforgeable refs, attenuation, revocation, no ambient authority); Plan 9 namespaces; K8s admission/RBAC (the ACL counterexample — powerful but requiring central policy evaluation on every request; INFERENCE MEDIUM: ocap scales better for delegation-heavy workloads like sub-agents).
- **Durable-execution features**: K8s desired-state reconciliation (crash = resume reconciling); Erlang supervision restarts with bounded intensity; Linux ABI guarantees making upgrade safe. ABSENT: deterministic replay à la Temporal in these systems.
- **Event system**: Wayland registry events (global/global_remove), K8s watch with resourceVersion resume, VS Code activation events (events as lazy-loading triggers), Erlang message passing.
- **Observability**: ABSENT as a distinguished subsystem in most; Erlang's behaviour-mediated sys/trace facilities show that putting the generic loop in the kernel is what makes uniform tracing possible (SOURCE-adjacent FACT, MEDIUM).

## Implications for a universal runtime kernel

The shortlist — 12 proven patterns with provenance — synthesized as kernel requirements:

1. **Two-sided declared capability sets at bind time** (LSP initialize; TLS extension vector; MCP already copies this). Feature-granular flags, `experimental` namespace, intersection semantics.
2. **Must-ignore-unknown, everywhere, asymmetric** (HTTP/TLS/QUIC/LSP): unknown declarations/parameters are ignored; *unsolicited responses and unnegotiated invocations are hard errors* (TLS `unsupported_extension` rule). Both halves, or evolution stalls or security leaks.
3. **Grease every extension point from v0** (RFC 8701/RFC 9000): the kernel routinely advertises reserved nonsense capability IDs, event types, and manifest fields; plugins that choke are caught in CI, not in the field.
4. **No load-bearing version integers; capability vectors instead** (TLS 1.3's frozen legacy_version; LSP `@since`): version fields ossify because intermediaries read them; per-feature negotiation survives.
5. **Unforgeable capability references, attenuate-on-delegate, transitive revoke, no ambient authority** (seL4/Zircon/Cap'n Proto/E): the only authority an agent has is the references it was handed; sub-agent spawning mints narrower, budget-bounded, revocable children; policy = interposition on references the holder cannot distinguish from the real thing. This is the entire answer to "the AI cannot grant itself privilege."
6. **Typed, language-neutral capability contracts — WIT worlds as the candidate format** (Component Model): capability = interface; plugin/agent type = world (imports/exports); resources with owned/borrowed handles; virtualizable imports give policy interposition and testing for free; semver at the package level.
7. **Liedtke's minimality test as the kernel constitution** (L4/seL4): a concept enters the kernel only if userland-competing implementations would prevent required functionality — models, tools, agents, planners, graphs all fail the test; capability issuance, events, checkpoints, budgets plausibly pass. Corollary from Mach: the kernel's crossing primitive (context/artifact handoff) must be near-zero-cost — pass references, never copy payloads — or minimalism loses to monoliths.
8. **Userland types on kernel machinery — the CRD move** (Kubernetes): new capability kinds, artifact schemas, and harness types are *data* registered with the kernel, which supplies storage, validation, multi-version serving (one storage version + userland conversion adapters), watch, and policy generically. Orchestration = desired-state objects + userland reconciliation controllers.
9. **Behaviour contracts for harnesses; supervision for failure** (OTP): kernel/stdlib owns the generic agent loop (event intake, checkpoint, budget, cancellation); strategies are callback modules. Failure handling is declarative supervision: restart classes, bounded restart intensity (MaxR/MaxT = runaway-loop budgets), escalation trees.
10. **Static manifests + activation events + isolated plugin hosts** (VS Code): the kernel indexes what a plugin contributes without executing it, starts it lazily on a matching event, and runs it out-of-process behind the kernel API — the same boundary where the ocap perimeter lives.
11. **Feature detection, never identity sniffing; experiments behind flags, never in shipped namespaces** (web platform; vendor prefixes as the canonical failure): frameworks branching on model/provider names are re-committing the UA-string sin; capability probes + conformance profiles replace them, and experimental capabilities must be unreachable by production dependents.
12. **Per-agent namespaces over a uniform verb set + generative artifact space + a regression constitution** (Plan 9 + Linda + Linux): an agent's world is a constructed namespace of mounted capabilities (attenuation by construction, network-transparent); agents coordinate through a capability-scoped shared artifact space (space/time-decoupled, matched on content); and the kernel↔userland contract, once stable, is never broken — even when the old behavior was a bug — while kernel internals refactor freely under stability-class metadata.

Cross-cutting synthesis: the negotiation cluster (1–4) and the authority cluster (5–7) are duals — *declaration* tells you what a peer can do, *capability* controls what it may do — and systems that conflate them (K8s RBAC-over-declared-APIs at scale, browsers pre-GREASE) accumulate either central-policy bottlenecks or silent ossification. Our kernel should keep them as two orthogonal primitives: a registry of declared interfaces (LSP/Wayland-shaped) and a graph of held references (seL4-shaped), with binding as the act that converts a discovery into a capability under policy.

## Open questions

1. WIT worlds are *static* contracts; LSP-style negotiation is *dynamic*. What is the precise composition — negotiate which world-version to instantiate, then treat the world as sealed? Who owns mid-session capability changes (Wayland-style global_remove) under a sealed world?
2. What is the quantitative kernel-crossing budget (the Mach question) for an AI runtime, where the payloads are megabyte-scale contexts rather than 64-byte messages? Does zero-copy artifact reference-passing actually survive crossing process/sandbox isolation boundaries?
3. Ocap revocation vs durable execution: transitive revoke of a delegation subtree conflicts with resumable checkpoints that embed capability references — do checkpoints hold refs (revocable but resurrection-fragile) or petnames re-resolved under policy at resume (safer but weaker than pure ocap)?
4. Conformance profiles: Wayland shows a minimal core fragments into per-vendor capability matrices without them. Who defines our "baseline agent world" profile, and how is it versioned without becoming exactly the monolithic version number pattern 4 forbids?
5. GREASE for semantic capabilities: random unknown *values* are cheap to ignore, but can we grease higher-order surfaces (unknown event schemas, unknown artifact fields inside signed/checkpointed records) without breaking hashing, signatures, or replay determinism?
6. Is there prior art for *budgets as attenuated quantitative rights* (capability with a spend meter)? seL4's untyped-memory retyping and Zircon job policies are close but not identical; this may be a genuinely novel kernel object needing careful design.
