# A2A (Agent2Agent) Protocol — Deep Protocol Study (spec v1.0.x, mid-2026)

## Scope

This note is a protocol-level study of the Agent2Agent (A2A) protocol as of 2026-08-15: the v1.0.0/v1.0.1 specification (canonical proto data model, task lifecycle state machine, Agent Cards, discovery, transport bindings, extensions, security), its version history (0.1.0 → 0.2.x → 0.3.0 → 1.0.x), governance under the Linux Foundation, the official SDK ecosystem, its officially-stated relationship to MCP and where that positioning genuinely holds vs. overlaps, and — per the mission's key question — an extraction of A2A's "opaque remote executor with a task lifecycle" contract and Agent Card capability-declaration design as candidate kernel patterns, plus a systematic inventory of what A2A deliberately or accidentally does NOT specify (budgets, verification, lineage, policy, durability).

Primary evidence: the full spec markdown and the canonical `a2a.proto` (812 lines) fetched from `github.com/a2aproject/A2A` at `main` (which renders as the v1.0.x spec on a2a-protocol.org), repo topic docs, GOVERNANCE.md, ADR-001, and the a2a-python SDK server source. The a2a-protocol.org website itself was blocked by the research proxy; the GitHub sources it is generated from were used instead and are noted as such.

## Findings

### F1. Identity, history, governance

- FACT: A2A is an open protocol for communication between "independent, potentially opaque AI agent systems," Apache-2.0, hosted at `github.com/a2aproject/A2A` under the Linux Foundation. The spec's stated goal: agents collaborate "without needing access to each other's internal state, memory, or tools."
- FACT: Version history per the official releases page: 0.2.1 (2025-05-27) → 0.2.2 (2025-06-09, gRPC+REST bindings and extensions added) → 0.2.3/0.2.4/0.2.5 (June 2025, multi-transport declaration, protocol version in card, multiple push configs) → 0.2.6 (2025-07-17) → **0.3.0 (2025-07-30**: mTLS scheme, OAuth2 metadata URL, extended-agent-card method, well-known URI renamed `agent.json` → `agent-card.json`, card `signatures`) → **1.0.0 (2026-03-12**: first stable release; breaking changes; `tasks/list` added; OAuth modernization with device-code + PKCE, implicit/password deprecated; multi-tenancy via `tenant` routing field; Part flattening/`kind` discriminator removal; "canceled" spelling standardization) → 1.0.1 (2026-05-28, editorial/binding fixes). The spec header lists released versions 0.1.0, 0.2.6, 0.3.0, 1.0.0.
- FACT (spec §3.6): protocol version is negotiated as `Major.Minor` via an `A2A-Version` service parameter (HTTP header or query param); an empty header MUST be interpreted as version 0.3 (grandfathering pre-1.0 clients); unsupported versions get `VersionNotSupportedError`. Servers MAY expose multiple versions of the same transport at same or different URLs.
- OBSERVED BEHAVIOR (HIGH): Google announced A2A on 2025-04-09 with 50+ launch partners; donated it to the Linux Foundation, announced 2025-06-23 at Open Source Summit NA; by the April-2026 one-year mark the LF reported 150+ supporting organizations and enterprise production deployments (press releases + Google OSS blog anniversary post, seen via search).
- FACT (GOVERNANCE.md): Technical oversight by a Technical Steering Committee with eight company-held seats: Google, Microsoft, Cisco, AWS, Salesforce, ServiceNow, SAP, IBM. One-vote-per-member, majority decisions, LF meeting infrastructure, GitHub as decision record, Discord for chat. A "steady state" TSC composition is due 18 months after inception.
- FACT (ADR-001, 2025-11-18): The TSC adopted the ProtoJSON specification as the normative JSON serialization of the proto data model — i.e., **the proto file is the canonical data model and JSON is derived**, explicitly acknowledging tool-chain coupling risk and reversibility.

### F2. Core data model (canonical proto, v1.0)

All from SOURCE-CODE OBSERVATION of `specification/a2a.proto` (`package lf.a2a.v1`) unless noted; confidence HIGH throughout (it is the canonical artifact).

- `Task { id (server-generated, REQUIRED), context_id, status: TaskStatus (REQUIRED), artifacts: repeated Artifact, history: repeated Message, metadata: Struct }`. Comment: "`Task` is the core unit of action for A2A."
- `TaskStatus { state: TaskState (REQUIRED), message: Message, timestamp }` — the status carries an optional human/agent-readable Message explaining the state (this is how "what input do you need?" is conveyed in `INPUT_REQUIRED`).
- **TaskState enum (the lifecycle state machine), exact wire names:** `TASK_STATE_UNSPECIFIED(0)`, `TASK_STATE_SUBMITTED(1)`, `TASK_STATE_WORKING(2)`, `TASK_STATE_COMPLETED(3)` (terminal), `TASK_STATE_FAILED(4)` (terminal), `TASK_STATE_CANCELED(5)` (terminal), `TASK_STATE_INPUT_REQUIRED(6)` (**interrupted**), `TASK_STATE_REJECTED(7)` (terminal; "agent has decided to not perform the task," at creation or later), `TASK_STATE_AUTH_REQUIRED(8)` (**interrupted**). JSON serialization uses these SCREAMING_SNAKE names verbatim (spec §5.5); pre-1.0 JSON used lowercase `submitted`/`working`/`input-required`/etc. So the state set is: 1 initial-ack state, 1 active state, 2 interrupted (resumable) states, 4 terminal states. The spec defines no explicit transition table — legal transitions are implied by the terminal/interrupted classification plus operation semantics (e.g., messages to terminal tasks → `UnsupportedOperationError`; `CancelTask` on terminal → `TaskNotCancelableError`). INFERENCE (HIGH): the machine is deliberately transition-permissive — any non-terminal state may move to any other — because agents are opaque and the protocol cannot know their internal progress structure.
- `Message { message_id (client/creator-generated, REQUIRED), context_id, task_id, role: ROLE_USER|ROLE_AGENT (REQUIRED), parts: repeated Part (REQUIRED), metadata, extensions: repeated URI-string, reference_task_ids: repeated string }`.
- `Part`: a `oneof content { text: string; raw: bytes (base64 in JSON); url: string; data: google.protobuf.Value }` plus `metadata`, `filename`, `media_type`. FACT (Appendix A.2.1): v1.0 **removed the `kind` discriminator** (`{"kind":"text",...}` / TextPart-FilePart-DataPart wrappers of 0.x) in favor of member-name-as-discriminator matching proto `oneof` semantics — a breaking change rationalized as aligning JSON-RPC and gRPC representations and simplifying codegen.
- `Artifact { artifact_id (unique within task, REQUIRED), name, description, parts (REQUIRED, ≥1), metadata, extensions }` — "Artifacts represent task outputs."
- Streaming events: `TaskStatusUpdateEvent { task_id, context_id, status, metadata }` and `TaskArtifactUpdateEvent { task_id, context_id, artifact, append: bool, last_chunk: bool, metadata }` — artifact chunking is done by re-sending an artifact id with `append=true` and finishing with `last_chunk=true`.
- `StreamResponse` = `oneof { task, message, status_update, artifact_update }` — the single envelope used by streams AND webhook payloads.
- FACT (spec §3.7): Messages are for communication (initiation, clarification, status, interaction); **"Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts."** Task history persistence is agent-discretionary, and "Messages MUST NOT be considered a reliable delivery mechanism for critical information."

### F3. Operations surface (binding-independent)

- FACT (spec §3.1): Eleven core operations, all mandatory-mappable in every binding: SendMessage; SendStreamingMessage; GetTask; ListTasks (new in 1.0, cursor-paginated, sorted by status timestamp desc, MUST be authorization-scoped); CancelTask (best-effort); SubscribeToTask (re-attach to a live task's event stream; first event MUST be a full Task snapshot to close the Get/Subscribe race); Create/Get/List/Delete TaskPushNotificationConfig; GetExtendedAgentCard.
- FACT: `SendMessage` returns **either a `Task` or a direct `Message`** — the agent chooses per interaction. This dual return is the protocol's escape valve for cheap stateless exchanges (see F6).
- FACT (spec §3.2.2): `SendMessageConfiguration.return_immediately` — **blocking is the default**: the call waits until the task reaches a terminal OR interrupted state. `return_immediately: true` gives async task-handle semantics with client-driven polling/streaming/webhooks. (INFERENCE, MEDIUM: defaulting to blocking is a DX concession that a universal kernel should invert — long-running-first with an awaitable veneer.)
- FACT: `SendMessageConfiguration` also carries `accepted_output_modes` (client's acceptable response media types — the only in-band modality negotiation), an inline `TaskPushNotificationConfig` (webhook can be registered at send time), and `history_length`.
- FACT (spec §3.3.1): idempotency is weak — Get ops naturally idempotent; SendMessage "MAY be idempotent" via agent-side `messageId` dedup; Cancel idempotent. No exactly-once anywhere.
- FACT (spec §3.3.2, §5.4): a two-layer error taxonomy: standard auth/validation/resource/system categories mapped per binding, plus nine A2A-specific errors with canonical mappings, e.g. `TaskNotFoundError` = JSON-RPC `-32001`/gRPC `NOT_FOUND`/HTTP 404; `TaskNotCancelableError` `-32002`; `PushNotificationNotSupportedError` `-32003`; `UnsupportedOperationError` `-32004`; `ContentTypeNotSupportedError` `-32005`; `InvalidAgentResponseError` `-32006`; `ExtendedAgentCardNotConfiguredError` `-32007`; `ExtensionSupportRequiredError` `-32008`; `VersionNotSupportedError` `-32009`. Error details use ProtoJSON `Any` with `google.rpc` well-known types.
- FACT (spec §3.3.4): capability gating is enforced at the protocol level: using streaming/push/extended-card operations against an agent whose card doesn't declare them MUST produce the specific errors above. Declared capabilities are thus a *contract*, not advertising.

### F4. Multi-turn correlation: contextId / taskId

- FACT (spec §3.4): `contextId` groups tasks + messages into a logical session. Server MAY generate it on first contact and MUST return it; server MAY accept client-provided ones but MUST reject (not silently re-map) unacceptable ones; clients SHOULD treat server-generated ids as opaque. `taskId` is **strictly server-generated**; "Client-provided taskId values for creating new tasks is NOT supported"; a client-supplied `taskId` MUST reference an existing task; mismatched (contextId, taskId) pairs MUST be rejected.
- FACT: the `input-required` flow: agent parks the task in `TASK_STATE_INPUT_REQUIRED` (with a status Message saying what it needs); client resumes by sending a new Message carrying the same `taskId`; blocking sends return at interrupted states so the caller can react.
- FACT (life-of-a-task doc): **task immutability** — once terminal, a task never restarts; refinements/follow-ups are *new tasks in the same contextId*, optionally citing `referenceTaskIds`. Rationale given: reliable referencing for orchestration and traceability, clean unit-of-work mapping, simpler implementations. Parallel follow-up tasks under one context are explicitly supported (flight → hotel → spa example).
- FACT (life-of-a-task doc): **artifact lineage is explicitly out of scope**: "the serving agent shouldn't be responsible for tracking artifact mutations, and this linkage is not part of the A2A protocol specification. Clients should maintain this version history on their end." Agents SHOULD keep artifact `name` stable across refined versions as a client-side correlation hint.

### F5. Update delivery: polling, streaming, webhooks

- FACT (spec §3.5): three complementary mechanisms — polling (GetTask), streaming (SendStreamingMessage / SubscribeToTask), push notifications (webhook CRUD). Streaming requires `capabilities.streaming`, push requires `capabilities.pushNotifications`.
- FACT: streaming ordering: events MUST be delivered in generation order, never reordered; multiple concurrent streams per task are allowed and MUST all receive the same events in the same order (fan-out/broadcast semantics); stream MUST close at terminal state; task lifecycle is independent of any stream's lifecycle (reconnect-by-subscribe is the recovery path).
- FACT: push notifications POST a `StreamResponse` JSON payload (media type `application/a2a+json`, always plain-HTTP-binding JSON regardless of the agent's transport) to the registered URL with credentials from `PushNotificationConfig.authentication`; delivery is **attempt-at-least-once** ("Agents MUST attempt delivery at least once"), retries with backoff only MAY; clients SHOULD process idempotently, MUST 2xx-ack, MUST validate task id; servers SHOULD SSRF-filter webhook URLs (reject private ranges/localhost). A per-config `token` field supports client-side source validation.
- INFERENCE (HIGH): delivery semantics are deliberately weak — reliable state lives only in the server-held Task record; streams and webhooks are lossy *hints* to go read it. GetTask-after-notification is the intended consistency anchor. This "state is authoritative, events are advisory" split is a load-bearing design decision.

### F6. Message-vs-Task duality and agent taxonomy

- FACT (life-of-a-task doc): the docs classify implementations as Message-only agents (thin LLM wrappers, stateless, contextId-correlated), Task-generating agents (everything is a task, even trivial responses become completed tasks), and Hybrid agents (Messages to negotiate scope, then a Task to execute). Once a task exists, the agent only returns Task objects for it, and terminal tasks accept no more messages.
- INFERENCE (MEDIUM): this taxonomy is evidence that a two-object interaction model (cheap message vs. durable task) creates real modeling ambiguity that A2A resolves by documentation rather than protocol; a kernel that makes *everything* a (possibly instantly-completed) task with cheap-path optimization would remove the ambiguity at the cost of bookkeeping.

### F7. Agent Card: declaration, discovery, integrity

- SOURCE-CODE OBSERVATION (proto, HIGH): `AgentCard { name*, description*, supported_interfaces*: repeated AgentInterface, provider {url*, organization*}, version*, documentation_url?, capabilities*: AgentCapabilities, security_schemes: map<string,SecurityScheme>, security_requirements: repeated SecurityRequirement, default_input_modes*, default_output_modes* (media types), skills*: repeated AgentSkill, signatures: repeated AgentCardSignature, icon_url? }` (* = REQUIRED).
- `AgentInterface { url*, protocol_binding* (open string; core: "JSONRPC", "GRPC", "HTTP+JSON"), tenant (opaque routing id for multi-agent/multi-tenant endpoints, new in 1.0 — MUST be echoed in every request's `tenant` field), protocol_version* ("0.3", "1.0") }` — ordered by preference, first entry preferred; all interfaces MUST be functionally equivalent (spec §5.1).
- `AgentCapabilities { streaming?, push_notifications?, extensions: repeated AgentExtension, extended_agent_card? }` — note these are *protocol-feature* capabilities, not domain capabilities. Domain capability description lives in `AgentSkill { id*, name*, description*, tags*, examples, input_modes, output_modes, security_requirements }`.
- FACT: **skills are advisory, not invocable.** `SendMessageRequest` has no skill-id parameter anywhere in the proto; the spec calls skills "largely a descriptive concept." Routing a message to a skill is the opaque agent's internal decision, informed by natural-language content. Per-skill `security_requirements` let an agent require different OAuth scopes per skill, but enforcement is again internal. (This is the sharpest single contrast with MCP tools, which are named, schema-typed, and directly invoked.)
- FACT (spec §8.2, §14.3): discovery mechanisms: (1) well-known URI `https://{domain}/.well-known/agent-card.json` (IANA registration template included; renamed from `agent.json` in 0.3.0); (2) curated registries/catalogs (mechanism unspecified by the protocol — explicitly an ecosystem concern, with "registry selective disclosure" noted in the discovery doc); (3) direct configuration.
- FACT (spec §8.4): cards MAY carry detached JWS signatures (RFC 7515): payload = card minus `signatures`, minus unset-optional/default-valued fields (proto field-presence semantics), canonicalized with RFC 8785 JCS; protected header MUST have `alg`, `typ:"JOSE"`, `kid`, MAY have `jku` to a JWKS. Clients SHOULD verify at least one signature before trusting a card. This is the protocol's only integrity primitive for identity/capability claims.
- FACT (spec §3.1.11, §13.3): the **extended Agent Card** is an authenticated variant fetched via `GetExtendedAgentCard` when `capabilities.extendedAgentCard: true`; it MAY reveal additional skills/details per authenticated identity and SHOULD replace the cached public card for the session. (1.0 moved the flag from a top-level `supportsExtendedAgentCard` field into `capabilities` — Appendix A.2.2.)
- FACT (spec §8.6): card freshness is plain HTTP caching (Cache-Control/ETag/conditional GET) — no push invalidation, no version-negotiation handshake beyond the card's `version` string.

### F8. Transport bindings

- FACT (spec §§9–12): three official bindings, all mandatory-equivalent: **JSON-RPC 2.0** over HTTP(S) with PascalCase method names matching gRPC (`SendMessage`, `GetTask`…) and SSE (`text/event-stream`) for streams; **gRPC** (the proto's `A2AService` with `google.api.http` annotations, server streaming); **HTTP+JSON/REST** (AIP-style URLs: `POST /message:send`, `POST /message:stream`, `GET /tasks/{id}`, `POST /tasks/{id}:cancel`, `GET /tasks/{id}:subscribe`, pushConfig CRUD under `/tasks/{id}/pushNotificationConfigs`, `GET /extendedAgentCard`; all with `/{tenant}/...` additional bindings). Custom bindings are allowed, SHOULD be URI-identified in `protocolBinding`, and MUST define data-type mappings, service-parameter transmission, error mapping, and streaming equivalents (spec §12).
- FACT: "service parameters" (`A2A-Version`, `A2A-Extensions`) are transport-mapped horizontal metadata — HTTP headers for HTTP bindings, gRPC metadata for gRPC (spec §3.2.6).
- INFERENCE (MEDIUM): tri-binding equivalence has a real cost — the method-mapping, error-mapping, and JSON-vs-proto naming appendices exist because three concrete encodings of one abstract service must be kept in lockstep; the 0.2.x→1.0 churn (kind-discriminator removal to align JSON with `oneof`) shows the JSON model ultimately surrendered to the proto model. A kernel should pick one canonical schema + one canonical encoding and treat other transports as gateways, which is where A2A effectively landed (proto canonical + ProtoJSON derived).

### F9. Security architecture

- FACT (spec §7, enterprise doc): identity and authentication are **entirely at the HTTP/transport layer** — "A2A protocol payloads don't carry user or client identity information directly." Requirements are declared in the card via OpenAPI-3.2-style `SecurityScheme`s: API key (header/query/cookie), HTTP auth (Bearer etc.), OAuth 2.0 (authorization-code w/ PKCE flag, client-credentials, device-code; implicit & password deprecated in 1.0), OpenID Connect (discovery URL), mTLS (added 0.3.0). `security_requirements` name required scheme+scopes combos, overridable per skill. Credential acquisition is out-of-band by design.
- FACT: servers MUST authenticate every request, MUST authorize every operation against the caller's boundaries (user/role/project/tenant models are "agent-defined, not prescribed"), MUST NOT reveal existence of unauthorized resources (404 for both not-exist and no-access), and MUST scope ListTasks results.
- FACT (spec §7.6, notable): **in-task authorization** — the `TASK_STATE_AUTH_REQUIRED` interrupted state lets an agent bounce a mid-task authorization need (OAuth token for a downstream API, human approval for a destructive action) back to its client; the client can resolve it, or — if it is itself an A2A server for someone else — propagate `AUTH_REQUIRED` upward, "forming a chain of Tasks in AUTH_REQUIRED." Credentials SHOULD flow out-of-band directly to the requesting agent; if in-band, they SHOULD be audience-bound and encrypted to the originating agent. The spec is explicit that the state transition itself confers no authorization and that scope/validity/revocation semantics are **not defined by A2A** (§7.6.4).
- INFERENCE (HIGH): §7.6 is the closest thing in any shipped agent protocol to a *recursive permission-escalation primitive* — approval requests propagating up an opaque delegation chain — but it is only a signaling convention: the semantic payload (what is being authorized, for how long) is entirely implementation/extension-defined.
- FACT: there is no delegated end-user identity primitive (no on-behalf-of token exchange profile, no SPIFFE-style workload identity) in the core spec; card JWS signatures are the only cryptographic identity binding, and they authenticate the *card document*, not the live endpoint.

### F10. Extensions mechanism

- FACT (spec §4.6, extensions doc): extensions are URI-identified, declared in `capabilities.extensions` as `AgentExtension { uri, description, required: bool, params: Struct }`; clients opt in per-request via the `A2A-Extensions` service parameter; a `required: true` extension that the client doesn't declare → `ExtensionSupportRequiredError`. Extension data rides in the `extensions[]` + `metadata` (keyed by extension URI) fields present on Message and Artifact. Version = new URI on breaking change; agents MUST NOT silently fall back to older extension versions.
- FACT (extensions doc): the sanctioned extension taxonomy is broad: **data-only** (extra card facts, e.g. GDPR compliance), **profile** (constraining/augmenting core flows, including *substates* of task states via status-message metadata, e.g. a 'generating-image' substate of WORKING), **method extensions / "extended skills"** (entirely new RPCs, e.g. a `tasks/search`), and **state-machine extensions** ("adding new states or transitions to the task state machine"). Official extensions get `https://a2a-protocol.org/extensions/` URIs and `ext-`/`experimental-ext-` repos under a2aproject; samples include a timestamp extension, a traceability extension, a "Secure Passport" context-sharing extension, and an Agent Gateway Protocol routing extension.
- INFERENCE (MEDIUM): allowing extensions to add states and RPC methods makes the "core" lifecycle a *minimum* rather than a closed algebra — good for evolution, hazardous for portable orchestrators, which can only rely on the 8 core states plus the terminal/interrupted classification.

### F11. SDKs and server-side execution model

- FACT: six official SDKs — Python (`a2a-sdk` on PyPI), JS/TS (`@a2a-js/sdk`), Java, Go (a2asrv/a2aclient), .NET (`A2A` package), Rust (`a2a-rs`) — under the a2aproject org; the Python SDK implements spec 1.0 with an explicit 0.3 compatibility mode, all three transports both client- and server-side, optional FastAPI/Starlette, gRPC, OpenTelemetry, and Postgres/MySQL/SQLite task stores.
- SOURCE-CODE OBSERVATION (a2a-python `agent_executor.py`, HIGH): the SDK's server contract is `AgentExecutor.execute(context: RequestContext, event_queue: EventQueue)` + `cancel(...)`: the agent's logic *publishes protocol events* (Task, Message, TaskStatusUpdateEvent, TaskArtifactUpdateEvent) to a queue and the framework does the rest (task store persistence, transport fan-out, push delivery). Documented semantics: single execution per request (no concurrent execute for one context); unhandled exceptions transition the task to a failed state; for `INPUT_REQUIRED` the executor *returns* (yields control) and the framework re-invokes `execute()` when input arrives; for `AUTH_REQUIRED` there are two models — in-band (return, framework re-invokes) and out-of-band (executor blocks awaiting the external auth completion); cancellation cancels the asyncio task and calls `cancel()`. Note: the docstring references `TaskState.TASK_STATE_ERROR`, a name that does not exist in the proto (which has `TASK_STATE_FAILED`) — a minor SDK/spec drift signal.
- INFERENCE (HIGH): the SDK reveals the *de facto* harness architecture of an A2A server: request → executor coroutine → event queue → task store + subscriber broadcast + webhook sender. The protocol's opacity means all of this is invisible to the caller; the SDK is where "agent loop meets task lifecycle" is actually implemented — i.e., the interruption/resumption continuation model (return-and-reinvoke) lives in the SDK, not the spec.

### F12. Relationship to MCP: official positioning and the real overlap

- FACT (spec Appendix B, a2a-and-mcp doc): official positioning — MCP standardizes agent↔tool/resource interaction ("how-to *use* a capability"); A2A standardizes peer agent↔agent collaboration ("how agents *partner* or delegate"). Canonical composition: an A2A server fulfills an A2A task by internally making MCP calls. The doc concedes: "An A2A Server could expose some of its skills as MCP-compatible resources… in a more tool-like, stateless manner."
- FACT: both protocols now live under the Linux Foundation umbrella — A2A as an LF project (June 2025), MCP donated by Anthropic to the LF's Agentic AI Foundation on 2025-12-09.
- FACT (MCP spec 2025-11-25, via official spec page + secondary coverage): MCP added an **experimental Tasks primitive** — any request can return a task handle with states `working / input_required / completed / failed / cancelled`, driven by `tasks/get` / `tasks/cancel` — i.e., MCP grew a near-isomorphic copy of A2A's lifecycle minus `submitted`, `rejected`, and `auth-required`.
- INFERENCE (HIGH): the crisp "tools are stateless primitives / agents are stateful peers" split has eroded from both directions. From MCP's side: elicitation (mid-call input requests), sampling, and now experimental tasks give tool calls statefulness, interactivity, and duration. From A2A's side: an A2A agent invoked with a structured `data` Part and returning one artifact is behaviorally a tool call. What *genuinely* remains distinct in A2A: (1) discovery of third-party endpoints across organizational trust boundaries (well-known URI + signed cards + declared auth), vs. MCP's largely client-configured, connection-oriented model; (2) the client-server topology intent — A2A servers are peers serving many mutually-invisible clients with server-generated task ids and authorization scoping, MCP servers are typically capability backends attached to one host; (3) natural-language-first, schema-optional invocation (no tool schema; skills advisory); (4) multi-task conversational contexts with cross-task references. What genuinely overlaps: long-running lifecycle management, streaming updates, input-required interrupts, and (increasingly) auth hand-offs — i.e., precisely the "opaque long-running executor" contract. A universal kernel should implement that contract *once* and treat A2A and MCP-tasks as two wire dialects of it.
- OBSERVED BEHAVIOR (MEDIUM): independent commentary (surveys such as arXiv 2505.02279, vendor analyses by Redis/Merge/Tyk/WorkOS, seen via search) converges on the same two critiques: the layers overlap more than the marketing suggests, and cross-protocol end-to-end observability/attribution ("which agent/tool produced this answer") is unsolved and hand-rolled per team.

### F13. What A2A does NOT specify (absences as findings)

All FACT-by-absence, verified against the full spec text:

1. **No budgets/economics**: no cost, token, or resource-budget fields on tasks, no quota negotiation, no billing/settlement hooks (rate limiting appears only as security guidance). 2. **No deadlines/TTL/priority**: no task deadline, expiry, priority, or QoS field; task retention/purge is implementation-defined ("expired… and purged" appears only in the TaskNotFound description). 3. **No verification/acceptance**: nothing represents acceptance criteria, evaluation, or client accept/reject of artifacts (the life-of-a-task doc explicitly assigns "acceptable result" judgment to the client, out of protocol). 4. **No provenance/lineage**: artifact version linkage explicitly out of scope; no cross-agent trace of which sub-agents/tools contributed. 5. **No policy language**: authorization models are "agent-defined"; no machine-readable policy exchange or capability attenuation. 6. **No durability/replay contract**: no event sequence numbers or resumption cursors in streams (reconnect = Subscribe and get a fresh snapshot), no exactly-once, no checkpoint concept; history persistence is discretionary. 7. **No progress representation**: no percent/steps; only states + free-form status messages (extensions can add substates). 8. **No delegation-depth/loop protection**: chains of A2A calls (incl. AUTH_REQUIRED chains) have no hop counts or cycle detection. 9. **No agent runtime semantics**: nothing about models, prompts, context windows, planning, or memory — fully opaque by design. 10. **No registry protocol**: registries are named as a discovery mechanism but their query/publish API is unspecified.

## Architecture decomposition

A2A is a *protocol*, not a system; the decomposition maps which layers of an agent system A2A touches, and who owns each.

| Layer | A2A's role | Status |
|---|---|---|
| Product/UI | ABSENT from protocol. The "User" is an actor in docs only. | n/a |
| Agent/Harness | Out of scope by the opacity principle; de facto shaped by official SDKs (AgentExecutor + EventQueue + TaskStore + push sender). | SDKs open source (Apache-2.0), portable across frameworks (ADK, LangGraph, Semantic Kernel etc. ship A2A adapters — OBSERVED BEHAVIOR, MEDIUM) |
| Planning/orchestration | ABSENT. A2A gives an orchestrator building blocks (tasks, contexts, referenceTaskIds, parallel follow-ups) but no graph/workflow construct. | client-side, proprietary per implementer |
| Context construction | Protocol carries `contextId` + optional task history + reference task ids; how an agent turns these into LLM context is internal. | server-internal, opaque |
| Model invocation | ABSENT entirely — A2A is model-independent by construction; no model names, tokens, or sampling anywhere. | n/a (provider-specific, behind the server) |
| Tool selection/execution | ABSENT — explicitly delegated to MCP or internal mechanisms behind the opaque boundary. | n/a |
| Environment | ABSENT — no execution-environment or sandbox concepts. | n/a |
| Observation (of task progress) | **Core protocol territory**: TaskStatus/Artifact events over polling, ordered broadcast streams, webhooks. | standardized, open (Apache-2.0, LF) |
| Verification | ABSENT — client judges artifacts out-of-band. | n/a |
| State update / state model | **Core protocol territory**: server-owned Task records with the 9-state lifecycle, contextId grouping, immutability of terminal tasks. | standardized |
| Discovery & identity | **Core protocol territory**: Agent Cards, well-known URI, JWS signing, security scheme declaration, extended cards. | standardized |
| Transport | JSON-RPC/gRPC/REST bindings + custom-binding rules; proto canonical, ProtoJSON normative. | standardized; gRPC/proto toolchain is Google-ecosystem-flavored but open |
| Governance | Linux Foundation project, 8-company TSC, public ADRs. | open, vendor-neutral (multi-vendor board) |

Summary: A2A standardizes exactly three layers — **discovery/identity declaration, the task-lifecycle state model, and progress observation** — and deliberately leaves every cognitive and execution layer opaque behind the server boundary. That narrowness is its main architectural lesson.

## Precise vocabulary (for this system)

- **Model**: ABSENT. No model concept anywhere in the protocol.
- **Model API / model adapter**: ABSENT.
- **Agent**: an *endpoint role* — the "A2A Server (Remote Agent)": any system exposing the A2A operations and an Agent Card. Behaviorally defined (accepts Messages, manages Tasks, emits Artifacts), never structurally defined.
- **Agent loop**: ABSENT from spec. In the official SDKs it materializes as `AgentExecutor.execute()` — a coroutine that consumes a RequestContext and publishes lifecycle events, with return-and-reinvoke continuation at interrupted states (SOURCE-CODE OBSERVATION).
- **Harness**: ABSENT from spec; de facto = SDK server framework (request handling, task store, event queue, stream fan-out, webhook delivery, capability gating).
- **Context-management system**: minimal and declarative: `contextId` as an opaque grouping key + optional per-task `history` (agent-curated, unreliable by contract) + `referenceTaskIds`. Actual context construction is internal to the opaque agent.
- **Memory system**: ABSENT (contextId "MAY" anchor internal state; nothing specified).
- **Tool runtime**: ABSENT (pointed at MCP in Appendix B).
- **Execution environment**: ABSENT.
- **Planner**: ABSENT.
- **Workflow/graph construct**: ABSENT; nearest primitives are parallel tasks under one contextId + referenceTaskIds (a client-maintained, protocol-visible-but-unenforced DAG hint).
- **State/session model**: the strongest part of the system: server-owned, immutable-when-terminal `Task` records with the 9-value `TaskState` enum (4 terminal, 2 interrupted, submitted/working, unspecified), `TaskStatus` (+message +timestamp), Artifacts as the output channel, contextId as the session key, ListTasks as the queryable index.
- **Delegation mechanism**: SendMessage to an opaque peer returning a Task handle; recursive delegation composes by chaining (including AUTH_REQUIRED escalation chains); no delegation metadata (depth, originator, purpose) is standardized.
- **Protocol usage**: itself a protocol; JSON-RPC 2.0 + SSE, gRPC, REST bindings; `application/a2a+json`; `A2A-Version` / `A2A-Extensions` service parameters; `.well-known/agent-card.json`.
- **Capability discovery/negotiation**: Agent Card (protocol capabilities = streaming/push/extendedCard/extensions; domain capabilities = advisory skills; modality negotiation = media-type lists + per-request `accepted_output_modes`; security = OpenAPI-style schemes). Negotiation is one-shot and declarative — no runtime capability bargaining beyond extension opt-in headers.
- **Policy/security layer**: HTTP-layer authn (OAuth2/OIDC/API key/mTLS declared in card), agent-defined authz with mandatory scoping, in-task authorization via AUTH_REQUIRED, JWS-signed cards. No policy language, no capability attenuation, no delegated-identity profile.
- **Durable-execution features**: partial: tasks survive disconnects and are re-attachable (Subscribe snapshot-then-events), webhooks cover disconnected clients, ListTasks recovers visibility. But: no event cursors/replay, no exactly-once, no checkpoints, discretionary history — durability of the *record*, not of the *event stream* or the *computation*.
- **Event system**: `StreamResponse` envelope (task | message | statusUpdate | artifactUpdate) over SSE/gRPC-stream/webhook; ordered, broadcast to all subscribers, lossy across reconnects by design.
- **Observability**: ABSENT from protocol; delegated by documentation to W3C Trace Context / OpenTelemetry over the HTTP layer plus logging/metrics/audit guidance (enterprise-ready doc); the Python SDK ships optional OTel instrumentation.

## Implications for a universal runtime kernel

1. **The task lifecycle is a directly liftable kernel pattern.** A2A's 9-state machine — with its two crucial classifications, *terminal* {completed, failed, canceled, rejected} and *interrupted/resumable* {input-required, auth-required} — is the minimum viable contract for ANY long-running capability, local or remote. `rejected` (executor declines) and `auth-required` (executor escalates a permission need) are the two states most runtime designs forget; A2A shows both are needed the moment executors are autonomous and policy-bearing. A kernel "capability invocation" should return exactly this shape: handle → status stream → artifacts, with blocking-vs-immediate as a caller convenience flag (but async-first as the default, inverting A2A's choice).
2. **"State is authoritative, events are advisory" is the right durability split for a kernel's cheap tier — but a kernel must go one tier further.** A2A's reconnect-by-snapshot (Subscribe returns full Task first) elegantly avoids event-log durability. A universal kernel that also wants replay/audit/checkpointing must add what A2A omitted: monotonic event sequence numbers/cursors and a persisted event log — while keeping A2A's snapshot-first recovery so simple executors stay simple.
3. **Separate protocol-capabilities from domain-capabilities, and keep domain capability claims advisory.** The Agent Card's split — machine-enforced feature flags (streaming/push/extensions, violations yield typed errors) vs. descriptive skills (routing hints, never a contract) — is a workable capability-declaration design under opacity. A kernel capability manifest should copy the enforced/advisory distinction, and copy the card-signing approach (JCS canonicalization + JWS) for integrity of capability claims; but a kernel can go further than A2A by making *some* domain capabilities schema-typed (MCP-style) where the executor opts in.
4. **The opacity principle defines the kernel boundary.** A2A proves you can standardize delegation while standardizing *nothing* about cognition: no model, planner, memory, or tool concepts appear anywhere in 156KB of spec. This validates the mission's thesis that models/agents/harnesses can be implementation details behind a capability contract. The corollary: everything the kernel wants to guarantee (budgets, policy, lineage) must live in the *envelope* (task/status/artifact/event objects), because it cannot reach inside executors.
5. **A2A's absences enumerate the kernel's value-add surface.** Budgets/deadlines/priority, acceptance/verification, artifact lineage, policy language, delegation depth/loop control, event replay, and progress semantics are all absent from A2A (F13) and all envelope-expressible. A kernel can add them as first-class task-envelope fields and still interoperate with A2A via extensions (A2A's URI-keyed metadata mechanism is expressly designed for this — including state-machine extensions).
6. **AUTH_REQUIRED chaining is a prototype of kernel-level policy escalation.** The pattern — an executor parks a task, the requirement propagates up the delegation chain to whoever can approve, work resumes on out-of-band fulfillment — generalizes to budget-exceeded, approval-required, and resource-grant escalations. A kernel should generalize the pair {interrupted-state, typed-requirement-payload} rather than hardcoding auth as the only escalation kind (A2A itself concedes the payload semantics are undefined, §7.6.4).
7. **Task immutability + refinement-as-new-task is the right lineage substrate — but the kernel must close the lineage gap A2A punted.** Immutable terminal tasks give a clean unit-of-work for audit and caching; A2A then explicitly declines to track artifact version chains (client's job). A kernel that owns both sides of delegation can and should record artifact→task→parent-task lineage in the envelope, which A2A shows is impossible only when you standardize the wire but not the runtime.
8. **One canonical schema, many wire dialects.** A2A's tri-binding equivalence tax (method/error/naming mapping tables, the kind-discriminator breaking change) and ADR-001 argue for a kernel with a single canonical typed model and transport gateways — and, given MCP's experimental tasks now mirror A2A's lifecycle (working/input_required/completed/failed/cancelled), the kernel's internal task contract can plausibly project onto *both* A2A and MCP-tasks as thin dialects, making "remote A2A agent" and "long-running MCP tool" the same kernel capability type.
9. **Discovery is standardizable only at the edges.** A2A got well-known-URI + signed self-description right, and left registries unspecified — evidence that a kernel should own the *format* of capability declaration but treat registry/marketplace as a pluggable service, not kernel.
10. **Version negotiation via a per-request header with a legacy default** (`A2A-Version`, empty ⇒ 0.3) is a pragmatic pattern for a kernel's own capability-contract evolution — cheap, stateless, and compatible with multi-version endpoints.

## Open questions

1. The exact legal transition graph of TaskState is spec-implied, not spec-enumerated (e.g., can a task go WORKING → SUBMITTED? INPUT_REQUIRED → AUTH_REQUIRED?). Do the official TCK/SDKs enforce a stricter transition table than the spec text, and should a kernel adopt a closed transition algebra instead?
2. How far has the announced extension ecosystem (ext-* repos, a2a-protocol.org/extensions URIs) actually matured by late 2026 — is there a de facto standard extension for tracing/lineage or payments that a kernel should interoperate with (e.g., AP2-style payment extensions)?
3. Will A2A and MCP converge formally now that both sit under the Linux Foundation (MCP in AAIF since 2025-12-09) — specifically, will MCP's experimental Tasks adopt A2A's rejected/auth-required states, or A2A adopt MCP's schema-typed invocation? Any joint interoperability working group output?
4. The multi-tenancy `tenant` field (new in 1.0) is opaque routing only — how are large platforms (Azure AI Foundry, Vertex, ServiceNow) actually using it, and does it leak a de facto namespace/identity model a kernel should align with?
5. Is anyone shipping the "Subscribe with resumption cursor" durability upgrade as an A2A extension, and what did they discover about the cost of retrofitting replay onto snapshot-first semantics?
6. The a2a-python docstring references a non-proto `TASK_STATE_ERROR` — SDK drift or an unreleased spec direction (splitting infrastructure errors from task-level failure)?
