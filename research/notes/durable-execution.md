# Durable Execution: Replay, Journals, Checkpoints, and Actors as Source Material for an AI Kernel

## Scope

This note mines mature durable-execution and distributed-systems runtimes for mechanisms an AI execution kernel should adopt, adapt, or reject. Systems covered: **Temporal** (event-history replay; docs source inspected at commit `7f42b11f`, 2026-08-14 — current as of Temporal Server v1.30.x), **Restate** (journal-based durable execution on the Bifrost virtual-consensus log; docs source at commit `de0378c9`, 2025-11-06, supplemented with release info through Restate 1.6, Feb 2026), **DBOS** (Postgres-backed durable-workflow *library*; docs source at commit of 2026-08-14, DBOS Transact across Python/TS/Go/Java, Java 1.0 shipped July 2026), **event sourcing fundamentals** (Fowler; Celery task-queue semantics from source docs), and **actor runtimes** (Orleans virtual actors from the dotnet/docs source, Jan–Mar 2026 revisions; Erlang/OTP supervision principles from the OTP repo).

Crucially, all three durable-execution vendors shipped **first-party AI-agent integrations in 2025–2026** (Temporal × OpenAI Agents SDK/LangGraph/Pydantic AI + Workflow Streams + External Storage; Restate's framework-independent `ai-examples` and the Pydantic AI Restate integration; DBOS's AI docs with durable streams and HITL). These integrations are the best available empirical record of *what breaks when an LLM loop is placed inside a durable runtime*, and this note treats them as primary evidence for the key question: **which durable-execution mechanisms fit an intrinsically nondeterministic AI core, and which fight it.**

## Findings

### 1. Temporal: the command-matching replay model

**FACT.** Temporal is a three-part system: **Client** (gRPC control requests only), **Temporal Service** (Frontend, History, Matching backend services; records Event History, schedules Tasks on Task Queues, persists to a database), and **Worker** (polls task queues; the *only* place user code runs). The server never executes workflow or activity code; the client never executes anything. The full loop: workflow code runs in a Worker until blocked, emits **Commands** (`ScheduleActivityTask`, `StartTimer`, …) instead of doing effects; the History service converts Commands into **Events**, appends them, and creates new Tasks; on the next Workflow Task any worker can **replay** the Event History to reconstruct state and continue.

**FACT — the determinism contract.** "Any time your Workflow code is executed it makes the same Workflow API calls in the same sequence, given the same input." On replay, each emitted Command is compared position-by-position against recorded Events; a mismatch (wrong type or Activity name at that history position) raises a *non-determinism error*. Ten API families produce Commands (timers, activities, child workflows, external signals, Nexus operations, terminating the run, patch markers, search-attribute/memo upserts, side effects). Nondeterministic operations must go through SDK APIs whose results are recorded in history (time, random) or through Activities. The docs explicitly name **LLM/AI invocations** as things that must live in Activities.

**FACT — limits (the numbers that matter for AI).** Event History is terminated at **51,200 Events or 50 MB** (warning at 10,240/10 MB), or **>2,000 Updates**, or **>10,000 Signals**. Max **2,000 pending** Activities/child workflows/signals/cancel-requests each. Per-payload cap **2 MB** (fixed on Temporal Cloud). No wall-clock limit on workflow duration.

**FACT — sticky execution.** Workers cache workflow state in memory; the service routes subsequent Workflow Tasks to a worker-exclusive **Sticky Queue**. If the sticky task isn't started within **5 s** (default), stickiness is disabled and the task falls back to the shared queue — any worker then rebuilds state by full history replay. Workflow task failure evicts the cache. INFERENCE (HIGH): replay is Temporal's *recovery* path, not its steady-state path; the steady state is an in-memory actor with an event-sourced backup. Cost of recovery is O(history).

**FACT — Continue-As-New.** Closes the current run and starts a new execution with the same Workflow Id, a fresh history, and state passed as arguments. The server signals `Continue-As-New Suggested`. Perpetual workflows built this way are called **Entity Workflows** — "durable objects, not just processes" (Temporal's own convergence toward virtual actors).

**FACT — messaging.** **Queries**: read-only, non-blocking, add no history events, work on completed workflows. **Signals**: async fire-and-forget writes. **Updates**: synchronous tracked writes with validators, history-recorded. **Reset**: terminates and forks a new execution with history copied up to a chosen `WorkflowTask*` event, optionally re-injecting later Signals.

**FACT — versioning.** Two strategies: (a) **Patching** — `patched(id)` writes a marker event; the documented semantics table (returns `true`/`false` depending on replay position vs marker position; a marker *later* in history than the patch call is a nondeterminism error; absence of the marker poisons all future calls of that ID to `false` even after replay ends) is intricate enough that the docs spend ~100 lines on edge cases. (b) **Worker Versioning** — pin executions to worker deployment versions (the pre-2025 experimental variant is removed from the server in March 2026). DX cost is explicit: workflow code is a versioned durable contract, and the docs recommend periodic Continue-As-New just to escape old code versions.

**FACT — effect semantics.** Activities are retried per policy; while retrying, only `ActivityTaskScheduled` exists in history (`Started` is written with the terminal event) — i.e., the history is an *outcome* log, not an *attempt* log. **Local Activities** and **Nexus operations** are at-least-once and "should always be idempotent." **Side Effects** (Go/Java/PHP) execute once and record the result, but "do not ever have a Side Effect that could fail" — a sharp edge the other SDKs dropped in favor of Local Activities.

**FACT — audit.** Principal Attribution (prerelease) stamps each history event with the authenticated caller (user/service-account/mTLS identity), set server-side so it can't be forged — event history doubling as a compliance audit log.

### 2. Temporal × AI: the empirical record of friction

Temporal's docs now carry a whole AI-integrations surface (OpenAI Agents SDK for Python and TypeScript, LangGraph, Google ADK, DeepAgents, Strands, Vercel AI SDK, Spring AI, LangSmith/Braintrust observability). The mechanics are consistent and revealing:

**FACT — the split.** "Agent orchestration — the agent loop, tool selection, and handoffs — runs inside the Workflow, while model calls run as Activities." Model calls "retry durably and are not repeated during Workflow replay." Inline tools running in the workflow "must not perform non-deterministic activities like I/O or reading wall-clock time." The Python README states the design rule at its purest: deterministic pieces = workflows, nondeterministic pieces = activities, and the LLM is *definitionally* on the activity side.

**FACT — what had to be rebuilt.** The upstream OpenAI `MemorySession` "is not replay safe because it depends on host process state"; Temporal ships `WorkflowSafeMemorySession`, whose history lives on the workflow heap, is rebuilt by replay — and **does not survive `continueAsNew`**; users must capture items and re-seed the new run manually. HITL approval flows serialize the SDK's `RunState` to a string, wait on a Signal via `condition()`, then Continue-As-New with the serialized state; "the agent passed to `RunState.fromString` must define the same tool names, handoff graph, and MCP servers as the run that produced the serialized state" — the harness configuration itself becomes part of the durable contract. Nested-agent interruptions are unsupported (a typed `ApplicationFailure`). Stateful MCP servers — inherently process-bound connections — require the plugin to start "a dedicated in-process Worker pinned to a per-run Task Queue": location transparency breaks down exactly where the environment holds session state.

**FACT — Workflow Streams (2026 contrib, experimental), the token-streaming answer.** A durable, offset-addressed event channel hosted *inside* a workflow, implemented entirely out of existing primitives: a publish **Signal** handler, a long-poll subscribe **Update** handler, and a head-offset **Query** (`__temporal_workflow_stream_publish/poll/offset`). Client-side batching (default 2 s; 200 ms recommended for LLM tokens — "a 30-second response generates roughly 150 publish Signals"; per-token force-flush on a 500-token completion = 500 Signals, "meaningful but tractable"; per-character "isn't"). Exactly-once landing via `(publisher_id, sequence)` dedup with a 15-minute publisher TTL that must exceed the 10-minute publish-retry window. Poll responses capped at ~1 MB. Every Signal and Update counts against the history limits, so long streams *require* Continue-As-New, and the carried state includes the entire in-memory log. Most instructive: **Activity retries surface to subscribers** — a failed attempt's partial tokens appear in the stream alongside the successful attempt's output, because "if the library waited for a successful Activity return before surfacing anything, there would be nothing to stream." The workflow's durable state sees only the successful return; consumers must handle retry sentinels. This is a crisp articulation of the two-plane problem: *the durable truth plane and the live observation plane cannot be the same channel.*

**FACT — External Storage (pre-GA).** Claim-check offload of any payload above a threshold to S3-style storage, leaving a reference in history; "AI agent conversations" are a named motivating scenario ("long conversation histories grow with each turn"). Threshold 0 externalizes everything (also pitched for data governance).

**FACT — Pydantic AI's `TemporalDurability` (co-maintained) leak inventory.** A run is durable *only* inside a workflow; the same agent object degrades gracefully outside. Tool functions inside activities receive a *reduced* `RunContext` (an enumerated field allowlist; accessing `messages` or `prompt` raises rather than returning defaults). The activity's context is a copy: **usage accounting mutations made inside activities are lost** — a delegate agent's tokens "are never charged against the parent's usage limits" (open issue pydantic-ai#6886 for a cross-backend return channel). Persisted payload schemas are "durable contracts across deployments." Streaming is buffered by default (model events replayed to the workflow after the activity completes); live streaming requires either an activity-side handler (must be idempotent — it reruns on retry) or a workflow-side handler (must be deterministic — it reruns on replay). Binary content pays base64 tax against the 2 MB cap (~1.5 MB effective); image output types are rejected outright.

**FACT — LangGraph plugin.** Each LangGraph node/task must declare whether it runs as a Temporal Activity or inline in the Workflow — the checkpoint-based graph runtime nests inside the replay-based runtime by classifying every node against the determinism boundary.

**INFERENCE (HIGH).** The integrations work, but every point of friction traces to one root cause: Temporal's kernel assumes *code is the durable artifact and data flows through it*, whereas an agent's durable artifact is *the conversation/event data*, and the code (prompts, model choice, tool wiring) is the volatile part. Where Temporal stores data in code-shaped history (payloads in events, session on the workflow heap, RunState tied to tool-graph identity), the AI integrations bend or break.

### 3. Restate: journal injection and virtual objects

**FACT — mechanism.** The SDK "tracks the progress of the execution" as a **journal**; the server durably records it and drives retries. On recovery the server re-invokes the handler and sends the journal; the handler re-executes, and "whenever it encounters an action on the Restate context, it will skip execution and will inject the response it finds in the journal." Determinism is still required of code *between* journaled actions ("non-deterministic results need to be stored in the execution log"; promise combinators journal resolution order; SDK provides UUID/random seeded by invocation ID) — the difference from Temporal is packaging, not physics: no separate workflow sandbox, no worker/task-queue topology, and any HTTP handler (including AWS Lambda) can be durable.

**FACT — service taxonomy.** (1) **Services**: stateless durable handlers, unlimited scale-out. (2) **Virtual Objects**: keyed handlers sharing isolated K/V state that Restate stores and *delivers with the request*; at most one write-handler runs at a time per key ("queue per key"); `shared` handlers read concurrently. The docs' own example use case list includes "Stateful agents, actors, and digital twins: e.g. AI chat sessions." (3) **Workflows**: a Virtual Object variant whose `run` handler executes exactly once per workflow ID, with other handlers signaling/querying it concurrently via K/V reads and **durable promises**.

**FACT — durable promises / awakeables.** `ctx.awakeable()` returns an ID and a promise; any external process resolves it over HTTP (`/restate/awakeables/<id>/resolve`). On FaaS, Restate *suspends* the handler while awaiting — "you don't pay while waiting." This is Restate's HITL primitive, and the ai-examples repo uses exactly this for human approval of agent tool calls.

**FACT — ingress idempotency.** Any invocation can carry an `Idempotency-Key` header (per the IETF draft); Restate retains the response for 24 h and dedups — "make any service call idempotent... without any extra code."

**FACT — architecture.** Three layers: control plane (metadata, leader assignment); **Bifrost**, a distributed append-only log based on virtual consensus (Delos) and Flexible Paxos, composed of sealed segments backed by loglets; and **partition processors** — state machines that consume the log and materialize "the state of the world" (ongoing invocations, per-invocation journals, durable promises, K/V state) into RocksDB, with snapshots to object store enabling log trimming and fast catch-up. Single Rust binary; roles (metadata/ingress/log-server/worker/admin) specialize nodes at scale. INFERENCE (HIGH): Restate is an event-sourced database whose "tables" are invocation journals and keyed state — the journal is the WAL and processor state is the materialized view, which is why journal introspection (SQL API) and trimming come naturally.

**FACT — 1.6 (Feb 2026) operational verbs.** Pause and resume invocations manually; **restart an invocation from any point in its journal**; move invocations between deployments. OBSERVED BEHAVIOR (MEDIUM): these are precisely the affordances agent debugging demands (re-run from step N with fixed code), arriving as generic runtime verbs rather than AI features.

**FACT — AI positioning.** The `restatedev/ai-examples` repo demonstrates a *wrapping* strategy: keep the vendor agent loop (Vercel AI SDK, OpenAI Agents SDK, Google ADK, Pydantic AI, LangChain) or hand-roll one, and journal the nondeterministic calls with `ctx.run("LLM call", ...)` / `ctx.run_typed(...)` with `RunOptions(max_attempts=…)`. Chat sessions are Virtual Objects: `ctx.get("memory")` → append → `ctx.set("memory", …)`, with a `shared` handler for reads — session state lives in the runtime's keyed store, not on a replayed heap, so it survives without Continue-As-New gymnastics. Patterns include multi-agent via durable RPC, parallel tools, racing agents with cancellation, and "interrupt & regenerate" (cancel in-flight, restart with new context). The Pydantic AI docs note the Restate integration "builds only on Pydantic AI's public interface, so it can also serve as a reference for integrating with other durable systems."

### 4. DBOS: checkpoint-skip in your own Postgres

**FACT — mechanism.** A library, not a server: annotate workflows and steps; DBOS checkpoints workflow inputs, step outputs, and workflow outcomes to a Postgres **system database**. Recovery: scan for `PENDING` workflows, re-invoke each with checkpointed inputs; before each step, check for a checkpoint — if present, return it without executing; the first missing checkpoint is where execution resumes. Requirements stated identically to the others: workflows **deterministic** ("same steps with the same inputs in the same order"; LLM/API/random/time must be steps), steps **idempotent** (a step interrupted mid-flight re-runs). Overhead: one DB write per step, two per workflow; benchmark >40 K workflows-or-steps/s on one Postgres; guidance to keep step outputs small (S3 + pointer).

**FACT — queues in Postgres.** Durable queues with worker concurrency, global/per-tenant flow control, rate limits, priorities (1…2,147,483,647), `deduplication_id` (only one ENQUEUED/PENDING workflow per dedup ID per queue), partitioned queues, and delayed starts — plus PL/pgSQL functions (`dbos.enqueue_workflow`, `dbos.send_message`) callable from database triggers. INFERENCE (MEDIUM): the entire orchestration control surface reduces to SQL rows, which is why introspection/management ("search workflows by name, time, queue, version; pause/cancel/resume") comes free.

**FACT — fork, and the fate of time travel.** `DBOS.forkWorkflow(workflowID, startStep)` starts a new execution reusing checkpoints up to `startStep` — used for mass recovery after downstream outages and, in the AI docs, as the *reproduction* tool: "rerun the misbehaving step under the exact conditions that originally caused the misbehavior," then re-test with a fixed prompt. OBSERVED BEHAVIOR (MEDIUM): the earlier "time-travel debugger" (DBOS Cloud provenance-DB feature) no longer appears in current docs; deterministic *fork/replay from checkpoints* is its successor.

**FACT — versioning.** Applications are stamped with `app_version`; workflows recover only on compatible versions (or use explicit patch statements). Cross-language interop exists via a documented Portable JSON Format (a TS app can enqueue onto a Python app's queues).

**FACT — Conductor.** The control plane is *out-of-band*: outbound websockets only, no DB access, "never involved in workflow execution"; it coordinates recovery (reassign a dead executor's PENDING workflows) and dashboards. Loss of Conductor degrades recovery coordination, not execution.

**FACT — AI surface.** (a) **Durable streams**: append-only channels written from workflows or steps (`DBOS.write_stream(key, token)` per LLM token, inside the step doing the provider streaming call), persisted per write, readable from anywhere by (workflow ID, key), surviving restarts mid-response. (b) **HITL**: `DBOS.recv(timeout_seconds=…)` durably waits days for a message; `DBOS.send(workflow_id, response)` from an HTTP endpoint; both persisted, deadline included. (c) **Status**: `set_event`/`get_event` key-value events for frontend polling; an "agent inbox" is just `list_workflows(status="PENDING", name=…)`. INFERENCE (HIGH): DBOS demonstrates the *minimum viable durable kernel* for agents — checkpoint store + queues + messages + streams over one database — at the cost of pushing distributed-systems concerns (recovery coordination, fencing) to an external control plane.

### 5. Event sourcing and task-queue fundamentals

**FACT (Fowler; via search snippets, site blocked).** Event Sourcing: "blow away the application state and confidently rebuild it from the log"; **snapshots** bound replay cost; external systems must be wrapped in **gateways** aware of replay mode (disabled during rebuild) — the pattern-level ancestor of Temporal's activities and Restate's `ctx.run`; schema evolution ("old event schema still has to work with new versions") is the enduring unsolved cost, addressed in practice by upcasters and versioned event types. Retroactive Events exist as a companion pattern for correcting the past — something none of the three runtimes expose (Temporal's Reset forks; it does not rewrite).

**FACT (Celery).** Default is *early ack* (message acknowledged just before execution — "a task invocation that already started is never executed again": at-most-once). `acks_late=True` gives at-least-once and the docs immediately require idempotency. Deliberate exception: even with `acks_late`, a task killed by SIGSEGV/OOM/`sys.exit` is acked and *not* redelivered — poison-pill protection built into the semantics. INFERENCE (HIGH): every queue system converges on the same triangle — lease/visibility-timeout (the SQS pattern), at-least-once redelivery, idempotent consumers — and the "exactly-once" experience is always a synthesis: at-least-once delivery + dedup keys (Restate's ingress idempotency, DBOS's `deduplication_id`, Workflow Streams' `(publisher_id, seq)`), never a transport guarantee.

### 6. Actor runtimes: the supervision and identity layer

**FACT (Orleans).** The **virtual actor**: "actors are purely logical entities that *always* exist... cannot be explicitly created nor destroyed... always addressable." Grains = user-defined identity + behavior + state; the runtime activates them on demand, deactivates idle ones, and places them freely (placement is pluggable; default became ResourceOptimized in 9.2). **Single-threaded execution model** per activation — each request processed to completion before the next — with opt-in reentrancy for interleaving. Persistence is explicit (`WriteStateAsync`, multiple named state objects); **timers** (volatile) vs **reminders** (durable, fire even if deactivated). Grain *interface versioning* supports heterogeneous clusters mid-upgrade. Streams are managed, with consumer-stored checkpoints/cursors. Distributed ACID transactions across grains, decentralized, serializable isolation. Orleans 9 cut failure detection from 10 minutes to 90 seconds; Orleans 10 (targeting .NET 10) is current.

**FACT (OTP).** Supervision trees: `one_for_one`, `one_for_all`, `rest_for_one`, `simple_one_for_one`; child specs declare start/restart/shutdown/type; **restart intensity** — more than `MaxR` restarts within `MaxT` seconds and the supervisor kills all children and *itself*, escalating failure up the tree. Automatic shutdown on "significant" child exit exists but is warned against for top-level supervisors (restart-loop exhaustion).

**INFERENCE (HIGH).** Restate's Virtual Objects and Temporal's Entity Workflows are both reinventions of the Orleans grain (keyed identity, single-writer serialization, activation on demand, durable state), each grafted onto a durable-execution substrate. The convergence across three independent lineages is strong evidence that *keyed single-writer stateful identity* belongs in an AI kernel's primitive set (sessions, agents-as-entities), while OTP shows the missing complement none of the durable runtimes has: **structured failure escalation with restart budgets** — Temporal/DBOS/Restate all retry *flat* (per-activity/step policies) with no supervision hierarchy above the workflow.

### 7. The comparative anatomy of durability

Three mechanisms, one invariant:

| | Temporal | Restate | DBOS |
|---|---|---|---|
| Durable record | Event History (commands→events) | Journal per invocation, on Bifrost log | Checkpoints in Postgres tables |
| Recovery | Re-execute code; match emitted commands against history positionally | Re-execute code; inject journaled results at context actions | Re-execute code; return checkpointed step outputs by lookup |
| Topology | Server + worker fleet + task queues | Server (log+processors) proxying HTTP to services | Library + shared Postgres (+ out-of-band Conductor) |
| Effect unit | Activity (separate task, own retry policy, own queue) | `ctx.run` closure (in-process, journaled) | Step (in-process, checkpointed) |
| History control | Continue-As-New, External Storage claim-check, Reset | Log trimming + processor snapshots (runtime-internal); journal restart points (1.6) | Retention policies; fork |
| Keyed state | Entity Workflow pattern (userland) | Virtual Objects (kernel primitive) | ABSENT (use DB tables) |
| HITL wait | Signal/Update + `condition()` | Awakeable (durable promise, HTTP-resolvable) | `recv`/`send` durable messages |
| Streaming | Workflow Streams contrib (Signals/Updates/Query, history-bounded) | ABSENT as kernel primitive (SDK/UI journal introspection instead) | Durable streams (per-write Postgres persistence) |

**FACT.** All three impose the *same* determinism requirement on orchestration code and the *same* idempotency requirement on effects. None exempts AI. The differences are in (a) how much machinery the boundary costs (Temporal: sandbox + task round-trips; Restate: an HTTP context object; DBOS: a decorator), (b) where the durable record lives (vendor service vs your log cluster vs your Postgres), and (c) whether recovery matching is *positional against a typed command stream* (Temporal — strictest, richest failure detection) or *lookup-shaped* (DBOS — loosest).

## Architecture decomposition

Mapping the canonical AI-system stack onto durable-execution runtimes (these systems occupy the lower half and are agnostic to the upper half):

- **Product/UI** — Temporal Web UI / Restate UI+SQL introspection / DBOS Console+Conductor dashboards. Open source (Temporal UI, Restate) or proprietary control plane (Conductor, Temporal Cloud). *Observation surfaces over the durable record; no AI-specific product layer.*
- **Agent/Harness** — **Userland in all three.** The harness is workflow/handler code the developer writes or a vendor integration package (Temporal's `OpenAIAgentsPlugin`, Restate's ai-examples wrappers, Pydantic AI's durability capabilities). Provider-specific, portable in source form.
- **Planning/orchestration** — Split: *control flow* is userland code (deterministic constraint applies); *scheduling* (task queues, retries, timers, leases, flow control) is the kernel. The kernel schedules; it never plans. Open source, provider-specific semantics, no cross-vendor standard.
- **Context construction** — Userland (message arrays on the workflow heap / VO state / step outputs), but *kernel-constrained*: payload caps (2 MB), history limits, serialization contracts. The kernel sees context only as opaque payloads — with claim-check offload (Temporal External Storage) as the escape hatch.
- **Model invocation** — Always at the nondeterministic edge: Activity / `ctx.run` / step. The kernel contributes retry, timeout, checkpoint-once semantics; knows nothing of models. Provider-specific adapters live in integration packages.
- **Tool selection/execution** — Selection: model + loop (userland). Execution: kernel-supervised effect unit, with idempotency delegated to the tool author. Temporal uniquely lets tools be cross-service via Nexus (at-least-once, its own protocol — provider-specific, aspiring standard).
- **Environment** — Worker fleets (Temporal), user's HTTP/Lambda services (Restate), the app's own processes (DBOS). The kernel is environment-agnostic by design; the stateful-MCP dedicated-worker hack shows where the abstraction leaks.
- **Observation** — The kernel's crown jewel: history/journal/system-tables are a *total* record of effects and their outcomes, queryable and auditable (Principal Attribution; Restate SQL; DBOS SQL). Standardized only via OTel export, not at the record level.
- **Verification** — **ABSENT in all three.** Success = no exception. Retry policies classify errors; nothing evaluates *outputs*. (DBOS's fork-based reproduction is a debugging aid, not a verifier.)
- **State update** — Kernel primitive: append event / journal entry / checkpoint row, transactional with scheduling state. Projections (VO K/V, Orleans grain state) are kernel-managed materializations.

Portability verdict: **no layer is standardized across vendors.** Durable execution in 2026 has no MCP-equivalent — each system's record format, effect contract, and management API is proprietary (open-source, but nonportable). Pydantic AI's four-backend `durable_exec` abstraction is the closest thing to a portability layer, and it lives in the *harness*, not the runtime.

## Precise vocabulary

For the durable-execution systems (with AI-integration mappings):

- **Model** — ABSENT as a kernel concept. Appears only inside integration packages as "the thing an activity/step calls."
- **Model API / adapter** — ABSENT in kernels. In integrations: Temporal's model Activity + `modelProvider` resolution (name string crosses the boundary, credentials stay in the worker); Restate: whatever SDK the user calls inside `ctx.run`.
- **Agent** — ABSENT in kernels. In integrations: a userland object whose loop runs in the deterministic zone. Restate's docs equate long-lived agents with Virtual Objects.
- **Agent loop** — Userland workflow/handler code, subject to the determinism contract; the kernel's only loop is task-dispatch/replay.
- **Harness** — The integration plugin layer (OpenAIAgentsPlugin, TemporalDurability, Restate wrappers). Notably *removable*: the same agent code runs undurably outside.
- **Context-management system** — ABSENT. Payload plumbing + claim-check only. Session memory is userland (workflow heap / VO K/V).
- **Memory system** — Temporal: ABSENT (Entity Workflow pattern in userland). Restate: Virtual Object K/V (kernel primitive). DBOS: ABSENT (your Postgres). Orleans: named grain states (kernel primitive).
- **Tool runtime** — The effect unit: Activity/`ctx.run`/step, with retry/timeout/heartbeat (Temporal activities), but no argument-schema or discovery layer — tools are just functions.
- **Execution environment** — Worker processes/services owned by the user; kernel provides routing (task queues / HTTP proxying), not sandboxing. No isolation primitives.
- **Planner** — ABSENT everywhere.
- **Workflow/graph construct** — Code, deliberately not a DAG DSL in all three ("regular code and control flow, no custom DSLs" — Restate; contrast Airflow/Prefect/Dagster, whose DAG-of-data-tasks model has no replay contract and no mid-node recovery, which is why the AI world routed around them).
- **State/session model** — Temporal: per-execution history + workflow heap; identity = Workflow Id across Continue-As-New chains. Restate: per-invocation journal + per-key VO state. DBOS: workflow rows + step rows keyed by workflow ID. Orleans: grain identity + persisted state.
- **Delegation mechanism** — Child workflows (Temporal, with ParentClosePolicy), durable RPC between services (Restate), child/enqueued workflows (DBOS). All are *structural* (parent-child trees), none are *semantic* (no capability handoff).
- **Protocol usage** — gRPC (Temporal, proprietary proto), HTTP/2 + custom SDK wire protocol (Restate), Postgres wire (DBOS). Nexus as Temporal's cross-boundary RPC. No shared standard.
- **Capability discovery/negotiation** — ABSENT. Restate registers service schemas at deployment registration; Temporal task queues are string-matched; nothing negotiates.
- **Policy/security layer** — Temporal: namespaces, mTLS, Authorizer/ClaimMapper, Principal Attribution, payload codecs (E2E encryption). Restate/DBOS: thinner (deployment-level). No effect-level policy ("may this workflow call this tool") anywhere.
- **Durable-execution features** — The whole system (see §7).
- **Event system** — Temporal: history events + Signals/Updates + Workflow Streams. Restate: Bifrost log + Kafka ingress + awakeables. DBOS: messages, events, streams tables. All kernel-level.
- **Observability** — History replay/introspection, SQL surfaces, OTel/Prometheus exports; Temporal's replay-safe OTel tracer for workflow code is a notable detail (even tracing must respect determinism).

## Implications for a universal runtime kernel

1. **Adopt the invariant, invert the emphasis.** All three systems agree: *durable record of effects at the edge; re-derivable control state in the middle; idempotent effects.* An AI kernel keeps this. But in agent workloads the "deterministic core" shrinks to a trivial fold (append message, check tool_calls, loop) while ~everything interesting is an effect. So the kernel should be **journal-first (record-and-inject), not replay-first (re-emit-and-match)**: treat model outputs, tool results, and human inputs as *events appended to a log*, and the loop as a *projection over that log*. Restate's injection model and DBOS's checkpoint-lookup fit this; Temporal's positional command-matching buys failure detection that agent code — whose prompts and tool wiring change weekly — pays for in versioning ceremony (`patched()` edge-case tables, RunState tied to tool-graph identity, "persisted payloads are durable contracts").

2. **The event log must be two-tier by design.** The single most repeated AI-specific pathology is history growth: 51,200-event caps, 2 MB payloads, base64 tax, sessions that die at Continue-As-New, streams whose carried state is the whole log. The kernel should natively split **references (in the log) from artifacts (in a content-addressed store)** — Temporal's External Storage claim-check, DBOS's "return S3 pointers" advice, and Workflow Streams' offload guidance are all retrofits of the same missing primitive. Continue-as-new is a workaround for absent log compaction; a kernel should have **snapshot + trim** (Restate's processor snapshots, Fowler's snapshots) as first-class, with sessions living in keyed state, not on a replayed heap.

3. **Separate the truth plane from the observation plane.** Workflow Streams' honest admission — retried attempts' partial output *must* reach observers even though durable state sees only successful returns — generalizes: an AI kernel needs a durable-truth log (outcomes, exactly-once-landing) *and* a live event channel (attempts, tokens, progress) with explicitly weaker guarantees (at-least-once, truncatable, retry-visible). Building the latter out of the former's primitives (Signals/Updates) works but inherits the former's cost model; DBOS's separate streams table is the cleaner shape.

4. **Keyed single-writer entities are a kernel primitive, not a pattern.** Orleans grains, Restate Virtual Objects, and Temporal Entity Workflows converge on it independently; agent sessions are its canonical AI instance. The kernel should provide: stable identity, activation-on-demand, single-writer turns with shared-read handlers, and state delivered-with-invocation.

5. **Exactly-once is an illusion to be engineered, and the kernel should own the parts.** Ingress idempotency keys with retention windows (Restate, 24 h), enqueue dedup IDs (DBOS), `(publisher, seq)` batch dedup with TTL-bounded windows (Workflow Streams), early-vs-late ack with poison-pill escape (Celery). Kernel contract: at-least-once delivery + leases/visibility timeouts + first-class idempotency keys on every capability invocation + dedup state that survives compaction — and *documented* dedup windows, since Workflow Streams shows the TTL-vs-retry-window coupling is a real correctness knob.

6. **Adopt OTP supervision above the loop; per-effect retry below it.** Durable runtimes retry effects flat; none supervises *agents*. An AI kernel should add supervision trees with restart budgets (intensity/period) and escalation — an agent that keeps failing exhausts its budget and escalates to its parent (or a human) rather than retrying forever; OTP's "supervisor kills itself upward" is the model, and budgets naturally extend to *token/cost budgets*, which no durable runtime tracks (the Pydantic AI usage-accounting hole is the cautionary tale: effect-boundary copies silently dropped cost data).

7. **HITL = durable promises addressable from outside.** Restate's awakeables (create ID → hand to the world → suspend → resolve over HTTP) are the cleanest primitive; DBOS `recv`/`send` equivalent; Temporal's Signal+Continue-As-New dance shows what it costs when promises aren't first-class. Suspension must be free (FaaS-compatible), because agents wait on humans for days.

8. **Versioning must assume the "code" is data.** Prompts, model IDs, tool schemas change faster than any patching discipline tolerates. Kernel implication: pin *policy/config versions in the log itself* (each event records the config hash under which it was produced), make fork-from-step (DBOS fork, Restate 1.6 journal restarts, Temporal Reset) the primary upgrade/repair verb, and never require old code paths to survive in new binaries (Temporal patching) for the AI layer. Deterministic replay-for-debugging (fork with recorded effects) is the durable-execution feature agents benefit from most — it replaced DBOS's time-travel debugger and drives Temporal's replay testing.

9. **Verification is the layer nobody has.** All three kernels equate success with "no exception." An AI kernel's checkpoint/commit step is the natural hook for verifiers (schema checks, judges, policy gates) *before* an effect's outcome is committed to the truth log — this is a genuine gap, not a feature to copy.

10. **Don't standardize prematurely, but leave the record portable.** There is no cross-vendor durable-execution protocol; lock-in lives in the record format. A kernel that specifies its event-log schema (types, envelopes, upcasting rules — the event-sourcing discipline Fowler flags as the hard part) as a public contract would be differentiated against all three incumbents.

## Open questions

1. Restate requires the code between journaled actions to be deterministic on replay, same as Temporal — how much of its "no handcuffs" DX advantage survives adversarial cases (framework internals doing hidden I/O between `ctx.run` calls), and how does its journal-mismatch failure mode compare to Temporal's nondeterminism errors in practice? (Marketing blogs were egress-blocked; needs hands-on testing.)
2. What are the real latency/cost numbers for a chat-grade agent turn on each substrate (Temporal task round-trips vs Restate HTTP proxying vs DBOS in-process + 1 write/step)? DBOS claims >10x latency advantage; unverified independently.
3. Does Temporal's Workflow Streams graduate from experimental with history costs reduced (e.g., server-side stream storage outside history), or does the Signals-as-transport design cap it permanently?
4. How do these runtimes handle *sandboxed/stateful environments* (browser sessions, VMs, long-lived MCP connections) beyond Temporal's pinned-worker hack — is worker-affinity-as-a-primitive (Temporal worker sessions / task routing) sufficient for agent environments?
5. Event-schema evolution for AI logs: are there production accounts of upcasting LLM conversation events across model/provider migrations (the event-sourcing versioning problem applied to prompts/messages)?
6. Orleans-style distributed ACID transactions across keyed entities: does any agent workload actually need cross-session transactional state, or are sagas + idempotency sufficient at the AI layer?
