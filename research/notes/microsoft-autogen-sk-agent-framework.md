# Microsoft's Agent Stack: AutoGen → Semantic Kernel → Microsoft Agent Framework

## Scope

This note covers Microsoft's three-generation agent stack and what its convergence teaches about which computational models survive production contact:

1. **AutoGen** (2023–2026, now maintenance mode): the conversation-centric multi-agent framework, rewritten in v0.4 (Jan 2025) around an event-driven actor core (`autogen-core`).
2. **Semantic Kernel (SK)** (2023–, now "successor-ed"): the kernel/plugin/planner framework, whose LLM planners were deprecated in favor of function calling.
3. **Microsoft Agent Framework (MAF)** (public preview 2025-10-01, 1.0 GA 2026-04-03, Python core at v1.14.0 as of 2026-08-14): the convergence — agents + typed graph workflows with Pregel-style supersteps, checkpointing, middleware, context providers, MCP/A2A, OpenTelemetry, and (new in mid-2026) a first-party **harness** layer and an information-flow-control security layer (FIDES).

Primary evidence is direct source inspection of shallow clones of `microsoft/agent-framework` (HEAD `12621e0a`, 2026-08-14) and `microsoft/autogen` (HEAD 2026-04-06), plus the in-repo ADR directory (`docs/decisions/`), READMEs fetched from raw.githubusercontent.com, and web search. **Access constraint**: the network egress proxy blocked `learn.microsoft.com`, `devblogs.microsoft.com`, `techcommunity.microsoft.com`, and `infoq.com`; claims sourced from those properties came through search-result summaries and are labeled accordingly (MEDIUM confidence at best). Source access more than compensates: nearly everything below is SOURCE-CODE OBSERVATION at HIGH confidence.

## Findings

### 1. Lineage and convergence timeline

- **FACT**: AutoGen is in maintenance mode: README carries a "Maintenance Mode" badge and caution — "AutoGen is now in maintenance mode. It will not receive new features or enhancements and is community managed going forward," pointing new users to MAF (commit "Update maintenance mode banner" 2026-04-06).
- **FACT**: Semantic Kernel's README opens with "Semantic Kernel is now Microsoft Agent Framework!" and calls MAF "the enterprise-ready successor to Semantic Kernel," with a migration guide. SK remains functional (Python 3.10+, .NET 10+, Java 17+) but is no longer the strategic path.
- **FACT (via search, MEDIUM on exact dates)**: MAF public preview 2025-10-01; MAF 1.0 GA for both Python and .NET on 2026-04-03, described as production-ready with stable APIs and long-term-support commitment.
- **SOURCE-CODE OBSERVATION (HIGH)**: The Python core package is at version **1.14.0** with active daily commits as of 2026-08-14 — post-GA velocity is high and features are still landing behind an in-library feature-stage gate (`_feature_stage.py`: `ExperimentalFeature`, `ReleaseCandidateFeature` enums with warning machinery). Version churn happens *inside* a stable 1.x line by gating, not by branching frameworks — a governance mechanism AutoGen/SK never had.
- **FACT**: SK's planners (Stepwise, Handlebars) were deprecated in 2024 in favor of automatic function calling; MAF has no planner concept at all. The "planner" as a distinct architectural component is dead across the entire Microsoft stack.

### 2. autogen-core: the actor architecture that was and wasn't kept

- **SOURCE-CODE OBSERVATION (HIGH)**: `autogen-core` defines `AgentRuntime` as a Protocol with two delivery modes: `send_message(message, recipient: AgentId, ...)` (direct RPC with response) and `publish_message(message, topic_id: TopicId, ...)` (pub/sub, no response). Agents are registered as *factories* under an `AgentType`; `AgentId = (type, key)` gives Orleans-style virtual-actor addressing (agents instantiated on first message). `Subscription` is a protocol mapping `TopicId → AgentId` (`TypeSubscription`, `TypePrefixSubscription`). `SingleThreadedAgentRuntime` processes one asyncio queue ("suitable for development and standalone applications... not for high-throughput"), with `InterventionHandler`s able to intercept messages pre-delivery — a policy hook at the message-bus level.
- **SOURCE-CODE OBSERVATION (HIGH)**: The distributed story was a gRPC worker protocol (`protos/agent_worker.proto`): `service AgentRpc` with bidirectional `OpenChannel(stream Message)`, a control channel, and `RegisterAgent`/`Add|Remove|GetSubscriptions` RPCs, plus CloudEvents envelopes (`cloudevent.proto`). The AutoGen core README says agents "are developed by using the Actor model" and that you can "easily move to a distributed system in the cloud."
- **SOURCE-CODE OBSERVATION (HIGH)**: AgentChat (the ConversableAgent lineage's v0.4 successor) implements teams as a layer *on top of* the actor runtime: `BaseGroupChat` "provides the mapping between the agents of the AgentChat API and the agent runtime of the Core API" — group chat participants publish messages to all others; managers (`RoundRobinGroupChat`, `SelectorGroupChat`, `Swarm`, `_graph/` GraphFlow, `_magentic_one/`) choose the next speaker. Conversation-as-control-flow was already a *pattern compiled onto message routing* in AutoGen 0.4, not a primitive.
- **INFERENCE (HIGH)**: AutoGen v0.4's own architecture proves Microsoft had concluded by early 2025 that the conversation is not the kernel; the kernel is typed message routing. MAF then went one step further and dropped the *distributed actor mesh* too (see §7).

### 3. MAF agent layer: model adapters, sessions, context providers, middleware

- **SOURCE-CODE OBSERVATION (HIGH)**: The model boundary is a structural Protocol: `SupportsChatGetResponse` (in `_clients.py`), implemented by `BaseChatClient` subclasses in provider packages (`openai`, `anthropic`, `azure`, `gemini`, `mistral`, `ollama`, `bedrock` (amazon), `foundry`, `foundry_local`, `github_copilot`, `copilotstudio`, `claude`...). Providers ship as separate pip packages but are lazily re-exported under stable `agent_framework.<provider>` import paths (ADR-0008 "stable-import-path guarantee").
- **SOURCE-CODE OBSERVATION (HIGH)**: **Capability discovery is structural typing.** `_clients.py` defines `@runtime_checkable` capability protocols per hosted tool: `SupportsCodeInterpreterTool`, `SupportsWebSearchTool`, `SupportsImageGenerationTool`, `SupportsMCPTool`, `SupportsFileSearchTool`, `SupportsShellTool`, `SupportsGetEmbeddings`. Framework code checks a client's capabilities via `isinstance` against these protocols (the harness factory takes `SupportsShellTool | SupportsWebSearchTool` intersections). This is a real, if informal, capability model: per-capability interfaces, discovered at runtime, no negotiation.
- **SOURCE-CODE OBSERVATION (HIGH)**: The session model: `AgentSession` is "a conversation session with an agent. Lightweight state container" holding `session_id`, optional `service_session_id` (service-managed history, e.g. OpenAI Responses conversation or Foundry thread — with an explicit docstring warning that it is *not* an end-user authorization boundary), and a mutable state dict. The earlier `AgentThread` naming is gone (ADR-0018 covers AgentThread serialization; ADR-0029 covers the session-identity redesign). Session persistence is via a `SessionStore` (`get`/`set`/`delete`, snapshot-on-read semantics per the hosting README) — the framework deliberately keeps "history in the session store" and "workflow resume via CheckpointStorage" as two separate durability mechanisms with an app-owned cursor between them.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Context construction is a provider pipeline.** `ContextProvider`s run per invocation over a `SessionContext` carrying `input_messages`, `context_messages` (a dict `source_id → messages`, insertion-ordered by provider execution), `instructions`, `tools`, and `middleware` — i.e., a provider can inject *messages, instructions, tools, and middleware* in one pass. Every injected message gets an `attribution` marker (`source_id`, `source_type`, optional `origin_session_ids` for cross-session memory) in `additional_properties` "for governance, audit, or behavioral-analysis purposes." Context provenance is a first-class, serialized annotation.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Middleware is a three-level typed pipeline**: `AgentMiddleware` (around a whole agent run), `ChatMiddleware` (around each model call), `FunctionMiddleware` (around each tool call), each with its own context object (`AgentContext`, `ChatContext`, `FunctionInvocationContext`) and pipeline class, composable via `MiddlewareBundle`. `MiddlewareTermination` is an exception-based short-circuit. This is SK's "filters" lineage generalized.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Compaction is a strategy library**, not a hard-coded behavior: `_compaction.py` ships `TruncationStrategy`, `SlidingWindowStrategy`, `SelectiveToolCallCompactionStrategy`, `ToolResultCompactionStrategy`, `SummarizationStrategy`, `TokenBudgetComposedStrategy`, and `ContextWindowCompactionStrategy`, exposed through a `CompactionProvider` that is itself a `ContextProvider`. Token counting is behind a `TokenizerProtocol` with a character-estimator default. Context management is thus a *plugin in the same extension slot as memory and skills*.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Skills are an Anthropic-style progressive-disclosure system**: `_skills.py` (4,900+ lines) defines `Skill` variants (`FileSkill` with YAML frontmatter, `InlineSkill`, `ClassSkill`, `MCPSkill`), `SkillResource`, `SkillScript` (executable scripts attached to skills, run through a `SkillScriptRunner` protocol), and composable `SkillsSource`s (file, in-memory, MCP, aggregating/filtering/deduplicating/caching), surfaced by a `SkillsProvider` context provider. ADR-0021 ("agent skills design") and ADR-0029 ("mcp-skill-templates-and-direct-references") document the design. MCP servers can serve skills — skills-over-MCP is a distribution channel.

### 4. The workflow subsystem: typed executors, edges, Pregel supersteps, checkpoints

This is the heart of the convergence and the direct comparison target for a kernel graph/loop hypothesis.

- **SOURCE-CODE OBSERVATION (HIGH)**: An `Executor` is "the fundamental building block of workflows" — a class whose `@handler`-decorated async methods declare, via Python type annotations, which message types it consumes; its `WorkflowContext[OutT, WorkflowOutT]` annotation declares which message types it may `send_message()` to downstream executors and which it may `yield_output()` as workflow-level output. Input/output/workflow-output types are *discovered by signature reflection* and validated at build time (`_validation.py`). The .NET side mirrors this with generic typing.
- **SOURCE-CODE OBSERVATION (HIGH)**: An `Edge` is "a directed, optionally-conditional hand-off between two executors," serialized to primitives (callable conditions recorded by name; deserialization installs a loud-failing proxy if the callable is missing — "Callable 'X' is unavailable after serialization"). `EdgeGroup` subclasses (registered in a type registry for deserialization) express fan-out, fan-in, switch-case (`Case`/`Default`), and multi-selection routing. `WorkflowBuilder` offers `add_edge`, `add_fan_out_edges`, `add_fan_in_edges`, `add_switch_case_edge_group`, `add_multi_selection_edge_group`, `add_chain`, then `build()`.
- **SOURCE-CODE OBSERVATION (HIGH)**: Execution is explicitly Pregel: `RunnerImpl` — "A class to run a workflow in Pregel supersteps" — drives iterations up to `max_iterations` (default 100). The `Workflow` docstring: "Messages between executors are delivered at the end of each superstep and are not visible in the event stream. Only workflow-level events... are observable to callers." Shared `State` implements superstep transaction semantics: `set()` writes a pending buffer; `commit()` at the superstep barrier; concurrent writers within a superstep are last-write-wins, "consistent with the .NET behavior." The .NET runtime has the same model (`ISuperStepRunner`, `SuperStep` events, `ExecutionMode`).
- **SOURCE-CODE OBSERVATION (HIGH)**: **Checkpointing is at superstep barriers and is definition-scoped, not instance-scoped.** `WorkflowCheckpoint` captures: in-flight messages between executors, committed state (including per-executor state under a reserved key), pending request-info events, iteration count, `previous_checkpoint_id` (lineage chain), and a `graph_signature_hash` "to validate checkpoint compatibility during restore." The docstring is explicit: "a checkpoint is not tied to a specific workflow instance, but rather to a workflow definition... This allows checkpoints to be shared and restored across different workflow instances." `CheckpointStorage` is a small protocol (save/load/list/delete/get_latest) with in-memory and atomic-write file implementations; external stores (Redis, CosmosDB packages exist) plug in.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Human-in-the-loop is a typed request/response port pattern, unified with checkpointing.** An executor calls `ctx.request_info()`; a `request_info` event (with `request_id`, `request_type`, `response_type`) is emitted; the workflow enters `IDLE_WITH_PENDING_REQUESTS`; the caller later resumes with `run(responses={request_id: value})`, which routes responses to `@response_handler` methods. Pending requests are stored *inside checkpoints*, so a paused-awaiting-human workflow can be fully rehydrated in a new process. The .NET side reifies this even harder: `RequestPort` with declared request/response types, `ExternalRequest`/`ExternalResponse` records, and `PortableValue` (a type-tagged serializable value wrapper) — external interaction is a typed port on the graph boundary.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Events are one discriminated union.** `WorkflowEvent` is a single generic class with a `type` discriminator covering lifecycle (`started`, `status`, `failed`), diagnostics (`warning`, `error`), executor bookkeeping (`executor_invoked/completed/failed/bypassed`), superstep boundaries (`superstep_started/completed`), data (`output`, `intermediate`), and `request_info`. Docstring: "This single generic class handles all workflow events through a `type` discriminator." Runs return `WorkflowRunResult(list[WorkflowEvent])` or stream events.
- **SOURCE-CODE OBSERVATION (HIGH)**: **Agents enter graphs by wrapping**: `AgentExecutor` adapts anything satisfying `SupportsAgentRun` into an executor via `AgentExecutorRequest`/`AgentExecutorResponse` messages; `AgentExecutorResponse` carries `full_conversation` explicitly "to prevent downstream agents losing user prompts" — conversation context is *threaded through graph messages*, not ambient. Sub-workflows compose via `WorkflowExecutor`, and a parent executor can *intercept* a child workflow's request-info messages (`SubWorkflowRequestMessage` handling) and answer them itself or escalate — a delegation/mediation mechanism at the graph boundary.
- **SOURCE-CODE OBSERVATION (HIGH)**: **The AutoGen patterns survive as a compilation layer**: `agent-framework-orchestrations` implements `_sequential.py`, `_concurrent.py`, `_group_chat.py`, `_handoff.py`, `_magentic.py` (Magentic-One's planner-orchestrator) — all importing `_workflows` internals (`AgentExecutor`, `Executor`, `handler`, `WorkflowContext`, `CheckpointStorage`) — i.e., group chat, handoff, and Magentic are *builders that emit workflows*. What was AutoGen's core abstraction is now a pattern library over the graph.

### 5. The harness: Microsoft ships a Claude-Code-shaped agent as library composition

New since GA, and the strongest evidence in the entire stack about where "harness" sits architecturally.

- **SOURCE-CODE OBSERVATION (HIGH)**: `agent_framework._harness` provides `create_harness_agent()` — "a factory function that assembles the full agent pipeline from a chat client, wiring up function invocation, per-service-call history persistence, compaction, and a rich set of default context providers (todo, mode, memory, skills)." Components:
  - `AgentLoopMiddleware` (`_loop.py`): re-invokes the agent until a `should_continue` predicate says stop — predicates include `todos_remaining` (loop while the todo list has open items), `background_tasks_running`, or an LLM **judge** (`with_judge`: a second chat client returns a `JudgeVerdict` structured output deciding whether the original request is answered, with text-marker fallback `VERDICT: DONE`/`VERDICT: MORE`). Supports a cross-iteration feedback log and `fresh_context=True` (restart each pass from the original task plus progress log, snapshotting/restoring the session). Verification-as-loop-termination is a middleware.
  - `TodoProvider` (`_todo.py`) — task-list state; `AgentModeProvider` (`_mode.py`) — mode switching; `FileMemoryProvider` + `AgentFileStore`/`FileSystemAgentFileStore` (`_file_memory.py`, `_file_access.py`) — file-backed memory and scoped file access; `BackgroundAgentsProvider` (`_background_agents.py`) — "delegate work to background sub-agents asynchronously... Each background task runs in its own session concurrently," exposed to the model as `background_agents_*` tools; `ToolApprovalMiddleware` (`_tool_approval.py`) — approval rules with scopes (`tool` vs `tool_with_arguments`), queued approval requests/responses in session state, and a **function-invocation budget** (`_FUNCTION_INVOCATION_BUDGET_STATE_KEY`).
  - The .NET twin exists (`Microsoft.Agents.AI.Harness`: `HarnessAgent`, `HarnessAgentOptions`).
- **OBSERVED BEHAVIOR (MEDIUM)**: InfoQ headline (2026-08): "Microsoft Agent Framework Harness and Hosted Agents Reach General Availability" — the harness is a promoted, GA'd product surface, not a lab experiment (body unreadable due to egress block).
- **INFERENCE (HIGH)**: Microsoft's harness is *pure composition*: middleware (loop, approval) + context providers (todo, memory, skills, mode, files, subagents) around the unchanged agent loop. No new kernel-level concept was needed to build a Claude-Code-class harness. This directly supports the thesis that "harness" is a configuration/plugin layer over a minimal loop, not a runtime primitive.

### 6. Policy and security: information-flow control in the data plane

- **SOURCE-CODE OBSERVATION (HIGH)**: `security.py` (~2,950 lines) implements **FIDES**, "a comprehensive deterministic prompt injection defense system": `IntegrityLabel` (TRUSTED/UNTRUSTED) and `ConfidentialityLabel` (PUBLIC/PRIVATE/USER_IDENTITY) attached to content; `LabelTrackingFunctionMiddleware` propagates labels and *automatically hides* UNTRUSTED content behind variable references (`var_xxx` indirection via `ContentVariableStore`); `PolicyEnforcementFunctionMiddleware` blocks tool calls violating policy (including `max_allowed_confidentiality` exfiltration prevention); `quarantined_llm` runs an isolated model call over labeled data; MCP tools are auto-labeled from MCP `ToolAnnotations` hints and per-result `_meta.ifc` labels (e.g. GitHub MCP with `X-MCP-Features: ifc_labels`) are parsed and enforced. Setup is one context provider: `SecureAgentConfig`. ADR-0024 records the decision. (This is the CaMeL/FIDES research lineage productized — labels flow with content through middleware, and policy is enforced *deterministically at the tool boundary*, not by prompting.)
- **SOURCE-CODE OBSERVATION (HIGH)**: **Sandboxed code execution is a pluggable environment**: ADR-0024 (`codeact-integration`) plus packages `agent-framework-hyperlight` (CodeAct in a Hyperlight WASM micro-VM sandbox; registered tools are callable *from inside* the sandbox via `call_tool(...)` but "are not exposed as direct agent tools") and `agent-framework-monty` (CodeAct on `pydantic-monty`, a Rust Python interpreter — "no hypervisor or WASM backend required"); .NET has `Microsoft.Agents.AI.Hyperlight` and `Microsoft.Agents.AI.LocalCodeAct`. There is also a shell tool package (`Microsoft.Agents.AI.Tools.Shell`, python `tools/shell`) with a `ShellExecutor`/environment-provider abstraction, and a `Microsoft.Agents.AI.Purview` package for compliance integration.
- **INFERENCE (MEDIUM)**: Microsoft is converging on *two* enforcement planes: label-based IFC inside the message/tool data plane, and sandbox isolation at the execution-environment plane — both delivered as middleware/providers/packages rather than runtime changes.

### 7. Durability, distribution, and what got dropped

- **SOURCE-CODE OBSERVATION (HIGH)**: MAF's Python packages contain **no gRPC agent mesh** — the only grpc references are OTLP exporters in observability. AutoGen's distributed worker protocol (`agent_worker.proto`, CloudEvents, host/worker runtimes) has no MAF successor in-repo. Distribution in MAF happens at *protocol boundaries*: hosting packages (ASP.NET `Microsoft.Agents.AI.Hosting.*`, python `hosting`, `hosting-a2a`, `hosting-mcp`, `hosting-responses`, even `hosting-telegram`) expose agents as A2A servers, MCP servers, OpenAI-Responses-compatible endpoints, or chat channels; `A2AAgent` is the client. The actor mesh died; the protocol boundary won.
- **SOURCE-CODE OBSERVATION (HIGH)**: Durable execution is an **extension, not the kernel**: ADR-0032 (accepted 2026-07-21, contact cgillum — the Durable Task Framework creator) extracts `agent-framework-durabletask` and `agent-framework-azurefunctions` into `microsoft/agent-framework-durable-extension`, consuming MAF as published packages, with lazy re-export shims preserving `agent_framework.azure` imports. The in-core durability primitive is only the superstep checkpoint; DTF-style replay durability attaches from outside. Orleans itself is nowhere in MAF (the actor inheritance is conceptual, via AutoGen, and was dropped).
- **SOURCE-CODE OBSERVATION (HIGH)**: ADR-0009 (2025-10-15) designs long-running operations by *surveying and aligning with* OpenAI Responses (`background=true`), Foundry Agent Runs, and A2A Tasks — a table compares initiation, status/result/cancel support across the three. MAF models long-running work to interoperate with all three rather than inventing its own.
- **SOURCE-CODE OBSERVATION (HIGH)**: A separate **declarative plane** exists: `declarative-agents/` YAML workflows (`kind: Workflow`, triggers like `OnConversationStart`, actions like `InvokeAzureAgent`, `SetVariable`, Power-Fx-style expressions `=System.ConversationId`) loadable via `DeclarativeWorkflowBuilder.Build("Marketing.yaml")` — the same format family as Copilot Studio / Foundry Workflows; plus `Microsoft.Agents.AI.Workflows.Declarative[.Foundry|.Mcp]`. Code-defined and YAML-defined workflows execute on the same runner.
- **SOURCE-CODE OBSERVATION (HIGH)**: Observability is OpenTelemetry-native and crosses the durability boundary: executors run inside `create_processing_span`; `WorkflowMessage` carries `trace_context` and `source_span_id` fields *in its serialized form*, so traces survive checkpoint/resume. A feature-usage telemetry system (`FeatureIndex`, `mark_feature_used`, ADR-0033 bitmask-in-user-agent) instruments which framework features are actually used — Microsoft is measuring feature survival empirically.

### 8. Answer to the key question: which computational models survived production contact?

**INFERENCE (HIGH), grounded in the source observations above**: Across three generations Microsoft tried (a) conversation-as-control-flow (AutoGen classic), (b) LLM-planner-over-plugins (SK planners), (c) distributed typed-actor pub/sub (autogen-core), and (d) typed dataflow graph with BSP supersteps + checkpoints (MAF workflows). What survived into the converged, GA product:

- **Survived**: typed message routing between typed nodes; deterministic superstep barriers; checkpoint-at-barrier with definition-scoped (not instance-scoped) identity; typed request/response ports for all external interaction (human input, parent mediation); middleware pipelines at agent/model/tool granularity; context assembly as an ordered provider pipeline with provenance attribution; function calling as the only model-driven planning primitive; protocols (MCP/A2A/OpenAPI) as the distribution boundary.
- **Demoted to libraries**: group chat, handoff, Magentic planning (orchestrations package compiles them to graphs); harness behaviors (loop/judge/todo/subagents/approval as middleware+providers); durability engines (external extension); declarative authoring (YAML → same graph).
- **Killed**: standalone LLM planners; the distributed actor mesh with topic subscriptions; conversation as the core state object (replaced by explicit `full_conversation` threading through graph messages and session stores).

Compared with LangGraph: MAF chose *typed message routing on edges* where LangGraph chose *shared channels/state reducers*. Both landed on Pregel/BSP supersteps and checkpoint-per-superstep — independent convergence on the same execution substrate (LangGraph's docs likewise cite Pregel). The difference is the data plane: MAF messages are point-to-point typed payloads with edge conditions (plus a small transactional shared `State`), while LangGraph's state is a merged document. MAF's choice makes serialization, IFC labeling, and cross-language parity (.NET/Python) easier; LangGraph's makes global-state patterns easier. **INFERENCE (MEDIUM)**: two of the three largest agent-framework vendors independently arriving at BSP-superstep + barrier checkpoints is strong evidence that this is the correct minimal durable-execution substrate for a kernel.

## Precise vocabulary

- **Model**: the remote LLM behind a provider API. Never represented in-framework beyond client configuration (model id strings on chat options).
- **Model API**: per-provider (OpenAI ChatCompletions/Responses, Anthropic Messages, Foundry, Bedrock, Gemini...). MAF normalizes to its own `Message`/`Content` types (a discriminated-union `Content` class mirroring the `WorkflowEvent` pattern).
- **Model adapter**: a `BaseChatClient` implementing the `SupportsChatGetResponse` structural protocol, shipped as a separate package per provider with stable re-export paths; optional capability protocols (`SupportsWebSearchTool`, `SupportsShellTool`, `SupportsMCPTool`, ...) advertise hosted-tool support.
- **Agent**: `Agent` — chat client + instructions + tools + context providers + middleware + session handling; anything satisfying `SupportsAgentRun` (`run(..., stream=...)`) counts, including remote `A2AAgent` and hosted Foundry agents.
- **Agent loop**: the function-calling loop inside the agent's run (spec `004-python-function-calling-loop`); extended outward by `AgentLoopMiddleware` (multi-pass until predicate/judge termination).
- **Harness**: literally named — `agent_framework._harness.create_harness_agent` / `Microsoft.Agents.AI.Harness`: a factory composing loop middleware, todo/mode/memory/file/skills/background-agents providers, tool approval, and compaction around a plain agent. A configuration, not a runtime concept.
- **Context-management system**: the `ContextProvider` pipeline over `SessionContext`, including `CompactionProvider` (strategy objects) and attribution-tagged message injection.
- **Memory system**: pluggable providers — `FileMemoryProvider` (harness), `mem0` package, Redis, Azure Cosmos memory; all are context providers. No single blessed memory model.
- **Tool runtime**: in-process function invocation wrapped by `FunctionMiddleware` pipeline + `ToolApprovalMiddleware` (rules, scopes, budgets); hosted tools delegated to providers via capability protocols; MCP tools via `MCPTool` with OTel propagation and optional FIDES labeling.
- **Execution environment**: host process; optional Hyperlight WASM micro-VM or Monty interpreter sandboxes for CodeAct; shell executor abstraction; Foundry Agent Service as managed environment.
- **Planner**: **ABSENT** as a first-class concept. SK's planners deprecated (2024); MAF ships none. Magentic (orchestrations) is the closest survivor — an LLM orchestrator-as-graph-node pattern, not a framework primitive.
- **Workflow/graph construct**: `Workflow` = typed `Executor` nodes + `Edge`/`EdgeGroup` routing (conditions, fan-in/out, switch-case), built by `WorkflowBuilder`, executed in Pregel/BSP supersteps by `RunnerImpl`; nested via `WorkflowExecutor`; agents wrapped via `AgentExecutor`; YAML-declarative variant compiles to the same thing.
- **State/session model**: dual — `AgentSession`+`SessionStore` for conversational history; workflow `State` (transactional per superstep) + `WorkflowCheckpoint` (definition-scoped, lineage-chained, topology-hash-validated) for graph execution.
- **Delegation mechanism**: `BackgroundAgentsProvider` (subagents as tools, own sessions, async); sub-workflow request interception; handoff orchestration; A2A for cross-runtime delegation.
- **Protocol usage**: MCP (client + server hosting + skills channel + IFC label extension), A2A (client + server hosting; A2A 1.0 "coming soon" at GA per announcement), AG-UI, OpenAPI, OpenAI-Responses-compatible hosting.
- **Capability discovery/negotiation**: structural (`@runtime_checkable` protocols, `isinstance` checks) inside the framework; MCP tool listings and A2A agent cards at protocol boundaries. No negotiation, no central capability registry.
- **Policy/security layer**: FIDES IFC (integrity/confidentiality labels propagated by middleware, deterministic policy enforcement at tool boundary, quarantined LLM, variable indirection); tool approval rules + invocation budgets; Purview integration; sandboxes.
- **Durable-execution features**: superstep checkpoints in core (pause/resume/rehydrate, HIL requests inside checkpoints); Durable Task Framework + Azure Functions in the separate durable-extension repo.
- **Event system**: `WorkflowEvent` — one generic discriminated-union event type for lifecycle/diagnostics/superstep/executor/data/request-info; returned as list or stream. Agent-level streaming via `AgentResponseUpdate`.
- **Observability**: native OpenTelemetry (spans per executor/model/tool, trace context serialized into `WorkflowMessage`, survives checkpoints); feature-usage bitmask telemetry.

## Implications for a universal runtime kernel

1. **The convergence validates a small kernel.** Microsoft collapsed three frameworks into: typed nodes + typed conditional edges + superstep barrier + checkpoint-at-barrier + typed external request ports + one discriminated event stream. Everything else — group chat, planners, harness behaviors, durability engines, declarative authoring — became libraries over that substrate. This is close to a proof-by-industrial-experiment that the kernel surface can be that small.
2. **Harness = composition, confirmed by the largest vendor.** Todo lists, judge loops, subagents, tool approval, memory, skills, compaction all landed as middleware/providers around an unchanged loop. A kernel needs good *interception slots* (per-run, per-model-call, per-tool-call) and an *injection pipeline with provenance*, not harness primitives.
3. **Checkpoint identity should bind to definition + topology hash, not instance.** MAF's `graph_signature_hash` + `previous_checkpoint_id` lineage makes checkpoints portable artifacts (shareable across instances, resumable in fresh processes). A kernel's checkpoint/artifact model should adopt exactly this: content-addressed topology validation + lineage chains.
4. **Human-in-the-loop and delegation are the same primitive**: a typed request leaving the graph with a correlation id, persisted in the checkpoint, answered by `run(responses=...)`. Parent graphs can intercept child requests. A kernel "capability request" port generalizes HIL, approvals, and cross-agent mediation in one mechanism.
5. **Durability engines attach from outside if the kernel is deterministic at barriers.** Microsoft deliberately extracted DTF/Azure Functions durability into an extension; the in-core contract is only "state is consistent and serializable at superstep boundaries." A kernel should specify the barrier/serialization contract and leave replay engines as plugins.
6. **Policy wants to live in the data plane.** FIDES shows labels (integrity/confidentiality) attached to content and propagated through tool middleware enable *deterministic* policy enforcement, including over MCP (`_meta.ifc`). A kernel capability model should carry label/taint metadata on every value crossing a capability boundary — retrofitting it as middleware works but is per-framework; making it a kernel invariant is the differentiator.
7. **Capability discovery via structural typing is the ceiling of the framework approach.** `Supports*Tool` protocols are informal, unversioned, and non-negotiable. A kernel can beat this with declared, versioned, negotiated capability contracts — but note that Microsoft got surprisingly far without negotiation.
8. **Distribution belongs to protocols, not the kernel.** The gRPC actor mesh died; A2A/MCP/HTTP hosting adapters won. A kernel should assume single-process execution semantics with protocol adapters at the boundary, and treat "distributed runtime" as an anti-goal.
9. **Feature-stage gating + usage telemetry is kernel-relevant governance.** MAF evolves fast post-1.0 inside a stable API by gating experimental features and measuring usage (bitmask telemetry). A kernel with plugins needs an equivalent maturity/telemetry story or its ecosystem will fragment.
10. **Events as one discriminated union worked.** Both `Content` and `WorkflowEvent` collapsed class hierarchies into single generic types with a `type` discriminator — chosen for serialization and cross-language parity. A kernel event log should do the same from day one.

## Open questions

1. What exactly GA'd in the InfoQ-reported "Harness and Hosted Agents" announcement (Aug 2026), and does the harness carry compatibility guarantees, given `_harness` modules still use `@experimental` gates in source? (Body unreadable — egress block.)
2. How does the durable extension reconcile DTF's replay-based determinism with MAF's checkpoint-based resume — does it replay supersteps or snapshot them, and what are the idempotency requirements on executors?
3. Is there any path back to a distributed *in-framework* runtime (e.g., multi-node superstep execution), or is Foundry Agent Service intended as the only scale-out story? (`ISuperStepJoinContext.AttachSuperstepAsync` hints at multi-runner joining.)
4. How much of Copilot Studio / Foundry Workflows actually executes on the open-source declarative runner vs. a proprietary cloud interpreter — i.e., where is the real product/kernel boundary for the YAML plane?
5. FIDES adoption: is IFC labeling on by default anywhere in Microsoft's hosted products, and does the `_meta.ifc` MCP extension have any standardization track in the MCP spec process?
6. The `monty` bet: does CodeAct-with-interpreter (tools called from inside sandboxed code) displace the function-calling loop for tool-heavy agents, and what does that imply for a kernel's tool-invocation primitive?
