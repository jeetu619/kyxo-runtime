# Google Agent Development Kit (ADK) — Event-Driven Runner, Workflow Runtime, and the 2.0 Graph Pivot

## Scope

This note covers Google's Agent Development Kit (ADK) as of **2026-08-15**, primarily via direct source inspection of `google/adk-python` at **v2.6.3** (clone at commit `1d2d1eda`, dated 2026-08-14) and the `google/adk-docs` repository (clone dated 2026-08-14), supplemented by web search for release/rebranding facts. Focus areas: the agent hierarchy and the ADK 2.0 `BaseNode`/Workflow Runtime pivot; the Runner and its event loop; the Event model; sessions/state/memory/artifacts; callbacks and plugins; the LLM flow processor pipeline; model abstraction; tools (function/MCP/OpenAPI/agent-as-tool); planners and code executors; durability (resume/rewind/compaction); streaming/live; A2A; deployment (Agent Runtime née Agent Engine, Cloud Run); evaluation; and what all of this implies for a minimal universal execution kernel.

A note on recency: ADK moved fast in 2026. **ADK Python 2.0 went GA on 2026-05-19** (announced around Google I/O 2026) and replaced the 1.x "hierarchical agent executor" with a graph-based **Workflow Runtime**. Much public commentary still describes the 1.x architecture; this note describes 2.x and flags what changed.

## Findings

### 1. Identity, languages, and the 2.0 pivot

- **FACT.** ADK is Apache-2.0 open source with five language SDKs: Python, Go, TypeScript/JS, Java, Kotlin (docs/release-notes.md lists all five repos). Python is the flagship; Python v2.0.0 went **GA 2026-05-19**, Go v2.0.0 GA 2026-06-30 (docs/2.0/index.md).
- **SOURCE-CODE OBSERVATION (HIGH).** `version.py` in the current main branch reads `2.6.3` (2026-08-14) — ~13 minor releases in 3 months post-2.0; the codebase is churning rapidly, with many `@experimental(FeatureName.…)` gates (a formal feature-flag registry in `features/`).
- **FACT.** ADK 2.0's headline change, in the docs' own words: *"The ADK 2.0 release introduces the Workflow Runtime, transitioning ADK from a hierarchical agent executor to a graph-based execution engine. In this new architecture, your Agents, Tools, and Functions are evaluated as individual nodes within a workflow graph."* (docs/2.0/index.md).
- **SOURCE-CODE OBSERVATION (HIGH).** `BaseAgent(BaseNode, abc.ABC)` — the agent base class now literally subclasses the workflow node base class (`agents/base_agent.py` line 94). `SequentialAgent`, `ParallelAgent`, and `LoopAgent` are all decorated `@deprecated('… in favor of Workflow …')` (their modules). This is the strongest possible confirmation that Google converged on "orchestration strategies as plugins over a node/event kernel" — they deprecated their own workflow-agent classes one major version after shipping them.
- **INFERENCE (HIGH).** The KEY QUESTION premise ("ADK separates workflow-agents from LLM agents under one BaseAgent, coordinated by a Runner") describes ADK 1.x. ADK 2.x goes further: the unifying abstraction dropped a level, from "everything is an agent" to "everything is a node" (agents, tools, plain functions, joins, nested workflows). The 1.x decomposition was apparently not minimal enough — deterministic orchestration written as *agents* inherited agent baggage (instructions, callbacks, sub-agent trees) it didn't need.

### 2. The Event model — one log, many meanings

- **SOURCE-CODE OBSERVATION (HIGH).** `Event` (`events/event.py`) **extends `LlmResponse`** — the runtime's universal envelope literally inherits from the model-response type. Fields added on top: `invocation_id`, `author` ('user' or agent name), `actions: EventActions`, `output` (generic workflow-node output, new in 2.0), `node_info` (workflow node path `"wf/A@1/B@1"`, run IDs, new in 2.0), `branch` (dot-path for peer-isolation of history), `isolation_scope` (context-visibility tag, marked "DO NOT USE DIRECTLY"), `long_running_tool_ids`, `id`, `timestamp`.
- **SOURCE-CODE OBSERVATION (HIGH).** `EventActions` (`events/event_actions.py`) is the side-effect vocabulary of the entire runtime: `state_delta` (session-state mutation), `artifact_delta` (filename→version), `transfer_to_agent`, `escalate`, `requested_auth_configs`, `requested_tool_confirmations` (HITL), `compaction` (summarized-history record), `end_of_agent` + `agent_state` (checkpoints, "should only be set by ADK workflow"), `rewind_before_invocation_id` (undo), `route` (graph edge matching value), `render_ui_widgets`, `set_model_response`, `skip_summarization`.
- **INFERENCE (HIGH).** A single `Event` type is simultaneously: chat message, tool call/response, state transaction, artifact version bump, checkpoint marker, routing signal, auth/HITL request, UI directive, and compaction record. The session's append-only event list is the *single source of truth*: state is folded from `state_delta`s, workflow resume is reconstructed by scanning events, rewind is computed as an inverse delta. This is event sourcing in the strict sense — and it is exactly the "events + artifacts + policy + checkpoints" kernel shape, except achieved by widening one Pydantic class rather than by typed event kinds.
- **FACT.** The 2.0 migration guide warns that adding `node_info` and `output` to the Event schema breaks custom session stores with rigid columns and downstream validators with `additionalProperties: false` (docs/2.0/index.md) — evidence of the cost of an untyped, ever-widening envelope.

### 3. Runner and the event loop — the yield-is-commit contract

- **FACT.** The documented loop (docs/runtime/event-loop.md): Runner receives the user query, appends it to the session, calls `agent.run_async(ctx)`; the agent *yields* an Event whenever it has something to report; the Runner **commits** the event's `actions` via services (`session_service.append_event` applies `state_delta`/`artifact_delta`), then forwards the event upstream; only after processing does the generator resume — *"The Agent's logic resumes from where it paused only after the Runner has processed the event."*
- **SOURCE-CODE OBSERVATION (HIGH).** `Runner.run_async` (`runners.py`) implements exactly that, wrapped in a plugin sandwich (`_exec_with_plugin`): `before_run` (can early-exit with content), per-event `on_event` (may return a modified event, which is merged and both persisted and streamed), append-if-not-partial, yield, then `after_run`, then post-invocation compaction. Errors trigger notification-only `on_run_error` callbacks and re-raise.
- **SOURCE-CODE OBSERVATION (HIGH).** Two execution paths coexist in `run_async` during the 1.x→2.x transition: (a) the **node runtime path** (`_run_node_async`): root node driven in a background `asyncio.Task` through `Context._run_node_internal`/NodeRunner, events flowing through `ic._event_queue` (an `asyncio.Queue`), with non-partial events *blocking the producer until the main loop has appended them to the session* (`InvocationContext._enqueue_event` uses a per-event `asyncio.Event` handshake); and (b) the **legacy agent path**: direct `agent.run_async` generator chaining. Root `LlmAgent`s (modes `chat`/`task`) and pure `BaseNode`s go through (a); other `BaseAgent`s still go through (b), with a TODO to unify. **INFERENCE (MEDIUM):** the queue-plus-handshake preserves the 1.x yield-is-commit semantics across an ownership boundary — the same contract, now enforced between concurrent tasks rather than by generator suspension.
- **FACT.** The 2.0 migration notes make the contract explicit and mandatory: manually appending events to the session (`context.session.events.append(...)`) "circumvents the graph engine and breaks determinism"; you *must* yield events so "the framework can manage its persistence, routing, and streaming natively" (docs/2.0/index.md).
- **SOURCE-CODE OBSERVATION (HIGH).** Budget primitive: `RunConfig.max_llm_calls` (default 500) enforced by a private `_InvocationCostManager` on `InvocationContext`, raising `LlmCallsLimitExceededError`. That is essentially the whole built-in budget system — no token/cost budgets, no per-subtree budgets.

### 4. The Workflow Runtime (2.0 graph engine)

- **SOURCE-CODE OBSERVATION (HIGH).** `workflow/_base_node.py`: `BaseNode` is a Pydantic model with `name`, `description`, `rerun_on_resume`, `wait_for_output` (JoinNode-style WAITING semantics), `retry_config`, `timeout` (→ `NodeTimeoutError`, integrates with retries), `input_schema`/`output_schema` (validated centrally by the node runner), and `state_schema` (Pydantic validation of `ctx.state` mutations; `app:`/`user:`/`temp:`-prefixed keys bypass). `BaseNode.run()` is `@final` and normalizes whatever `_run_impl` yields — `Event` passes through, `RequestInput` becomes an interrupt event, any other value becomes `Event(output=value)`.
- **SOURCE-CODE OBSERVATION (HIGH).** `workflow/_workflow.py`: `Workflow(BaseNode)` — *the graph engine is itself a node*, whose `_run_impl` "IS the graph orchestration loop: SETUP (build graph, seed triggers) → LOOP (schedule ready nodes via NodeRunner, handle completions) → FINALIZE." Mutable `_LoopState` is *not persisted*: "static node state is reconstructed from session events on resume; dynamic node state is lazily scanned on demand." Trigger buffers dispatch downstream nodes; `max_concurrency` throttles graph-scheduled nodes (explicitly *not* dynamic nodes, to avoid deadlock); `EventActions.route` values match edges; a `ReplaySequenceBarrier` enforces "deterministic replay ordering" during resume; `replayed_nodes` distinguishes genuine executions from history fast-forwards. A code TODO notes "resume from checkpoint event" is still pending — today resume is a full event-log scan.
- **SOURCE-CODE OBSERVATION (HIGH).** Dynamic nodes: `Context.run_node(node, node_input, use_as_output=…, use_sub_branch=…, override_isolation_scope=…)` lets any node schedule a child node imperatively and await its output — the docs call this "dynamic workflows" (code-based control flow) versus declarative graphs. Node types include `FunctionNode` (plain Python functions with parameters auto-bound from state), `ToolNode`, `JoinNode`, `_llm_agent_wrapper`, and nested `Workflow`s.
- **FACT.** Docs position **three complementary composition styles**: graph-based workflows (declarative edges + routing), dynamic workflows (imperative `ctx.run_node`), and the pre-built workflow agents (sequential/parallel/loop) as legacy higher-level building blocks (docs/graphs/index.md). LLM-driven delegation (coordinator + sub-agents) remains a fourth style ("collaborative workflows").
- **INFERENCE (HIGH).** ADK 2.x thus realizes, in one shipped system, the thesis under investigation: a small event-driven substrate (Event log + Runner + services) with *multiple orchestration strategies as libraries on top* — declarative graph, imperative code, LLM-driven routing — all producing the same event stream and all resumable from it. The graph engine gets no private persistence: it is a *client* of the same event log as everything else.

### 5. Agents: LlmAgent, modes, delegation, isolation

- **SOURCE-CODE OBSERVATION (HIGH).** `LlmAgent` fields: `model` (string or `BaseLlm`; default `gemini-3.5-flash`), `instruction`/`global_instruction` (static or provider functions), `static_instruction`, `tools`, `generate_content_config`, **`mode: 'chat' | 'task' | 'single_turn'`** (new in 2.x), `parallel_worker`, `disallow_transfer_to_parent/peers`, `include_contents: 'default'|'none'`, `input_schema`/`output_schema`, `output_key` (write final text into state), `planner`, `code_executor`, and six callback slots (`before/after_model`, `before/after_tool`, `on_model_error`, `on_tool_error`) plus inherited `before/after_agent`.
- **SOURCE-CODE OBSERVATION (HIGH).** **Task mode** is a first-class delegation primitive: a task-mode agent runs to completion via an injected `finish_task` tool, its events are stamped with an `isolation_scope` (the originating function-call id, or `node@run_id` when dispatched as a graph node), and the content-builder filters session events by scope — so a delegated task sees only its own events, isolated from the coordinator's conversation. `Runner._find_active_task_scope` walks the log to route a user's next message to a paused task. The task result is promoted onto the terminal event's `output` field (and becomes an A2A artifact when served over A2A).
- **SOURCE-CODE OBSERVATION (HIGH).** **LLM-driven transfer** (`flows/llm_flows/agent_transfer.py`): a request processor injects a `transfer_to_agent` tool plus instructions listing target names/descriptions (parent, siblings unless disallowed, sub-agents); the model calls the tool; `EventActions.transfer_to_agent` reroutes execution. Delegation is therefore implemented *entirely with the existing tool + event machinery* — no dedicated protocol.
- **SOURCE-CODE OBSERVATION (MEDIUM).** `langgraph_agent.py` wraps a LangGraph graph as a `BaseAgent`; `agent_tool.py` wraps any agent as a callable tool; `remote_a2a_agent.py` wraps a remote A2A endpoint as a local agent. Competing frameworks and remote agents are adapters into the same node tree.
- **SOURCE-CODE OBSERVATION (HIGH).** Context isolation primitives: `branch` (hierarchical dot-path; sub-agents in parallel branches don't see peers' history) and `isolation_scope` (task delegation). Both live *on the event*, and filtering happens at context-construction time — visibility is a query over the log, not separate stores.

### 6. Context construction — the LLM flow processor pipeline

- **SOURCE-CODE OBSERVATION (HIGH).** `flows/llm_flows/base_llm_flow.py` defines `BaseLlmFlow` with ordered `request_processors` and `response_processors`. `SingleFlow` wires the standard request pipeline: `basic` → `auth_preprocessor` → `request_confirmation` → `instructions` → `identity` → `compaction` ("before contents so compacted events are reflected") → `interactions_processor` (extracts a chain id so "chained requests only need the current turn because the service retains prior state" — server-side-state Gemini Interactions API) → `contents` (builds the message history from session events, applying branch/isolation filters) → `context_cache_processor` → NL planning → code execution → output schema. `AutoFlow = SingleFlow + agent_transfer`. **INFERENCE (HIGH):** context construction is a deterministic, ordered middleware pipeline over an `LlmRequest`; "memory," "planning," "caching," and "delegation" are all just processors. This is a second, inner plugin system distinct from Plugins/callbacks.
- **SOURCE-CODE OBSERVATION (HIGH).** Compaction: `EventsCompactionConfig` (on `App`) with `compaction_interval` (every N user invocations), `overlap_size`, `token_threshold`, and a pluggable `BaseEventsSummarizer` (default LLM summarizer); the Runner triggers compaction *after* yielding all events for an invocation; results are stored as `EventCompaction` records in the log and honored by the `contents` processor.

### 7. Sessions, state, memory, artifacts

- **SOURCE-CODE OBSERVATION (HIGH).** `BaseSessionService`: `create/get/list/delete_session`, `append_event` (the commit point: applies `state_delta`, strips `temp:` keys), `get_user_state`, `flush`. Implementations: in-memory, SQLite, generic database (SQLAlchemy), `VertexAiSessionService` (managed Agent Platform Sessions). State prefixes: `app:` (shared across users of the app), `user:` (shared across that user's sessions), `temp:` (never persisted), unprefixed = session-scoped. `State` keeps `_value` + `_delta` (pending commit) with optional Pydantic `state_schema` validation (prefixed keys bypass).
- **SOURCE-CODE OBSERVATION (HIGH).** **Rewind**: `Runner.rewind_async(rewind_before_invocation_id)` computes an *inverse* state delta (replaying deltas up to the rewind point, ignoring `app:`/`user:` keys) and an inverse artifact delta (restoring prior artifact versions via the artifact service, marking post-rewind artifacts inaccessible), then appends a single rewind Event. Undo is itself an event in the log.
- **SOURCE-CODE OBSERVATION (HIGH).** Memory is a separate, minimal interface: `BaseMemoryService` (`add_session_to_memory`, `search_memory`) with in-memory, **Vertex AI Memory Bank** (managed extraction/consolidation), and Vertex RAG implementations; exposed to agents as tools (`load_memory`, `preload_memory`). Memory is explicitly *cross-session knowledge*, distinct from session events.
- **SOURCE-CODE OBSERVATION (HIGH).** Artifacts: `BaseArtifactService` (in-memory, local file, GCS) — named, **versioned** binary blobs (filename → auto-incrementing int version), session-scoped or user-scoped via `user:` filename prefix; every save is recorded as `artifact_delta` on an event. No content-addressing, no lineage/provenance beyond the event log.

### 8. Callbacks and Plugins — the policy layer

- **SOURCE-CODE OBSERVATION (HIGH).** Two-tier interception: (1) per-agent **callbacks** (`before/after_agent`, `before/after_model`, `before/after_tool`, `on_*_error`) — return a non-None value to *override* the default behavior (skip the agent, replace the model response, fake a tool result); (2) global **Plugins** (`BasePlugin`, registered on `App`) with a superset lifecycle: `on_user_message`, `before_run`, `on_event`, `after_run`, all agent/model/tool callbacks, `on_model_error`, `on_tool_error`, `on_agent_error`, `on_run_error`, `close`. Plugin callbacks run **before** canonical agent callbacks and short-circuit them if they return content.
- **SOURCE-CODE OBSERVATION (MEDIUM).** Shipped plugins reveal the intended role: retry-with-reflection on tool/model errors, context filtering, global instructions, logging/debug, BigQuery agent analytics, save-files-as-artifacts. Docs' safety guidance also leans on callbacks/plugins as guardrails. **INFERENCE (MEDIUM):** Plugins are ADK's de facto policy engine; there is no declarative policy language — policy is imperative Python in the process.

### 9. Model abstraction

- **SOURCE-CODE OBSERVATION (HIGH).** `BaseLlm`: `supported_models()` (regex list), `generate_content_async(LlmRequest, stream) → AsyncGenerator[LlmResponse]`, and `connect(LlmRequest) → BaseLlmConnection` for live bidi sessions. `LLMRegistry.resolve(model)` matches regexes: native `Gemini` (Google AI Studio + Vertex variants), `anthropic_llm` (`claude-*`, optional dependency), `apigee_llm`, `gemma_llm`, then a **LiteLLM fallback for any `provider/model` string** (100+ providers). Model wire types (`LlmRequest`/`LlmResponse`) are built on `google.genai` types (`types.Content`, `types.Part`, `FunctionDeclaration`).
- **INFERENCE (HIGH).** ADK is model-*pluggable* but not model-*neutral*: the interlingua is Gemini's GenerateContent schema, and — notably — `Event` itself subclasses `LlmResponse`, so the Gemini response shape leaks all the way into the persistence layer and every event consumer. Non-Gemini providers are adapted into Gemini shapes (as Anthropic's SDK does the reverse). Live/bidi (`connect`) is effectively Gemini Live API-specific.

### 10. Tools, MCP, code execution, environments

- **SOURCE-CODE OBSERVATION (HIGH).** `BaseTool`: `_get_declaration() → FunctionDeclaration`, `run_async(args, tool_context)`, and `process_llm_request` — a tool can *rewrite the outgoing LLM request* (add instructions, config), which is how built-in tools (google_search, code execution) and the transfer tool integrate. `FunctionTool` auto-derives declarations from Python signatures. `BaseToolset` provides dynamic, context-dependent tool lists (`get_tools(readonly_context)`). Long-running tools mark `long_running_tool_ids` and pause the invocation; `ToolConfirmation` implements HITL approval; authenticated tools integrate a credential service with an auth-request/response event dance.
- **SOURCE-CODE OBSERVATION (HIGH).** Interop adapters: **MCP** (`McpToolset` consuming MCP servers; plus `_agent_to_mcp.py` and an `MCP_AGENT_SERVER` feature flag exposing an ADK agent *as* an MCP server), OpenAPI-spec toolsets, LangChain and CrewAI tool wrappers, computer-use toolset, bash tool, plus a large first-party Google portfolio (BigQuery, Spanner, Bigtable, Pub/Sub, Maps grounding, Search, Discovery Engine, Application Integration, API Hub…).
- **SOURCE-CODE OBSERVATION (HIGH).** Parallel tool execution: multiple function calls in one model turn are executed via `asyncio.create_task` + `gather`, and their responses merged into one event (`functions.py`).
- **SOURCE-CODE OBSERVATION (HIGH).** Code executors are pluggable (`BaseCodeExecutor`): model-native (Gemini code execution), unsafe local, container, GKE, Vertex, Agent Engine sandbox. Separately, a new experimental **`BaseEnvironment`** abstraction (`environment/`) defines `execute(command)`, `read_file`, `write_file`, `working_dir` with Local, and feature-flagged **Daytona** and **E2B** sandbox backends. **INFERENCE (MEDIUM):** ADK is growing a genuine "execution environment" capability (computer-use + sandboxes), converging on what Claude Code/Codex treat as primary.
- **FACT.** ADK adopted the cross-vendor **Agent Skills specification** (agentskills.io): `SkillToolset` loads skills (instructions/resources/scripts) with incremental context loading; experimental since Python v1.25.0 (docs/skills/index.md, `skills/` module).

### 11. Planners

- **SOURCE-CODE OBSERVATION (HIGH).** `BasePlanner` has exactly two methods: build planning instruction, process planning response. `BuiltInPlanner` merely passes a `thinking_config` through to Gemini; `PlanReActPlanner` is a prompt-format planner (`/*PLANNING*/`, `/*ACTION*/`, `/*REASONING*/` tags). **INFERENCE (HIGH):** "planner" in ADK is a thin prompt/thought-shaping shim, not an orchestration component; real planning is either in the model (thinking) or in the workflow graph.

### 12. Durability, resume, HITL, ambient agents

- **FACT.** `App(resumability_config=ResumabilityConfig(is_resumable=True))` makes workflows resumable after crashes/network failures (docs/runtime/resume.md, since Python 1.16). Long-running functions, confirmations, and auth interact with resumability.
- **SOURCE-CODE OBSERVATION (HIGH).** Durability is **event-sourced, not journal-replayed**: agents write `agent_state` checkpoint events (e.g., `SequentialAgentState(current_sub_agent=…)`); `Runner` resumes an invocation by `invocation_id`, repopulating `agent_states`/`end_of_agents` from the log; the Workflow engine reconstructs node status by scanning events with a replay sequence barrier and fast-forwarding completed nodes. Interrupts (`NodeInterruptedError`) implement HITL pauses; `rerun_on_resume` chooses re-execution vs. resume-with-input per node. The 2.0 docs *warn users not to catch `BaseException`* because it traps the interrupt control flow — durability leaks into user code discipline.
- **FACT.** "Ambient agents" (docs/runtime/ambient-agents.md, Python v1.29+): trigger ADK agents from cloud events (Cloud Storage, queues, schedules, Eventarc) — but the triggering infrastructure is external (Cloud); ADK itself has no scheduler.

### 13. Streaming and live

- **SOURCE-CODE OBSERVATION (HIGH).** Dual-mode from the base class up: every agent has `run_async` *and* `run_live` (`LiveRequestQueue`, `BaseLlmConnection`); `RunConfig` carries `StreamingMode` (NONE/SSE/BIDI), speech/audio transcription configs, VAD, proactivity, affective dialog, session resumption handles, and live-blob artifact capture. Live media events are diverted to artifacts rather than the session log. **INFERENCE (MEDIUM):** live mode is a second runtime path with its own state (transcription caches, realtime caches) that only partially unifies with the event-sourced model — e.g., `SequentialAgent._run_live_impl` needs a model-called `task_completed()` tool hack to know when to advance.

### 14. A2A, deployment, evaluation, observability

- **SOURCE-CODE OBSERVATION (HIGH).** A2A integration is bidirectional and adapter-shaped: `RemoteA2aAgent` consumes a remote agent (agent card → local `BaseAgent`); `A2aAgentExecutor` exposes a `Runner` as an A2A server, converting the event stream into A2A Task updates and promoting task-mode outputs into A2A artifacts (`a2a/executor/a2a_agent_executor.py`; `runners.py` docstring). Docs mark A2A support Experimental (Python/Go/Java).
- **FACT.** Deployment targets: **Agent Runtime** (formerly Vertex AI Agent Engine; docs now say "Google Cloud Agent Platform Agent Runtime"), Cloud Run, GKE (docs/deploy/). Web search corroborates the Cloud Next 2026 rebrand of Vertex AI to **Gemini Enterprise Agent Platform**, with Agent Engine → Agent Runtime, Sessions → Agent Platform Sessions, Memory Bank → Agent Platform Memory Bank. The managed runtime supplies sessions/memory/sandbox services that ADK's service interfaces plug into.
- **SOURCE-CODE OBSERVATION (MEDIUM).** Evaluation is a first-class subsystem (`evaluation/`): eval sets, per-invocation scenarios, LLM-as-judge, final-response match v1/v2, hallucination metrics, rubrics, local and Vertex-managed eval services, GCS-backed managers. The dev UI (`adk web`, the Angular `adk-web` repo) and CLI (`adk eval`) integrate it.
- **SOURCE-CODE OBSERVATION (MEDIUM).** Telemetry: OpenTelemetry instrumentation throughout (`telemetry/_instrumentation.py` context managers wrap invocations and agent runs), with experimental + stable GenAI semantic-convention modules, an Agent Engine metric exporter, and auto-tracing plugins. `RunConfig.telemetry` allows per-run config.

## Architecture decomposition

| Layer | ADK realization | Status |
|---|---|---|
| **Product/UI** | `adk web` dev UI + Visual Builder (experimental AI-assisted graph editor), `adk api_server` (FastAPI), CLI; Agent Runtime console on Google Cloud | Dev UI open source (adk-web); cloud console proprietary |
| **Agent/Harness** | `App` (deployable unit: root agent/node + plugins + compaction + resumability + context-cache config) + `Runner` (per-invocation orchestrator, service wiring, plugin sandwich) | Open source, portable across the 5 SDKs (contract documented cross-language) |
| **Planning/orchestration** | Three interchangeable strategies over nodes: `Workflow` graph (declarative edges/routes/joins/retries), dynamic `ctx.run_node` (imperative), LLM-driven (`transfer_to_agent`, task-mode delegation); legacy Sequential/Parallel/Loop agents deprecated; `BasePlanner` is only prompt-shaping | Open source; strategy choice is user-level, not kernel-level — matches "orchestration as plugin" |
| **Context construction** | `BaseLlmFlow` request-processor pipeline (instructions → compaction → contents-from-event-log with branch/isolation filtering → cache → planning); compaction summaries stored as events | Open source; pipeline order is hard-coded per flow class, extensible by subclassing |
| **Model invocation** | `BaseLlm` + `LLMRegistry` (regex dispatch) + `LlmRequest/LlmResponse` in google.genai shapes; native Gemini, Anthropic, Apigee, Gemma; LiteLLM fallback | Open source but **provider-shaped**: Gemini schema is the interlingua; live/bidi is Gemini-specific |
| **Tool selection/execution** | Declarations injected by processors; model selects; `functions.py` executes in parallel asyncio tasks; toolsets resolve per-context; MCP/OpenAPI/LangChain/CrewAI adapters; HITL confirmation + auth flows as event round-trips | Open source; MCP is the standardized edge; FunctionDeclaration format is Gemini's |
| **Environment** | Pluggable code executors (local/container/GKE/Vertex/sandbox) + experimental `BaseEnvironment` (Daytona, E2B) + computer-use toolset; no default sandbox | Open source interfaces; managed sandboxes proprietary (Agent Runtime) |
| **Observation** | Everything returns as Events on the session log; tool responses summarized or raw (`skip_summarization`); live media diverted to artifacts | Open source |
| **Verification** | No inline verifier in the loop; offline evaluation subsystem (LLM-as-judge, rubrics, trajectory match); node-level input/output schema validation and `state_schema` enforcement are the only inline checks | Open source; verification-as-eval, not verification-as-gate |
| **State update** | `append_event` is the single commit point: state deltas, artifact versions, checkpoints, compaction, rewind all fold from the log; session services in-memory/SQL/managed | Open source interfaces; Vertex-managed implementations proprietary |

**Cross-cutting**: policy = Plugins/callbacks (imperative, in-process, open source); budgets = `max_llm_calls` + node timeouts/retries (thin); protocol edges = A2A (agent↔agent, standardized, Linux-Foundation-governed) and MCP (tool edge, standardized); events themselves have **no cross-language serialized spec beyond the Pydantic/camelCase JSON schema**, though five SDK implementations plus the 2.0 schema-migration warnings show it functions as a de facto wire format.

## Precise vocabulary

- **Model**: the LLM behind `BaseLlm` (Gemini by default; `gemini-3.5-flash` is the coded default).
- **Model API**: Gemini GenerateContent shapes (`google.genai` types) used as the internal normal form in `LlmRequest`/`LlmResponse`; live bidi via `BaseLlmConnection`.
- **Model adapter**: `BaseLlm` subclasses (`Gemini`, `Claude`, `LiteLlm`, `ApigeeLlm`, `Gemma`) resolved by `LLMRegistry` regex dispatch; LiteLLM as the long-tail adapter.
- **Agent**: `BaseAgent` — a named node (subclass of `BaseNode` since 2.0) with description, sub-agent tree, and lifecycle callbacks; `LlmAgent` adds model/instructions/tools/mode.
- **Agent loop**: `BaseLlmFlow.run_async` — repeated (preprocess → call model → postprocess → run tools → maybe transfer) until a final response; surfaced as an async generator of Events.
- **Harness**: `App` + `Runner` + services. `App` is the deployable unit; `Runner` binds an agent/node tree to session/artifact/memory/credential services and drives invocations.
- **Context-management system**: the request-processor pipeline (`contents`, `instructions`, `compaction`, `context_cache_processor`) building `LlmRequest` from the event log with branch/isolation filtering; `ContextCacheConfig` for provider-side caching; `EventsCompactionConfig` for summarization.
- **Memory system**: `BaseMemoryService` (searchable cross-session store; Vertex Memory Bank managed impl), exposed as tools — distinct from session state and from context construction.
- **Tool runtime**: `functions.py` (parallel asyncio execution, merged response events) + `BaseTool/BaseToolset` + confirmation/auth/long-running machinery.
- **Execution environment**: pluggable `BaseCodeExecutor`s and the experimental `BaseEnvironment` (local/Daytona/E2B); managed sandboxes in Agent Runtime; otherwise host-process Python.
- **Planner**: `BasePlanner` — prompt/thinking-config shim (`BuiltInPlanner`, `PlanReActPlanner`). Not an orchestrator.
- **Workflow/graph construct**: `Workflow(BaseNode)` with `edges`, routes, joins, retries, timeouts, `max_concurrency`, dynamic nodes via `ctx.run_node`; deprecated Sequential/Parallel/Loop agents.
- **State/session model**: event-sourced `Session` (append-only Events) + folded `state` dict with `app:`/`user:`/`temp:` prefixes and optional Pydantic schema; artifacts as versioned blobs.
- **Delegation mechanism**: three: LLM-driven `transfer_to_agent` (tool + event action), `AgentTool` (agent-as-function), and task-mode delegation with `isolation_scope` context isolation; plus `RemoteA2aAgent` across process boundaries.
- **Protocol usage**: A2A for agent↔agent (consume + expose, experimental), MCP for tools (consume + expose an agent as an MCP server), Agent Skills spec (agentskills.io) for packaged capabilities. Internal Runner↔agent contract is in-process, not a protocol.
- **Capability discovery/negotiation**: ABSENT internally (tools are statically or contextually listed, no negotiation); at the edges, A2A agent cards and MCP listing provide discovery.
- **Policy/security layer**: Plugins + callbacks (imperative overrides), tool confirmation (HITL), auth/credential service, `state_schema` validation. No declarative policy engine, no capability tokens, no sandbox-by-default.
- **Durable-execution features**: resumability via checkpoint events + log-scan replay (`ResumabilityConfig`, `agent_state`, `rerun_on_resume`, `ReplaySequenceBarrier`), invocation resume, rewind (inverse deltas), HITL interrupts, node retries/timeouts. No external durable-execution engine (no Temporal-style journaling of arbitrary code).
- **Event system**: the `Event`/`EventActions` model over an append-only per-session log; yield-is-commit contract; queue-based handoff in the node runtime. No pub/sub, no cross-session event bus (ambient agents rely on external cloud triggers).
- **Observability**: OpenTelemetry tracing/metrics with GenAI semconv, dev-UI trace view, logging/analytics plugins, Cloud Trace integration on Agent Runtime.

## Implications for a universal runtime kernel

1. **The strongest external validation of the kernel hypothesis to date.** Google shipped "everything is an agent" (1.x), found deterministic orchestration didn't fit the agent abstraction, and within a year re-founded the system on "everything is a node emitting events, with orchestration strategies (graph / imperative / LLM-driven) as interchangeable layers." That is our hypothesis, executed at scale — including deprecating their own workflow agents. A kernel design should start where ADK *arrived*, not where it started.
2. **Yield-is-commit is a real kernel primitive.** ADK's one non-negotiable contract — a step's effects (state delta, artifact delta, checkpoint) are committed atomically when its event is accepted by the runner, and execution resumes only after commit — survived the 1.x→2.x rewrite intact and was re-implemented across a task boundary with a queue+ack handshake. This transactional event-append is a better kernel foundation than "call agent, get result."
3. **One event log, many projections — but type it.** ADK proves that state, checkpoints, undo, compaction, routing, HITL, auth, and UI can all fold from one append-only log. It also shows the cost of doing that with a single widening Pydantic class (`Event` extends `LlmResponse`; `node_info`+`output` broke downstream validators in 2.0). A kernel should keep the single log but with a versioned, typed event envelope that does *not* inherit from any model-provider shape.
4. **Keep the model shape out of the kernel.** ADK's deepest coupling is `Event(LlmResponse)` + google.genai types as interlingua: every persisted event and every adapter bends to Gemini's schema. A universal kernel must define its own content/tool-call normal form and treat provider schemas as adapter concerns — otherwise "model-independent" is one inheritance edge away from false.
5. **Context construction as an ordered processor pipeline is a proven pattern** (instructions → compaction → contents-from-log-with-visibility-filters → caching → planning). The kernel should make the pipeline itself a first-class, inspectable construct rather than hard-coded per flow class.
6. **Context visibility belongs on events, not in separate stores.** `branch` and `isolation_scope` show that multi-agent context isolation can be a *filter over the shared log*. A kernel can generalize this to a visibility/capability label on every event, giving subagent isolation, task delegation, and parallel-branch hygiene from one mechanism.
7. **Durability via log-scan replay has limits ADK is already hitting.** Resume requires rescanning all session events, deterministic replay barriers, and user discipline (don't catch `BaseException`, don't swallow interrupts, allow exceptions to reach RetryConfig). The kernel should make checkpoints explicit, first-class records (ADK's own TODO) and make interrupt/cancel a typed signal rather than an exception convention.
8. **Policy and budgets are the weakest layers — an opening.** Policy = imperative in-process plugins; budgets = one integer (`max_llm_calls`) plus per-node timeout/retry. No declarative policy, no capability grants, no cost/token budgets, no per-subtree limits. A kernel with real capability/budget/policy objects would be differentiated *and* could host ADK-style plugins as one policy backend.
9. **Protocol edges confirm the plugin thesis.** A2A (agent edge), MCP (tool edge), Agent Skills (capability packaging), LangGraph/CrewAI wrappers — ADK treats every external ecosystem as an adapter into its node/event model. A universal kernel should expect to interoperate the same way, and note that with 5 language SDKs Google is effectively evolving a de facto cross-language event schema without ever specifying it as a protocol — a standardization gap a kernel spec could fill.
10. **Verification is absent from the loop.** ADK has rich *offline* eval but no inline verifier/gate primitive (only schema validation). If the kernel treats verification as a first-class step kind (gating commits), that is a genuine architectural addition, not a repackaging of ADK.

## Open questions

1. The node runtime is mid-migration (legacy `BaseAgent` generator path vs `NodeRunner` queue path, with TODOs to unify). What is the end-state contract — and will `Workflow` become usable as an `LlmAgent` sub-agent (currently documented as not possible)?
2. Is the Event JSON schema (camelCase, five SDKs) governed as a compatibility surface anywhere, or is each language port re-deriving it? (2.0's breaking-change notes suggest no formal versioning beyond docs.)
3. How does Agent Runtime (managed) actually execute the Runner — one container per session? How do its Sessions/Memory Bank services shard the event log, and does managed resume use the same log-scan replay? (Proprietary; not determinable from source.)
4. The Gemini "Interactions API" processor implies server-side conversation state ("the service retains prior state"). How far will ADK lean on provider-side state, and what does that do to the event-log-as-source-of-truth model?
5. `BaseEnvironment` (Daytona/E2B) is feature-flagged and minimal — is ADK heading toward sandboxed-environment-first execution (Claude Code-style), and will code executors merge into it?
6. The A2A "V2 implementation" extension in the docs suggests protocol evolution — what changed in A2A v2 mapping (task lifecycle, artifacts) relative to v1?
