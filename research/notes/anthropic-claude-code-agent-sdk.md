# Anthropic Stack: Claude Code, the Claude Agent SDK, and the Model/API/Harness Boundary

Research note — 2026-08-15. Part of the universal-runtime architecture research mission.

## Scope

This note maps Anthropic's agent stack as of mid-August 2026: **Claude the model** (trained behaviors), the **Claude API** (Messages API and its server-side agentic features), the **Claude Agent SDK** (Python/TypeScript library, formerly "Claude Code SDK"), **Claude Code the product** (CLI/desktop/IDE/web), and **MCP** as the external protocol. The goal is precision about *where each mechanism lives*, because the mission is to determine which of today's concepts (agents, subagents, harnesses, hooks, skills, workflows) could become plugins over a minimal kernel of capabilities, events, artifacts, policy, budgets, and checkpoints.

Version anchors observed in the docs: Claude Code CLI v2.1.x (behaviors cited up to ~v2.1.223), TypeScript Agent SDK v0.3.219+, Python Agent SDK v0.2.127+, models through Claude Opus 5 / Sonnet 5 / Fable 5, API betas `context-management-2025-06-27` and `compact-2026-01-12`.

## Findings

### 1. The layer boundary (the key question)

**(a) Claude the model.** The model is trained to emit `tool_use` content blocks against JSON-schema tool definitions and to interleave extended thinking with tool calls. FACT: tool use is activated by a special system prompt the API injects when `tools` is present, with a *per-model* token count (e.g., Opus 5: 286 tokens for `auto`; Sonnet 5: 354) — evidence that tool-calling is partly a trained convention with model-specific prompt scaffolding, not a pure protocol. FACT: Anthropic ships "Anthropic-schema client tools" (`bash`, `text_editor`, `memory`, `computer_use`) where *Anthropic publishes the schema and trains Claude on it* but the client still executes the call — a distinct category between user-defined tools and server tools, existing purely because of training. FACT: the `effort` parameter (`low`→`max`) is a model-level knob; docs recommend `xhigh` on Fable 5/Opus 4.7+/Sonnet 5. FACT (behavioral, documented): "Claude Opus 5 delegates to subagents more readily than earlier models," and the Claude Code system prompt adds a model-conditional line suppressing Agent-tool use on Opus 5 — the harness compensates for model-version behavioral drift in its prompt. INFERENCE (HIGH): the loop's termination condition ("stops when a response has no tool calls") means *task-completion judgment lives in the model*, and the harness merely detects the absence of tool calls.

**(b) The Claude API (Messages API).** Stateless HTTP: client sends full message history each call; `stop_reason: "tool_use"` hands control back. Three server-side agentic services have migrated *into* the API:
- **Server tools** (`web_search`, `web_fetch`, `code_execution`, `tool_search`, MCP connector, advisor tool) execute on Anthropic infrastructure inside a single API call (FACT).
- **Context editing** (beta `context-management-2025-06-27`): server-side strategies `clear_tool_uses_20250919` and `clear_thinking_20251015` prune tool results/thinking blocks before the prompt reaches the model, while "your client maintains the full unmodified history" (FACT). Explicit cache-invalidation tradeoffs are documented.
- **Server-side compaction** (beta `compact-2026-01-12`, type `compact_20260112`): the API detects a token threshold (default 150k), generates a summary, and returns a `compaction` content block; on subsequent requests "the API automatically drops all content blocks prior to the compaction block" (FACT). Docs call it "the recommended strategy for managing context in long-running conversations." This is a major boundary shift: compaction, historically the harness's flagship job, is now an API primitive.
- **Prompt caching** is an API feature the harness exploits automatically (FACT).

**(c) The Claude Agent SDK.** SOURCE-CODE OBSERVATION (HIGH): the SDK is a *thin supervisor*, not a reimplementation. `query()` spawns a bundled native `claude` CLI binary as a subprocess and speaks newline-delimited JSON over stdio (`--input-format stream-json --output-format stream-json --verbose`), with a `_LineFramer` reassembling 64KB anyio chunks, a 1MB message buffer, and options translated to CLI flags (`--system-prompt`, `--allowedTools`, `--resume=<id>` in equals-form to prevent flag injection, `--mcp-config`, `--plugin-dir`, merged `--settings` JSON). FACT: "Both the TypeScript and Python SDKs bundle a native Claude Code binary… The bundled binary is pinned to the SDK package version, so updating the SDK is how you update the CLI." So the agent loop itself lives in the (closed-source) CLI binary; the SDK contributes the host-process surface: the message stream, hooks-as-callbacks, `canUseTool`, in-process MCP servers ("custom tools"), programmatic `agents`, `SessionStore` adapters, structured outputs, and budget/turn caps. FACT: the loop yields five core message types — `SystemMessage` (subtypes `init`, `compact_boundary`, `informational`, `worker_shutting_down`, `mirror_error`), `AssistantMessage`, `UserMessage` (tool results), `StreamEvent`, `ResultMessage` (subtypes `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, `error_max_structured_output_retries`, plus `stop_reason` including `refusal`).

**(d) Claude Code the product.** The CLI binary is simultaneously the product and the runtime the SDK embeds. Product-only layers: terminal/desktop/IDE/web/Slack UIs, permission-prompt UX (Shift+Tab mode cycling), checkpoint rewind (double-Esc), `/commands`, bundled skills (`/code-review`, `/deep-research`, `/doctor`…), agent view/agent teams, the `/workflows` progress UI, managed enterprise settings, and the OS sandbox integration. FACT: the docs explicitly name the harness role: "Claude Code serves as the **agentic harness** around Claude: it provides the tools, context management, and execution environment that turn a language model into a capable coding agent."

**(e) MCP.** The external protocol boundary. Claude Code is an MCP *client* supporting stdio, HTTP, SSE, and in-process ("SDK") servers; tools are namespaced `mcp__<server>__<tool>`; MCP tool schemas are *deferred by default* via tool search and loaded on demand; tool results over 25,000 tokens are spilled to a file and replaced with a path (FACT). MCP elicitation surfaces as hook events (`Elicitation`/`ElicitationResult`). OAuth is deliberately not handled interactively — the host app must supply tokens (FACT).

**Portability verdict.** The loop shape, hook event model, permission pipeline, session log, and MCP client are model-agnostic *in design* and would port. What assumes Claude: the tuned system prompt (including model-conditional lines), effort levels and model aliases (`opus`/`sonnet`/`haiku`/`fable`), trained Anthropic-schema tools, reliance on API-side caching/compaction/tool-search, and the auth path (Anthropic API/Bedrock/Vertex/Foundry only). FACT: Anthropic's terms prohibit third parties from offering claude.ai login on SDK-built agents; the SDK is not offered as a bring-your-own-model harness.

### 2. The agent loop

FACT: the documented cycle is (1) receive prompt + system prompt + tool definitions + history; (2) model responds with text and/or tool calls; (3) harness executes tools, feeds results back; (4) repeat; (5) when a response contains no tool calls, emit final result. "A turn is one round trip inside the loop." `max_turns` counts tool-use turns only; `max_budget_usd` caps estimated spend, enforced across the whole subagent tree since Claude Code v2.1.217 (spawning fails with `Budget limit reached`, running background subagents are stopped). FACT: the conceptual framing is "gather context → take action → verify results," with verification explicitly a phase the *model* performs using tools (running tests, comparing screenshots) — there is no separate harness-level verifier. FACT: parallel tool execution is annotation-driven: read-only tools (and MCP tools marked `readOnlyHint`) run concurrently; mutating tools run sequentially.

### 3. Hooks — the event system

FACT: 32 lifecycle events as of the current docs, spanning session lifecycle (`SessionStart`, `Setup`, `SessionEnd`), prompt lifecycle (`UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `StopFailure`), tool lifecycle (`PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`), subagent lifecycle (`SubagentStart`, `SubagentStop`), task tracking (`TaskCreated`, `TaskCompleted`), compaction (`PreCompact`, `PostCompact`), config/environment watching (`ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `InstructionsLoaded`, `WorktreeCreate`/`Remove`), MCP elicitation, teams (`TeammateIdle`), and display (`Notification`, `MessageDisplay`). FACT: five handler types — `command` (shell, JSON on stdin), `http` (POST), `mcp_tool`, `prompt` (single-turn LLM evaluation), and `agent` (experimental subagent verification). The last two are notable: *the event system can itself invoke models as policy evaluators.* FACT: exit code 2 blocks on blockable events with stderr surfaced to the model; JSON output carries typed decisions (`permissionDecision: allow|deny|escalate`, `updatedInput`, `additionalContext`, `continueLoop`). FACT: hooks are configured in settings files, plugins, skill frontmatter, and subagent frontmatter, and (SDK) run "in your application process, not inside the agent's context window." INFERENCE (HIGH): hooks are the closest thing in this stack to a kernel event bus — typed events, matcher-based subscription, synchronous veto semantics, multiple handler runtimes.

### 4. Permissions — the policy layer

FACT: a fixed six-step pipeline evaluates every tool call: **hooks → deny rules → ask rules → permission mode → allow rules → canUseTool callback**. Deny rules and hooks apply even in `bypassPermissions`. Bare-name deny rules remove the tool definition from the request entirely (the model never sees the tool); scoped rules (`Bash(rm *)`) filter calls. Rule specifiers include path anchoring semantics (`//abs` vs `/relative-to-source`). Modes: `default`, `acceptEdits`, `plan`, `dontAsk`, `auto` (a *model classifier* adjudicates prompts), `bypassPermissions`. FACT: subagents inherit the parent's mode; `bypassPermissions`/`acceptEdits`/`auto` cannot be overridden per-subagent. FACT: `allowed-tools` in skill frontmatter grants permissions *for one turn only*, cleared on the next user message — a scoped, expiring capability grant. OBSERVED DESIGN (HIGH): the docs repeatedly distinguish "context, not enforced configuration" (CLAUDE.md) from "enforced by the client regardless of what Claude decides" (settings/hooks) — a clean two-tier trust model of persuasion vs enforcement.

### 5. Sandboxing and the execution environment

FACT: the sandboxed Bash tool uses OS primitives — Seatbelt on macOS; bubblewrap (filesystem namespaces) + socat (network relay) + optional seccomp filter (Unix-socket blocking) on Linux/WSL2 — enforcing per-command filesystem and network rules so most commands run *without* permission prompts. FACT: network egress goes through a sandbox proxy with domain allowlists; credential *masking* replaces secrets with per-session sentinels inside the sandbox and re-injects real values at the proxy for allowlisted hosts (requires proxy TLS termination; AWS requests are re-signed). FACT: when the sandbox blocks a command, violation details are appended to the command output *so the model can see what was blocked*, and Claude may retry with `dangerouslyDisableSandbox`, which re-enters the normal permission flow; `allowUnsandboxedCommands: false` closes this escape hatch. INFERENCE (MEDIUM): this is a deliberate three-way design — sandbox for cheap default containment, permission prompts for exceptions, model-visible violation feedback for self-correction — rather than hard isolation.

### 6. Context construction and management

What enters context (FACT): system prompt (preset `claude_code` or custom), CLAUDE.md chain (managed-policy → user → project → local, concatenated root-down; *delivered as a user message after the system prompt, not in the system prompt*), `.claude/rules/*.md` (path-scoped rules lazy-load on file match), auto memory (first 200 lines / 25KB of MEMORY.md), skill *descriptions* (bodies on invocation), tool schemas (MCP schemas deferred via tool search), then accumulating conversation.

Compaction (FACT): Claude Code "clears older tool outputs first, then summarizes the conversation if needed" — a two-stage strategy (tool-output clearing ≈ what the community calls microcompaction, then full summarization). Auto-compaction emits `compact_boundary`; `PreCompact` (blockable) and `PostCompact` hooks fire; CLAUDE.md is re-read and re-injected after compaction; nested CLAUDE.md and path-scoped rules are not until re-triggered. Compaction is steerable via a CLAUDE.md "summary instructions" section matched *on intent, not a magic string* (FACT). Invoked skills survive compaction under an explicit token-budget policy: most-recent invocation of each skill re-attached, first 5,000 tokens each, 25,000-token shared budget (FACT). A thrashing detector stops auto-compaction with an error if context refills immediately (FACT). INFERENCE (HIGH): given API-side `compact_20260112`, the client-side compactor is likely to become a fallback; the docs already recommend the server-side path for API users.

Context-engineering doctrine (from the engineering blog, via secondary sources — MEDIUM confidence on exact wording): context is a "finite attention budget"; "context rot" degrades performance with length; the three sanctioned strategies are compaction, structured note-taking (memory files outside the window), and sub-agent architectures returning "compact summaries" to a coordinator. Claude Code implements all three natively (auto-compact, auto memory, Agent tool).

### 7. Subagents and delegation

FACT: delegation is a tool call. The `Agent` tool (renamed from `Task` in v2.1.63; the `system:init` tools list still says `Task` — a live inconsistency) spawns a fresh session: own system prompt (`AgentDefinition.prompt`), the Agent-tool prompt string as its only parent-supplied input, project CLAUDE.md, and a tool subset; it does *not* receive parent history. Only the final message returns to the parent as the tool result. FACT: since v2.1.198 subagents run in the **background by default**; Claude sets `run_in_background: false` when it needs the result to continue. FACT: resource caps are environment variables plus one option: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (default 3), `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20), `maxBudgetUsd` (tree-wide). FACT: subagents persist their own transcripts and are *resumable* by `agentId` within a resumed session. FACT (security): since v2.1.210 the harness scans subagent final messages for instruction-shaped patterns before the parent reads them — neutralizing imitation `<system-reminder>` tags, flagging permission-config mentions with a `[harness: …]` marker, escaping `Human:`/`Assistant:` turn markers — an explicit prompt-injection defense at the inter-agent trust boundary. Related: agent teams (peer sessions with a shared task list and `SendMessage`), and forks (`context: fork` skills / `--fork-session`) which *do* inherit parent conversation.

### 8. Skills, plugins, commands

FACT: a skill is a directory with `SKILL.md` (YAML frontmatter + markdown body) plus optional supporting files/scripts; Claude Code follows the **agentskills.io** open standard (six spec fields) and extends it (invocation control, `context: fork`, hooks, `paths`, model/effort overrides, dynamic context injection via `` !`command` `` lines executed *before* the model sees the content). FACT: progressive disclosure is the core economic mechanism: descriptions load at session start; bodies load on invocation and persist in context; `disable-model-invocation: true` keeps even the description out of context. Custom slash commands have been merged into skills. FACT: plugins package skills + agents + hooks + MCP servers + workflows under a namespace, distributed via marketplaces. INFERENCE (HIGH): skills are *pure context artifacts* — no code contract; their power comes from convention (frontmatter → capability metadata; body → lazily-loaded instructions; bundled scripts → executed through the ordinary Bash tool under ordinary permissions).

### 9. Dynamic workflows — the graph construct

FACT: a dynamic workflow is a JavaScript script (written by Claude, saveable and re-runnable as a command) executed by a runtime *outside the conversation*: "the script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer." Primitives: `agent(prompt, {schema, label})` spawns one subagent (with JSON-schema-validated output), `pipeline(list, fn)` fans out. Runtime constraints (FACT): no user input mid-run, no direct filesystem/shell access from the script, no `import()`, ≤16 concurrent agents, ≤1,000 agents/run, 5s prompt-cache stagger for identical-prefix fan-outs. Runs are resumable within a session with completed-agent results replayed from cache (order-dependent). The `ultracode` effort mode makes Claude plan workflows autonomously. INFERENCE (HIGH): this is Anthropic's answer to graph frameworks — orchestration as *generated imperative code against two primitives*, not as a declarative graph DSL; determinism/repeatability come from saving the script.

### 10. Sessions, state, durability

FACT: the session is an append-only JSONL transcript at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`. `continue` = most recent session in cwd; `resume` = by ID (cross-directory lookup since v2.1.223); `fork` = copy history into a new ID. Subagent transcripts are separate files. `SessionStore` adapters mirror transcript batches to S3/Redis/Postgres (dual-write; mirror failures emit `mirror_error` and drop the batch — best-effort durability). `persistSession: false` keeps a session memory-only. FACT: file checkpointing is a *separate* mechanism: pre-edit snapshots of affected files, rewindable, explicitly not covering external side effects ("Actions that affect remote systems… can't be checkpointed, which is why Claude asks before running commands with external side effects"). FACT: there is no top-level session timeout and no per-subagent wall-clock deadline (a stall watchdog exists for background subagents only) — durability is log-replay-based, not workflow-engine-based; a crashed run resumes only from its transcript, and in-flight work is lost.

### 11. Observability and budgets

FACT: OpenTelemetry export of traces/metrics/logs via standard OTEL env vars (`CLAUDE_CODE_ENABLE_TELEMETRY=1`; traces additionally gated by `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`); prompt text and tool inputs excluded by default. Cost accounting: `total_cost_usd`, `usage` (main loop only), `model_usage` (whole agent tree). Budgets: `maxBudgetUsd` is the only first-class monetary budget; turns via `maxTurns`; everything else (depth, concurrency) is env vars. INFERENCE (MEDIUM): budget enforcement arriving late (v2.1.217 for tree-wide) and via mixed mechanisms suggests budgets were retrofitted, not a kernel primitive.

## Precise vocabulary

- **Model**: Claude (Opus 5/Sonnet 5/Fable 5 etc.) — trained tool-use emitter and sole planner/terminator of the loop.
- **Model API**: Anthropic Messages API (plus Bedrock/Vertex/Foundry variants). Stateless; hosts server tools, context editing, server-side compaction, prompt caching, tool search.
- **Model adapter**: ABSENT. No abstraction for non-Claude models anywhere in the stack; "model" options accept only Claude aliases/IDs.
- **Agent**: an application embedding the loop (SDK framing), or a named `AgentDefinition` (subagent framing). Overloaded term, resolved by context.
- **Agent loop**: evaluate → tool calls → execute → feed back → repeat until a no-tool-call response; turn = one round trip.
- **Harness**: Claude Code itself — Anthropic's own documented term ("agentic harness"): tools + context management + execution environment around the model.
- **Context-management system**: layered — startup assembly (system prompt, CLAUDE.md, rules, memory index, skill descriptions), in-loop accounting, two-stage auto-compaction, skill re-attachment budgets, deferred tool schemas; increasingly delegable to API-side compaction.
- **Memory system**: CLAUDE.md (human-authored, four tiers) + auto memory (model-authored MEMORY.md index + topic files, size-gated) + the API-level `memory` tool (client-executed, separate feature).
- **Tool runtime**: in-process built-ins + sandboxed Bash + MCP client (4 transports) + in-process SDK MCP servers + Anthropic server tools. Naming (`mcp__s__t`), annotations (`readOnlyHint`), and output-size spill are runtime policies.
- **Execution environment**: the CLI subprocess's cwd/shell/filesystem; sandbox + proxy; local, Anthropic cloud VM, or self-hosted runner.
- **Planner**: ABSENT as a component. Planning is model reasoning; "plan mode" is a permission stance; workflows are model-*written* plans as code.
- **Workflow/graph construct**: dynamic workflows — generated JS scripts over `agent()`/`pipeline()`, executed by an out-of-conversation runtime; saved as commands. No declarative graph.
- **State/session model**: append-only JSONL transcript keyed by session ID; continue/resume/fork; separate subagent transcripts; SessionStore mirroring; file checkpoints as a parallel undo log.
- **Delegation mechanism**: the Agent tool (fresh-context child session, result-as-tool-result, background by default), plus forks (shared history), agent teams (peer sessions + shared tasks + SendMessage), and workflows (scripted fan-out).
- **Protocol usage**: MCP for external tools (client role); agentskills.io for skills; OTEL for telemetry; NDJSON-over-stdio as the internal SDK↔CLI control protocol (undocumented publicly, observed in SDK source).
- **Capability discovery/negotiation**: partial — MCP tool listing + tool search (deferred schemas); skill descriptions as discoverable capability metadata; no negotiation protocol.
- **Policy/security layer**: the six-step permission pipeline + hooks (pre-everything veto) + OS sandbox + subagent output scanning + workspace trust dialogs + managed enterprise settings. Two-tier: context-persuasion vs client-enforcement.
- **Durable-execution features**: transcript replay (resume/fork), SessionStore, workflow per-agent result caching, file checkpoints. No wall-clock deadlines, no exactly-once semantics, no external-effect journaling.
- **Event system**: hooks — 32 typed lifecycle events, matcher subscription, 5 handler runtimes (including LLM-as-handler), blocking semantics; plus "channels" for pushing external events into a running session.
- **Observability**: OTEL traces/metrics/logs; message stream itself as an observability feed; cost/usage on every result.

## Implications for a universal runtime kernel

1. **The entire stack reduces to four primitives already**: (i) a model call, (ii) a tool call, (iii) a typed event with veto semantics, (iv) an append-only transcript. Subagents are (new transcript + tool call); skills are (lazy artifact + context insertion + expiring grant); workflows are (external program invoking the subagent primitive); checkpoints are (artifact snapshots keyed to transcript positions). This is strong evidence the mission's kernel hypothesis is viable — Anthropic effectively built one, just hard-coded and Claude-locked.
2. **Policy must be an ordered pipeline with non-bypassable stages.** The hooks→deny→ask→mode→allow→callback order, with deny-and-hooks surviving `bypassPermissions`, is a proven capability-evaluation design; a kernel should make the pipeline itself declarative and let "modes" be plugins.
3. **Separate capability *metadata* from capability *payload*.** Progressive disclosure (skill descriptions vs bodies, deferred MCP schemas via tool search, lazy rules/nested CLAUDE.md) is the single most consequential context-economy mechanism; a kernel should address descriptions and bodies as distinct artifacts with independent lifecycles.
4. **Context management is migrating server-side** (API context editing + `compaction` blocks). A kernel should model compaction/checkpointing as *events with pluggable executors* (client, server, or provider-API), not as a fixed harness function — this is exactly where provider capabilities will keep differing.
5. **Budgets are currently bolted on** (env vars for depth/concurrency, one USD cap, no deadlines). A kernel should make budget (tokens, money, wall-clock, spawn-tree size) a first-class, hierarchical resource attached to every execution scope, with the documented pattern (refuse-spawn, stop-background-children, typed error result) as the enforcement contract.
6. **Trust labels at agent boundaries are a real, shipped need**: subagent output scanning, synced-skill sanitization, human-origin stamping for the `ultracode` keyword, hook-source trust rules. A kernel should carry provenance/taint metadata on every message and artifact rather than pattern-scanning text after the fact.
7. **Orchestration-as-generated-code beats graph DSLs in this stack**: the Workflow runtime shows that once you have a subagent primitive with schema-validated outputs plus a sandboxed script runtime, graphs become ordinary programs — and repeatability comes from persisting the program as an artifact. A kernel needs a deterministic script sandbox with only kernel-API bindings, not a graph engine.
8. **Event-sourced sessions are the durability model that works with LLM nondeterminism**: replayable transcripts with fork-as-copy, plus result-caching keyed by start order (workflows). But the gaps (no external-effect journal, best-effort mirroring, no deadlines) mark exactly what a kernel must add for production durability.
9. **The model boundary is thinner than it looks but not zero**: loop mechanics port to any tool-calling model, but termination judgment, delegation eagerness, and effort semantics are model-behavioral, and Anthropic patches them in the system prompt per model version. A universal kernel needs a per-model *behavior profile* (prompt fragments, caps, defaults) as part of its model-adapter contract — the one component this stack conspicuously lacks.

## Open questions

1. The CLI binary is closed-source: the exact system prompt assembly order, compaction prompts, and the internal control protocol (`initialize` control requests over stdio) are only observable, not documented — how stable is that protocol as an integration surface?
2. How does Claude Code's client-side compactor interact with API-side `compact_20260112` when both are available — does the harness already delegate, and on which surfaces?
3. Managed Agents (Anthropic-hosted REST agent runtime) vs Agent SDK: does Managed Agents run the same CLI engine, and does it expose hooks/permissions parity? (Docs list a distinct built-in toolset.)
4. Workflow runtime internals: what sandbox executes the JS (the docs say no `import()`, no fs) — is it the same seccomp/bubblewrap machinery or a JS-level isolate?
5. Agent teams' shared task list and cross-session messaging: what is the consistency model, and is the task list a kernel-worthy artifact type?
6. How far does the `auto` permission mode's model classifier generalize — is a policy-LLM-in-the-loop a dependable kernel pattern or a product convenience?
