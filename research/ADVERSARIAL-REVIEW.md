# Adversarial Architecture Review — full record

Ten reviewers (eight personas + two auditors), run against the complete document set, the design spine, the open-issues register, and the prototypes.


## Distributed-systems architect (15 years: consensus protocols, event stores, workflow engines)

**Useful-layer verdict:** QUALIFIED-YES. The gap map is real: hierarchical metered grants, commit-point verification, and a portable execution-record format genuinely do not exist in MCP/A2A/LangGraph/MAF/Temporal, and the journal+checkpoint composite is the shape four ecosystems independently patched toward from both directions — that is primitive-layer material, not repackaging. But a primitive layer earns the name only when its concurrency and recovery semantics are closed under composition, and today the composite's semantics are not: fork-vs-dedup, cell-vs-computation granularity, and cross-node identity are all open exactly where a kernel must be airtight. As specified it is a very good design sketch of a primitive layer with an abstraction layer's level of rigor at the joints; the difference is decidable with a formal spec and three measurements, none of which have been done.

**Vote:** BUILD WITH CHANGES — The BUILD half: the differentiators (grant lineage with budgets, commit-gate verification, published record format) are structural and the EXTEND rejection is credible — I probed it and agree you cannot retrofit unforgeable budget lineage or a kernel commit gate into LangGraph's checkpointer contract or MAF's middleware model without breaking their public APIs; both are correctly kept as integration targets. The prototypes are unusually honest and actually validated the universality and grants-as-lineage claims. The WITH CHANGES half: three of my findings (fork/dedup incoherence, cell-granularity mismatch, unmeasured crossing cost) sit at the exact points where workflow engines historically die — I have watched two commercial event-store products fail on precisely the 'checkpoint is a cache, journal is truth, except when we fork' ambiguity Kyxo currently has. These are specifiable-and-fixable, not thesis-invalidating, which is why this is not DO NOT BUILD; but building the storage interface before writing the fork/dedup/checkpoint state machine down formally would bake the incoherence into the 'forever-contract' record format the program itself says is the product. Sequence the fixes as Wave-0 gates and the program is sound.

**Strongest objection:** The checkpoint composite is advertised as the reconciliation of journal-as-truth with cheap resume, but its semantics are undefined for the one operation the whole failure story rests on: fork-from-checkpoint when the parent journal extends past the cut. The prototype hit this (replay rebuilds past the checkpoint; restore can only validate), and the design's answer — fork lineage — renames the problem instead of solving it: nobody can say today whether a forked lineage's idempotency-key matching consults the inherited dedup state (re-executing world effects the parent suffix already committed) or the shared journal (injecting post-cut outcomes, i.e., replaying past the cut). Combined with ADR-009's self-cancelling mitigation — definition hashes in keys are vacuous within a lineage and destroy effect reuse across forks — the 'primary repair and upgrade verb' has no consistent specification. I will not vote to freeze a forever-contract record format until the journal/checkpoint/fork/dedup state machine is written down formally and shown consistent; if it cannot be, the composite decision itself must be reopened, and that is a go/no-go matter, not polish.

**MVP changes:** CUT cross-node checkpoint-transfer migration from V1 entirely: keep the portable record format plus an offline export/import format test, drop the live migration verb — it currently drags undesigned chain-anchoring, seq-continuity, and grant-rerooting problems into the MVP for zero validated demand (ADR-016 itself rates single-node sufficiency an assumption).; CUT Kind multi-version serving with conversion machinery from the MVP: single storage version + schema validation + watch streams is enough to validate the CRD bet; conversion webhook-equivalents are pure carrying cost before any userland Kind has ever needed a v2.; ADD a Wave-0 crossing-cost microbenchmark with a published budget (journal append + N-stage policy route + depth-D grant decrement per invocation commit, p50/p99, SQLite and JSONL) as a hard exit gate — the design's own admission rule demands a number that does not exist.; ADD an executable formal specification (TLA+ or property-test suite) of the journal/checkpoint/fork/dedup state machine — covering fork-with-parent-suffix, fork-with-pending-invocations, and lineage-scoped key matching — as a Wave-0 deliverable that must close before the record-format schema freezes.; ADD the kernel-enforced commit gate to the MVP kernel: both the harness and graph prototypes independently proved the claimed core differentiator ('verification at the commit point') exists only as userland convention today; a differentiator that is not in the kernel is marketing.

### Findings

- **[FATAL]** *ADR-002 (Decision §2), ADR-009 (Decision §4), doc 08 §6.4–6.5 + §7.1 (dedup state in the checkpoint composite)*
  - Attack: The checkpoint composite, fork-from-checkpoint, and journal-as-truth are mutually incoherent, and the prototype already hit the incoherence (replay rebuilds PAST the checkpoint; restore() can only validate, never rewind — kernel.ts:769-786). Concretely: fork cell c2 from ck7 at pos 4180 while the parent journal contains commits at 4181+ for invocations that were 'pending' in ck7. The forked lineage inherits ck7's dedup state, which says those keys are uncommitted — so re-leasing pending invocations re-executes external effects the world already saw (duplicate world effects presented as safe repair). Alternatively, if key matching consults the shared journal, the fork injects outcomes produced AFTER the cut under the abandoned definition — replay-past-the-checkpoint in a different guise, the exact bug the composite claims to prevent. The docs never say which store governs key matching in a forked lineage. Fork lineage papers over the prototype finding: it renames the reconciliation problem (which lineage's dedup state is authoritative) without solving it, and 'fork is the primary repair verb' (spine §7) is therefore a verb without defined semantics for the one case that matters — repair after post-checkpoint effects. Doc 13's scenario E (irreversible effects repair by compensation, contradicting spine §7) is the authors brushing against this without seeing that it is not an edge case but the general case of every fork whose parent suffix contains effects.
  - Resolution: Before any storage-interface freeze: write the journal/checkpoint/fork/dedup interaction as a small formal spec (TLA+ or executable property tests over the prototype) covering (a) linear crash recovery, (b) fork with non-empty parent suffix, (c) fork with in-flight pending invocations, (d) key lookup scope per lineage. Likely shape of the fix: effect-identity is lineage-scoped by default; forking with pending invocations requires an explicit per-invocation disposition (adopt-commit-from-parent-suffix / re-lease / compensate), journaled as part of kyxo.cell.forked; world-effect divergence between lineages becomes a first-class documented state, and doc 13's compensation carve-out is promoted into ADR-002 as normative. If this spec cannot be written consistently, the composite decision itself must be reopened.

- **[SERIOUS]** *ADR-009 (Negative consequence 1: idempotency-key matching vs orchestration drift) and doc 08 §7.1 key derivation*
  - Attack: The drift risk is understated and the stated mitigation is self-defeating. Quantified: with position-derived keys — doc 08 §7.1 specifies (cellId, turn/step, spawn path) — the common editing operation on AI code (change a prompt, swap tool A for tool B at the same call site, insert one step) preserves key coordinates while changing semantics; key matching silently injects a stale outcome in essentially 100% of same-arity edits, where positional matching flags 100% of them. The mitigation 'key derivation includes definition hashes' is vacuous inside a lineage (refuse-then-fork means the definition hash is constant within a lineage, so it never discriminates) and destructive across forks (a fork with an amended definition gets all-new keys, hence zero injection of recorded effects — contradicting ADR-009 Decision §4's 'recorded effects are reused up to the fork point' for anything not already folded into the snapshot, and re-buying tokens is the exact cost Alternative B was rejected for). Meanwhile the docs disagree with each other: doc 08 §7.1 says position-derived keys, doc 10's generated-code section says (script hash, call-site, iteration counters, args hash), and the graph prototype used content-derived keys (planId + nodeId + hash(winner+input)) — which is the only variant that actually bounds the drift risk, because a semantically different invocation produces a different args hash.
  - Resolution: Design change plus honest wording: mandate content-inclusive key derivation (args hash mandatory, position optional) as the kernel default; specify collision semantics for nondeterministic control flow (doc 10's admitted open case); and rewrite ADR-009's consequence to state plainly that Kyxo trades Temporal's drift detection for content addressing, quantifying what each catches. Add a conformance test: edit-harness-then-recover must either re-execute or fail loudly, never inject a semantically stale outcome.

- **[SERIOUS]** *doc 08 §7.1 (dedup windows), graph-prototype delta-execution finding, doc 08 §6.4 (dedup state in checkpoint)*
  - Attack: Two mechanisms with opposite requirements are conflated under one idempotency key. Reliability dedup needs a bounded window (dedupTTL ≥ maxRetryHorizon — correct, and the bind-time coupling rule is good engineering). Memoization/delta-execution — the graph prototype's celebrated 'delta execution fell out of kernel idempotency for free' — needs indefinite, content-keyed retention. The prototype only worked because of the dedup-window-forever cheat (kernel.ts:485). Under the real bounded window, re-running plan v2 a week later silently re-executes every 'unchanged' node: budget re-charged, non-idempotent external effects re-performed, with no signal to the caller. Worse, doc 08 §6.4 puts dedup-window state inside the checkpoint composite: if the window is extended to serve memoization, checkpoint size grows monotonically with invocation count — the exact LangGraph DeltaChannel growth pathology ADR-002 cites as a failure to avoid. And the prototype's lookup order is an authority bypass in miniature: invoke() consults the idempotency table BEFORE grant revocation and policy checks (kernel.ts:483-488), so a caller under a revoked grant can retrieve cached outcomes with zero policy evaluation — the spec never states whether a dedup hit re-runs policy.
  - Resolution: Split the mechanisms: (1) reliability dedup — bounded, epoch-fenced, in the checkpoint composite, kernel-owned; (2) memoization — a separate content-addressed result cache over the CAS with explicit TTL/eviction, consulted by strategies, never conflated with exactly-once. Specify that dedup hits re-evaluate grant validity and deny-class policy stages before returning a cached outcome. Surface bounded-window re-execution in the contract as doc 06 axis data (the graph prototype's own caveat, promoted to normative text).

- **[SERIOUS]** *doc 05 §2.6 Cell / §2.8 Checkpoint ('consistent cut'), prototype reentrancy finding, doc 07 §7.3 migration*
  - Attack: Single-writer cells plus no-default-reentrancy forces child invocations into fresh cells (prototype: the promise-chain deadlocks otherwise; kernel.ts:489 silently creates an 'auto:' cell per unhomed invocation). Consequence the docs never confront: the consistency unit (one cell) is strictly smaller than the computation unit (a harness run plus its children scattered across auto-cells). A Checkpoint is a 'named consistent cut of a cell' — but the harness cell's pending-invocations set references invocations executing in OTHER cells whose journals are not part of the cut. There is no multi-cell atomic checkpoint, so: fork of the harness cell does not fork its children's lineages; migration by checkpoint transfer moves one cell and strands its children on the source node; and 'consistent cut of the computation' — the property recovery, fork, and migration all actually need — does not exist as a kernel object. Fresh-cell-per-child also inflates cell count by roughly (turns × tools-per-turn) per run, each with its own journal partition, checkpoint lineage, and scheduler queue — a locality and bookkeeping cost presented nowhere. Orleans and Restate both solved this (reentrant call chains / shared handlers) precisely because 'no reentrancy, spawn a new grain' was measured and rejected at scale; the spine adopts their grain and drops their solution.
  - Resolution: Design change required before build: either (a) causal reentrancy — a child invocation carrying its ancestor chain may re-enter an ancestor cell's turn (the Orleans call-chain reentrancy model), or (b) promote the cell-tree to a kernel concept with a coordinated cut (checkpoint of a cell subtree, cheap because children created within a turn quiesce with the parent). Then re-state Checkpoint's definition honestly: a cut of a cell tree, or a documented non-guarantee about children. The prototype should demonstrate whichever is chosen; today it demonstrates the deadlock.

- **[SERIOUS]** *doc 05 §1 (Mach corollary as admission rule) + §7.4 (cheap-path bet), doc 07 §8.2, doc 04 self-report (unbuilt prototype task #4)*
  - Attack: The L4 lesson is invoked as constitutional law — 'an isolation boundary is admitted only with a published crossing benchmark inside budget' — while the design ships zero measurements of its own crossing. Liedtke's contribution was not the slogan; it was a measured order-of-magnitude number that falsified Mach. Kyxo's per-invocation truth-plane cost is at minimum: two journal appends (submitted + terminal transition), the full policy route, grant decrement up the entire ancestor lineage, hash-chain computation, and canonical serialization — and the Task-vs-Invocation unification (doc 05 §7.4) bets the ergonomics of every trivial call on this being 'near-free', explicitly flagged as unmeasured. The only number in the entire evidence base is DBOS's (one DB write per step, >40K/s on Postgres), which supports feasibility of a much thinner pipeline than Kyxo's. Prototype task #4 (measure policy-pipeline + journal-append overhead per crossing) was self-assigned and never executed. This is invoking the L4 lesson without the L4 discipline, and the failure mode is exactly Mach's: a correct minimal architecture that loses to monoliths on the hot path.
  - Resolution: Measurement, promoted to a gate: Wave-0 exit criterion is a published crossing microbenchmark (p50/p99 per invocation commit: journal append + policy route of N stages + lineage decrement of depth D, in-process, SQLite and JSONL backends) against a stated budget (propose: p50 ≤ 100µs at N=6, D=4, i.e., invisible next to a 1ms tool call and 500ms model call). If the number misses, the cheap-path bet and the two-events-per-trivial-call envelope get redesigned before the record format freezes, not after.

- **[SERIOUS]** *ADR-016 / doc 07 §7.3 (distribution by checkpoint transfer), doc 07 §4 ('causation is a tree', 'blast radius computed from the journal')*
  - Attack: This is a cold-migration story marketed as a distribution story. What actually transfers is (position, snapshot, pending, definition hash) plus CAS closure — the journal does not ship. After migration: the hash chain's anchoring across nodes is unspecified; seq continuity is unspecified; and every headline audit claim quietly assumes one journal — 'blast radius computed from the journal' (doc 08 row 12), 'causation is a tree rooted at e1' (doc 07 §4), provenance-driven fork of affected cells — none of these queries has a defined cross-node execution model, because there is no journal federation surface at all. Grants are worse: 're-validating and re-attenuating grants at the target node's policy root' (doc 07 §7.3) means the migrated cell's charges stop rolling up to the origin root — hierarchical budget lineage, differentiator #1 in the gap map, is domain-local by construction and dies at the first migration. ADR-016 admits each piece separately ('federation guarantees degrade at every edge', 'grants do not cross') but the program-level documents keep presenting portable checkpoints as 'the distribution story' without conceding that every flagship invariant is single-node-scoped. Cross-node causation identity is asserted in doc 07 self-reports as 'asserted but not designed' — I confirm: it is not designed.
  - Resolution: Honest scope reduction now, design later: reword spine §8 and ADR-016 from 'distribution = portable checkpoints + protocol edges' to 'V1 is single-domain; portable checkpoints provide cold migration and vendor-portable audit records; cross-node budget lineage and cross-node provenance queries are future work with no current design.' Separately, specify the two things cold migration does need before V1 ships it: chain anchoring of a migrated cell's first event to the source checkpoint hash, and a journal-export bundle format so audit queries can be answered by concatenating lineage segments offline.

- **[MODERATE]** *doc 08 §7.3 (cancellation) vs §3.1 event taxonomy; loop-prototype finding*
  - Attack: Doc 08 §7.3 step 1 states 'the request is journaled', but the §3.1 taxonomy contains no kyxo.invocation.cancel-requested kind — only the honored .canceled transition — and the prototype confirms the gap: kernel.cancel() flips an in-memory flag (kernel.ts:545-550) and a cancel that races completion leaves zero truth-plane trace. This directly violates the document's own 'nothing fails silently' banner and the two-plane doctrine (operator intent is an authority exercise with audit weight, like denials, which the same section correctly puts on the truth plane). In a compliance scenario — 'we ordered the agent stopped at 14:02, it committed a trade at 14:03' — the journal cannot establish that the order was given. This is the authors' own prototype finding, but it was left as a bullet in OPEN-ISSUES rather than fixed in doc 08's taxonomy, which was written afterward: the spec repeats the prototype's bug in prose while claiming the opposite.
  - Resolution: Wording plus schema fix: add kyxo.invocation.cancel-requested (truth plane, carrying requesting principal, reason, target subtree) to §3.1; define the race semantics explicitly (cancel-requested followed by completed is a legal, auditable interleaving; the request event is what discharges operator responsibility). One paragraph and one event kind; no design change needed.

- **[MODERATE]** *doc 07 §4 event trace (e2, e15, e20) vs doc 08 §3.1 (kyxo.policy.evaluated = advisory)*
  - Attack: The two documents contradict each other on which plane allow-path policy decisions live. Doc 08 §3.1 assigns kyxo.policy.evaluated (allow traces) to the advisory plane, with a justification paragraph; doc 07 §4 presents its trace as 'the journal — the truth plane' and includes plain allow decisions at e2 and e15 (e20's require-approval is defensibly truth as a suspension cause, e2/e15 are not). One of the two flagship documents is wrong, and it matters beyond consistency: doc 08's own self-report concedes regulated deployments may need journaled allow traces, and the reconstructibility argument ('policy stages are deterministic over journaled inputs') holds only if every input to the stage — including grant remaining-balances and probe-cache state at that seq — is itself recoverable from the fold, which is asserted, not demonstrated, for the probe cache (probe TTL expiry is wall-clock, not journal, state).
  - Resolution: Pick one: either allow-traces are advisory (fix doc 07's trace and add the journaled-allows policy knob doc 08's self-report already proposes for regulated deployments), or allows at effectful invocations are truth (fix doc 08 §3.1 and price the journal growth). Then close the reconstructibility gap: enumerate every policy-stage input and verify each is a fold-derivable quantity; journal probe-cache snapshots if not.

- **[MODERATE]** *doc 08 §7.1–7.2 and §9 rows 4–5 (exactly-once illusion at the world boundary; manifest-declared idempotence)*
  - Attack: Lease epochs close the journal-commit race (good — fencing is the correct mechanism) but the documents' language repeatedly slides from 'exactly-once journal landing' to implied exactly-once effects. Row 5's 'next attempt commits exactly once via dedup' is true of the journal and false of the world: the zombie worker whose stale-epoch commit is rejected may have already performed the external effect (sent the email, executed the trade); the world saw two effects, the journal records one, and the journal is supposed to be truth. Row 4 makes manifest-declared idempotence load-bearing for auto-retry while doc 06's self-report admits the promotion path from advisory annotation to enforced axis is 'asserted, not designed' — so the load-bearing input is unverifiable and the failure mode of a lying manifest is a silent double effect attributed as absorbed. ADR-009 words this honestly ('the kernel cannot make a non-idempotent tool safe'); doc 08's failure table does not, and the failure table is the headline deliverable. This is oversold rather than wrong.
  - Resolution: Wording pass on doc 08: every 'exactly-once' is qualified as journal-landing; rows 4-5 gain an explicit 'world-effect divergence' column entry stating that for non-fencable external effects the guarantee is at-least-once-world/exactly-once-record, with reconciliation-by-probe as the sanctioned closer. Add a conformance requirement that redelivery-capable providers accept the fencing token (lease epoch) so effect-side fencing is at least possible for providers that can implement it.

- **[MODERATE]** *doc 05 §2.2/§2.7 (sealed Binding, decrement-only Grants) vs kernel-prototype re-grant finding vs doc 08 row 8*
  - Attack: budget-exceeded is classed as an interrupted (resumable) state, but the spine gives no mechanism to refill authority: Grants are sealed into Bindings and decrement-only. The prototype had to invent a re-grant verb — resume(id, payload, {grantId}) swapping the invocation's effective grant (kernel.ts:535-541) — which quietly breaks the Binding's 'sealed grant' property that §2.2 calls the reason Binding is a kernel object at all ('a userland binding is a forgeable claim'). Doc 08 row 8 says 'parent or human issues an attenuated top-up grant and resumes' as if the mechanism existed; doc 13's scenario P independently forces reserve/settle accounting, contradicting spine §3.7's decrement-at-commit. Three documents assume three different budget mechanics and none is ratified. Since Grants-as-budgets is self-described as 'the one genuinely novel kernel object' and the least-evidenced admission, leaving its exhaustion-recovery semantics as an unratified prototype hack is not acceptable pre-build.
  - Resolution: Decide and ratify in one ADR: adopt reserve-at-lease/settle-at-outcome (doc 13's fix) plus an explicit grant-substitution rule (a Binding seals the grant LINEAGE, not the grant instance; resume-under-descendant-of-original is legal, anything else is a new bind through policy). Update spine §3.7, doc 05 §2.2/§2.7, and doc 08 row 8 to the same mechanics.

- **[MINOR]** *doc 08 §9 closing paragraph ('seventeen scenarios... zero scenario-specific machinery')*
  - Attack: The economy claim is rhetorically inflated. Several rows quietly depend on machinery that is not among the nine objects and two mechanisms: row 2 requires a health-scoring/telemetry subsystem ('failure-rate spike... mark capability unhealthy') that is elsewhere deferred to an undesigned routing strategy (spine C3's 'telemetry drives selection' has no mechanism, per the graph prototype's own finding); row 4 requires reconciliation-probe capabilities; row 12 requires a blast-radius query engine. These may all be legitimately userland/stdlib, but then the honest claim is 'seventeen scenarios map onto kernel mechanisms plus five pieces of unspecified stdlib', which is a different — still decent — result.
  - Resolution: Wording: annotate each row with its stdlib/userland dependencies and downgrade the closing claim accordingly. Add the telemetry/selection mechanism to the explicit open-design-holes list, since three failure rows now depend on it.


## AI infrastructure engineer (built model-serving and agent platforms at scale)

**Useful-layer verdict:** QUALIFIED-YES. There is a genuinely primitive core here that no existing project owns and that sits below the framework layer where churn lives: grant lineage with quantitative budgets charged at journal commit (the prototype's atomic ancestor-decrement result is real and novel), the portable journal/checkpoint record format, the opaque carry-through invariant (which converts a documented cross-provider 400-class breakage into a structural impossibility), and fail-loud bind-time gating on the handful of mechanically checkable axes. Those survive provider churn because they don't encode provider semantics. But the design wraps that core in a contract surface that IS another abstraction layer: a 16-axis hand-curated enforced vocabulary, behavior profiles in manifests, and telemetry-routing claims with no mechanism — all of which decay at provider-release speed exactly like the framework-layer adapters this project positions itself beneath. Build the core; shrink the wrapper.

**Vote:** BUILD WITH CHANGES — The spine's own recommendation (BUILD WITH CHANGES) is directionally right, but the changes it names are not the changes it needs. The kernel-object set is well-evidenced by convergent evolution and the prototypes genuinely stress-tested it (universality held, harness-independence held, loops-as-policy held — with honest abstraction-failure reports). EXTEND was correctly rejected: grants-with-lineage and commit-gate verification are structural and demonstrably absent from LangGraph/MAF, and the prototype showed even Kyxo's own kernel lacks the commit gate — retrofitting it into someone else's public contract is strictly harder. DO NOT BUILD is wrong because the carry-through invariant, budget lineage, and record format solve documented, measured production failures (400-class replay breakage, the 40%→80% cache delta, absent budget attenuation) that no one else owns. But BUILD-as-specified would die under its own curation tax: the negotiation catalog is an unfunded standing institution, the selection half of C3 does not exist, and the federation story claims a mirroring surface no provider exposes. My changes: probe-generated manifests with a small structurally-enforced axis core, an explicit V1 selection policy plus a designed Router socket, federation re-scoped to coarse-effect + reserve/reconcile with quantified overrun bounds, provider-side compaction deferred behind a bind-time taint-homogeneity rule, and pair-scoped behavior profiles. With those, the primitive core ships without the oversold wrapper.

**Strongest objection:** Headline differentiator #3 — 'axis-typed capability negotiation with probes + telemetry' — is, as specified, an unfunded curation institution bolted to an unimplemented selection mechanism. The enforced manifest catalog decays at provider-release speed with no staffing answer and includes axes the kernel cannot actually verify (enforcement badges on manifest-trusted claims — the exact 'policy built on hints' failure this project accuses the ecosystem of); probes cover a minority of the enforced set; and the telemetry that supposedly 'drives selection' has no consumer, no ranking contract, and keys so fine-grained — pair × version × axis-config, mandatorily segmented at every migration — that it is guaranteed perpetually sparse while first-fit registration order remains the real selection policy. Until eligibility shrinks to the probe-verifiable core and selection gets a designed contract, this layer is a capability catalog, not a capability contract — and catalogs are what die of staleness.

**MVP changes:** CUT telemetry-driven selection from the MVP: ship explicit declared preference-order routing with telemetry recorded but not consumed, plus a designed Router capability contract (interface only) so V2 selection has a socket to fill.; CUT the enforced model-axis set to the probe-verifiable core (~6 axes: unknownFields, reasoning.replay, structured tier, tools.emission, streaming, tasks); demote caching/sampling/state/resources to probe-enforced-or-advisory, and make model manifests probe-generated rather than hand-authored.; CUT provider-side compaction from the MVP (client-side executors only), shipping the bind-time label-homogeneity rule as the documented condition for ever enabling the provider path.; CUT behavior profiles from the adapter manifest schema; MVP ships two hand-tuned pair-scoped profile artifacts (e.g. reactive-harness×Anthropic, reactive-harness×vLLM) instead of a general profile schema.; ADD: indexed manifest eligibility query + negotiation cache keyed on (requirementsHash, manifestHash) to kill O(candidates) trial binds, and span-reference-manifest representation for recorded compiled views to kill the CAS duplication problem.

### Findings

- **[SERIOUS]** *ADR-003 (Consequences), 06-CAPABILITY-SPEC §2.3/§2.4, DESIGN-SPINE §10 ('manifest + probe suite as standalone early value')*
  - Attack: The negotiation catalog is priced as a schema but is actually a standing curation institution, and the enforced-axis set conflates two different things. Doc 06 §2.4 marks 14 of 16 model axes 'E' (enforced = 'the kernel gates on them at bind and invoke time'), but the kernel can structurally verify only a minority at its boundary: unknownFields, reasoning.replay, structured tier, tools.emission, streaming grammar are probe-checkable; model.caching (billing semantics), model.sampling (per-parameter status across a drifting parameter surface), model.state, model.resources are manifest-trusted — the kernel 'gates' on a declaration it cannot check, which is exactly the 'policy built on hints' failure ADR-003 Force 5 indicts, wearing an 'enforced' badge. Meanwhile the maintenance economics are unfunded: 16 axes × settings subsets ('exact schema subset descriptor'!) × 20+ providers × model-version churn, with ADR-006 admitting 'headcount, forever' and behavior profiles that 'cannot be mechanically re-derived', and doc 12 self-reporting no staffing answer. LiteLLM's flat model catalog — a far simpler artifact — is perpetually stale with hundreds of contributors. As specified, the 'standalone early value' claim inverts into a standing liability: a wrong-but-signed enforced manifest is worse than no manifest because bindings seal against it.
  - Resolution: Split the enforcement taxonomy in doc 06 §2.3 into three classes: structurally-enforced (kernel-checkable at its boundary), probe-enforced (gated only when backed by fresh Evidence), and declared (manifest-trusted, never usable by deny-class policy). Shrink the V1 enforced model-axis set to the probe-verifiable core (~6 axes); demote caching/sampling/state/resources to probe-enforced-or-advisory. Invert the authoring model: manifests for model targets are probe-GENERATED artifacts (probe-first, manifest-as-cache) with declared fields only where no probe exists. Re-word spine §10: the standalone early value is the PROBE SUITE, not the manifest catalog.

- **[SERIOUS]** *DESIGN-SPINE §1 C3 ('telemetry drives selection'), 06-CAPABILITY-SPEC §4.2–4.3, 10-HARNESS-AND-GRAPH-RUNTIME §2.3 step 5, prototype finding (graph-strategy.ts trial negotiation)*
  - Attack: C3 is confirmed unanswered, and it is worse than the prototype self-report says. There is no selection mechanism anywhere in the design set — not just the prototype: no ranking contract, no exploration/cold-start policy, no API surface a routing strategy would implement; doc 07 punts to 'a routing strategy' and doc 06 §4.3 step 3 is a normative sentence with no design behind it. First-fit registration order IS the shipped selection policy (verified: prototypes/graph/graph-strategy.ts line 124 iterates listCapabilities() and takes the first successful bind). And the telemetry that is supposed to fill the hole is keyed per (capabilityId, version, consumer identity, negotiated axis configuration) (06 §4.2) AND mandatorily segmented at every migration boundary (09 B.6 step 5). Model adapters version at provider-release cadence, so telemetry keys rotate faster than samples accumulate — the selection signal is guaranteed perpetually sparse by the design's own keying rules. ADR-003 already concedes cross-org pooling 'may be unachievable'. As it stands, spine §6 differentiator 3 and every routing claim in doc 10 are empty at the margin.
  - Resolution: Two changes before build. (1) Design the Router contract now: a userland capability with a defined interface — (eligible candidate set, telemetry projection, budget) in, ranked choice + journaled rationale out — with the V1 default being explicit declared preference order + probe recency, honestly documented as the selection policy. (2) Fix telemetry keying with hierarchical backoff: aggregate across versions and axis-configs with decay weighting (standard sparse-bandit practice) so a new adapter version inherits a discounted prior instead of a cold start. Amend spine C3 to 'declarations gate eligibility; selection is an explicit routing policy that MAY consume telemetry' — stop claiming telemetry-driven selection until the mechanism exists.

- **[SERIOUS]** *DESIGN-SPINE §5 ('remote cells with mirrored artifacts/budgets/policy, federated rather than proxied'), 07-RUNTIME-ARCHITECTURE §6, 11-SECURITY-AND-POLICY federation claims*
  - Attack: The federation story is oversold at the spine level and honest only in doc 07's fine print. No provider today exposes the surface 'mirrored policy' implies: there is no interposition on hosted-tool calls, no per-effect usage attribution inside a Responses background run, no enumerable event stream for provider-internal steps (doc 04 self-reports that deterministic invocation identity is unresolvable for provider-internal steps). Doc 07 §6 concedes runtime interposition is 'impossible by construction' and collapses policy to bind-time coarse allow/deny over the UNION of declared authorities — that is structural over-granting, not mirroring. Budget 'mirroring' is reserve-then-reconcile with an overrun window bounded only by lease expiry, against providers whose usage reporting is sparse (background mode reports at completion). The 'remote cell' is, operationally, a labeled handle plus a hope of reconciliation. Calling this 'federated rather than proxied' with 'mirrored budgets/policy' is fiction at the spine's altitude; the workable design underneath — coarse effect + reserve/reconcile + carry-through artifacts — is real but much weaker than advertised.
  - Resolution: Amend spine §5 to the honest form: provider-side execution domains are modeled as coarse-grained effects with (a) bind-time authority-union gating, (b) reserve/reconcile budgets with a quantified overrun bound (lease TTL × provider max burn rate, computed and journaled at bind), (c) opaque carry-through artifacts. Write the accepted-risk ADR doc 07's self-report asks for. Add the leading indicator the roadmap lacks: per-provider tracking of exposed federation surface (usage granularity, event streams), so the design tightens as providers expose more rather than pretending they already do.

- **[SERIOUS]** *09-CONTEXT-AND-MEMORY §A.5 (provider-side compaction as first-class executor) vs §A.2 contract #4 (provenance-preserving compile) and §A.6 (FIDES-style label enforcement)*
  - Attack: These two commitments are contradictory, not merely 'undecided' as open issue 5 frames it. The taint architecture's whole value proposition is deterministic enforcement over labeled spans (a processor may lower, never raise, integrity; tool calls from views containing untrusted spans are FIDES-denied). Provider-side compaction (compact_20260112 — which Anthropic documents as 'the recommended strategy') feeds the FULL history, untrusted spans included, to a provider-side summarizer outside survivor policy and label enforcement, and returns one opaque summary block. Both mirroring options destroy the invariant: accept-and-label forces the summary to the meet of all input labels (a single untrusted web span taints the entire compacted history — utility collapse), and client-side re-summarization of labeled ranges forfeits the provider feature the design says it must not hard-code against. So the flagship structural-taint differentiation silently degrades to nothing precisely on the vendor-recommended path for long-running agents — the design's primary workload.
  - Resolution: Decide it now with a bind-time rule, which the axis grammar can already express: a provider-side compaction executor is only bindable when the compaction range is label-homogeneous at-or-above the executor's declared clearance; otherwise the bind fails loudly (consistent with §5.6) and the client-side executor is selected for the mixed-label range (hybrid: provider compacts trusted prefix, client handles tainted tail). Cut provider-side compaction from the MVP entirely; ship the rule as the documented V1 posture.

- **[MODERATE]** *06-CAPABILITY-SPEC §5.3 (bind = rights check + intersection + policy stages + journal) combined with the trial-negotiation resolution pattern (prototype finding; 10 §5.2–5.3 graph node resolution)*
  - Attack: Resolution-by-trial-negotiation performs O(candidates) REAL binds per node per execution — each running the policy pipeline's bind-phase stages (which per §4.3 may include require-evidence checks) and appending a truth-plane binding.rejected record per loser (verified in kernel.ts:438-450). At realistic scale — hundreds of registered capabilities, graphs of dozens of nodes, re-resolution on every escalation-ladder rung and every plan-version rebase — this is O(N×C) policy evaluations and journal appends on the hot path, bloating the journal with rejection records of capabilities that were never plausible candidates. The prototype's self-audit benefit ('why did X win is answerable from the truth plane') is real but does not require paying full bind cost for every loser.
  - Resolution: Two-phase resolution as a normative design: (1) a cheap indexed eligibility query over manifest axes (pure data, no policy, no journal — the registry index the VS Code precedent already justifies) produces the candidate set; (2) exactly one real bind against the selected candidate. Record the eligibility computation as a single compact advisory-plane record (candidate set + per-candidate failing predicate), reserving truth-plane binding.rejected for actual attempted binds. Add a negotiation cache keyed by (requirementsHash, manifestHash) — both hashes already exist in the sealed Binding record.

- **[MODERATE]** *09-CONTEXT-AND-MEMORY §A.2 (compiled-view-as-artifact), §A.4 (cache-prefix layout), open issue 4*
  - Attack: Two hot-path problems the open issue understates. First, storage: content-addressing WHOLE compiled views gets zero cross-turn dedup by construction — successive turns' views share a large prefix but differ at the tail, so each turn stores a near-duplicate multi-hundred-KB blob; a 50-turn loop at 500KB views is ~25MB of CAS per run, with CAS garbage collection already deferred (roadmap self-report). Second, economics: the compiler is deterministic per invocation but nothing contracts prefix STABILITY across invocations — a version bump in any 'resident' source cell reorders/resizes an early span and silently invalidates the provider's entire prefix cache, a ~10× cost swing on Anthropic-style explicit caching that the 'cache-prefix layout' stage does not prevent because it runs per-compile with no memory of the previous layout.
  - Resolution: Make the recorded view a span-reference manifest by construction: the view IS a list of (artifact-ref, range, labels) plus small glue — the spans are already CAS content, so the recorded artifact is kilobytes and dedup is structural, resolving open issue 4 without measurement. For cache economics, add an inter-invocation prefix-stability contract: pinned/resident span layout is frozen per cell epoch, and layout changes are only applied at declared boundaries (compaction events, checkpoint cuts), journaled as an explicit prefix-invalidation event with its estimated cost delta.

- **[MODERATE]** *10-HARNESS-AND-GRAPH-RUNTIME §2.2 ('pairs are the unit') vs §2.4 and ADR-006 element 3 (behavior profiles homed in the adapter manifest)*
  - Attack: The profile's normative home contradicts the pair doctrine. §2.2 establishes the harness×model PAIR as the unit of deployment and measurement, but §2.4/ADR-006 place toolNamingStyle, promptPatches, delegationBias — which are pair knowledge, produced by harness-side tuning (Cursor renamed ITS tools for ONE model in ITS harness) — into the model ADAPTER's manifest, a one-sided object authored by whoever ships the wire codec. The adapter author does not possess harness-tuning knowledge, and all harnesses would share one profile per model, which is exactly the flattening §2.2's evidence refutes. ADR-006 further admits profiles 'cannot be mechanically re-derived' and rot into misinformation across model versions — so the design homes decaying, hand-tuned pair knowledge in an artifact with the wrong owner and the wrong cardinality.
  - Resolution: Restrict adapter manifests to model-INTRINSIC facts (replay contract, dialects, termination signal type, effort semantics — things true regardless of harness). Make the behavior profile a pair-scoped override artifact — (harness@ver, adapter@ver) → profile — which doc 10 §2.2's own pair definition ('profile-overrides') already gestures at; make that the normative home, registered as a Kind with provenance and telemetry-updatable fields, and delete the profile section from the adapter manifest schema.

- **[MODERATE]** *10-HARNESS-AND-GRAPH-RUNTIME §2.3 (benchmark matrix), §7.3 cost (4)*
  - Attack: The matrix's 'mechanical enumeration' claim is empty at the margin, by the program's own evidence. §2.3 sanctions per-pair profile variation because unadapted harnesses understate models by ~30%-class margins (C2) — but then a matrix cell without an invested, hand-tuned profile measures adaptation debt, the very thing the design says invalidates comparison. Cursor spends WEEKS per pair; nobody will tune N×M cells. So the honest matrix is a handful of tuned pairs plus a large field of cells whose scores are scientifically meaningless, and telemetry feedback (step 5) inherits the same sparsity (see the C3 finding). The doc concedes this may not survive review (§7.3 item 4 and the self-report) but still presents the matrix as a headline DX deliverable (spine §9).
  - Resolution: Scope the claim: matrix cells carry a profile-provenance grade (tuned / default-profile / untuned), only same-grade cells are comparable, and published results require tuned grade. Reframe the deliverable from 'N×M matrix' to 'reproducible pair benchmarking for pairs someone has invested in' — which is still differentiated (nobody else pins corpus + policy + profile hashes) and is what the infrastructure can actually support.

- **[MINOR]** *09-CONTEXT-AND-MEMORY §A.2 ('we can answer what exactly did the model see for any past invocation')*
  - Attack: The claim is false under exactly the provider features the same document embraces: with Responses server-side state, provider-side compaction, or encrypted carry-through items, part of what the model 'saw' is provider-held or opaque-by-design. The journal records what was TRANSMITTED and which opaque state handles were in play — a weaker and still-valuable guarantee, but the wording claims total reconstruction, which a customer audit or incident review would discover to be untrue on the first Responses-with-store workload.
  - Resolution: Wording fix: 'we can answer what the runtime transmitted, under which sealed Binding, with which opaque provider-state handles attached — and enumerate exactly which portions were provider-held and not locally reconstructable.' Add the provider-held remainder to the B.6 survives-the-swap table's audit column.

- **[MODERATE]** *ADR-006 (in-process code-bearing adapters, V1 posture) and 07-RUNTIME-ARCHITECTURE §8.1*
  - Attack: The self-reports treat in-process adapters purely as a security gap; from an operations standpoint it is also an availability gap the docs never state: the adapter is the single highest-churn, third-party-authored code in the system (per ADR-006's own treadmill admission), and in V1 it runs on the hot path of a single-node, single-process kernel. A buggy streaming decoder that wedges or leaks doesn't just risk exfiltration — it stalls the cell's single-writer queue and can take down every cell in the process. The failure domain of the most-frequently-updated component is the whole runtime, and the spine's headline 'the AI cannot grant itself privilege' coexists with 'any adapter bug is a whole-kernel fault' for the entire pre-WASM era.
  - Resolution: Accept for V1 but state it: add the availability consequence to ADR-006's negative consequences, add per-adapter-invocation watchdog timeouts and crash-loop circuit breakers (cheap, in-process, no isolation needed) to the V1 scope, and make the WASM wave's release gate include an adapter fault-injection suite, not just the crossing-cost benchmark.


## Model-provider platform engineer (frontier-lab serving/agents API team)

**Useful-layer verdict:** QUALIFIED-YES. For execution the kernel actually mediates — local tools, self-hosted/open-weight models via vLLM/Ollama, regulated single-node deployments — Grants-with-lineage, commit-gate verification, and the portable execution record are genuine primitives no provider will ever build cross-provider, because we have no incentive to: cross-provider lineage and audit structurally cannot live inside any one provider. But at the frontier-provider edge, which is where the market's execution volume is moving by the program's own evidence (Responses hosted tools, background mode, server-side compaction, Assistants sunset, Managed Agents), the kernel's objects degrade to mirrors and reconciliation records — an accounting overlay, which is exactly the pejorative sense of 'another abstraction layer.' The layer is a primitive layer below the provider waterline and an abstraction layer above it; the documents currently sell the former's guarantees across both.

**Vote:** BUILD WITH CHANGES — BUILD, because the durable value — the published execution-record format, budget lineage for kernel-mediated execution, and the capability manifest + probe suite — occupies ground providers provably will not contest (MCP's scope statement, and the simple fact that no provider ships cross-provider anything). WITH CHANGES, because three core claims do not survive a provider-side reading as written: (1) enforcement positioning must be honestly stratified per Binding (enforced vs observed vs declared) — the two growth paths, vendor delegated harnesses (Manifest B) and provider execution domains (remote cells), both reduce the crown-jewel guarantees to bind-time declaration checks plus lagged reconciliation; (2) the superset internal block model is decided at HIGH confidence while its constructibility is an open question in its own evidence note — it needs a Wave-0 round-trip proof before the journal schema hardens on it; (3) the axis catalog omits the operational axes (quota/rate-limits, server-state retention/TTL) that dominate real routing and bound fork-from-checkpoint, the spine's primary repair verb. EXTEND is correctly rejected — grants/ocap and commit gates cannot retrofit into LangGraph/MAF without breaking their public contracts, and I find that argument sound. DO NOT BUILD would require believing provider absorption reaches cross-provider lineage and audit; it will not.

**Strongest objection:** Your own evidence base proves the market's execution volume is migrating into exactly the two domains where your guarantees are weakest — vendor delegated harnesses with hook-only interposition, and provider execution domains where policy is bind-time-only and budgets are lagged reconciliation — yet the architecture's closing promise is 'structural invariants rather than per-vendor conventions.' Until every Binding carries an honest enforced/observed/declared guarantee grade and the positioning is rewritten around it, you are selling kernel-grade enforcement while shipping, for the growth path, an audit log with good intentions — and as a provider engineer I can tell you we will keep enlarging the opaque domain, because it is where our margin and our moat live.

**MVP changes:** CUT the A2A edge from the MVP entirely (both the deferred server and the F8 projection-mapping test, which doc 14 already admits is the weakest falsification of the eight): ship MCP southbound plus the surface protocol only, and let A2A land with the converged MCP/A2A picture rather than against a moving target.; CUT closed-vendor behavior profiles from the MVP; keep behavior profiles only for the vLLM/Ollama open-model adapters, where no vendor harness exists and the profile is genuinely the missing artifact.; ADD a Wave-0 superset round-trip gate: fixture-driven decode→internal→re-encode tests across Anthropic Messages and OpenAI Responses recordings including signed thinking blocks and reasoning items, gating the journal block schema before it becomes ADR-002's forever-contract.; ADD quota/rate-limit/retention handling to the Wave-2 adapters: a model.limits advisory axis, retention/TTL settings on model.state and model.caching, and a specified scheduler backpressure contract for 429/retry-after — this is the first wall real traffic hits and the spec is silent on it.; ELEVATE the capability manifest + probe suite for the top model targets from 'standalone early value' to the actual MVP wedge, shipped and versioned independently of the kernel: it is the one deliverable that retains full value under every provider-absorption scenario, including the ones that gut the enforcement story.

### Findings

- **[FATAL]** *DESIGN-SPINE §6 (differentiation) + 07-RUNTIME-ARCHITECTURE §3.1/§6/§9 + ADR-007 Consequences*
  - Attack: The enforcement value proposition inverts under the program's own 'providers are becoming runtimes' evidence, and no document confronts the composition. Each piece is admitted separately: Manifest B (Claude Code) gets hook-only interposition and coarse budget observability (07 §3.1); remote cells get policy evaluated at bind time only, 'one effect with the union of its declared authorities' (07 §6, self-flagged as structural over-granting); ADR-007 concedes 'projections are lossy by construction, and the losses are Kyxo's crown jewels... federation weakens exactly the guarantees Kyxo sells.' Compose these: the two dominant execution paths going forward — vendor delegated harnesses and provider-side execution domains — are precisely the paths where per-effect policy, fine-grained budget enforcement, taint propagation, and commit-gate verification all degrade to declaration-checking plus after-the-fact reconciliation. Doc 07 §9 nevertheless closes by promising 'structural invariants rather than per-vendor conventions.' For a growing majority of real workloads that sentence is false, and the provider has every competitive incentive (margin capture, first-party SDK gravity, trained-in tool schemas) to keep enlarging exactly the opaque domains where Kyxo's guarantees are weakest. This invalidates the positioning as written — the six §6 differentiators are enforcement claims that hold only below the provider waterline.
  - Resolution: Honest scope stratification, not a design change: (a) make guarantee grade a first-class, per-Binding property (enforced / observed / declared) sealed into the Binding record, surfaced in the journal and to users; (b) rewrite spine §6 and 07 §9 to claim enforcement for kernel-mediated execution and attestation/audit for federated domains; (c) target V1 at segments where kernel mediation dominates (self-hosted open models, regulated environments, air-gapped) rather than frontier-provider passthrough; (d) define the R5 leading indicator doc 15 admits is missing — e.g., quarter-over-quarter share of journal events originating in remote cells is itself the early-warning metric.

- **[SERIOUS]** *07-RUNTIME-ARCHITECTURE §6 (budget mirroring) + DESIGN-SPINE §3 object 7 (Grants) + ADR-014 via open issues*
  - Attack: The one 'genuinely novel kernel object' decrements estimates, not money, exactly where budgets matter most. USD charging at commit depends on (a) adapter-maintained provider price tables — out-of-band artifacts that decay at repricing speed (cache-read discounts of ~10x, batch tiers, priority tiers, invoice-time adjustments), (b) provider usage events that are sparse in background mode and never itemize hosted-tool sub-steps in-band, and (c) a reserve-then-reconcile window the docs themselves admit is bounded only by lease expiry with no quantitative treatment. Meanwhile providers already ship the actual enforcement primitive: org/project/key-scoped hard spend caps at the metering source. The docs present kernel Grants as the enforcement and provider caps as absent ('budgets absent everywhere'); from the serving side the truth is inverted for USD — the provider's meter is ground truth and the kernel ledger is a fast-path estimate. Cline's per-subagent cost tracking and MAF's invocation budgets were already flagged as near-misses; scoped provider keys with spend limits are a nearer miss the gap map does not mention.
  - Resolution: Design change plus measurement: specify reserve/settle semantics with quantified worst-case overrun bounds per provider reporting class (streaming usage / completion-time usage / invoice-lag); mandate defense-in-depth pairing of high-value Grants with provider-side scoped keys/caps as the backstop, minted per remote cell where the provider admin API allows; re-word the Grant claim from 'kernel-enforced budgets' to 'kernel-accounted, provider-backstopped' for monetary units while keeping hard enforcement claims for units the kernel truly meters (invocations, spawn depth, wall-clock).

- **[SERIOUS]** *06-CAPABILITY-SPEC §7 (opaque carry-through) + 09-CONTEXT-AND-MEMORY A.5 (compaction) and B.5 (redaction/erasure)*
  - Attack: Signature-verified provider state and the kernel's own history-rewriting machinery are on a collision course the documents never compose. Doc 06 §7 mandates verbatim replay 'at the bound position' and forbids stripping; doc 09 A.5 makes compaction a first-class fold that drops and reorders prefix content; doc 09 B.5 defines erasure as CAS payload deletion plus tombstone. Three concrete failures: (1) kernel-side compaction that removes or reorders any span ahead of a signature-bound block changes the very history the provider verifies — Gemini hard-400s, Anthropic rejects — so survivor policy is not free policy, it is provider-constrained, and the 'deterministic compile' must be signature-aware, which no compiler-contract clause states; (2) a GDPR-class erasure of a payload inside a signed span bricks the conversation on signature-verified targets: a tombstoned artifact cannot be replayed verbatim, so 'redaction that survives audit' silently forfeits resumability and nothing prices or journals that forfeit; (3) provider-side compaction (compact_20260112) drops blocks outside kernel survivor policy — flagged in open issues — but its interaction with signature-bound blocks in the retained suffix is unexamined. This is a kernel-invariant-vs-kernel-invariant conflict, not an edge case: both invariants are MUSTs in the same spec.
  - Resolution: Design change: add a signed-span integrity constraint to the compiler contract — compaction and drop boundaries MUST align with provider-verifiable boundaries declared in the adapter manifest (a settings object on model.reasoning.replay); define erasure semantics for carry-through spans explicitly (fork-from-pre-erasure-checkpoint with declared, journaled quality/cost forfeit); add a prototype task exercising real Anthropic signature and Gemini thought-signature enforcement under kernel compaction before the compiler contract hardens.

- **[SERIOUS]** *ADR-006 Decision element 5 (superset internal block model) + 06-CAPABILITY-SPEC §6.5*
  - Attack: The superset internal block model is decided at HIGH confidence while its constructibility is an explicitly open question in its own evidence base: open-model-infrastructure.md Open Question 1 asks whether Responses' item model and Anthropic's block/signature model can coexist in one superset, and no document answers it. The semantics genuinely conflict: Responses items carry server-side identity and reference semantics (item ids, include-projections, server-optional state) while Anthropic blocks are positional with signed integrity over exact content; a superset must carry both identity models and both integrity models simultaneously. The program's own prototype already demonstrated the failure seed — CAS content-addressing produced false first-writer provenance on identical payloads, and content-addressing an item whose canonical identity is a server-assigned id discards the provider's identity semantics. Realtime/Live event vocabularies are a second unresolved axis (note OQ5, echoed but not resolved in 06 §6.5). Additionally ADR-006 underweights the passthrough consequence: providers ship new item types monthly, so the 'two-speed semantics' it admits becomes the steady state — the newest, competitively decisive features live permanently in provider-locked passthrough, which is the lock-in the kernel exists to prevent. The journal schema (ADR-002's forever-contract) will fossilize whatever answer is chosen, so deciding this by assertion is the single most dangerous unforced bet in the set.
  - Resolution: Measurement gate before build: construct the actual superset schema for the four V1 targets as a Wave-0 exercise with a fixture-driven round-trip test (decode provider wire → internal blocks → re-encode same dialect, byte-faithful for signed/stateful items; cross-dialect where portable), including Responses reasoning items and Anthropic signed thinking blocks. If stateful-item round-trip fidelity fails, downgrade the decision to per-family internal models under a common envelope and amend ADR-006 before the journal schema ships.

- **[SERIOUS]** *06-CAPABILITY-SPEC §2.4 (model-facing axis catalog) + DESIGN-SPINE §7 (fork-from-checkpoint)*
  - Attack: The 16-axis catalog omits the operational axes that dominate real provider integration: there is no axis for quotas, rate limits (RPM/TPM/ITPM/OTPM buckets, burst, retry-after semantics), concurrency ceilings, or priority tiers — so a sealed Binding can be perfectly 'eligible' and immediately, persistently 429, and the scheduler section (07 §2) owns leases and deadlines but has no backpressure contract for provider throttling, the first thing real traffic hits. Worse, there is no retention/TTL declaration for server-held state: stored Responses have bounded retention, cachedContents are TTL'd server resources, session handles expire. Fork-from-checkpoint is the spine's primary repair verb, yet a checkpoint referencing a remote cell older than the provider's retention window is unresumable, the manifest cannot express that bound, and restore discovers it only at replay time. As a provider engineer I can state plainly: quota state and retention windows change routing and recovery decisions more than half the declared axes do, and they lag or shift without notice — the negotiation grammar as specified negotiates the wrong things first.
  - Resolution: Design change: add a model.limits axis family (advisory, telemetry-fed, never bind-gating) plus retention/TTL settings on model.state and model.caching; specify the scheduler's 429/retry-after backpressure contract (lease-aware, budget-charged waiting vs failover); require checkpoint metadata to carry remote-state expiry horizons so restore/fork fails loudly at planning time; add a probe suite row for observed throttle behavior.

- **[SERIOUS]** *ADR-006 Decision element 3 (behavior profiles) + DESIGN-SPINE C2 + 02/03 evidence chain*
  - Attack: Third-party behavior profiles cannot be competitive for closed-vendor models, and the Cursor evidence cuts against the design it is cited to support. Two problems. Evidence-grade: the load-bearing ~30% reasoning-trace figure and weeks-per-model tuning claims were retrieved via search-engine extracts of egress-blocked pages (self-reported), then laundered to FACT/HIGH through the spine into at least five documents that never read the note — this is below the program's own methodology bar for a claim carrying H2, harness.modelRequirements, Manifest B treatment, and ADR-005/006. Substantive: the same evidence proves competitive per-model tuning requires frontier-scale eval infrastructure and proprietary telemetry that Kyxo lacks (doc 14 admits the Phase-37 benchmark corpus does not exist), while providers bake harness behavior into the model+API bundle where no third-party profile can reach it — trained Anthropic-schema tools, server-injected per-model tool-use scaffolding (286/354 tokens, invisible to the adapter), vendor system prompts as trade secrets patched per model version. A community profile for a closed vendor model will underperform the vendor's own harness; rational users then bind the vendor harness as Manifest B, which is exactly the enforcement-degraded path of finding 1. The 'updatable from outcome telemetry' promise additionally rests on cross-tenant telemetry pooling flagged as an unvalidated operational bet.
  - Resolution: Scope reduction plus measurement: re-fetch and re-grade the Cursor sources before publication; restrict the behavior-profile competitiveness claim to open-weight targets (vLLM/Ollama), where no vendor harness exists and profiles are genuinely the missing artifact; for closed vendors, reposition profiles as compensation patches whose deltas must be demonstrated by the benchmark harness before any parity language ships.

- **[MODERATE]** *09-CONTEXT-AND-MEMORY A.2 (compiler contract, 'what exactly did the model see')*
  - Attack: The claim 'we can answer what exactly the model saw for any past invocation' is oversold by one full layer. The journal records the compiled typed view, but the wire request adds adapter encoding, and the provider then adds what the kernel structurally cannot see: server-injected tool-use scaffolding with per-model token counts (FACT in the anthropic note), server-side context editing (clear_tool_uses/clear_thinking prune before the prompt reaches the model while the client keeps 'the full unmodified history'), and provider-rendered chat templates (model.encoding: provider-rendered means rendering happens on my side of the wire). What the kernel can honestly answer is 'what view did we compile and what request did we send' — for a subset of targets. This matters because the claim is marketed as a differentiator ('absent from every surveyed system').
  - Resolution: Wording fix plus small design change: require adapters to journal a wire-request hash where the wire is observable, and declare observability tier as a manifest setting (view-only / wire-request / provider-transformed) so the audit claim is scoped per target rather than asserted globally.

- **[MODERATE]** *07-RUNTIME-ARCHITECTURE §6 (remote cells: 'single writer is the provider')*
  - Attack: Mapping provider state onto single-writer Cells is a modeling error for forkable and shared provider state. A previous_response_id chain forks: two continuations from one response id yield a DAG, not a line, and the client — not the provider — decides when to fork; a Conversations object can be appended by other clients entirely outside the kernel's mediation. The Cell's defining guarantee (kernel-serialized single-writer consistency) is precisely what the kernel cannot provide for a handle it does not exclusively own; divergence handling is 'compare at checkpoint,' which detects but does not prevent, and the mirroring-lag weakness is self-reported while the DAG/shared-writer shape is not. Keying a Cell by a handle whose write set the kernel cannot close makes the consistency claim decorative.
  - Resolution: Design change: model provider state handles as leased external resources with manifest-declared mutation semantics (linear / forkable / shared-append) rather than as Cells, or restrict remote-cell mapping to handles the adapter can attest are exclusively owned by this kernel instance; journal fork events explicitly when the strategy branches a chain.

- **[MODERATE]** *ADR-003/06 §4.1 probes (Evidence cache validity) — via 06 §4.1 and doc 13 scenario R*
  - Attack: Probe Evidence is 'valid while (capabilityId, version, manifestHash, suiteVersion) is unchanged' — but for closed providers that key does not capture what actually changes. From the serving side: model ids are aliases that get re-pointed, weights and system scaffolding drift without version bumps, and the same model id can behave differently across regions, priority tiers, and serving-stack rollouts. Doc 13's scenario R already concedes the design depends on providers quantizing drift into declared epochs; we do not, and will not, because undeclared drift is operationally cheaper for us. Cache-forever-until-manifest-change means probe Evidence silently rots, and since Evidence gates eligibility (§4.3 rule 2), stale Evidence either wrongly admits or wrongly excludes targets.
  - Resolution: Design change: default TTLs on probe Evidence for closed-provider targets with budgeted continuous canary probing; telemetry-triggered re-probe when observed outcomes contradict cached Evidence (the §4.3 advisory alert should force re-probe, not just alert); treat manifest-hash-keyed permanence as valid only for content-addressed open weights.

- **[MODERATE]** *ADR-007 Decision 4 (dialect projections) and Consequences*
  - Attack: The project-don't-invent posture is right, but the ADR treats the external protocol landscape as static tracking overhead when the self-reported risk is convergence on Kyxo's own ground within the build window: MCP's roadmap carries task retry/expiry semantics, MCP and A2A now sit under one foundation, and providers are shipping their own agent-protocol surfaces (App Server, Managed Agents REST). If the converged MCP/A2A task lifecycle lands with usage/budget extension slots — which is exactly what a provider-backed WG would add first, since we already emit usage events — Kyxo's closed internal algebra becomes a superset of a live standard it chose not to shape, every dialect projection needs simultaneous revision, and the admitted budget-exceeded→input-required mapping (a funding decision surfaced to remote users as 'provide input') goes from confusing to standard-violating. Passive tracking across three governance bodies is not a strategy; it is a standing correctness debt the ADR itself quantifies (five MCP revisions in ~20 months) without staffing.
  - Resolution: Scope/process change: allocate explicit standing capacity for MCP/A2A working-group participation with the goal of landing the suspension-class vocabulary (approval-required, budget-exceeded) as a registered extension rather than a private projection; add a per-edge projection-revision budget to the roadmap; re-evaluate ADR-007's closed-algebra bet (also flagged by doc 05's open issues) when MCP tasks retry/expiry ships.

- **[MINOR]** *06-CAPABILITY-SPEC §5.5 (GREASE in signed/hashed records)*
  - Attack: The self-reported [V0-OPEN] anxiety about greasing signed manifests is overweighted relative to its difficulty: TLS solved the same problem by keeping GREASE inside the negotiation vector and outside the transcript-hash inputs, and JCS gives a clean carve-out (a reserved top-level field excluded from the signing input by construction). The residual worry — that excluding greased fields from signed payloads weakens ignore-path coverage — is real but small, since the ignore paths that matter (axis intersection, event streams) are unsigned surfaces anyway. This should not remain an open design question into the build; it is a half-page of spec.
  - Resolution: Wording/spec fix: define the reserved unsigned envelope field for grease, exclude it from JCS signing input and journal hash by schema construction, and add a conformance check that greased fields never appear inside signed payloads; close the open issue.

### Findings

- **[SERIOUS]** *prototypes/kernel/types.ts KernelApi (getGrant/attenuate) + ADR-013 invariant I1 + doc 05/07 API surface*
  - Attack: The kernel API is not object-capability-shaped: `getGrant(grantId: string)` and `attenuate(parentGrantId: string, ...)` resolve ANY id string any in-process caller presents against a single global grant table, and grantId appears on every journal event, so grant identifiers circulate as bearer strings. This is precisely the property ADR-013 uses to disqualify Codex/Cursor ('nothing distinguishes holding authority from knowing a string'), reproduced in the program's own reference kernel — and it is NOT in the prototype's self-reported cheat list. Worse, the spine commits to protocol-first ('the kernel API is defined as a versioned schema... from day one'), so this string-addressed shape risks being frozen into the contract before the WASM wave; isolation alone will not fix an API where designation resolves globally. I1 ('a Grant is a kernel reference, never a string') is currently false at the API level, not merely unenforced at the process level.
  - Resolution: Design change before any protocol freeze: c-list semantics. Each Cell receives a per-cell KernelApi instance whose handle arguments resolve only against that cell's capability list (kernel-held table of handles the cell was explicitly passed); grant IDs appearing in journal events become non-resolvable audit names distinct from invocation handles. Add a validate.sh-style gate: no kernel API method may accept a globally-resolvable authority identifier. Ratify in doc 05 and ADR-013.

- **[SERIOUS]** *11-SECURITY-AND-POLICY headline invariant + §1 threat table + §8 residual risks (vs 07 §8.1 and 13 scenario Q)*
  - Attack: The security document states 'no sequence of model-emitted tokens may cause the authority held by any Cell to grow' with neither of its two known boundaries. (a) The V1 boundary lives only in doc 07 §8.1 (auditability, not containment); doc 11's threat table credits T3/T4/T6/T9 to §4 mechanisms (isolate-tier sandboxes, Grant-to-credential/egress compilation) that do not exist until waves 2–3, and §8 has no residual row for 'V1 in-process = no containment' — note that a hostile in-process plugin can also write the SQLite/JSONL store directly, voiding even the auditability claim against non-cooperative code, so V1's honest guarantee is 'auditability of cooperative code' only. (b) Doc 13 scenario Q explicitly mandates 'Doc 11 must state the guarantee boundary' for brought/ambient authority (wallets, pre-existing credentials); grep confirms doc 11 contains zero mention of brought or ambient credentials. The program's single headline security claim is stated unqualified in the one document buyers will read.
  - Resolution: Three changes: (1) add a guarantee-boundary section to doc 11 stating both scopes (kernel-issued authority only; V1 = auditability of cooperative code, containment only where the tool runtime provides OS sandboxes) plus a 'V1 status' column in the threat table and new residual rows R9 (V1 no-containment, journal-integrity-against-hostile-code) and R10 (brought authority, with the manifest axis forced to 'undeclared-unknown' for sandbox tier `none`); (2) pull wave-2 subprocess hosting for code-bearing THIRD-PARTY capabilities (MCP servers, tool providers) into the MVP so the marketed differentiator is exercisable in the shipped artifact; (3) ban the word 'containment' from V1 docs and positioning.

- **[SERIOUS]** *11 §5.1 taint join calculus vs 08 §2.2 event example ('model-output' label) — the model-output taint rule*
  - Attack: The taint calculus for the system's central actor — the model itself — is unspecified, and the two documents contradict each other. Doc 11 §5.1 mandates structural join (outputs labeled with the join of inputs); doc 08's worked example labels a model result `integrity: "model-output"`, a third vocabulary neither trusted nor untrusted. Both consistent resolutions are bad: strict join means that after the first untrusted read (any web fetch, any MCP result) every subsequent model emission is untrusted, so the label gate blocks all further effectful calls — the agent halts or the workload becomes a declassification firehose (R4 admits this migration); loose join (model output as its own class) makes the model a structural laundering function and the Claude-Code-class injection attack is merely relabeled, not stopped. As specified, structural labels do not defeat the realistic attack — untrusted content persuading the model to invoke a capability it legitimately holds with model-composed arguments — they either forbid all work or permit exactly that.
  - Resolution: Design change, not wording: specify the model-output label rule explicitly and adopt a control/data split in the CaMeL lineage doc 11 already cites — effectful-invocation admission requires the *decision* provenance (plan/tool-call intent) to derive from trusted-context spans, while untrusted data may flow into argument positions only by opaque reference (the var_ref mechanism, extended from quarantine to the main loop). Make R4's declassification-volume measurement a named MVP exit criterion gating any claim that injection is 'a labeled-dataflow problem'.

- **[SERIOUS]** *11 §4.1 advisory Grants vs spine §4 / 07 §9 no-silent-degradation rule*
  - Attack: 'A Grant that cannot be compiled to an enforcement backend is flagged as advisory at bind time' directly contradicts the spine's 'fails loudly at bind time; the kernel never silently degrades' and doc 07's 'no silent policy degradation across any boundary.' A flag is not a failure: nothing specifies who observes the flag, whether it is journaled per-invocation or once, or whether policy can demand enforced-only. The contradiction is not hypothetical — in V1 essentially every Grant to an in-process capability is advisory (no credential minting, no egress compilation, no sandbox for in-process modules), so honest application of fail-loud would reject nearly all V1 binds, and honest application of the advisory flag makes declared-exceeds-enforced the V1 norm, which is the definition of the silent-degradation anti-pattern the spine documents across providers.
  - Resolution: Resolve the contradiction by making enforcement status a negotiated Binding axis: each right in a Grant compiles to {enforced(backend) | advisory}, sealed into the Binding, journaled on binding.sealed AND stamped on every effectful invocation event; risk-class floors in the policy pipeline require enforced status for irreversible/external-effect classes (those binds DO fail loudly when only advisory is available); profiles choose whether advisory binds warn or fail. Amend spine §4 to distinguish silent degradation (forbidden) from negotiated, journaled, policy-visible degradation (permitted below risk floors).

- **[SERIOUS]** *11 §8 R3 / ADR-013 open question — checkpoint resurrection: petname re-resolution (the pick, defended, with a missed hole)*
  - Attack: Asked to pick one: petname re-resolution is correct and I defend it — a checkpoint is data at rest, and refs-in-checkpoints embeds live authority in portable data, i.e., bearer tokens in backups; revocation that a restore can undo is not revocation, and 'resumed cell holds current-policy authority' is the security-desired semantics, not a weakness. But R3 leaves the resolver unspecified, and that is the real hole: checkpoints are explicitly portable across processes (spine §3.8, Cursor-style handoff), so petname designators resumed in a different trust domain resolve names against THAT domain's grant tree — an authority-minting API keyed by names, the exact name-to-authority move ADR-013 alternative B rejects, and a confused-deputy at resume. Nobody has stated whose authority backs re-resolution.
  - Resolution: Specify resume-as-delegation and amend the spine: re-resolution mints fresh Grants attenuated by the intersection of (the resuming principal's live authority) and (the attenuation recorded in the checkpoint's designators), so no principal can obtain via resume anything it could not mint directly; a resumer lacking parent authority for a designator gets a typed `rejected` binding, which the resumed cell must already handle per R3. Document that cross-domain checkpoint portability transfers state, never authority.

- **[MODERATE]** *11 §3.1 stage ordering (label gate before verdict) + §5 declassification-as-capability*
  - Attack: Escalating the self-reported ordering issue because the two mechanisms compose badly: label-gate hard-blocks before the verdict stage, so human approvers never see taint-blocked calls — precisely the most-likely-injection traffic is invisible to the principal best able to judge it — while R4 concedes the workload 'migrates into declassification requests.' The system thus creates a pressure gradient toward bulk, routinized declassification grants, and ADR-013 itself names a bad declassifier 'a laundering machine.' The mitigation path IS the attack path, and the fixed stage order removes the human visibility that would catch it.
  - Resolution: Make label-gate disposition configurable per risk class: violations may resolve to hard-block OR escalate-to-verdict (approval-required with the taint evidence and provenance chain attached), so approvers see blocked flows for consequential capabilities. Add per-grant declassification budgets (declassifications are countable Grant units, ADR-014 machinery) and declassification-rate telemetry as a first-class prototype measurement, so laundering is budget-bounded and observable.

- **[MODERATE]** *11 §8 R6 covert channels + ADR-014 attenuation-against-parent-remaining (prototype finding)*
  - Attack: R6 scopes covert channels to the observability plane and mitigates via exporter Grant audiences — but the missed channel is in-band: the grant lineage itself. The prototype confirms attenuation checks run against parent REMAINING budget and child charges decrement every ancestor atomically, so sibling cells under a shared ancestor observe each other's spending through their own mint failures and budget-exceeded suspensions. Two confidentiality-separated cells sharing any budget ancestor have a bidirectional signaling channel that no exporter grant bounds. For single-tenant V1 this is acceptable; any multi-tenant or confidentiality-partitioned deployment claim is not honest while this exists.
  - Resolution: Adopt the scenario-P reserve/settle amendment in a channel-aware form: children draw against a pre-reserved carve-out and can observe only their own reservation, never live ancestor remaining; document the residual channel (reservation-refusal timing) in R6; state explicitly that confidentiality partitions must not share budget ancestors, and that multi-tenant deployment is out of V1 scope.

- **[MODERATE]** *08 §2.3 redaction (kyxo.artifact.redacted) as an ordinary Grant right*
  - Attack: Redaction permanently deletes CAS payload bytes under a single ordinary Grant right. The incident-response story for the compromised-capability scenario (doc 08 §9 row 12) depends on payload-level provenance for blast-radius computation and post-mortem replay — but a compromised or coerced principal holding redaction rights can destroy evidence *content* while the hash chain still verifies, converting the anti-audit action into a policy-legal operation. The design audits THAT a redaction happened but cannot recover WHAT was destroyed; erasure-compliance and evidence-destruction are currently the same verb with the same authorization strength.
  - Resolution: Harden the redaction path: require a multi-principal verdict (operator plus data-subject/user, via the existing §3.3 verdict primitive) for hard deletion; insert a delay-window soft-delete (tombstone-quarantined but recoverable) before bytes are destroyed; and make redaction rights structurally non-delegable into agent-facing cells (a Grant right class the attenuation algebra can only drop, never carry past a human principal).

- **[MODERATE]** *11 §3.4 model judges as policy handlers + spine C3 telemetry-driven selection*
  - Attack: §3.4's caveat correctly bounds privilege (model verdicts never sole gate on irreversible effects) but misses the steering surface: judges 'may add denials anywhere,' so injected content that reaches a judge's context can selectively trigger denials, shaping which paths the agent takes — a bias/DoS channel that never trips the privilege analysis. Compounding it, judge verdicts and outcome telemetry feed capability selection (C3), so adversarial content can demote honest capabilities or promote a malicious one over time; ADR-001's self-report already flags cross-tenant telemetry pooling as unvalidated, and adversarial poisoning makes it worse. Additionally the reversible/irreversible tiering hangs on a doc-06 risk-class taxonomy that ADR-014 itself calls 'judgment wearing math's clothes.'
  - Resolution: Three bounded fixes: journal every judge denial with the taint labels of the judge's own input context (so injection-correlated denial patterns are queryable); exclude model-verdict-derived signals from any cross-tenant telemetry pool and decay them faster than probe evidence; rate-bound judge denials per content source with escalation to a human when the bound trips. Defer model-judge stages from the MVP entirely (deterministic stages + human verdicts suffice to validate the pipeline shape).

- **[MINOR]** *11 §1 threat table T1 ('user input is trusted-integrity')*
  - Attack: Labeling user input trusted-integrity is wrong at the edge: users routinely paste web content, emails, and documents — the user channel is a primary carrier of indirect injection (the Copilot hidden-character filtering the same row cites exists precisely because of this). 'User-attributed' and 'trusted-integrity' are different properties.
  - Resolution: Wording plus a default: give user input a distinct source label (user-attributed) whose integrity level is a per-deployment policy choice, defaulting to trusted for typed instructions but with pasted/bulk content eligible for the same quarantine machinery as southbound results.
